# An acceptance suite: one command, cases, a report

- Status: In progress — step 1 (the runner plus ten cases and a report) is the current slice.
- Priority: High
- Written: 2026-11-11
- Language: English only in this file.

## What it is

The rows read today are driven by hand: a person runs one recipe, reads one answer, judges
it. This ticket turns that into a suite: the harness launches the game itself (once or
several times, with the parameters a case needs), drives each case through the acceptance
channel, asserts on the readings, and writes one report that names every case, its verdict
and its evidence. A case is data-shaped — setup, drive, assert, evidence — not a bespoke
command run by hand.

## The three rules the user set (2026-11-11, translated)

1. **The suite launches the game, not the person.** A case declares what it needs (which
   clients, a fresh world or the current one, a restart) and the runner starts or restarts
   the clients with those parameters. A restart is a case property, not a harness failure.
2. **Randomness is judged in ranges, not exact numbers.** A drop's kind must be one of the
   kinds the loot table can produce, its count within the range the probabilities allow; the
   assertion states the range and the reading shows the value.
3. **Visual rows are not automated.** A row whose judgment needs a human eye on a picture is
   out of the suite and stays a named manual check; the suite says which rows it does not
   cover and why.
4. **A covered ticket and its scripts are deleted (2026-11-11, translated).** Once a ticket's
   rows are expressed as a passing case, that ticket and its bespoke recipe(s) leave the
   repository — the case in code is the record. The backlog therefore shrinks as the suite
   grows: no parallel history of the same row, no recipe kept for a case that no longer needs
   it. A ticket with rows the suite cannot judge (the visual ones) stays with exactly those
   rows named.

## Shape

- **A C# project, not a set of scripts (2026-11-11, translated: "a separate csproj … the
  project will be complex and scripts cannot expose problems at compile time").** The suite is
  a `net8.0` console project under `tests/`: typed cases, typed readings, typed assertions, so
  a case that names a reading the game does not expose fails at build time. It drives the
  clients over the acceptance channel's socket (the same protocol `drive-in-process.ps1`
  speaks today); launching clients and the box/exe values stay with the existing launcher,
  which the project calls (they are machine facts, not suite logic).
- **Runner**: launches clients (host desktop + boxed guests over the offline IP-direct
  protocol), waits for a state, drives, asserts, stops what it started. One command runs a
  suite; the suite lists the cases and their parameters.
- **Case**: a typed class or record with `Setup`, `Drive`, `Assert`, `Evidence`; a case may
  declare `Launch: fresh | warm | restart`.
- **Assertions**: a reading plus a comparison — equality, a numeric range, a set membership,
  or a presence. The report prints the reading beside the expected range, so a failure is
  readable without the harness.
- **Report**: one markdown per run under the artifacts folder: case, verdict, the reading,
  the expected range, and the evidence path; a summary line with the counts.

## Network conditions (2026-11-11, translated: "add a fake delay … real latency and packet loss (loss mainly for
non-guaranteed-delivery packets), to test latency, loss and race scenarios; add cases where the suite can do more")

The suite must be able to make the network bad on purpose, the way a real player's network is bad, and then judge the
rows under that condition. The shape:

- **A diagnostics-only transport shim.** The IP-direct transport (`IpDirect*`) gains a shim behind a
  `[Diagnostics] NetConditions` config: `LatencyMs`, `JitterMs`, `LossPercent`, and `LossScope` (`unreliable` only, by
  default). Every outbound frame is delayed by `LatencyMs ± JitterMs`; a frame on an unreliable channel is dropped with
  `LossPercent`; reliable channels are never dropped (a dropped reliable frame would be a bug in the shim, not a test).
  Off by default and invisible to a normal install.
- **A case-facing control**: a recipe `net-conditions mode=set|read|clear` that writes the profile on the host (and the
  member where the case needs it) and reads back what is in force, so a case states the network it ran under.
- **Cases that use it**: reliable-delivery under 20% loss + 150 ms latency (every guaranteed packet still lands, no
  duplicate, no reorder on a channel that promises order); a race row (a cut or a restore requested while the network is
  slow — the deferral/retry path is exercised); an unreliable-row row (a stream frame that is allowed to drop: the world
  keeps running, the next full frame repairs it). The sweep rows that involve timing move into this family.
- **The report names the profile**: a case's reading carries the latency/loss it ran under, so a pass is
  "passes at 150 ms and 20% loss", not "passes".

## Not covered (named, not hidden)

- Visual typography and feel rows (the user's third rule).
- Rows whose judgment needs a hand on the physical mouse for timing (none known today; the
  channel drives the input the game reads).
- Rows that need a different game build (the mixed-version row) — they run as their own
  suite with their own artifact.

## The member after an ending (reading, 2026-11-11)

The ending case ends the run on purpose. After it, the member's client keeps a session it no longer owns: `state` reads `role Guest`, `lobby 0`, `transport IpDirect`, `inWorld false`, and the home page's leave answers `ok` without clearing the role. A fresh host session then lists no members and the member never enters, so the suite cannot join it again; relaunching the member client clears the state, and the suite-level join works from there. The next slice makes the suite own the member's relaunch (quit + the same launch command for one client) when the role will not clear, so one suite run can cover the ending and the cases after it.

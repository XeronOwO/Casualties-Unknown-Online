# 1.0: a customized item's label, colour and favourite mark reach the other clients

- Status: Todo — night mode, split from `in-progress/adapt-to-1.0.md`.
- Priority: Highest
- Category: Items / release
- Source: the 1.0 map (`docs/design/game/items.md`): 1.0 lets a player customize an item — `PlayerCamera.cs:841`
  (colour swatch), `:851` (favourite mark), `:861` (label). The wire's item facts today carry condition, contents and
  the container children; the three customization writes are not in that fact set, so another client must render the
  item as it was before.

## The question

Does the wire carry a customized item's label, colour and favourite mark, and does the other client's copy show the
same three after a pickup, a drop or a world entry?

## Design

- `docs/design/game/items.md` — the item surface and the three customization writes.
- `docs/design/game/items.md:1` (the same page, the section that names them) and the wire's item fact definition in
  `src/CasualtiesUnknownOnline.Runtime/Protocol/Messages/` — the fact set is the page to extend.

## Chain

1. The customization write (the game's own call) → the local `Item` fields.
2. The item fact capture → the wire.
3. The other client's materialization → its `Item` fields.

## Design

- Extend the state with the two missing values: `ItemData` gains `string Label` and `int ColorSwatch`; `Snapshot` gains
  the same; `WireItemData` gains `Label` (proto 6, a string; empty means "nobody set one") and `ColorSwatch` (proto 7,
  encoded `index + 1`, because 0 is a legal swatch and protobuf drops 0).
- Capture writes `item.label`/`item.colorSwatch` beside `item.favourited`; materialize writes them back at the two
  sites; the reconciler and the wearable restorer follow; the clone renderer draws the label and tints the swatch from
  the same values it already reads condition from.
- Protocol version moves with the wire change; `docs/contracts/wire-surface-baseline.txt` is regenerated and the sync
  coverage matrix gains the two members under the item row's entry.
- A default item sends neither field (protobuf omits the string's empty default and the `+1` of 0), so a world of
  untouched items pays nothing.

## Acceptance

1. A host changes a carried item's label and colour; the guest's copy of that item shows the same label and colour
   after the item crosses a boundary (a drop and a pickup, or a world entry).
2. The favourite mark follows the same path.
3. An item nobody customized keeps the default three, and the wire's size does not grow when the marks are empty.

## Open questions

- Whether the label is per-instance or per-definition in 1.0 is read from `Item.cs` before the design is fixed; if it is
  per-definition, the fact belongs to the run's content table rather than the item row.

## Batch 20261110-a (two instances, IP direct)

The wire is in `9cc7a119`, deployed to the 1.0 install. The second instance (a byte copy
of the install) was synced to the same build and joined over IP direct (host 7777, guest
7778), both in the world; the first attempt was refused by the handshake on CuoBuild
because the copy still carried the previous build — the refusal named the build, exactly
as designed.

On the host, `item-customize slot=0 label=Hermes swatch=3` set the two values and read
them back (`{"ok":true,"label":"Hermes","swatch":3}`). On the guest, `clone-customization`
found no display-clone items (`count: 0`): the carried-inventory clone is only built
while the teammate's displayed backpack is open, and that view needs a held drag on the
guest — the guest's own slot 0 was empty, so `drag-from-slot` refused and
`remote-backpack-open` answered "hold a drag first".

Next: the host drops the customized item, the guest picks it up, and a small reader
(`body.GetItem(slot).label/colorSwatch`) reads the guest's own carried copy — the item
then crossed a boundary, which is exactly acceptance row 1. The clone view is the other
path and needs a drag staged on the guest first.

Measured in the same session: the host dropped the customized bandage (drag + release);
the host's own reader (`world-customization`) read one item with `label "Hermes"`,
`swatch 3`; the guest's reader at the drop read zero items and `item-world-read` near the
body also read zero — the guest's world has no copy of the dropped item, so the next
check is the drop's item path itself (which message carries the item's state to the guest
on a drop, and whether the label/colour ride it), not the reader.

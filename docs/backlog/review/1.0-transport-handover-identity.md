# The same player must keep one identity across transports

- Status: Review — blocked on user: the Steam↔IP half needs a second Steam account that owns the game (the account, not the code, is the missing piece). The IP-direct reconnect adoption landed 2026-11-16 (the section below: a peer that rejoins under a new transport id adopts its own unclaimed character by the recorded link, with the same-name ambiguity refused and read); what remains is the Steam↔IP direction, which needs a build where the other side is a different owning account. The user's standing requirement (2026-11-11): every player has one identity, and the online and offline modes hand over seamlessly — a Steam LAN failure that falls back to VPN/IP direct must recover the same character, inventory and progress.
- Priority: High
- Created: 2026-11-11

## What the player sees

A player joins a friend's room over Steam. The Steam path fails (LAN blocked, Steam offline), so both sides switch to IP direct. The player rejoins — and should continue as the same person: the same character, the same items, the same position in the run. Today the transport switch is a different player to the save.

## The chain (read 2026-11-11)

- The identity is the save key: `src/CasualtiesUnknownOnline.Runtime/Persistence/PlayerKeySpace.cs` (`Unknown`, `Steam`, `IpDirect`) is derived from the character file name, and `PlayerKey` (`steam-<id>` vs `name-<sanitized name>`) is built by `PlayerKeyResolution.KeyOf(peerId, displayName, space)`.
- Decision 162 makes the two spaces disjoint: a claim resolves only inside the space of the peer that joins. An unclaimed character of the other space is "that player joins as a new character" — which is exactly the behaviour the requirement rejects.
- The restore path: `WorldRestoreApplier` plans the claims (`WorldCharacterBinder.Plan`) before the kernel write; unclaimed characters' carried rows are filtered out of the restored checkpoint (`WorldContinueUnclaimedCharacterTests`). A cross-space claim therefore never happens by itself.

## Design

- `docs/design/cross-cutting/saves-and-recovery.md` — the archive's character keys and the claim rule (decision 162) are the surface this ticket changes: the same player's key must stop depending on the transport, while a save taken in one transport still restores in the other.

## The design (options and a recommendation)

- **A. Explicit profile key.** Every player carries one key that does not depend on the transport (a display name plus a stable digest, or a user-chosen profile id), and both transports claim it. Costs: a new key space (`profile-<name>`), the Steam id no longer names a character, and a collision (two players with the same name) needs a disambiguation step.
- **B. Adoption at join.** The claim looks across spaces when the join is unambiguous: one unclaimed character with the same display name, or a recorded link from the old key to the new one. Costs: a name-only match can adopt the wrong character; the link must be recorded in the save and shown at join.
- **C. (A) with (B) as the fallback.** A stable profile key is the default; when a player arrives under a key that has no character but the save holds exactly one unclaimed character with the same display name, the host adopts it and records the link.

**Recommendation: C.** It keeps the Steam id as the primary key (no migration for existing saves), gives a stable identity for IP-direct players, and never guesses when the match is ambiguous — the ambiguous case stays "a new character" and is named on the join screen.

**Chosen (2026-11-11): C.** The slices:

1. `SavedCharacter` carries the player's display name (`string? DisplayName`, absent in old saves — null means "no name recorded"); the cut writes it from the peer's `PlayerIdentity.DisplayName`.
2. At restore, `WorldCharacterBinder.Plan` adds an adoption pass: a present peer whose own key is unclaimed adopts an unclaimed character of the OTHER key space when exactly one stored character's display name matches (case-insensitive, compared through `PlayerKey.Normalize`), and the plan records the adoption so the next cut writes that character under the peer's current key.
3. Two matches, or a name that normalizes to nothing, adopt nothing — the peer joins as a new character exactly as today.
4. The link is visible in the restore line and (later) on the join screen.


## Acceptance

1. A host and a guest meet over Steam, the guest customizes an item, the transport is switched to IP direct and the guest rejoins — the same character, the same item label and the same position (a measured reading, one run).
2. Two guests with the same display name and different keys in one save: the adoption does not pick either; both join as new characters (the ambiguity rule, a unit fact).
3. The link is persisted: a save taken after the adoption restores the adopted character for the IP-direct key (read back from the archive's characters).

## IP-direct reconnect adoption (2026-11-16)

The live host character table (`CharacterDataStore._savedCharacters`) is keyed by
the IP-direct transport id, which changes on every reconnect, while the archive is
keyed by the stable display name. A member that left and rejoined was therefore a
new player: `SendSavedCharacter(newId)` missed, the guest started a fresh kit, and
its fresh item reports replaced the host's clone.

Fixed by `9aa14ad14`: `CharacterReconnectAdoption` adopts the one saved record whose
recorded display name matches, only while any old presence is out of the world; two
same-name players or an old owner still playing refuse. If the old presence is
already gone, the name each report arrived under is the fallback. The live proof is
`save-continue` in `.acceptance/color8/report/report.md`: before the save the host
stores `MemberColor/5`; after the member rejoins with a new transport id both
players still read `MemberColor/5` and `HostColor/3`.

This closes the same-IP-direct reconnect leg. The Steam↔IP-direct mixed-transport
row (acceptance row 1 above) remains open: it needs a Steam session on both clients.

The start gate now follows the same reconnect: it retries `WorldJoin` every
second while a host gate is armed, drops a waiter when its session leaves, and
the Continue path re-invites a returning member for ten seconds. `d40087460`
and `b25e6e42e` are the product commits; the 39-row run in
`.acceptance/glyphfull1/report/report.md` has no 30 s forced start and no
revision-gap storm.

## The fixture's limit (2026-11-13)

Acceptance row 1 needs a Steam session on BOTH clients. The boxed clients' Steam accounts do not own the game, so they
never start Steam (`launch-clients.ps1 -AllowOfflineSteam`); a mixed Steam + IP-direct session is a different row (it
tests two transports in one room, not one player switching). On this machine row 1 is therefore **not driven — a named
residual**, not a weaker check: what it needs is a second Steam account that owns the game, which the fixture does not
have. Rows 2 and 3 are covered by `CharacterAdoptionTests` (the ambiguity fact and the adoption fact); the live leg of
the same code is exercised on every IP-direct rejoin the suite's own session performs.

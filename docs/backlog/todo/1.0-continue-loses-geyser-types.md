# A continued world loses the geyser types

- Status: Todo
- Priority: High
- Created: 2026-11-16

## Design

The restore contract is `docs/design/cross-cutting/saves-and-recovery.md`: the cut carries the host's world facts and Continue repairs them per entry; the native geyser set is line 75. The archive and restore audit are in `docs/architecture/save-archive-format.md`. The path is `RestoredWorldFactReplay` -> `IRestoredWorldFactSink` -> `GameRestoredWorldFactSink` -> `GeyserStateTable`.

The native geyser is a world entity. `GeyserScript.Start` rolls `liquidType = (Random.value > 0.75f) ? 2 : 1` and overrides it to 6 when `isLava` (`reversing/release-1.0.2/Assembly-CSharp/GeyserScript.cs:8-20`). The host's cut carries the typed geyser state; Continue writes it back by position.

The row's behaviour assertions passed: the colours and the restored item set came back, the member joined after 11.9 s. Only the host's error count made the row FAIL.

## Root cause

`GameRestoredWorldFactSink.IsReadyForGeysers` (:95-106) and `GeyserStateTable.Apply` (:60-93) use `Object.FindObjectsOfType<GeyserScript>()`. Unity's parameterless overload returns only ACTIVE objects. The live query saw 64 of the 110 saved positions at the restore seam. Whether the 46 were inactive, not yet instantiated, or both is not settled by that reading (no native call site for deactivating a chunk or geyser was found); the includeInactive scan covers the inactive case, and the post-fix acceptance is the evidence. `RestoredWorldFactReplay` waits 5 s (:151-170) and then applies the partial set; the 46 positions have no match and are reported refused.

`GeyserScript.Start` rolls the type. The save-side half: a geyser that started and was deactivated still has a decided type, so the save must capture it even while inactive; a geyser that has not started has none. The restore's Apply and readiness scan include inactive, and the remembered type is re-applied after the geyser's own Start, or an activation can overwrite it.

## Fix

1. `GameRestoredWorldFactSink.IsReadyForGeysers`: use `Object.FindObjectsOfType<GeyserScript>(true)`.
2. `GeyserStateTable.Apply`: scan with `includeInactive: true`; remember the restored type per geyser; expose a re-apply used by a `[HarmonyPatch(typeof(GeyserScript), "Start")]` postfix (nested in `GeyserStateSync` so the capability catalog owns it).
3. `GeyserStateTable.Capture` is the started set: every geyser whose own `Start` has run, active or not (the `GeyserScript.Start` postfix marks it; a geyser that has not started has no decided type). This closes the save-side half: a save taken while far chunks are inactive still carries them.
4. Update `docs/design/cross-cutting/saves-and-recovery.md:75`: the restore's live geyser set means every geyser in the world, active or not; the restored type survives the geyser's own Start; the 5 s bound stays a safety net.
5. Family audit: `KeypadCodeTable.Capture` (:34) and `KeypadCodeTable.Apply` (:99) use `Object.FindObjectsOfType<Openable>()` (active only); a keypad code is decided at generation, so the same includeInactive fix applies there. `WorldBuildingEntitySync`'s only scan (:317, `MarkSupportLossRemote`) is the support-loss drop row, not the building-health lookup; that ticket keeps its own path.

## Review (2026-11-16)

The independent review (fresh context, FULL tier, read-only, against the frozen tree) found no blocker as a build/unit-gate matter, two majors, three minors and two nits. Every finding is dispositioned in this change:

- **Major 1 — the save half was still active-only.** `GeyserStateTable.Capture` enumerated `Object.FindObjectsOfType<GeyserScript>()`, so a save taken while far chunks were inactive carried only the active decided types (the quoted line: `foreach (var geyser in Object.FindObjectsOfType<GeyserScript>())`). The `>=` readiness in `GameRestoredWorldFactSink.IsReadyForGeysers` then let a 64-row archive pass silently: `Apply` matched 64, returned 64 applied / 0 refused, and the 46 omitted geysers rolled a fresh type when they started. Fixed: `Capture` scans `includeInactive: true` and keeps only geysers whose own `Start` has run (a `Started` mark set by the `GeyserScript.Start` postfix in `GeyserStateSync`); the remembered type is stored only after the write lands; the applied count is per saved row (`HashSet<int>`), so two live geysers inside one row's 3 m radius cannot over-count and rows - applied cannot go negative.
- **Major 2 — no runtime test.** `SaveContinueCase` never read a geyser, and the cited run predated the fix (`AcceptanceSuite.dll` 22:51 vs `GeyserStateTable.cs` 23:12). Fixed: the `geyser-types` recipe reads every geyser, active or not, with its decided type and started mark; `geyser-start` forces the not-started geysers' own `Start`; `SaveContinueCase` now requires the host's restore audit to read the saved count applied / 0 not taken, the type table to be equal across the save/continue, and every type to equal the pre-save reading after the forced Start.
- **Minor 3 — the deactivation premise had no native call site.** No native `SetActive(false)` on a chunk or geyser was found. The design page and this ticket now state the 64/110 reading as an observation, not a proven mechanism; the includeInactive scan covers the inactive case and the post-fix run is the evidence.
- **Minor 4 — stale native citation.** Updated to `reversing/release-1.0.2/Assembly-CSharp/GeyserScript.cs:8-20`; the 1.0.2 `Start` also overrides `isLava` to type 6, which the remembered type preserves.
- **Minor 5 — the 306.8 s suite wall was unsourced.** The performance ticket now cites only the report's 306.1 s.
- **Nits.** The CWT write now follows the successful write; the applied count is per row.
- **What the review could not check:** the in-game N/N, the forced Start, the Harmony install and a post-fix 39-row run (no game was available); the acceptance below is that evidence. The reviewer's `--no-build` run confirmed 6708 unit and 836 gate tests green on the changed binaries.

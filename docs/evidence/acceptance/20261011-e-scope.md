## Why this is one batch

The seven rows are ONE world and one chain: mark an item in the owner's backpack (row 1), read the owner's
item and a third peer's view in the same instant (rows 1, 5), leave and rejoin (row 2), cut and continue
(row 3), hand the item over (row 4), press the key on the operator's own inventory (row 6), and let a
marked item be destroyed (row 7). Rows 2 and 3 need the same session in two later states, so they are the
same run continued, not three batches.

## The one hard staging problem, and the two ways out

**The gesture needs the physical cursor over a ring button in the frame the key goes down.** Batch
`20261011-d` proved the store path fires (its refusal line is in
`docs/evidence/acceptance/remote-inventory-native-parity-rework-20261011-d.md`, row 7d) and could not
stage the store itself: the remote view's ring is anchored to the displayed clone, and the acceptance
tooling must not take the pointer (`AcceptanceDriverGateTests` bans the cursor and `SendMessage`
families; decision 237). So the batch must pick one of:

1. **Ask the user to place the pointer** — one hand on the mouse for one key press per row, with the run
   reading everything else. This is the only way row 1's GESTURE half and row 6 are judged as gestures.
2. **Drive the store through the game's own input state, if a legal seam exists** — investigate first, and
   do not invent one: the tooling's ban is a decision, not an obstacle to route around.

If neither is available in the batch, the rows that need a mark to EXIST can still be judged by driving
the set through a fixture (`LocalFavouriteMarkStore.Current.Toggle(instanceId, ownerSteamId, itemId)`
followed by a capture), and the run must then say so in the record: rows 2, 3, 4, 5, 7 are judged
end-to-end, while row 1's gesture half and row 6 stay `unproven` as GESTURES.

## Limits this batch must state in its record

- The behaviour of an item that has LEFT an inventory is not a row of this batch, because it is the game's
  own: the static `PlayerCamera.ItemHoverDescription` draws the favourite sprite for whatever item the
  cursor is over (`PlayerCamera.cs:1313-1316`), so a dropped item keeps carrying and drawing its own flag
  exactly as it does in single-player. Judge it only as "unchanged native behaviour" if it appears at all.
- The mark's identity rests on the item instance id, and the id-reuse path is
  `review/item-id-counter-is-not-resumed-by-a-restore.md`; a reading that would need it (row 7's
  "destroyed" half) says which of the two it exercised.

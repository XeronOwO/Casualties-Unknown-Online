# A live member never resyncs the host's block table

- Status: Review
- Priority: High
- Area: Runtime / world state (block table)

## What the player sees

Two players stand in one run in front of the same spot, and the ground under it differs: one sees a hole where the
other sees a block, or a different block material. The world stays wrong for the whole run — nothing ever repairs it.

## What was measured (2026-11-14)

- `block-idle-drift` on the acceptance pair: 54 rows of the block table differ between the clients, the first at row
  966, with no player action in between.
- The generation is NOT the source: both clients' generation ran 19 segments with identical `[GenStream]` fingerprints,
  so the world was built from the same random stream on both sides.
- The differing cells were written by different steps of the same chain on each client (`GenerateBlockCircle` on the
  host, `GenerateObjectAtPos` on the member for the same cell), so the pod/circle centre — the local body position at
  `WorldPlacePlayer` — is the remaining root-cause candidate.

## What the code does today (read, not assumed)

- The host records a live write into its own table: `WorldEventSync.OnBlockSet` → `WorldService.ReportBlockState` →
  `WorldStateMessageService.ReportBlockState` (`src/CasualtiesUnknownOnline.Runtime/Session/World/WorldStateMessageService.cs:354-369`),
  which only stores the cell in `_damagedBlocks`.
- That table reaches a member at world ENTRY: `WorldEntryFanout` calls `SendBlockStateSnapshot(steamId)` (`:105`, `:158`).
- A live member hears only the two event shapes: a break (`BlockDamaged`) and a placement (`BlockPlaced`). Any other
  write — the game's own structure stamping, a cell a member never reported, a report the host refused — is never
  re-sent, so the member's table keeps its own value for the rest of the run.
- The existing periodic traffic is the opposite direction only: a member's pending mutation is re-reported to the host on
  a 60 s cadence (`docs/design/mechanics/world-interaction.md`). Nothing re-sends the host's table to a live member.

So the answer to "is there a periodic sync?" is: **no, not to live members** — only at entry.

## The two fixes this needs, and why both

1. **Root cause: the generation must produce the same world and the same pod centre on every client.** The remaining
   probe is the body position at the `WorldPlacePlayer` segment (logged on both clients). A fallback must never be used
   to paper over this: if the two clients build different worlds, the table they disagree about is not the defect.
2. **Fallback: a periodic block-table reconcile from the host to every live member.** It exists because a single lost or
   refused message must heal (`we already do this for the member→host direction; the host→member direction is missing`),
   and because a write the event shapes do not cover must eventually reach everybody.

## The fallback's shape (so it does not eat bandwidth)

- The host keeps, per member, the last snapshot it sent (a compact baseline). A reconcile tick (60 s, the same cadence
  the member→host re-report already uses) computes the DIFFERENCE against that baseline and sends only the changed rows;
  no change means no message at all.
- The row set is bounded by the game's own table (128 live damaged cells, `docs/design/mechanics/world-interaction.md`),
  so a full reconcile is at most 128 × (x, y, block) ≈ 1 KB; the differential is normally zero rows.
- The member applies a reconciled row through the same path it already uses for `BlockStateMsg` (idempotent, same value
  writes nothing), and the next reconcile's baseline moves only by what was actually sent.
- No snapshot is sent while the member is not in the world, and none is sent to a peer that has not confirmed the
  handshake.

## Acceptance rows

- [ ] A live member whose table was made stale by a host-side write realigns within one reconcile interval, read from
      both clients' own `block-read-at` on the same cell.
- [ ] A reconcile with no changed rows sends no message (read: the wire counter stays flat over an idle interval).
- [ ] A reconcile carrying N changed rows sends exactly those rows (read: the message's row count).
- [ ] The generation streams stay identical (the `[GenStream]` fingerprints keep matching) — the fallback never replaces
      the deterministic generation.

## What must not change

- The block table stays the host's (one table, the game's own capacity and order — the existing decision).
- A break and a placement keep their existing messages and their existing verdicts (first-writer-wins for a break).
- The fallback is invisible when everything works: no extra traffic on an idle run.

## Design

- The block table's owner and its report/verdict loop: `docs/design/mechanics/world-interaction.md` (the report is
  checked against a fact the receiver already holds, the host answers every reported cell authoritatively, and the member
  re-reports its outstanding set on the steady 60 s step).
- The generation the table describes: `docs/design/game/worldgen-and-layers.md` (one generation chain, the pod stamped
  around the local body).
- The direction this ticket adds is the same shape in reverse: the host is the owner, so the host's table must be able to
  reach a live member after entry — as a difference, never as a blind resend.

## Correction: two tables, and only one of them has a backstop (2026-11-14)

The measured divergence is **terrain**: `block-band-digest` reads `WorldGeneration.world.GetBlock(...)` (the recipe's own
`v = (int)world.GetBlock(new Vector2Int(x, y))`), and `WorldService`'s `_damagedBlocks` is a separate overlay of the
DAMAGE the host applied. The reconcile that landed (`BlockTableReconciler` → `ReconcileBlockTable`) drains exactly that
overlay, so it heals a member that missed a damage record — it does not, and cannot, heal the generated terrain the 54
differing rows belong to.

That is the ticket's own design gap, recorded here rather than papered over: the backstop covers one table, the measured
divergence is in the other. A terrain backstop needs its own shape (per-row digests the host can compare against what it
sent, then only the differing cells — the rows are 2048 wide, two bytes each, so a digest pass is ~4 KB per member and a
reconcile of even a whole row is a few hundred bytes), and it must be built only after the root cause is named, or it
will hide a generator defect behind traffic.

## The forced-write reading (2026-11-14)

A scratch recipe called `WorldGeneration.SetBlock` directly on the host (no break, no placement — the shape the game's
own generation uses). Readings on the live pair: the host's cell `6,503` read `14` before and after; `7,503` read `14`
before, then `0` on BOTH clients immediately. Two facts:

- a direct `SetBlock` write DOES reach the member live (something in the write path already carries it), so this probe
  cannot stand in for "a write the member never hears";
- the reconcile path is therefore still unexercised on the real game; its unit facts (5) are the only reading today.

The scratch recipe was removed after the probe (it is not part of the suite; the forced-drift row stays open until a
write that bypasses the live path exists).

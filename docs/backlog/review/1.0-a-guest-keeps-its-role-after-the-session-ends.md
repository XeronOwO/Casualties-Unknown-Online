# 1.0: a guest keeps its role after the session ends, so it can never rejoin

## The reading (2026-11-13, the boxed guest on the release install)

- After the host's run ended and the host restarted its own session, the member's client answered
  `role=Guest, inWorld=false, page=Home, hostId=0, lobby=0`, controls `tab.admin,tab.home,...,window.close`
  — no `home.leave` and no `ip.join` path that a click can reach.
- The driver's `leave-world` action answered without changing the state: the world is gone, the ROLE is not.
- Its own log carries `[GuestHostSilenceWatchdog] No frame from the host 1 for 15000 ms — ending the
  session locally.` followed by `Session ended (role Guest kept).`
- The host meanwhile waits with `gateText "waiting for the remaining players to load (0 s)"` (translated) and `members: []` — it never
  names the member, so the member's later joins are refused (`IP-direct start refused: a world is running
  or generating` or an ignored join), and the suite recreates the client to get a clean one.

## Design

- `docs/design/cross-cutting/saves-and-recovery.md` — who owns a session's identity and what survives a
  session end; the role is part of that identity, not of the world.
- `docs/design/game/README.md` — the game's own menu and world entry, which the ghost leaves half-way.

## The mechanism

- `src/CasualtiesUnknownOnline.Runtime/Session/SessionService.cs:522-557` — `TeardownSession` sets
  `SessionActive = false`, clears presence and `HostSteamId`, fires `FireSessionEnded`, and deliberately
  KEEPS the Role (the comment says `EndSession` models a same-lobby outage the returning host rebuilds).
- Only `OnLobbyLeft` (`:411-418`) resets `_identity.Role = SessionRole.None` — its comment says the role
  follows the ACTUAL lobby state.
- IP-direct has NO lobby: a session that ends there never produces a lobby event, so the Role survives the
  session. On Steam the same hole exists when a guest ends the session without leaving the lobby (the
  watchdog path), because the watchdog calls the session end, not the lobby leave.

## Options

- **A (recommended): the session end drops the role when no lobby owns it.** `TeardownSession` sets
  `_identity.Role = SessionRole.None` when `_currentLobbyId == 0` (IP-direct, or a Steam session whose
  lobby is already gone); a same-lobby Steam outage still keeps the role for the returning host. One
  branch, the domain's existing rule, and the guest is back at the menu with no identity — the state the
  UI already renders.
- **B: the UI offers a leave control whenever the role is not None.** Treats the symptom: the player can
  clear it, but the ghost still exists between the session's end and their click, and every automated
  fixture still meets it.

## What the fix must not change

- A Steam guest inside the SAME lobby keeps its role through a host outage (`EndSession` path today), and
  the returning host rebuilds the session with the same identity — that is decision 162's handover and the
  reason the role is kept.

## Acceptance

1. A guest whose host ends the run and starts a new session reads `role=None` once its own session ended,
   and joins the new session without a restart (one client launch, two sessions).
2. A Steam guest that stays in the lobby across a host outage still keeps `role=Guest` and rejoins the
   same lobby.
3. The acceptance suite deletes its forced relaunch fallback (`SessionDriver.MemberRelaunches`) and the
   full suite runs on one launched pair.

## The row read on the deployed build (2026-11-14)

The suite case `role-clearing` drove a fresh IP-direct pair: the host clicked `home.leave` (leave the
session, not only the world), and the member's own state then read `active: false`, `hostId: 0`,
`inWorld: false` — the session had ended — while `role` still read `Guest`. The member's own log
carries `Session ended (role Guest kept).` and NOT `No lobby owns this session — role cleared.`, so
the clearing branch (`SessionService.cs:560-564`) did not fire: its second condition,
`_currentLobbyId == 0`, is false on this path. The next probe is one log line that names both values at
the teardown (role and lobby id) on the deployed build; the fix is not re-opened until that reading
exists.

The same run also confirms the fixture's sequence is the right one for the row (host ends the session,
member must be left with no role, then the host opens a second session and the member joins it without a
restart) — the case stops at the first requirement today.

Evidence: `.acceptance/suite/report.md` (the role-clearing section) and the boxed client's
`BepInEx/LogOutput.log`.

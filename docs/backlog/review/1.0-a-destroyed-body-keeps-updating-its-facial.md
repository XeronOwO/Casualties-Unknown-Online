# A destroyed body keeps running its facial update

- Status: Review
- Priority: High
- Area: GameAdapter / character presentation

## What the player sees

Nothing at first — the game works. Then, after a while on a busy run, the host slows down and the log grows without
bound. In one working session the host's `BepInEx/LogOutput.log` reached 94,195,368 bytes, and a fresh client already
carries 3473 `NullReferenceException` lines.

## What was measured (2026-11-14)

Two per-frame exception shapes, both from our own code paths:

```
[Unity:Exception] NullReferenceException
  Body.get_peekingBehind ()            (Body.cs:262 — reads base.transform.position)
  FacialExpression.get_doBackEye ()    (FacialExpression.cs:15 — reads this.body.peekingBehind)
  FacialExpression.Update ()           (FacialExpression.cs:89)
```

and (fixed in `541466396`, its lines are gone):

```
[Unity:Exception] NullReferenceException
  UnityEngine.Component.GetComponent[T] ()
  CasualtiesUnknownOnline.GameAdapter.Character.PainkillersSync.Apply (Body body, CharacterHealthMsg health)
  ... HostVitalsBodies.ApplyComponentInputs ... HostVitalsBodies.Seed ...
```

The remaining stack says: a `FacialExpression` still updates while the `Body` it points at has no transform — a
destroyed body the component still references. The facial is the game's own component; the destroyed body is one this
framework creates or destroys.

## Where our code destroys a body

- `src/CasualtiesUnknownOnline.GameAdapter/Character/RemotePlayerRenderer.cs` destroys the displayed clone's parent
  GameObject when a member leaves the world or a scene changes (the entry is dropped first, the parent is null-guarded
  at both sites — fixed with `bb9206178` for a different NRE).
- `src/CasualtiesUnknownOnline.GameAdapter/Character/RemoteMedicalCoordinator.cs` creates a display body by cloning
  `PlayerCamera.main.body.gameObject` for the wound view.

## The question this ticket cannot answer alone

Which of the two shapes is it, and what should the facial do?

- **A** — our clone removal leaves a `FacialExpression` alive on an object the game keeps: destroy the component with
  the body (or destroy the whole subtree in one call) so nothing ticks after the body is gone.
- **B** — the game's own transition destroys the local body while its facial still updates: patch nothing of the game's,
  and make our exception hook drop this known shape from the log (it is the game's own defect, not ours).

The recommendation is **A** first: the body is ours to destroy, and a component that outlives it is a lifetime bug on
our side. B is only the answer if the reading shows the body is the local player's during a transition.

## The reading that decides it

Patch the acceptance recorder (acceptance-only build) on `FacialExpression.Update`'s throw path to log the facial's
`transform.root.name`, its parent chain, whether `body == null`, and the body's `GetInstanceID()` when it is alive — then
reproduce a member leaving the world and read which root the facial belongs to.

## Design

The lifetime rule this ticket is judged by lives in `docs/design/game/README.md` (which objects this framework creates
and who owns their destruction) and in `docs/design/mechanics/medical-view.md` (the display body the wound view clones
from the local body). Both were read before the ticket was written: a body this framework instantiates is destroyed by
the same owner that created it, and a component that keeps a reference to it must not outlive that call.

## Acceptance rows
- [ ] After a member leaves the world, the host's log carries no `Body.get_peekingBehind` exception for that member's
      body (read: the log line count over a leave/rejoin cycle).
- [ ] The host's log growth over a ten-minute run is bounded (read: the file size before and after).

# 1.0: the pinyin search filters but matches no Chinese recipe name

The host's own crafting panel, read on the 1.0 release: the search filters the recipe list but the
pinyin query finds nothing, so a Chinese client cannot search by pinyin. What is missing is the
mapping step inside the filter for this build of the game.

## The reading (2026-11-13, the host on the release install, its UI in Chinese)

- `crafting-search query=flimsy` → `{"ok":true,"query":"flimsy","panelActive":true,
  "fieldText":"flimsy","rowCount":1}`; the plugin log carries `[Pinyin] recipe list filtered by
  'flimsy'.` then `[Pinyin] extended match: 'flimsy' matched 'flimsyknife'.`
- `crafting-search query=cuiruo` → `{"ok":true,"query":"cuiruo","panelActive":true,
  "fieldText":"cuiruo","rowCount":0}`; the plugin log carries `[Pinyin] recipe list filtered by
  'cuiruo'.` twice and no `extended match` line.

The plugin is installed and running (its log lines appear), the search reaches the game's own
recipe list, and the field text lands in the panel; only the pinyin-to-name matching produces no row.
The panel itself shows Chinese names (the crafting panel showed the fragile knife row in the same
session).

## What the row needs

1. Read the plugin's own matching path for this game build: which name it compares the pinyin
   candidate against (the recipe's display name vs the item's localized name), and whether the
   Chinese name is present at that point (the game may load the English name into the recipe object
   and localize only at the panel).
2. A fix in the plugin (a mapping loaded from the game's own localization) or, if the name is not
   reachable, the row is a product limit to record on the plugin's page.

The suite's crafting row (`crafting`) covers the crafting entry itself and passes; this pinyin row
stays parked on the sweep ticket (`docs/backlog/in-progress/1.0-regression-sweep.md`) until the
mapping is readable.

## Root cause read on the release decompile (2026-11-13)

- `reversing/release-1.0/Assembly-CSharp/PlayerCamera.cs:297` filters the recipe list with
  `r.Item1.simpleName.Contains(this.recipeFilter, StringComparison.OrdinalIgnoreCase)` and the row
  text at `:304` uses `fullName`; the tooltip at `:320` uses `simpleName`.
- `Recipe.cs:24-52` `fullName` = the sprite/repair prefix + `Locale.GetItem(result.id)` (+ condition,
  + amount); `Recipe.cs:56-88` `simpleName` = `Locale.GetItem(result.id)` for a solid result (the
  liquid branch uses `Locale.GetOther`). Both read the item's own localized name.
- The plugin's patch (`src/CasualtiesUnknownOnline.PinyinSearch/Patches/PinyinSearchPatches.cs:44-66`)
  hooks `string.Contains(string, StringComparison)` inside the refresh scope and matches
  `NameSearchMatcher.Matches(__instance, value)`. The logged instance for the `flimsy` match was
  `'flimsyknife'` — an id, not a Chinese name — so at least one call inside the filter scope carries
  the raw id, and the `cuiruo` query found no instance to match.

The ambiguity is which string the matcher receives: `simpleName` (Chinese name via `Locale.GetItem`)
or an id. The next probe logs `__instance` and `value` at every in-scope call for one query, which
tells whether the localization is missing for those ids or the call is on a different string.

## Options

1. If the in-scope calls carry ids because the game's locale table has no entry for them, the mod
   owns a small id-to-name table for the recipes it must match (its own data, loaded at build time).
2. If the calls carry the Chinese name and the matcher misses it, the matcher's normalization is the
   defect (the demo-era row passed, so a 1.0 string shape changed).
3. If the filter never runs through the patched overload for this build, patch the refresh's own
   filter step instead of `string.Contains`.

Recommendation: probe first (option 3's log line is one line in the existing patch), then pick 1 or 2
from the reading; this is a fixture-grade change, not a product redesign.

## Design

The crafting panel is a native surface named by [docs/design/game/README.md](../../design/game/README.md),
which is the page this row was read from.

## The probe read (2026-11-13 01:26, the rebuilt mod on the host, run in the crafting panel)

- `crafting-search query=flimsy` → `rowCount 1`; the log carries `[Pinyin] recipe list filtered by
  'flimsy'.` then `[Pinyin] probe filter='flimsy' instance='example.dressing'.` then
  `[Pinyin] extended match: 'flimsy' matched 'flimsyknife'.`
- `crafting-search query=cuiruo` → `{"ok":true,"query":"cuiruo","panelActive":true,
  "fieldText":"cuiruo","rowCount":0}` and the log carries NO `filtered by 'cuiruo'` line at all — the
  game's refresh did not run the filter step for that text.
- The deployed mod is the one built from this tree (`CasualtiesUnknownOnline.PinyinSearch.dll`,
  2026-11-13 00:55), so the probe line's absence for `cuiruo` is the game's behaviour, not a stale
  build: the strings the filter DOES see are English recipe ids (`example.dressing`), never Chinese
  names.

So the row has two halves: (a) the filter's own input is the English id on this build, so a pinyin
match against a Chinese name cannot fire; (b) a query that produces no id substring is not even
filtered (the row count goes to zero before the filter runs). The fix has to supply the Chinese name
the panel displays (`fullName`) to the matcher, and its entry point is the refresh, not the string
comparison.

## The root cause (read 2026-11-13 on the deployed 0.1.0 build)

The native filter compares `Recipe.simpleName`, which is `Locale.GetItem(result.id)` (`reversing/release-1.0/Assembly-CSharp/Recipe.cs:56-70`).
On this client that call returns the ID, not the Chinese the panel draws: with the new `[Pinyin] compared
'<text>'` line (12 distinct strings per refresh, the pinyin mod's own log) a `cuiruo` query compared
`rippeddressing`, `example.dressing`, `rope`, `canvas`, `sterilizedbandage`, `milk (500mL)`, … — every
one an English id. The Chinese the player reads comes from the game's translation mods, which draw text
the filter never sees.

The game's own table does have the names: `CasualtiesUnknown_Data/Lang/zh-CN.json` (431 KB) contains
`flimsyknife`, `rippeddressing` and `纤维绳`. A client whose GAME language is 简体中文 therefore compares
Chinese names and the pinyin layer matches; a client whose game language is English (the fixture's, with
Chinese drawn by a translation mod) compares ids and no Chinese query can match.

## The design (options and a recommendation)

- **A. Respect the game's language.** Keep the current rule (match what the filter compares) and document
  that pinyin search needs the game language set to 简体中文. Smallest change, zero new coupling; a player
  who runs English plus a translation mod gets no pinyin search.
- **B. Resolve names from the language table.** When the compared instance is an ID, look the Chinese name
  up in `Lang/zh-CN.json` (the game's own file, id → name) and match the query against that name as well.
  Works on every client, including the fixture's; couples the mod to the game's Lang file format and its
  presence (a missing file simply keeps rule A's behaviour).

**Recommendation: B**, because the user's stated goal is that a Chinese player can search by pinyin, and the
players who need it most are exactly the ones running an English base language with the community
translation mods. The cost is one file read and one dict, both already in the mod's own process.

**Open question for the user:** may the mod read the game's `Lang/zh-CN.json` directly (rule B), or must the
search follow the game's language setting (rule A)? The fixture cannot judge a zh client here — the boxed
clients run English and the game's language switch is a UI setting — so B's live row would be read on the
desktop host after this decision.

## The language reading (2026-11-13)

The client that ran the earlier probes had the game's language unset (Locale.LoadLanguage falls back to
EN), so Recipe.simpleName resolved to the English ids and the Chinese pinyin query had nothing to match.
With the game language set to Simplified Chinese (HKCU\Software\Orsoniks\CasualtiesUnknown, value
locale_h1422303533, UTF-8 zh-CN) and the host relaunched, the same query matched:
`[Pinyin] extended match: 'cuiruo' matched '脆弱小刀'`. So the matcher and the hook work for a player
whose game language is Chinese; the open question is only the English-language client (options A/B above).

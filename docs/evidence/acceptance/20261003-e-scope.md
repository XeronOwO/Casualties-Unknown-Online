# Batch 20261003-e — scope and acceptance plan

The acceptance plan for batch `20261003-e`, written before its session (workflow §3): the ticket set, the
setup the session runs, the trade row table the run writes first, and the capability boundary the verdicts
must respect.

- Commit under acceptance: the batch's scope commit (the commit that carries this page). The deployed
  artifact is built from it after it lands; every record carries its sha as the artifact's `+<sha>`.
- Artifact: `CasualtiesUnknownOnline.dll`, ProductVersion `0.1.0+<sha>`; `tools/verify-deploy.ps1` must
  report the deployment matches this tree's build output before the session.
- Preflight (2026-10-03, before the session): **11 present, exit 0**; `session-environment -Mode status`
  reported `active=cuo`, `game-running=false`, `swap-needed=false`, `launch=ok` before anything was
  launched. The Steam client was already running and is used, never restarted or stopped; the guest's
  sandbox Steam stays up, so the guest launch starts no second Steam.
- Dependencies used: the ids `tools/acceptance/preflight.ps1` reports present.
- Session: one world, host on the physical machine (launched through Steam, so Steamworks initialises),
  guest in the primary `Steam1` sandbox. No third client: the window plan assigns the third-peer families
  to batch `20261003-g`, so a row that needs a third peer is named in its record, never guessed from the
  two participant views.

## 3. Setup the session runs

S0 — **session and smoke.** Both clients enter one world through the Online UI. Smoke the batch's
instruments before any row depends on them: `trade-drive mode=list` (a trader with readable credit and
stock), `craft-drive mode=list` (the recipe table is built), `block-read-at` at the two cells the batch
will mutate, and `net-receive-blackout mode=status` on both ends (`armed:false`). Record the baselines
this batch's diffs use.

S1 — **recipe unlock, guest report swallowed** (`recipe-unlock-fallback` rows 1, 5 and 7;
`guest-report-fallback-first-resend` row 3; `sync-cadence-review` row 1).
Provide the craft fixture on the guest (recipe 0 is `2 × foliage → rope`): two `item-provide type=foliage
mode=create` calls, then `craft-drive mode=list` to record the recipe's `INT`/`visible` baseline. Arm the
host's inbound blackout, then have the guest create and use a `blueprint` (`item-provide type=blueprint
mode=create`, `item-use type=blueprint`): the guest's native branch reports the recipe index its blueprint
carries and the one-shot report is swallowed. Lift the blackout well inside the 15 s watchdog and read: the guest's local native
unlock line, its fallback re-report line, the host's merge apply, and both ends' `craft-drive mode=list`
reads. The record names whether the healing re-report landed on the entry phase's 5 s step or the steady
60 s step. Row 5's duplicate half is read from the repeated set deliveries that follow (the host's 60 s
repair cycle): repeats apply idempotently and no alert fires again. The no-blackout control for
`guest-report-fallback-first-resend` row 3 is the same block break staged with the host's inbound open:
the live report is adopted once and the pending entry clears with no re-send. `recipe-unlock-fallback`
row 7 is the crafting-report half: the guest crafts once (`craft-drive mode=make`) while the host's inbound
is blacked out, and the host's item table must still show the crafted item through the unchanged
keyframe/snapshot paths.

S2 — **recipe unlock, host relay swallowed** (`recipe-unlock-fallback` rows 2, 3, 4 and 5;
`sync-cadence-review` row 5). Arm the guest's inbound blackout; the host creates and uses a `blueprint`, so
its own unlock applies locally and its broadcast is dropped on the guest. Lift and read the host's set
send (`[Crafting] sent N unlocked recipe(s) to …`) on its 60 s in-session repair cycle and the guest's
`applied N unlocked recipe(s) from …'s set` with no per-recipe popup, then both ends' list reads. The
late-join rows are staged next: the guest leaves the lobby through the Online UI and rejoins the running
lobby, so its entry group carries the host's set; a second leave/rejoin re-delivers it idempotently
(rows 3 and 4). The entry-repair carrier for `sync-cadence-review` row 5 reuses the shape batch
`20261003-c` proved: the guest's inbound blackout around a host mutation, then the guest's own
readiness-window repeat (`scene-repeat`), read from the host's entry-repair answer and the guest's
converged state.

S3 — **guest-report fallback phases** (`guest-report-fallback-first-resend` rows 1, 2, 4 and 6).
Inside the guest's entry phase (the 60 s window after its own InWorld report — the re-entry staged at the
end of S2 opens it, and a further leave/rejoin re-opens one if the window closes before the break is
staged), arm the host's blackout,
have the guest break a known block (`block-set-at` then `block-break-at`) and, separately, inject a
runtime creation (`building-template-inject`); lift the blackout and read the guest's re-report and the
host's adoption, measuring the latency against the 5 s dense step. Then wait out the entry phase and
repeat the swallowed report: the re-report must land on the steady 60 s step — the record names the
measured interval. Count the dense re-sends inside the entry minute (the declared bound is 11) and read
the run's own traffic windows against the recorded baseline.

S4 — **trade rows** (§2). Both ends read the baseline with `trade-drive mode=list`.
Guest give: `trade-drive mode=give type=neuralbooster` (the credit fixture the batch-d record proved),
read the guest's report line, the host's executed line and both ends' lists. Guest buy: `trade-drive
mode=buy index=<the index read immediately before>`, then read the buy result's bought type and id, the
host's executed line, a host-side `container-read mode=host` for the bought id, and both ends' lists.
Host-local give/buy: the same calls on the host, read from the host's broadcast line and the guest's
converged list. Refused purchase: with the guest's inbound blacked out, the host consumes the stock entry
the guest will use, then the guest buys its stale copy; lift and read the host's `accepted=False` and the
guest's rollback line, plus both ends' lists. Lost broadcast: a host action while the guest is blacked
out, then the guest's convergence inside the fallback window (the host's `[Trade] snapshot` line at the
level the run sets). Late joiner: repeat the re-entry and read the guest's trader state against the
host's within the fallback window. Position key: compare the guest's `[Trade] report … trader=(x,y)`
line with the host's `[Trade] executed … trader=(x,y)` line.
Recruit (row 8, attempted last): the guest is killed with a declared `body-force brainHealth=0`; the host
stands at the trader; if the natural gates cannot be met in-session the run forces the trader's
reputation to its gate as a declared substitution, clicks the Online UI's own recruit control
(`member.recruit.<steamId>`), and reads the host's recruit lines, the target's revive line, a target
`body-read` and the target's carried items for the 1–3 gifts. Hostile swing (row 9, only if cheap): force
the nearest trader hostile as a declared substitution, stand a body in range, read the swing report/relay
on both ends and capture the non-acting side's window at the swing moment. A row whose fixture cannot be
produced ends `unproven` with the fixture named.

S5 — **close.** Both clients quit through the game; the run confirms no orphan process it started is left,
and collects the log channels, probe dumps and window captures for the records.

## 4. Capability boundary

- One two-client session serves the batch; a third peer's view is not judged here.
- The blackout is a blunt inbound cut: single-stepped, checked before arming and after lifting, and kept
  well inside the 15 s host-silence watchdog. A missed lift ends a session rather than a row.
- Late-join rows reuse the guest's own leave/rejoin into the running lobby, the shape batch `20261003-d`
  recorded; a bare rejoin that does not re-activate is a session problem, not a row verdict.
- Forced states the game gives no drive for (the recruit reputation gate, a hostile trader) are declared
  substitutions, never silent setup.
- The max-pressure harness is not part of this batch: `sync-cadence-review` rows 2–4 are handed to batch
  `20261003-l` and the ticket stays in `review/`.
- The guest sandbox's shadow is checked before launch — an older sandbox copy runs old code.

## 5. Exit criteria

- One record per ticket, `docs/evidence/acceptance/<slug>-20261003-e.md`, carrying the batch, the commit,
  the deployed artifact identity, one verdict and one evidence pointer per row, the dependencies used,
  the limits and any residuals.
- Transitions: all rows pass (or the remainder are residuals) → `docs/backlog/done/`; a `fail` → back to
  `docs/backlog/todo/` with `- Status: Todo — Rejected (…)` naming the row; a capability-limit `unproven`
  or a `blocked` row keeps the ticket in `review/` with the gap named. The index rows move in the same
  change as the tickets.
- Lessons fold into `docs/acceptance/lessons.md`, machine facts into `docs/acceptance/AGENTS.local.md`,
  and the moved-slug reference sweep re-runs before the closing commit.
- The gates run before the commit; the session ends with both clients closed and the machine free.

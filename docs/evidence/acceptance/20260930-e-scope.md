# Acceptance batch 20260930-e — scope, run plan and row classification

- Batch: `20260930-e` — one session with three scenario groups: (A) the three-client carry/pose run,
  (B) the carried-container run, (C) the session-special reconnect run. The groups share the world, so
  they share the bring-up; the run log records which group ran, in which order, and any deviation.
- Run A's first step is a capability check: does the alternate sandbox (`sandbox-alt-root`) start as a
  third client with its own Steam account, reach `hotrepl-alt-url`, and enter the same world? The answer
  decides group A's rows; the check and its outcome are recorded in the run log, and the `sandbox-alt`
  capability row is added to `docs/acceptance/dependencies.md` in the same change as the run's records.
- Run B needs the container recipes built in this batch's development half (committed under
  `tools/acceptance/recipes/`): guest pickup → load into a carried container → movement, plus the
  host-side drop/table reads. It is planned only once the recipe smoke passes in the session; if it does
  not, group B keeps its setup gap and the reason is recorded.
- Run C is driven through the committed driver: guest `quit`, relaunch of the sandbox client, rejoin of
  the same world, host-side reads. It runs after groups A and B in the same session.
- The artifacts of this run live under the directory named by `acceptance-artifacts-dir`, subdirectory
  `batch-e`; the records cite artifact ids only.
- Rows judged here are judged from this run's own evidence against the deployed artifact, per
  `docs/acceptance/AGENTS.md`. A row this run cannot decide is named with its class and the ticket stays
  in `review/`.

## Group A — three-client carry/pose (4 tickets)

### `carrier-sit-while-carrying` — row 3 (third-party view)

- Class: visual.
- Scenario: force the carrier's `idleTime` while the carry relation is live, in both directions; the
  third client reads its carrier clone (`Sitting` false, no sit replay, `Grounded`) and captures its own
  window; the non-carried idle-sit control was already judged in batch d.
- Expected: the suppression is visible on the third client's view and the clone never replays the sit.
- Evidence: a third-client evaluator reading + a third-client window frame.

### `carry-piggyback-rider-position-smoothing` — row 3 (third-party view)

- Class: feel (frame read plus the instrumented reading).
- Scenario: a carry relation in each direction while the carrier walks, turns and crouches (a
  `move-drive` slide window, since walk is frame-window dependent); the third client's clone diagnostics
  are read across the window.
- Expected: the third view keeps the rider attached within the same tolerance as normal remote-player
  smoothing (`pinned-to-carrier`, `riderDrift=0`, `limbSeparation=0`, no `Carried rider clone …`
  warning).
- Evidence: third-client readings across the window + window frames; the millisecond remainder is a
  residual.

### `carried-rider-own-body-stops-simulating` — row 7 (third peer watching the carry)

- Class: visual.
- Scenario: the same carry scenes read from the third client.
- Expected: unchanged from the two-client behaviour.
- Evidence: third-client clone readings + window frames.

### `carried-player-idle-sit-suppression` — row 5 (remote-clone sit-end transition)

- Class: machine.
- Scenario: a stationary non-carried body (the third client's own body while neither carrying nor
  carried) is forced into the native idle-sit while another client watches its clone; it then moves
  (`slide`) and the watching client reads the sit-end transition.
- Expected: `Sitting` returns false, `Grounded` is restored, and no sit clip lingers on the clone.
- Evidence: probe reads on the watching client before and after + the clone diagnostics line.

## Group B — carried container (2 tickets)

### `guest-container-contents-ghost-drops-on-host`

- Row 1 (no periodic ghost drop on the host) — class machine: with the guest carrying the loaded
  container, the host's world-item ids and drop events are read before and after a movement window and
  must not gain the container's nested item.
- Row 2 (both views show the contents consistently) — class visual: the container contents are read on
  both clients and the native inventory/container panels are captured; those panels are large enough to
  read, unlike the world at the game's native zoom.
- Row 3 (no ghost or dropped item after reconnect) — class machine + visual; decided in group C.
- The recipe states the concrete item pair it uses and the setup sequence; the run log records it.

### `carried-inventory-registration-re-report`

- Row 1 (a swallowed registration converges) — class machine; the run clears the host's per-guest
  carried-id table through the evaluator, a direct precondition for the swallowed frame (recorded as a
  substitution in Limits), then reads the table after the dense re-report cadence and confirms the ids
  return and arbitrate.
- Row 2 (an id added after the first report converges) — class machine; an item added in the container
  scenario is read into the host's table on the next report.
- Row 3 (reconnect rebuilds the table exactly once) — class machine; decided in group C.
- If the host table is not reachable from the evaluator, rows 1–2 are recorded `blocked` with the
  missing setup and the ticket stays in `review/`.

## Group C — reconnect (rows from both group-B tickets)

- Class: machine, with a frame where the item state is visible.
- Scenario: while in world, the guest quits through the driver; the run relaunches the sandbox client,
  waits for `hotrepl-guest-url`, joins the host's lobby id again, and reads the host's carried-id table,
  the kernel item state and the container contents on both views.
- Expected: the table is rebuilt exactly once per id; no duplicate, ghost or dropped item appears; the
  container contents still read consistently.
- Evidence: host and guest reads before and after the rejoin, the CUO log's registration lines, frames.

## Split out

Every other waiting ticket is out of this batch: its scenario needs a capability this run does not
carry (a different world or save, a native-menu path, sound capture, a long-run timing window, or a
peer count beyond this session's). Those tickets keep the setup gap named on their own records and stay
in `review/`; nothing outside the six tickets above is judged here.

## Run sequence (one session, one world)

1. Preflight (now including the `sandbox-alt` row), `session-environment -Mode status` and
   `-Mode ensure-cuo` when needed; build, deploy and verify the artifact identity before any row.
2. Bring-up: host through Steam; guest in the primary sandbox; third client in the alternate sandbox;
   all three evaluator endpoints answer; create/join/start through the Online UI driver; each client
   sees the other two clones.
3. Spawn check: the game's own `origColSize` OverlapBox against the `Ground` layer; a caught body is
   lifted before any movement scenario.
4. Group A scenarios (both carry directions, movement windows, forced sit and idle states), with
   third-client readings and frames.
5. Group B container scenario (recipe-backed), host/guest/third reads and frames.
6. Group C reconnect (guest quit → relaunch → rejoin), host reads and frames.
7. Close: quit all clients through the driver; collect the three log channels; verify no game process
   remains.

## Method

Every row is classified before the run (above), and each ticket's record carries the same
classification with its verdict and its evidence pointer. `machine` rows are read from the probes, the
logs or the repository suites of this run; `visual` rows from window-level frames this run captures
and the agent reads; a row that stays subjective after the frame read is named a residual for the
user, never a pass. The third client is part of the same session rather than a separate run because it
shares the world and the setups.

## Limits

- The third client is a new capability: its Steamworks and account state is `unknown` from outside, and
  the run's first attempt settles it. If it cannot start, join or reach its evaluator, group A's rows
  are recorded `blocked` with the failure and groups B and C continue with the two remaining clients.
- The world frames render characters a few pixels wide at the game's native zoom (lessons.md,
  2026-09-28); a pose row the frames cannot resolve becomes `residual` or `unproven`, never a pass. A
  camera-override probe may be attempted to read a frame: if it is used, the record says so and the
  deviation is part of the Limits.
- The swallowed-registration row is judged against a forced precondition (the table cleared through the
  evaluator), not a real dropped frame; the record states the substitution.
- One session does not disprove a rare race; a row about timing repeats inside its window and the
  repetition count is recorded.

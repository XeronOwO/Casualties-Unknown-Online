# Each acceptance row is rebuilt from the game, not from the row's own code

- Status: In progress (2026-11-22) — the user's ruling after the 39-row batch drifted between runs: every row is
  reviewed one at a time, in order, and each review may read only two sources — the game's own code (`reversing/`)
  and what the machine actually shows — never the existing case implementation. Writing the gate, or patching a
  row from what the row already does, is out.
- Priority: High
- Created: 2026-11-22

## Why this ticket exists

The reader's ruling: the acceptance chain itself is the fault, not one row.

- A row that calls the game's own function proves the function works, never that a player can reach it.
- The rows must assert what a player sees — the identities offered when somebody joins mid-run, the loading
  background — not only internal readings.
- Mashing a key to dismiss a surface is not a player action, and its side effects leak into later rows.
- The inner loop is build, unit tests, gates and reading the report; a suite run happens once per finished unit of
  work.
- Each row is reviewed on its own, and its sources are the game's own code and the running game — never the row's
  existing implementation.
- The ruling is written down before anything is done with it.

## The review a row gets (same steps for every row, in the suite's own order)

1. **The player's claim.** One sentence a player would say, in the player's words, that the row either confirms
   or refutes.
2. **The game's own mechanism.** Read the game's code for that claim: which class holds the fact, which input
   the player presses, what the game does with it, what the player then sees. Quote it with file and line.
3. **The machine's fact.** Do it on the real game as a player would and record what happened — the reading, and
   a window capture when the claim is visual.
4. **The row.** Written from 1–3 only: the preconditions it declares, the keys and pointer moves it posts, the
   visible facts it asserts (identities, screens, sounds, the world), and what it restores afterwards.
5. **The fault sheet.** Fault-finding with no charity — for the row as it stands today, three questions answered with an example
   each, never "looks fine": what does it judge too loosely, what does it not judge at all, and which of its
   operations is not something a player does.

## Row 1 — world-fingerprint

**The player's claim.** "I see the same world my friend sees, and when they dig a block out, that block is gone on
my screen too."

**The game's mechanism (read from `reversing/release-1.0.2/Assembly-CSharp`, not from the row).**

- The world is one `ushort[,]` grid, `private ushort[,] worldBlocks;` (`WorldGeneration.cs:5579`), read through
  `GetBlock(Vector2Int)` (`WorldGeneration.cs:809`) and written through the setter at `WorldGeneration.cs:777`.
- What the player sees is not that grid: each chunk's `Tilemap` is drawn from it with `SetTile` at
  `WorldGeneration.cs:1595` (and `:1506` during generation), one tile per cell.
- A break is damage, not a delete: `blockDamage.damage += dmg`, `blockDamage.UpdateSprite()` shows the crack stage,
  and only at `damage >= blockInfo.health` does the game play the block's hit and step sounds, spawn the
  `blockBreakPrefab` particles shaped from the cell's own sprite, and hand out loot (`WorldGeneration.cs:840-900`).
- The input is the player's own attack: the player holds the attack key pointing at a cell (mouse position read at
  `WorldGeneration.cs:1062`); nothing in the game needs a "set block" call to break one.

**What that says about the row.** Its claim is about the drawn tile on both screens, so the assertions have to be
the cell's tile and the sounds, and the action has to be the attack key at that cell's screen point. The row's
current shape (a hash plus a recipe call) is in the fault sheet above for exactly that reason.

**The machine's fact, first pass (2026-11-22 11:36, host in an IP run).**

- The host answered the game's own search: `block-find-breakable count=3` → `{"count":3,"cells":[{"x":14,"y":505},{"x":15,"y":505},{"x":16,"y":505}]}`, so the cells this row can break exist and are named in world coordinates.
- The cell's screen point came from the game's own camera: `screen-project x=15 y=505` → `{"screenX":848,"screenY":724,"screenHeight":720}`. The point sits four pixels below the drawn area: the camera was parked with the player under the row, so the first attempt to act on it was looking at the wrong part of the screen, not at a missing block.
- OS-level input is not available for this: `input --action key` refused with `could not bring 'CasualtiesUnknown' to the foreground (the click/key would go to another window)`. The suite never steals focus, so a row that wants the game's own attack key has to post the key message on the client's own window (`key-hold`), which needs the `window-key` declaration on that client's connection.
- Declaring it through separate `drive` calls does not work: each call opens its own connection, so the declaration is gone before the recipe compiles (`The name 'AcceptanceWindowKey' does not exist in the current context`). The declaration has to be sent inside the run that uses it — the suite's cached driver — which is exactly the shape the rebuilt row will take.

**The row as it now stands (2026-11-22 11:47, measured four times).** The row was rewritten to the player's shape: it asks the game for breakable cells beside the host's player (`block-find-breakable count=24`), keeps the first whose projection lands inside the drawn area, reads that absolute cell on both clients (`block-read-at`), stages the game's own pointer over it (`virtual-input mode=move`), holds the attack, and then requires the crack stage to rise and the cell to be gone on both clients.

The measurements so far: the cell is found and projected (e.g. `(13,470)` at `688,976` was off-screen and rejected; `(15,430)` was accepted); the pointer is staged; and the attack never lands — `block-read-at` keeps answering `{"block":1,"damage":-1}` after 15 s of holding, both with `mode=press` (the game's `GetMouseButton` answer) and with `mode=press-key` (its `Input.GetKey(KeyCode.Mouse0)` answer).

**Why it does not land, from the game's own code.** `WorldGeneration.Update` only *reads* the mouse while Mouse0 is held (`:1062`) and discards the result; the damage itself is applied by the player's body: `Body.cs:2168` calls `WorldGeneration.world.DamageBlock(raycastHit2D3.point + vector * 0.05f, atk.structuralDamage * num2, …)` from inside the body's own attack swing, raycasting from `this.limbs[1]` along `vector` (the aim direction) for `atk.distance`. So a block break is a *swing* of the player's held item, not a held button: the next thing this row has to establish is the swing's own preconditions (what the body must be holding, its attack cooldown, and the aim vector it derives from the pointer) before the assertion can be written from a real break.

**The reading that narrows it (2026-11-22 11:52).** The row now asks the staging for its own report right after pressing. The host answers `{"installed":true,"buttonPatches":3,"keyQueries":77,"keyDownAnswers":0,"keyHeld":false,"keyDown":false,"pointerX":"656","pointerY":"710"}`: the game does ask the staged seam (77 key queries answered with the pointer sitting on the cell), but the attack key it asks for never reads as held, and `GetKeyDown` never answered at all. So the miss is inside the staging's key state, not in the row's cell choice or the pointer.

**The next question this leaves (2026-11-22 11:58).** The staging's own answer is not the game's answer: `Input.GetKey` is deliberately not detoured (the patches replace the call sites inside the game's methods), so the `keyHeld:false` in the report is a fact about the *report*, not about the game — the counters are the game's side, and they say the same "not held". Two candidates are left, and the cheaper one is first: the bind the game asks for may not be `Mouse0` at all (`KeyBinds.GetBind("attack")` is set from `Settings.cs:464`), so the next probe reads that bind on the client and compares it with the key the batch staged; only if they match does the staged `ButtonState` itself become the suspect.

**That candidate is now measured and gone (2026-11-22 12:04).** `keybind-read --action attack` on the sandboxed client answers `{"ok":true,"action":"attack","bind":"Mouse0"}`, so the batch stages exactly the key the game asks for and the `ButtonState` lookup cannot miss on the key. What the counters still cannot say is the split the row needs: `KeyQueries` counts every held/down/up question together and `KeyDownAnswers` only counts `down` answers, so "the game asked 77 times" is compatible with "every held answer was false". The next probe must count the *held* answers that came back true (`InputQueryPatches` keeps only the down tally today), and read the body's own `conscious` and `attackCooldown` in the same breath, because `Body.Attack` is gated by both (`Body.cs:2038`).

**The counters now answer, and they point at the client's frame loop (2026-11-22 12:10).** The held tally is in: a 15 s hold on the attack, with the pointer on the cell, reads `{"keyQueries":77,"keyDownAnswers":0,"keyHeldAnswers":1,"handleAttacksEntries":3,"handleInputEntries":3}`. One held answer in seventy-seven questions, and `PlayerCamera.HandleAttacks` entered three times in the whole hold, is not a staging fault: it says the client's own update loop is barely running while the row waits. The same three entries explain why a swing never completes. The next measurement is therefore the client's own time — read `Time.frameCount` twice a second apart during the hold — and, if it is advancing at a fraction of real time, the cause is the client running unfocused (`Application.runInBackground`) rather than anything in the row.

**The frame clock clears the client of starving (2026-11-22 12:20).** The new `frame-clock` recipe read twice a second and a half apart on the sandboxed client answers `{"frame":2,"realtime":3.871,"timeScale":1,"runInBackground":true}` then `{"frame":525,"realtime":7.122,"timeScale":1,"runInBackground":true}` — about 160 frames a second with the window in the background, so the client is not throttled and the pause is not the window's focus. Three `HandleAttacks` entries therefore mean that code path itself was not entered during the hold, not that the game was standing still. The next question is exactly that gate: which condition keeps `PlayerCamera.HandleAttacks` from running while the row holds the attack with the cell on screen.

**That method's early returns are now measured (2026-11-22 12:35).** `PlayerCamera.HandleAttacks` (`PlayerCamera.cs:1995`)
returns before it reads the attack key while the pointer is over a UI element: `if (this.woundView.activeSelf ||
UIUtil.IsPointerOverUIElement() || MinigameBase.main.currentMinigame || LiquidTransfer.instance || this.blockItemUsage)
return;`. `UIUtil.IsPointerOverUIElement` raycasts the EventSystem at `Input.mousePosition` (`UIUtil.cs`), so the row can ask
the same question the game asks. It does: `ui-raycast` on the host, right after staging the pointer on the cell, answers
`{"overUi":false,"count":0}`, so the pointer is not over UI at the moment of the press. The first version of the cell
search did put the pointer under the bottom bar (`screenY 682–732` of 720) and every swing was refused there; the search
now walks cells nearest-first around the player and the row rejects any projection inside `(120, width-120) × (120,
height-140)`.

**And the swing's own geometry is now measured (2026-11-22 12:45).** `attack-swing-probe` reads the body the swing would
use: `{"ok":true,"conscious":true,"cooldown":-6.013,"bodyX":0,"bodyY":506,"handX":-0.65,"handY":504.66,
"lookX":2.25,"lookY":502,"distance":3.94,"aimDegrees":-42.5,"targetDistance":675.46,"inRange":false,"hitName":"Body"}`.
The body is conscious and its cooldown is spent, so `Body.Attack` would run; but the cell the row pressed at stood 675
world units away from the body — the scan answered cells around x=672 while the body stood at x=0, i.e. the scan's
coordinates are not the body's. That is the current blocker: the cell the row picks has to be filtered against the body
position the scan itself reports (`bodyX`/`bodyY` are now part of its answer, and cells further than the swing's reach
of 4.5 units are dropped), and the aim vector has to point at that cell (`lookX/lookY` currently aim at `2.25,502`,

**The row is parked on a fixture fact, not on a product fact (2026-11-22 23:20).** Everything up to the swing now works
and is measured: the aim closes on the cell with the game's own camera loop, the attack is held with the game reading it
(`keyHeldAnswers` rises every frame), the ray is read before the swing, the row adopts the block the ray really meets,
and the air-block and pod-exit steps are in. What it cannot do is get a spawned body next to real rock:

- the capsule's shell stops the body at `x ±4.085` whatever the direction held (`row1-166`, `row1-167`, `row1-168`), and
  `up`/`down` move nothing from a settled body (`[up 0.00] [down 0.00]`), so the body never gets out of the pod;
- the breakable scan answers with rock outside that shell, and from inside the pod the hand's ray meets only the pod's own
  fixtures (`DisinfectButton`, `lifepodpump`) or nothing at all — the game's damage branch then never runs;
- the floor slides: three 120 ms presses carried the body from x 0 to x 30 with `velX 25`, so the walk now brakes and
  coasts, and it still cannot pass the shell.

Options, with the cost of each:

1. **Start the row in a saved world where the body already stands outside** (a `--reuse` world from an earlier row, or a
   save cut taken after the capsule is left). Cheapest, and true to the claim ("a block the host digs out is gone on the
   member's client"), because the row no longer has to reproduce the intro. Risk: the row then depends on another row's
   world, which the standing order (one run, every case) makes acceptable only if the dependency is declared.
2. **Teach the fixture the capsule's exit** — measure which key or interaction opens it, per spawn. Honest but expensive:
   three rounds have gone into it and the vertical keys read zero from a settled body.
3. **Drop the row to a different world action the body can perform from where it spawns** (digging is not the only way a
   world changes: dropping an item, opening the pod, cutting a limb each change the world on both ends). Loses the
   original "dig a block" claim, which is the one the user named.

Recommendation: option 1, with the dependency written in the row's own comment and in the run sheet, and option 2 kept as
the next step only if the user wants the intro reproduced. The row itself stays red until one of them lands.


## Row 2 — starting-supplies

**The player's claim.** "A friend who joins my run for the first time starts with the run's starting supplies —
the same kit I got — and sees it in their own inventory."

**The game's mechanism (read from `reversing/release-1.0.2` and from our own adapter, not from the row).**

- The game hands the kit out inside generation, in `WorldGeneration.WorldPlacePlayer`, and only on the run's first
  layer: the branch is guarded by `totalTraveled <= 0 && biomeOverride == None && debugStartDepth == 0`
  (`WorldGeneration.cs:1891`), reads the run setting at `:1899`, and creates the items at `:1904-1912`.
- The setting is `startingsupplies` with three values, `none` / `light` / `full` (`RunSettings.cs:53`).
- Because that branch lives inside generation, every later entry — a member joining, a restored world — gets
  nothing from the game. CUO reproduces the same grant for those paths (`StartingSupplyCoordinator`,
  `StartingSupplyPolicy`), with the same setting, the same content ids and the same slots, and names why it did or
  did not supply (`Granted`, `Disabled`, `AlreadyOwned`, `CharacterRestored`, `NoBaseline`).
- For setting `light` the plan is exactly four items, each in a fixed slot: `lantern` → 3, `dogfood` → 4,
  `waterbottle` → 5, `trashbag` → 1 (`StartingSupplyPolicy.cs:83-89`); `full` is `emergencylight` alone → 3.
- The player's own view of that fact is the inventory screen, which the game draws from the body's container
  slots; the game's own pickup refuses an occupied slot silently, so a duplicate grant is invisible except as
  items left on the floor or a bag that never matches the plan.

**The machine's fact (to measure, not yet taken).** Join a member into a fresh run with `startingsupplies = light`;
capture the member's inventory screen; read the bag's ids *and slots*; rejoin the same character and confirm
nothing is granted twice. Until that is recorded the row below is a plan, not a row.

**The row (planned, from the three steps above).** Host starts a run with `light`; the member joins for the first
time; the row opens the member's own inventory (the game's key, not a container read), asserts exactly the four
ids in slots 3, 4, 5 and 1 with nothing else added, asserts a rejoin grants nothing new, and leaves the run as it
found it.

**Fault sheet (the row as it stands today).**

- **Judged too loose.** It accepts `carried >= 3` and only checks that every id is one of five names, so a bag of
  three of the four light items passes, and a swapped slot passes: the plan's slots are the fact the player sees.
  It also reads `container-read mode=local`, a container, instead of the screen the player looks at.
- **Not judged at all.** Nothing asserts a second entry of the same character gets no second kit (the
  `AlreadyOwned` path); nothing asserts the setting `none` yields nothing and `full` yields its own item; nothing
  asserts the host's view of the member's bag agrees with the member's own.
- **Not a player's operation.** The row's only action is the join itself (which is real); it never opens the
  inventory, so the visible half of the claim is never exercised.



## Row 3 — crafting

**The player's claim.** "I open the craft screen, pick something my starting materials allow, press make, and the
thing I made is in my bag."

**The game's mechanism (read from `reversing/release-1.0.2`, not from the row).**

- The screen is the game's own toggle: `PlayerCamera.OpenCraftScreen()` flips `craftingPanel.SetActive(...)`
  (`PlayerCamera.cs:192-203`), and `PlayerCamera.cs:1039` stops movement while that panel is open — the same gate
  the row-1 review met.
- The list the player sees is built from `Recipes.recipes` (`PlayerCamera.cs:377-388` renders each recipe's
  ingredients and quality), and the row is chosen by the player (the selected recipe index).
- The make itself is one call from the panel: `Recipes.recipes[this.selectedRecipe].TryMake();`
  (`PlayerCamera.cs:510`). Everything a player observes — materials consumed, product count, the item landing in a
  slot — follows from `TryMake` and the game's own pickup path.

**The machine's fact (to measure, not yet taken).** Open the craft screen with the game's own key on a fresh run,
capture the panel, select the first recipe the starting materials allow, press make through the panel, capture the
bag before and after, and read which materials left and which slot the product took.

**The row (planned).** The row presses the game's craft key, reads the panel's recipe list from the game, selects
the first recipe the game itself calls craftable, presses the make control, and asserts on the visible result:
the exact materials the recipe names are gone, the product appears in the bag in the slot the game picked, and the
panel still shows the recipe as uncraftable afterwards.

**Fault sheet (the row as it stands today).**

- **Judged too loose.** It asserts only `afterCount > beforeCount` from the driver's own reading — a product count
  it never ties to an item identity, a slot, or the crafting panel. A craft that produces the wrong item, or one
  whose materials were never taken, passes.
- **Not judged at all.** Nothing asserts the materials the recipe names actually left the bag, nothing asserts the
  product's identity or slot, and nothing asserts the panel's own state changed (the recipe's craftable flag).
- **Not a player's operation.** It calls `craft-drive mode=make` with an index parsed out of the driver's own text;
  the player opens the panel with a key and presses the make button, which is `TryMake` (`PlayerCamera.cs:510`).



## Row 4 — lockpick

**The player's claim.** "I walk up to a locked door, start picking, keep my hand steady in the sweet spot until it
gives, and the door is open afterwards."

**The game's mechanism (read from `reversing/release-1.0.2`, not from the row).**

- The minigame is `LockpingMinigame` (the game's own spelling), constructed with the building it locks and a
  precision (`LockpingMinigame.cs:39-46`).
- The hand's angle is not a stored value: it is `VectorToAngle(Minigame.game.handPos.normalized)`
  (`LockpingMinigame.cs:58-62`), so the pointer drives it through the game's own hand physics.
- Progress comes from holding the hand inside the target angle: `MaxTurnProgress()` compares `HandAngle` with
  `correctAngle` under `anglePrecision` (`:77-80`), and `Update` only counts while the hand is inside the ring —
  `HandAngle` between 0 and 180 degrees and the hand 195–247 units out (`:106-123`), `lockProgress +=
  Time.deltaTime * (0.66 + num * 0.065)`.
- The completion is the game's own: the break sound and the unlocked building, which is what the player hears and
  then walks through.

**The machine's fact (to measure, not yet taken).** On a fresh run, walk to a locked door, press the game's own
interact key, hold the hand in the sweet spot until the pick completes, and record: the progress while held, the
sound, and the building's locked flag before and after — plus the member's screen showing the same door open.

**The row (planned).** The row presses the game's interact key at the door, moves the pointer so the hand enters
the ring, holds the pick through the game's own attack key, asserts the progress rose while held and the door's
locked flag flipped, and asserts the member's client draws the same door unlocked.

**Fault sheet (the row as it stands today).**

- **Judged too loose.** Its reading is the game's completion sound, so a door that plays the sound while staying
  locked passes; nothing asserts the lock's own state. The angle precision the game shows the player is never read.
- **Not judged at all.** Nothing asserts progress rising while the hand is held (the mechanic the player performs),
  nothing asserts the lock cannot be picked twice, and nothing asserts the member sees the door unlocked.
- **Not a player's operation.** `lockpick-open` builds the minigame and `lockpick-aim` places the hand; a player
  presses interact on the door and moves the mouse. The row also opens our own CUO window first to make Escape
  deterministic — a fixture workaround the player would never do.



## Row 5 — capability-report

**The player's claim.** There is none, and that is the finding. A player never reads our boot log; what a player
can see is the panel saying a system is missing, or a session that refuses to start. This row's subject is the
adapter's own self-report, which the gate suite can read without a world, a client or a pad.

**The mechanism it reads (our own writer, plus the game-assembly probe).**

- The report is written by `AdapterCapabilityReporter.Publish` (`src/CasualtiesUnknownOnline.GameAdapter/Capabilities/AdapterCapabilityReporter.cs:45`),
  which prints each capability with its Required/Optional class, its contract count, and the game-assembly probe's
  own line (`AdapterCapabilityProbe`), and logs a refusal at Error level.
- The row greps that block out of the host's `latest.log`, counts the `[Required]`/`[Optional]` rows, and compares
  the ids against a list of thirteen names held in the row itself.

**The machine's fact (to measure, not yet taken).** With one capability deliberately removed (the adapter's own
fault-injection path exists: `InstallFaultInjection`), the report must say which system is missing in the same
place a player can see it — the panel — and a session must refuse to start rather than half-work.

**The row (planned).** Keep the log reading, but make it a gate, not an acceptance row; in acceptance the row
should assert the player-visible half: with a required capability missing, the panel names it and the session
does not start, and with everything present the panel says the session is available.

**Fault sheet (the row as it stands today).**

- **Judged too loose.** It asserts a row count and the presence of thirteen ids; the counts themselves are never
  required to be non-zero, so a report of thirteen zeros passes. `WaitForReportAsync` looks for the block's header
  anywhere in the log, so a stale report from an earlier boot in the same file passes too.
- **Not judged at all.** Nothing ties a missing Required capability to what the player sees (panel text, refusal to
  start); the game-assembly probe line's content (which build it named) is never compared with the build under test.
- **Not a player's operation.** The row's only action is reading our own log file — no key, no pointer, no screen.
  Its subject is the adapter's self-report, which belongs among the gates that run without a game.

## Row 6 — medical-chart

**The player's claim.** "I look at my friend's body and the medical chart I get is theirs — their wounds, their
numbers, their name — and it doesn't offer me the things I could only do to myself."

**The game's mechanism (read from `reversing/release-1.0.2` and from our adapter).**

- The chart is the game's own wound view: `PlayerCamera` toggles `woundView` and refuses to open it on a viewer that
  is not alive and conscious, which is the refusal the row met in the full run (`alive true, conscious false`).
- The numbers the chart draws come from the body it is focused on, so "which body" is the whole claim: our adapter
  focuses a remote body through `medical-open`, and a per-frame pass hides the three local-only surfaces (nap,
  workout, HUD hand swap) because the game builds them for a local body.
- Nothing in the game provides a "remote focus" flag: the adapter's per-frame pass is the mechanism, so the row's
  subject is that pass plus the game's own drawing of the focused body.

**The machine's fact (to measure, not yet taken).** Walk to the member, open the chart with the game's own key, and
compare what the panel draws with the member's own chart: same name, same wounds, same numbers on both screenshots,
and the local-only actions present on your own body but not on theirs.

**The row (planned).** Host walks to the member and presses the game's wound-view key with the member focused; the
row asserts the panel's header is the member's identity, that the wound list and numbers equal what the member's own
client shows for its own body, and that the three local-only controls are absent and, when the panel is forced to
show them, pressing them changes nothing.

**Fault sheet (the row as it stands today).**

- **Judged too loose.** It asserts `medical-open` answered `opened`/`nativeOpen`, the panel's `viewOpen`, and the
  presence/absence of control labels. It never compares a single number the panel draws with the member's actual
  body, so a panel that draws the host's body under the member's name passes.
- **Not judged at all.** Nothing asserts the chart's numbers equal the member's own readings, nothing asserts the

# The item colour does not survive save/continue

- Status: Review — the live clones show the edit, but the character snapshot written at the save still carries the old item colour. The 2026-11-16 live run is red.
- Priority: High
- Created: 2026-11-16

## What the player sees

A player opens the native item customizer, sets a colour on a carried item, closes it, and the other client immediately shows the new colour. The host saves and leaves; after Continue the item is back to its old colour, and the saved character record has `swatch: 0`. The live view and the saved view disagree.

The user's requirement (m11880): the colour is local to each player, travels as multiplayer data, and survives exit/rejoin.

## Evidence (2026-11-16)

- `.acceptance/color5/report/report.md`: `save-continue` fails with `the member's colour did not survive the save/continue`; the after list is the four starting items with `swatch: 0`.
- Before the save, both live clone reads pass: host sees the member's `MemberColor/5`; member sees the host's `HostColor/3`.
- Saved world `...cuo\saves\w-...` `live/characters/name-host.json` and `name-guest.json` both write the item `colorSwatch` as 0.
- `latest.log`: `/save` Command cut committed at 02:10:46; the MenuReturn cut committed at 02:10:49. The host logged `[CloneRender] local body changed — immediate re-report` at 02:10:45.943, so the customizer-close report ran.
- `CharacterDataClone.Of` now copies `Label` and `ColorSwatch` (commit `57233c9b5`, unit 3/3), yet the saved record is still 0. The clone is not the last loss point.

## Chain read

- `CharacterDataSync.ReportInventoryChanged` sends a `CharacterDataMsg`; `CharacterDataHandler` on the host calls `CharacterDataStore.SaveReportedCharacterData(sender, msg)`.
- `CharacterDataStore.SaveReportedCharacterData` refuses a whole report only for non-finite values; otherwise stores `CharacterDataClone.Of(msg)` under the `sender` key.
- At the cut, `WorldCharacterBinder.Collect` uses `characters.GetSavedCharacter(peer.PeerId)`; the key may not be the same identity as the transport `sender` under IP-direct (the `PeerId` vs transport-id question from the identity ticket).
- If the key differs, the cut writes an older/initial record while the live clone renders the newer report under the sender key. This is the leading hypothesis; it must be confirmed by printing both keys at the cut.

## Design

- `docs/design/game/items.md` — the item snapshot and the customizer's completion event.
- `docs/design/cross-cutting/saves-and-recovery.md` — the character record is keyed by the transport-scoped player key; a reconnect with a new transport id is the open seam.

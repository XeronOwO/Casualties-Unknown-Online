# Acceptance batch 20261001-j — scope, run plan and row classification

- Batch: `20261001-j` — one two-client session for the Online UI presentation and geometry family.
- Tickets in scope (6): `online-ui-layout-and-input-detail-pass`, `online-ui-art-and-controls-overhaul`,
  `cuo-launcher-button-obscures-the-view`, `online-ui-panels-request-alpha-blend-false`,
  `remove-the-online-ui-console-page`, `official-game-name-in-window-title`.
- Why one batch: every row below reads the same surface on a running client — the Online UI window,
  its controls, the launcher, and the world-space overlays it draws — so the six tickets share one

  not inject OS input, so that family has no executable setup path in this run; it is not judged here
  and stays in `review/`.
- Row classes are fixed here, before the run. Each ticket's record repeats the same classification
  with its verdict and its evidence pointer.

## Run sequence (one session, one build)

1. Offline chain: build → the pin suites and the full suite → `deploy.ps1` → `verify-deploy.ps1`. The
   artifact identity is recorded before any row is judged; group E row 5 rides this chain.
2. Host bring-up: launch through Steam; `ping` / `state` through the in-process driver; `open-window`;
   first frame capture.
3. Groups A, B, E and F on the host alone (the window is local), in the order their tables list.
4. Group C on the host: idle reads, click toggles, frames.
5. Guest bring-up and the world half: join and start the run through the driver; the console overlay
   and the world overlays for groups D and E; group A's forced medical panel (row 8); group A's world
   surfaces (row 11).
6. Close: `quit` on both clients; collect the log channels; verify that no game process remains.

## Method

`machine` rows are read from the in-process evaluator, the log channels or this run's own suites;
`visual` rows from window-level frames this run captures and the agent reads. A row this run cannot
put the world into is `unproven` with the missing setup named; a subjective remainder is a residual
for the user, never a self-issued pass. Rows are repeated where the row is about timing or frequency,
and the repetition count is recorded.

## Limits (declared before the run)

- **No OS input.** Hover, drag and key rows have no executable OS-level setup: each is driven through
  its own in-process entry point (the driver's channel, or a forced precondition the record names) or
  recorded `residual` / `unproven`. A row that needs a real pointer is never called a pass.
- **The `/` key and ESC are not injectable.** Group E row 2 opens the overlay through its own entry
  point and says so in its record; the ESC ticket is not in this batch at all.
- **The guest half reads the same UI.** The window is a local surface, so the guest's rows repeat the
  host's reads rather than adding a new view; the third client is not needed by this family.
- **One session does not disprove a rare flicker.** The idle and open-window rows repeat their reads
  and record how many ran.
- **The art row's "reads as this game" stays subjective.** It is captured for the user and recorded
  as a residual, not self-passed.

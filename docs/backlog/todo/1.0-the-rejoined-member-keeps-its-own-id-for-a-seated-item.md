# The rejoined member keeps its own id for an item the restore seated

- Status: Todo
- Priority: High
- Opened: 2026-11-25
- Owner: night run
- Area: saves/recovery, items, character

The continue seats the member's carried bandage under a restored id and keeps its colour on the character record.
The member's client, which left the world with the cut and comes back with the run, then reports the item under the id
its own body still holds, and the host cannot bind it: the clone shows a fresh, uncoloured starting supply instead of
the restored one. Measured on the acceptance row `save-continue` (2026-11-25 23:04, `.acceptance/dep-1`), which fails
with `the member's colour did not survive the save/continue: {"ok":true,"count":0,"items":[]}`.

## The four lines

1. **The reading.** `save-continue` FAIL 82.6 s (setup 45.5, case 37.0). The host log of that row:
   `23:04:41.265 [Items.ItemArbitration] Carried registration of item 1606317768705 for 17650405219979012464 ignored — the kernel already holds it as World.`
   and one millisecond later
   `23:04:41.266 [Character.CloneFactTable] [CharSync] divergence for 17650405219979012464's bandage (id 1606317768705): left the inventory without an event sync (the 1 Hz snapshot carried it).`
   The clone's carried set was then filled from the member's own report:
   `23:04:41.265 [CarriedSync] merged 1 starting supplies into 17650405219979012464's snapshot.`
2. **The line.** `src/CasualtiesUnknownOnline.Runtime/Session/Items/ItemArbitration.cs:310` — the branch that logs
   "already holds it as {Kind}" — is reached from `TryAdoptCarried` (`:290-314`) whenever the kernel's row for the
   reported id is not Carried for this guest. It is doing what its docstring says (`:280-288`: "an absolute re-report
   must never resurrect a terminal fact or hand one item to two guests"); the fault is that the id the member reports
   is not the id the restore seated.
3. **The chain.** The cut's archive carries the bandage as a carried row —
   `.acceptance/dep-1/saves/w-20261125-47d0/backups/mid-run-20261125-150542.cuoz` `items.json`:
   `{"identity":{"instanceId":3345779523585,"definitionId":"bandage",...},"location":{"kind":2,"owner":17650405219979012464,...},"data":{"colorSwatch":0,...}}`
   — and its colour on the character record (the row's `host stored character before the damage` read carried both
   `MemberColor` 5 and `HostColor` 3). The restore seats that row and the character. After the continue the member
   rejoins into the continued run still holding its pre-cut instance id 1606317768705 in its own body, re-grants
   itself a starting supply locally, and reports that id; the host refuses it and the clone keeps only the fresh
   supply, which carries no label.
4. **Why this is the cause and not the symptom.** Nothing about the restore's seating is wrong — the archive row and
   the character record both survive, and a guess at the colour would not be testable. The identity the member reports
   after a continue is the thing that does not match the run it came back into, so that is what the fix must change.

## Where the fix belongs

The rejoin path is what hands a member their character back; that is where the restored carried ids should be
adopted instead of a fresh local supply being minted. The reads that decide it:

- who grants the starting supply on a rejoin into a *continued* run (`StartingSupplyCoordinator` and the invite
  payload the member receives), and whether that payload can carry the seated ids;
- whether the restored carried row can be re-keyed to the id the member reports instead (the kernel's row is
  authoritative; re-keying would be the wrong side to decide);
- whether the member's client can be told to adopt the ids before it re-reports (the carried-inventory statement is
  an absolute re-report, so its timing is the window).

A fixture cannot paper over this: the row must judge the colour that comes back, and it comes back only if the member
and the host agree on which item it is.

## The 23:04 rejoin, read from both logs (2026-11-26 01:20)

The dep-1 row's host log shows the rejoin in order: `23:04:27.196 Re-keyed 0 item row(s) from the old transport id
1379479759796047400 to the new one 17650405219979012464`, `23:04:27.196 Sent saved character data to 17650405219979012464
(1 items, 0 death(s))` (sent twice more, at `27.200` and `41.198`), then `23:04:41.191` the member's scene reads InWorld
and at `23:04:41.263` the host sends the world-item snapshot (373 items). One millisecond later the refused registration
and the merged supply land, and at `23:04:41.266` the clone's only bandage is recorded as having left the inventory.

The member's own log window starts too late for its restore lines (the row keeps 200 lines, from `23:04:44.265`), but it
carries the consequence: `23:04:47.611 [CarriedInventory] the registration captured nothing although this session
already registered 1 carried item(s) — if the guest still carries them, the capture has stopped seeing them and the
re-report cannot converge.` So after the rejoin the member's own carried report stops naming any item, while the id it
did name once (1606317768705) is the one the host had materialized into the world at `23:03:54.836`, before the cut.

Two reads follow, and they are the next attempt rather than a conclusion:

- whether the restore's `ApplyItems` reached the member's body before its first carried re-report (the two-frame
  wipe/items rhythm starts only once a body exists, and the scene report above says the body was already InWorld at
  `41.191`, 74 ms before the report), and whether `CancelOwnRunRestore` dropped the peer hand-over on the follow;
- which id the cut's own archive carries for that member, read from the archive the row's cut wrote (the file under
  `.acceptance/dep-1/saves/w-20261125-47d0/backups/` is the 15:05 one, so the 23:03 cut's archive is the file this
  reading still needs).

## Design

The continue's claim is `docs/design/cross-cutting/saves-and-recovery.md`: a restore reproduces the frame the cut
froze, carried items included, and the member's own re-report after a rejoin must not be judged as a second item.
Item identity and the absolute re-report are `docs/design/model/item-custody.md` — an id is minted once, and every
later operation on that item names the same id on both sides.

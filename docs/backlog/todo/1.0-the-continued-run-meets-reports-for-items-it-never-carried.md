# The continued run meets reports for items it never carried

- Status: Todo
- Priority: High
- Opened: 2026-11-25
- Owner: night run

## The reading

`.acceptance/sc-2` (`save-continue`, single case, 2026-11-25 21:56) failed on its own log-error gate with one
error line: `the suite's host log holds 1 error(s) (its rule is 0)`. The host's dated log names it:

```
21:56:27.931 [ERR] Protocol violation: 13578745855655734773 reported ItemDestroy on item 32575778293 whose
creation this host has never judged. Refused at once — a sender must report an item's creation before any
operation on it (creation-before-operation).
```

The row's own steps around it all passed: the restore's audit answered after 8.6 s at 92 saved geyser rows, 120
block-state rows written, every row taken, and the geyser table was identical before and after the continue. The
row's last step (the member rejoining) succeeded 37.5 s later; the violation is the only failure.

## The four lines

1. Reading: a member's `ItemDestroy` reaches the restored kernel for an item id the archive did not carry, and the
   kernel answers it as a protocol violation.
2. The line: `src/CasualtiesUnknownOnline.Application/Kernel/KernelProtocolCommandHandler.cs:204` — the error is
   logged when `_items.FindItem(id)` is null and `_refusedCreations` has no record
   (`TryRefuseUnjudgedOperation`, `:182-208`).
3. The chain: the fixture detonates a staged mine next to a crate before the cut, so the crate is a terminal row at
   the cut (`.acceptance/sc-2/report/timeline.txt`: `staged blast` 21:56:11.513, `blast` 21:56:11.564, cut queued
   21:56:13.265) → the continue rebuilds the kernel from the archive into the SAME run, so the epoch guard at
   `KernelProtocolService.cs:399-407` passes (a continue keeps the run's epoch) → the member's client still holds the
   pre-restore row for that crate and destroys its local copy when the restored item set arrives → it reports the
   destroy → the host has no row and no refused-creation record → the handler logs a violation instead of answering
   "this id is not in my record".
4. Why this is the cause and not a symptom: the report is legitimate (the client was in this run when the row
   existed); the gap is that the restored kernel has no memory of the ids the archive dropped, so a late report is
   indistinguishable from a sender inventing an id.

## What to check first

- Whether the archive carries terminal item rows at all (`WorldSaveService` / the cut's item table), and whether the
  restore replays them. If it does, the fix is (b) below and the archive is already right.

## Options

- (a) Remember the dropped ids: when the restore rebuilds the item table, record every id the archive carried but the
  live world did not get as a known-tombstone, and answer a report about one with a warning-level
  `UnknownAggregate` instead of an error. Cheap, keeps the invariant for ids nobody ever saw.
- (b) Keep terminal rows across the restore: replay the archive's terminal item rows so a late destroy matches a real
  terminal row. Most faithful, but the restore's item half must accept terminal rows it currently drops.
- (c) Member-side suppression: let the client not report a destroy for an id it learned before the restore's
  checkpoint. Puts the rule on the side the host cannot verify; not recommended alone.

Recommendation: (b) if the archive already carries terminal rows, else (a). Both keep the creation-before-operation
invariant for genuinely unknown ids; neither hides a lost item, because the row itself compares the carried set
across the continue.

## Design

`docs/design/cross-cutting/saves-and-recovery.md` — the restore applies the archive's facts onto the live world; a
report that arrives after a restore is about a row that existed before it.

## The report came from a client that had already left the world (2026-11-25 22:45)

The same failure twice, and the second time with the guest's own log: `.acceptance/sc-2` refused item 32575778293 at
21:56:27.931, `.acceptance/sc-3` refused item 30630641659 at 22:35:02.085 — both "reported ItemDestroy … whose creation
this host has never judged", both from the member that had just rejoined the continued run.

The guest names the line. At 22:35:01.750 it began a drop for that item and at 22:35:01.760 its `OnItemDestroyed`
committed the destroy report — while its scene state was `InMenu (PreGen)` (exit re-reported 22:34:40.017 and
22:34:45.017, session ended 22:34:47.981, reconnected under a new transport id at 22:34:50.095, world entry only at
22:35:02.047). The object was a leftover of the world the cut had frozen; the client destroyed it during the scene
teardown and announced it as a player operation.

The host has no row for the id, and that is not a lost archive row: the cut's archives carry 349 and 351 item rows
(`.acceptance/sc-3/saves/w-*/backups/mid-run-20261125-143400.cuoz`, `mid-run-20261125-143404.cuoz`) with the maximum id
near 1.48e12, and neither contains that id; the sc-2 cut's 364 rows do not contain its id either, and the host log names
each id only in the refusal.

Owner: `src/CasualtiesUnknownOnline.GameAdapter/Items/ItemWorldSync.cs` `OnItemDestroyed` announced every destroy that
carried an item id — with the display-proxy and standing-item exceptions, but with no test for whether this side still
has a world. A scene teardown outside a live world is not a player operation, and the kernel of the world it belonged to
has already been replaced, so the report can only be judged against rows that no longer exist.

Fix (option (d), the narrow member-side suppression, taken because the evidence names the shape): the method now answers
`!HarmonyTraverse.HasLiveWorld` the way it answers a display proxy — the pending-drop bookkeeping still runs, the report
does not. Inside the world nothing changes, so the creation-before-operation invariant still refuses genuinely unknown
ids there. Options (a)/(b) above stay open for archives that do carry the rows; this section only removes the shape that
was misjudged.

The file sits exactly on the architecture gate's 600-line aggregate ceiling, so this guard's comment was written to fit
it; the comments it replaced lost no fact (the display-proxy and standing-item ones keep their batch references).

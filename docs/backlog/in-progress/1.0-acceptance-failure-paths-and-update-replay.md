# The acceptance suite must catch failures, not only happy paths

- Status: In progress -- started 2026-11-20. The 39-row suite covers one green path per system; this ticket adds the failure paths that lose a character or an item, a game-update replay, and branches where the defect history says the happy path is not enough, all inside the five-minute ceiling.
- Priority: High
- Created: 2026-11-20

## What the player sees

Two players are in a run. Steam1 is handing an item over when its connection drops. It rejoins; the item is gone, or there are now two. Or the host's game dies after a save, and Continue brings back one character instead of two. Or the game updates, every hook still resolves, and a behaviour changes under the suite's feet because nothing replayed the old readings against the new build.

The suite answers the first question ("do the main paths still work?") and not these. This ticket makes the failure the row.

## Why now

`host-run6` reads 39/39 in 276.1 s with every per-case warning/error column clean, so the happy-path batch is a stable instrument. It is also 23.9 s under the five-minute ceiling and 11 s under the old 287.2 s target, which is the room this ticket has to spend.

The 39 rows are one path per system: world generation, clock, save/continue, late join, roles, items, medical, blocks, enemies, UI, trader, run end. The rows that matter most when something goes wrong -- a drop mid-action, an interrupted save, a crash, a duplicate identity -- are absent. A suite that only walks the green path cannot tell a recovered failure from a lost character.

The update runbook has a structural half (`docs/development/game-update-runbook.md`: the contract tool names moved types and signatures) and an offline replay half. The live half -- run the suite on the new build and compare its readings with the old build's -- is not written down; this ticket adds it.

## Scope

### A. Failure rows (one case each)

Each row stages a real failure on the live clients, observes what the player would see, and asserts the recovery. The candidates, in order:

1. `drop-mid-transfer` -- Steam1 disconnects while an item handover is in flight; it rejoins; the item exists exactly once, on the side the handover reached, and both characters keep their own items.
2. `save-write-interrupted` -- the host's save write is interrupted (truncated or locked file); Continue falls back to the previous save or a backup; both characters and their items restore; the failure is reported, never silent.
3. `host-crash-restart` -- the host process dies after a save; it relaunches and continues; both characters and items are present; Steam1 is not stranded; the host can host again.
4. `duplicate-identity-join` -- a second client arrives with the same client identity (not only the same display name); the join is refused or replaces cleanly; there is one character for that identity, never two.
5. `host-leaves-mid-run` -- the host leaves while Steam1 is in the world; Steam1 is not stranded; the session end is clean and Steam1 can join the next run.

The survey step decides which of these can be staged safely. A row that cannot be staged without risking the user's real save is dropped with its reason, not weakened into a unit test.

### B. Game-update replay

- A command (a new `host` verb or a suite option) that takes a new report and a stored baseline report and compares: row verdicts, per-case wall time, per-case warning/error counts, row count, and the recorded game/mod artifact identity. It prints the deltas and exits non-zero on a regression.
- The report records the game build and the mod build it ran against, so a diff is attributable to an update.
- The runbook gains a live step after the structural diff: run the batch, replay the reports, read the deltas.
- The comparison is proven twice: a green report against its own baseline passes; a report with one deliberately broken row fails.

### C. Branches with a defect history

Only where the record already shows the happy path hid a failure, and where a branch can be folded into an existing case instead of adding a full batch row:

- `save-continue`: a second re-entry into the same continue, because the restore race was intermittent (the row was red while the single entry was green).
- `block-reconcile`: a member whose block baseline is already stale when the reconcile runs (the known staging race, "member was not stale before the reconcile").
- `remote-backpack`: an item dropped or picked up while a remote backpack is open (the 2026-11-07 refresh baseline bug).

### D. Soak and performance (last)

A short soak (about ten minutes of active play or a scripted loop) with a memory-growth budget, a log warning/error budget, and a per-case wall-time regression bound. Only after A-C; if the evidence says the suite is not the right instrument for a soak, record that and leave it out.

### Non-goals

- Visual rows stay manual (the suite's own rule).
- The Steam transport half stays blocked on a second account that owns the game.
- Host migration is outside the MVP.
- No full gameplay matrix: this ticket adds the failure and branch rows, not one row per mechanic.
- No weakening of the per-case warning/error gate or the five-minute ceiling to fit a row.

## What "enough" means

1. Every chosen A row has a C# case with a real-game reading: the failure is staged, the recovery is observed, and the row fails when the recovery is removed.
2. Every C branch is folded into its case (or is a new case only when folding is impossible) and reads green.
3. The replay passes a green report and fails a deliberately regressed one; the runbook names the step.
4. The full batch is green, every row's warning/error columns are clean, and the wall is under five minutes, cited with the report path.
5. Unit, gate and format checks are green; a source change deploys and its identity is verified.
6. The ticket, index, census and linked pages move together; the completion gate exits zero for this ticket.

## Time budget

The 39-row batch stays under the five-minute ceiling and keeps its 282.2 s baseline. The failure rows run in a named second batch (the survey's decision): that batch's baseline is its own first green full run, recorded with its report. That is a scope change with its own reading, not a goalpost move for the 39-row suite.

If the new rows cannot fit under 300 s, the options, in order, are: fold a branch into an existing case; remove dead time in the harness; run the slow failure rows in a second, explicitly named batch that is not the per-commit gate, with the gate's reading and the slow batch's reading both recorded. Dropping a row or weakening an assertion is not an option.

### Decisions this survey fixes

- The 39-row `--suite all` batch does not grow. Every A/C case above is `RunsInBatch => false`, and the failure rows run
  in a named failure batch selected with the existing `--suite <comma names>` option. The 39-row batch keeps its current
  reading (39/39, 276.1 s, `.acceptance/host-run6/report/report.md`); the failure batch's baseline is its own first green
  full run, recorded with its report. Both runs stay under the five-minute ceiling. The old 282.2 s baseline is untouched.
- A5 is folded into `HostAfterContinueCase`; it does not get a separate A case. Its stranded assertion is added there.
- The A3 restart is a deliberate failure injection: the case kills the host process and the suite starts it again as the
  recovery under test. This is not the fixture repair the 2026-11-14 rule forbids; a client that answers but cannot join
  is still never restarted, and the deliberate restart is recorded in the case's note and the ticket.
- Every failure row uses the per-run scratch save root (`host run` already sets `CUO_SAVE_ROOT` to `<out>/saves`); the
  user's real save is never staged or corrupted.

## Design (step 2)

product defect gets a normal product fix in this ticket's chain (steps 6-8, 13), not a test-only workaround. The player's
frame comes first; the suite only stages the failure and reads what the player would see.

### The instrument, not the product

- The failure injection uses the suite's own CLI, the committed recipes and the scratch archive. No product wire message,
  console verb or config key is added for a test. The new recipe is the `net-drop-message` probe promoted to
  `tools/acceptance/recipes/`, and the new read is the remote-backpack read for C3.
- The one deliberate product exception is a test-only fault: the A2 red-first run may disable the backup promotion in a
  local build to show the case goes red; that patch is reverted before the commit and never ships.
- The A3 restart is the row's recovery, not a fixture repair. The case kills the host process it owns, the launcher starts
  it again, and the report records it; `SessionDriver`'s refusal to restart a client that answers stays untouched.
- The user's real save is never named. `host run` already sets `CUO_SAVE_ROOT` to `<out>/saves`; it will pass the same
  root to the suite so a case can corrupt only that world.

### Harness shape

- `host run` passes `--save-root`, `--pids` and an optional `--all` (three clients) and `--twin-identity` (A4) to the
  suite/launcher; the launcher writes `<out>/pids.json`, can set the alternate box's identity from the guest box for A4,
  and restores the box's original identity on the next launch without the flag.
- `Suite.Options` gains `SaveRoot` and `PidsPath`; the report JSON and Markdown gain the game build, the mod build and the
  deployed artifact identity.
- `SessionDriver` gains a public host-restart path used only after the host is confirmed down; it drops the cached driver
  connection before the new host starts. The existing `RelaunchAsync` still refuses an answering client.
- New cases are `RunsInBatch => false`: `drop-mid-transfer`, `save-write-interrupted`, `host-crash-restart`,
  `duplicate-identity-join`, `save-continue-reentry`, `remote-backpack-refresh`. `HostAfterContinueCase` and
  `BlockReconcileCase` are extended in place; no batch row grows.
- The failure batch is one run: `host run --all --twin-identity --suite drop-mid-transfer,save-write-interrupted,host-crash-restart,duplicate-identity-join,save-continue-reentry,remote-backpack-refresh`. The host-crash case runs last. The 39-row `all`
  batch keeps its own launch, report and 276.1 s reading.
- `host replay` lives in `tools/acceptance/host` and compares row sets, verdicts, per-case wall, per-case W/E counts and
  the build/artifact identity; it exits non-zero on a regression and prints the deltas. The default tolerance is an
  explicit per-case `max(5 s, 20%)` and a suite wall `max(10 s, 5%)`; the tests pin both a within-tolerance green pair and
  a beyond-tolerance regression.
- The runbook gets the live step after the structural diff: run the batch on the new build, replay the reports, read the
  deltas.

### Who judges, what travels, refusals, records

- **Who judges:** the case's own assertions, the per-case host/member warning/error gate, the restore report line, the
  replay comparer. The suite never infers a build or a row set.
- **What travels:** the in-process driver calls and recipes, the scratch archive files, the pids file, the report JSON.
  No product message or config key travels for a test.
- **Refusals:** a row that cannot be staged deterministically is dropped or folded with the reason in this ticket; a
  client that answers is never restarted; the real save is never touched; the W/E gate and the five-minute ceiling are
  never weakened to fit a row.
- **Records:** this design, the run sheet, the failure batch report, the replay output, the runbook step, and the
  deliberate red/green readings. No new docs/design page: no game surface changes, so the design corpus is not the owner
  of a test harness.

### Gaps this design still carries

- A1's session end is the game's own leave, not a transport-level disconnect that leaves the process alive; the row's
  item-loss window is the same, and the difference is recorded. A process kill would add a second failure the row does
  not own.
- A4's two boxes share a display name in the existing twin-name session; the identity override is a launcher config write,
  so the row depends on that machine path; the launcher backs up the original beside the config and restores it on the
  next launch without the flag. If the write cannot be made reliable, the row drops with that reason.
- A3's process lookup and the 120 s restart wait are machine-shaped; the pids file is the primary path, the exe lookup the
  fallback.
- C2's stale staging is bounded; if the member is not stale after the force, the case fails with the named precondition,
  and that failure is a fixture finding to fix, not a pass.
- D remains deferred until A-C; the decision and its evidence will be written after the failure batch.
- The failure batch's own baseline is its first green full run; the 39-row 282.2 s baseline and its 276.1 s reading are
  untouched.

### The A2 restart: the reconnect journal loop (2026-11-20)

The first `save-write-interrupted` run on the real game produced no report: both clients stopped answering. The guest's
`latest.log` repeated from 20:46:11 `Applying batch from 1 failed: carried item 42404365466 references unknown player
8880128706030328158` and `Batch from 1 creates a revision gap: expected 984, received 985..1039 — buffering and
requesting range.` The host repeated `Sent N journal batch(es) 984..M to 8880128706030328158` with N rising to 194 and
falling back to 1, always resending from 984: the guest could not apply revision 985, so the host's journal never
advanced.

1. Reading: the guest's unknown-player refusal and the host's 984 resend loop, above.
2. The refusing line: `PlayerDomainModule.AssertInvariants`
   (`src/CasualtiesUnknownOnline.GameState/Domains/Players/PlayerDomainModule.cs:136`) throws on a carried or applied
   item whose owner is not in the players table.
3. The trigger: reconnect → `CharacterDataStore.SendSavedCharacter` → the A1 adoption re-keyed the items to the new
   transport id and let that batch be committed first → the guest replays batches in commit order, meets the item
   before it has learned the new player, throws, and can never apply revision 985 → the guest keeps requesting from
   984 and the host keeps resending.
4. Why the fix removes the cause: the player's status batch must precede any batch that names that player as an owner.
   `SendSavedCharacter` now projects the kernel's terminal facts over the snapshot, commits the player row, and only
   then re-keys and arbitrates the items (`CharacterReconnectRestore.Prepare`). The resend loop is the symptom; the
   batch order was the cause.

The fix's first form called `SyncFromCharacterData` before the kernel restore projection; the full suite caught it with
two red restore tests (`SendSavedCharacter_ProjectsKernelTerminalFactsOverSnapshot`,
`SendSavedCharacter_ProjectsKernelSkillsOverSnapshot`) because the snapshot then overwrote newer kernel terminal facts.
The final order is kernel projection, player-row commit, item re-key and arbitration.

  3,072-byte step-file budget. Both now read 2,877 and 3,004 bytes with no rule dropped; the tool mechanics of `-Intent`
  and the commit hook's step record moved to `rules/README.md`, where the reading discipline already lives.
- `CharacterDataStore` had grown past its recorded 687-line allowance. The restore ordering and the item arbitration move

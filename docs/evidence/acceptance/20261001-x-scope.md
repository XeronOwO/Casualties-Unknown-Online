## The capability boundary (declared before the run)

- This machine has **no message-swallow injection**. The only recorded transport injection pair is the
  whole-pump switch (`guest-pump-off` / `pump-on`, batches `20261001-r`/`s`): it stops the client's
  send AND receive pumps until restored, so what it produces is a failed send, not the production
  "sent but swallowed by the lazy-P2P window" contract the swallowed-report rows name — and its
  silence ends that client's session through its own watchdog within 15 s. It is therefore not used as
  a substitute, and every row whose scenario names a dropped report is listed as open below.
- Layer regeneration is reachable through the game's own debug entry (`game-console command=skiplayer`,
  the same generation boundary a natural descent crosses; batch `20261001-m` used it). The trap
  scenarios are reached by a live census of the generated layer's components (`JumpPadScript`, the
  batch `20261001-m` / `q` census shape), never by guessing a position.

## The evidence channel (declared before the run)

- **machine**: in-process recipe and probe results (one JSON per invocation, under the local artifact
  directory), the three clients' `BepInEx/logs/latest.log`, and the deployed artifact identity.
- **visual**: window-level captures of the client that must show the row (the drop-presentation rows),
  read by the agent.
- **feel**: the drop-motion row gets a frame sequence; what stays subjective is a residual.
- **re-derived / static**: the unhooked-caller seal is additionally read from the source gate's own
  record — the run's half is the live crush observation; `guest-break-drops-recovery` row 2b's
  payload-free premise is a static premise, not a live row.

## Session structure

One three-client session covers rows 1-14. The setups run in this order so that no scenario destroys
what a later one needs, and everything a later step would replace is read before that step:

1. **Race scenarios** on a shared cell band (rows 1, 10): both orders plus one concurrent attempt.
2. **Destruction family** (rows 8, 9, 11): the host and then the guest destroy a jump-pad's support
   block; captures and item reads on the non-destroying clients.
3. **Crush family** (rows 12, 13, 14, 7): a `health <= 1` cell under each body in turn.
4. **Capacity fill** (rows 5, 6): the host's damage list is filled past its cap; the third client joins
   late and reads the set.
5. **Re-entries** (rows 2, 4): the solo→lobby→join delivery and the rejoin.
6. **Layer descent last** (row 3): `skiplayer` replaces the world; nothing after it needs the old one.

## Limits (declared before the run)

- The swallowed-report family is not judged here: no injection on this machine produces a send that
  reports success while the peer never receives it. Those rows stay open, are named in each record,
  and are not replaced by a weaker check.
- Two planned rows are attempted, not promised: Row plan #2 (the rejoin — the rejoin wedge is a known
  behaviour of this machine) and Row plan #1's concurrent attempt (the two writes must land inside
  one relay window). If the world cannot be put into the state the row needs, the row is `unproven`
  and named.
- One session is not a race proof; the race rows are read from the state each end converges to and from
  the bounded windows the logs bracket.
- The `health <= 1` crush setup declares how the remaining health was produced (a measured damage
  roll), not an assumption.
- This page declares what the run would SERVE, never that every planned row would be reached: the run
  did not drive the crush family, the capacity fill or the layer descent, and those rows are `unproven`
  in their records rather than quietly passed.

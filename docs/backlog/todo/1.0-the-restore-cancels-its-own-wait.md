# The restore cancels its own wait when the world is generated under it

- Status: Todo
- Priority: High
- Opened: 2026-11-25
- Owner: night run

## The reading

`.acceptance/reds-2` ran `save-continue` on the release install (`0.1.0+38016a31f`) and the row failed with
`the restore did not apply the 102 geyser types the live world held before the save`. The host's own dated log
(`BepInEx/logs/latest.log`) says what the row's message cannot:

```
06:08:40.001  World join sent to 1 member(s) (tutorial: False, run 4, baseline follows: True).
06:08:40.084  [GenStream] segment 15 … stage=<WorldGenerateStructures>
06:08:42.212  [GenStream] segment 16 … stage=<Wrap>
06:08:43.256  [SaveFacts] cancelled the pending restored native values — world facts (33 keypad code(s), 102 geyser type(…
06:08:43.256  [ERR] [SaveFacts] the live world did NOT take every restored fact (… 4 geyser type(s) applied …)
```

The restore was not merely short of time: it was **cancelled** while the layer was still generating (the
generation stream is at segment 15–16 of the same second), and the replay then ran against a world that did not
yet hold the geysers — four applied, ninety-eight refused.

## Why the wait did not save it

`RestoredWorldFactReplay` holds the restore while `GeyserFillWait.Holds(live, saved, stable, elapsed)` is true
(`RestoredWorldFactReplay.cs:185`), and that wait is bounded by the archive-scaled ceiling (30 s + 0.1 s per row,
hard cap 60 s). A cancel is a different event: it discards the pending values, so no ceiling can help.

## What to read next

1. Who cancels: the cancel line is logged by `NativeWorldFacts`; read its caller and the condition it acts on
   (a second restore, a fresh run, a generation restart).
2. Whether the cancel is right: a world regenerated under a pending restore cannot take the values, so the
   cancel may be the honest answer — in which case the row has to restore into a world that is already generated,
   or the restore has to be re-armed once generation ends.
3. Which of those two the product wants, and what the row then judges.

## Design

`docs/design/cross-cutting/saves-and-recovery.md` — the restore applies the archive's world facts onto the live
world; it does not regenerate the world to suit them.

## The fixture's budget was smaller than the product's own wait (2026-11-25 21:50)

Three batch runs (`.acceptance/all-9`, `all-10`, `all-11`) failed this row the same way: the row's message ended
with an empty audit (`the restore did not apply the 107|108|121 geyser types the live world held before the save:`),
so the fixture's 20 s wait for `restored the live world` expired before the product wrote that line. The product
writes it once the hold ends, and the hold is bounded by `GeyserFillWait.CeilingFor(saved)` — 30 s plus a tenth of
a second per saved row, capped at 60 s (`GeyserFillWait.cs:20-33`). A restore that is still waiting is not a
restore that failed.

One single-case run after the budget changed (`.acceptance/sc-1`, 21:47) passed in 80.9 s with the audit answering
after 9.6 s in a world of 95 saved rows: 101 block-state rows written, 49 keypad codes, 95 geyser types, 138 recipe
unlocks, 6 world-entity rows, 0 row(s) not taken. That world was two minutes old; the batch's worlds had run for
hours and the same continue outlived 20 s there. The number was measured on a smaller world, not on the restore.

The row now waits 70 s (the 60 s hard cap plus a settle margin), and when the wait expires it reports the restore's
last `[SaveFacts]` line instead of an empty string — that line says whether the hold was still legitimate or the
replay refused rows.

Cost on the same run: setup 44.8 s, of which `member after continue: the suite joined the member to the host's run
after 40.5s` — the guest rebuilding the continued world, the same 37.6 s the drop row paid in `pin-3`. A second
single-case run (`.acceptance/sc-2`, 21:56) paid 37.5 s the same way, and the join note did not name a run mismatch:
the member was out of the world, so the suite's rejoin is a genuine guest world build, not a stale run. That rejoin
is the largest per-row cost left in the suite and belongs to the 480 s batch budget, not to this defect.

The `reds-2` refusal (4 applied of 102) did not reproduce: this continue took every row. It stays on this ticket as
a separate reading, because a refusal means the replay wrote into a layer that was still filling.

## The same refusal came back on a larger archive (2026-11-26 04:16)

`.acceptance/sc-10` (save-continue alone, 95.0 s, exit 1) failed on the row's own claim, and the audit line in the row's
note names the shape: `[SaveFacts] restored the live world: 126 block-state row(s) written, 0 partial-damage row(s)
applied, 47 keypad code(s) applied (the archive carried 47), 5 geyser type(s) applied (the archive carried 120), 138
recipe unlock row(s) applied (the archive carried 138), radiation line applied, 9 applied / 0 refused world-entity
row(s), 115 row(s) not taken, restore INCOMPLETE (reported at error level, not retried).` So the wait held (`Holds`
answered with the layer stable), the audit was written, and the replay still left 115 geyser rows on the floor — 5 of
120 went in. The row is therefore red for two independent reasons today: this incomplete geyser replay, and the clone
that later lacks the member's seated item. This reading is the stronger one for this ticket: the refusal is not only
`reds-2`'s; on a 120-row geyser set it is the common case, and the code path that decides "the layer is filling, hold
the write" is deciding wrong at least on archives of this size.

## The wait cannot see a layer that has not started filling (2026-11-26 04:35)

The refusal above was read against the rule that produced it. `GeyserFillWait.Holds(live, saved, stable, elapsed)` is
`live < saved && elapsed < CeilingFor(saved)`, and `CeilingFor(120)` is 42 s. So the replay released after 42 s with the
live set at **5** objects, wrote the audit, and refused 115 rows: the rule did exactly what it says. The exception is
what the rule assumes - that a growing set is being watched. A world whose geyser layer has not begun to fill reads the
same as a world that is finished: both are small. The log says which it was only through the count itself, and the
comment on `Holds` records the older failure (a 96-of-115 set that paused three seconds between chunk bursts and was
read as complete).

What the next reading has to answer, before a fix: at the moment the audit was written, was the host's own generator
still streaming the geyser layer (a segment line at or after the cut), or had it finished and produced five objects?
The two answers split the fix - a generator that is still streaming needs the wait tied to the generator's own "layer
complete" fact rather than a clock, and a finished generator that produced five objects is a replay problem, not a
wait problem. That reading is one single-case run with the failing row's own log window (`host-window-save-continue.json`,
which the log-window artefact now keeps beside the report), not a guess.

Two runs were taken after that (2026-11-26 04:40-04:45, `.acceptance/gs-1` 96.5 s and `.acceptance/gs-2` 97.4 s, both
green). Both answered the audit after 7.6 s and applied the whole archive: `98 geyser type(s) applied (the archive
carried 98)`. So on these two runs the layer was filled before the wait's ceiling and the replay took every row - the
42 s ceiling was never reached. Against the eight earlier single-row runs (seven green, one red at 5/120) the row's red
is a 1-in-9 event whose trigger is still unidentified; the two new runs show it is not "the archive is large" alone.
The next reading that can settle it is the failing run's own window, and that only exists when the red happens again.

One code question was closed while looking for a cheap fix: the replay can already tell "the world is still
generating" (`IRestoredWorldFactSink.IsWorldReady` is the seam's own precondition, and `HarmonyTraverse.IsGenerating` is
what the adapter answers it with), so a wait that gives up too early could have been lengthened. It was not the cause:
the red run released with the world READY and only five geyser objects live, and `GeyserStateTable.Apply` matches saved
rows to live geysers by position within 6 m. A ready world holding five geysers means that world never had the
archive's geysers to match, not that the wait was short. What can name it is the failing run's live geyser positions
against the archive's - one window from a red run, which is why this stays open rather than patched blind.

# A restored character's item operation is refused as creation-before-operation

- Status: Todo — Rejected (2026-11-18)
- Priority: High
- Owner: unscheduled
- Created: 2026-11-18

## What the player sees

A player who continues a saved world and comes back in finds their own items intact, but the host's copy of that
player shows no items at all. Anything the host answers about that player's inventory (the player list, a hand-over on
the next rejoin) is empty or stale, and the host's log fills with protocol violations while it happens.

## The reading

`.acceptance/full-round17` (`-Suite all -Fresh`, deployed `0.1.0+40e439bc5`): `save-continue` FAIL.

- Before the save: host's stored character for the member read `{"ok":true,"found":true,"count":1,"items":[{"id":"bandage","label":"MemberColor","swatch":5}]}`.
- After the continue: the host's answer about the member read `{"ok":true,"count":0,"items":[]}`.
- The restore audit was complete: `3 applied / 0 refused world-entity row(s), 0 row(s) not taken, restore complete`,
  92 geyser rows applied of 92 carried.
- Host's first error: `[KernelProtocolService] Protocol violation: 17650849439675613236 reported ItemDestroy on item
  47576285236 whose creation this host has never judged. Refused at once — a sender must report an item's creation
  before any operation on it (creation-before-operation).`

## Why it matters

The character hand-over path sends a restored character and its items to the member before the world-entry
instruction; the member then reports its body, and that report carries an operation on an item the host never judged
created. The host refuses the report, so the host's stored copy of the member loses the items — and the next
save/continue inherits the loss.

## Design

`docs/design/cross-cutting/saves-and-recovery.md` carries the hand-over rule (a member pulled back into a restored
world receives its character before the entry instruction). The host's judged-creation record for items is the
applied-items ledger; the member's report path is `CharacterDataStore.SaveReportedCharacterData` followed by the
kernel's creation/operation checks.

## Next steps

1. Read the hand-over path in `CharacterDataSync.SendSavedCharacter`/`CharacterRestoreApplier` and check whether the
   applied-items ledger is seeded with the restored items under the member's peer key.
2. Reproduce with the focused `save-continue` row and read the host's item ledger before and after the hand-over.
3. Fix the ledger seeding (not the check), then re-run the focused row and a full batch.

# The run change reaches the guest after its first batches

- Status: Todo
- Priority: High
- Opened: 2026-11-22
- Owner: session

## Why

On 2026-11-22 the guest logged, in this order:

```
08:04:05.199  Batch from 1 has epoch 2; current is 1 — dropped.
08:04:05.211  Batch from 1 has epoch 2; current is 1 — dropped.
08:04:05.213  Host announced run 2; checkpoint sets are validated against it from here.
```

The host's first run-2 batches arrived 14 ms before the announcement that would have told the guest to
accept run 2. The guest dropped five batches as foreign-epoch; those revisions can never be applied, and
the journal repair then re-sent history forever (see `docs/backlog/done/1.0-the-journal-repair-resends-forever.md`,
which bounds that amplifier but does not remove this cause).

## The four lines

1. Reading: the three log lines above, from the guest's `latest.log` at 08:04:05.
2. Code: `KernelProtocolService.HandleCommittedBatch` drops a batch whose epoch differs from the current
   run (`Batch from … has epoch …; current is … — dropped.`); the announcement that adopts the new run is
   `GuestCheckpointReceiver`'s world-join instruction / run announcement.
3. Chain: the host commits its first batches of a new run before (or concurrently with) the announcement
   frame; the transport keeps per-channel order but the announcement travels on a different path, so the
   guest sees batches first.
4. Why a fix at the announcement removes the cause: if the announcement is ordered before any batch of
   its run — a barrier the host obeys — the guest's epoch is current when the first batch arrives and no
   batch is dropped.

## Design

The kernel's replay model is host-authoritative and strictly ordered: a batch is applied only in the
revision order the host committed it, and only inside the run (epoch) it was committed in. Read
`docs/design/cross-cutting/saves-and-recovery.md` for the run lifecycle and
`docs/architecture/current.md` for the kernel protocol, before touching either side of the announcement.

## Options

1. **Order the announcement before the first batch of its run** (host-side barrier: no run-2 batch is
   sent until every peer has been told run 2). Cost: one round of bookkeeping on the host; keeps the
   guest's epoch guard strict. **Recommended.**
2. **Tolerate a newer epoch**: the guest adopts the batch's epoch when it is ahead, applying the same
   state transition the announcement carries. Cost: two places adopt a run; the announcement becomes
   advisory and the guard loses its meaning.
3. **Drop the epoch guard**: rejected — a batch from an older run would be applied to a newer world.

## Done when

A run change on the host produces, on every guest, the announcement line before the first batch of the
new run (checked from the guest's log), and the dropped-batch warning does not appear across a full batch
run.

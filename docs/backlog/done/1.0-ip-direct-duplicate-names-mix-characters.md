# IP-direct players who share a display name lose a character

- Status: Done (2026-11-19) — a shared display name is allowed and each client's own identity keeps the two
  characters apart. The first close called this a config collision and put a refusal in `preflight.ps1`; the user's
  requirement is the opposite, and the fix now carries it: two clients named the same keep both characters across a
  continue (`.acceptance/twin-names1`, reading below, decision 272).
- Root cause: the IP-direct character key is the display name itself (`PlayerKey.ForDisplayName`), so two present
  players with one name resolved to one key, the cut refused to write either character (decision 177), and after the
  continue each came back as a new character.
- Priority: High
- Created: 2026-11-19
- Related: `done/1.0-acceptance-rows-as-c-sharp-cases.md` (scope row 1), `docs/design/cross-cutting/saves-and-recovery.md`,
  `docs/architecture/save-archive-format.md` §2/§6, `docs/decisions/active.md` 162/177/272

## The chain (2026-11-19, by execution)

1. The player types a display name into the IP-direct config and hosts or joins
   (`src/CasualtiesUnknownOnline.Plugin/IpDirectConfigEditor.cs:40` `DisplayName => _displayName.Value`).
2. The action hands it to the transport: `src/CasualtiesUnknownOnline.Plugin/IpDirectActions.cs:60` and `:92`
   `_ipSteam.SetDisplayName(_config.DisplayName)`.
3. The guest's handshake carries it: `src/CasualtiesUnknownOnline.Runtime/Session/SessionPeerMaintenance.cs:323`
   `DisplayName = _steam.GetPersonaName(...)` into `HandshakeMsg.DisplayName`
   (`Protocol/Messages/HandshakeMsg.cs`, ProtoMember 4).
4. The host stores it on the member: `Session/Handlers/HandshakeHandler.cs:105` `member.DisplayName = displayName`.
5. The cut builds one identity per peer from that name:
   `Session/Persistence/WorldCharacterBinder.cs:252` `new PlayerIdentity(member.SteamId, member.DisplayName)`, and
   `Persistence/PlayerKeyResolution.cs:23` `PlayerKey.ForDisplayName(displayName)` turned it into the key.
6. Two peers, one key: `WorldCharacterBinder.Collect` (`:95`) logged "Character key … is shared by 2 present players"
   and (`:100`) removed both rows, so the cut carried neither character; after the continue each peer's key had no
   file and decision 162 made it a new character.

Acceptance: with both clients presenting the same display name, save and continue, then read each client's own
character — both keep their marker items, no cross-merge, and the host's view of both is complete.

## What the player saw

Two friends joined a host's run. The host saved and continued. One friend kept the character and items they had;
the other came back as a fresh character with the starting supplies.

## The reading (`.acceptance/twomember2`, 2026-11-19 00:49) — the false loss

The row (`two-member-continue`) joined host + two members (ids `9819874492779337119` and `4294629808900910865`),
granted each member a bandage marker through the game's own grant, saved, left the world, continued, and waited for
both members to follow.

- The cut carried **one** character: the restore line reads `… 3 player row(s) … 1 character(s) …`.
- `Restored characters: 1 bound to present peers, 0 left unclaimed, 0 refused (key space IpDirect).`
- The second member's own client read a fresh kit after the continue and no bandage.

## Root cause (`.acceptance/twomember3`, 2026-11-19) — a shared player key, refused by design

Reproduced on the current build, then read from the host log:

- `[WRN] [WorldCharacterBinder] Character key name-host is shared by 2 present players (1, 7560364048153771310); no
  character is written for it — the archive holds one character per key, and a file under a shared key could be
  claimed by the wrong player at a restore.`
- The two claimants are the host (peer 1) and the second member. The IP-direct player key is the display name
  (`PlayerKey.ForDisplayName`), and both installs carried `[IpDirect] DisplayName = Host`: the alternate sandbox's
  config had been copied from the host's.
- `WorldCharacterBinder.Collect` therefore refused to write either file (decision 177), the cut carried only the
  first member's character, and the second member joined as a new character. The "items merged onto the first"
  line was the first member's own transfer-table merge (5 items), not the second's.

## The fix (2026-11-19) — the key follows the client, not the name

- Each client generates a persistent `[IpDirect] ClientIdentity` (32 hex characters) on its first IP-direct start
  (`src/CasualtiesUnknownOnline.Plugin/IpDirectConfigEditor.cs`), the handshake carries it
  (`HandshakeMsg.ClientIdentity`, ProtoMember 10), and the host stores it on the member record
  (`HandshakeHandler.NormalizeClientIdentity` accepts only 32 hex characters).
- `PlayerKeyResolution.EffectiveKeys` folds the identity into the key as `-c<digest8>` only while two present peers
  share a normalized base name. A unique name keeps the bare key, so every save written before the identity existed
  still loads. `Claim` answers through the same map, so a member that follows a continue reclaims the character it
  owned.
- `tools/acceptance/preflight.ps1`'s `ip-names` row now reports a shared name as allowed (each client's
  `ClientIdentity` keeps the keys apart) and fails only when a shared-name client has no identity yet — the state its
  first IP-direct start repairs.
- Decision 272 records the rule; `docs/design/cross-cutting/saves-and-recovery.md` carries the identity bullet.

# The rejoined member keeps its own id for an item the restore seated

- Status: Todo
- Priority: High
- Opened: 2026-11-25
- Owner: night run
- Area: saves/recovery, items, character

The continue seats the member's carried bandage under a restored id and keeps its colour on the character record.
The member's client, which left the world with the cut and comes back with the run, then reports the item under the id
its own body still holds, and the host cannot bind it: the clone shows a fresh, uncoloured starting supply instead of
the restored one. Measured on the acceptance row `save-continue` (2026-11-25 23:04, `.acceptance/dep-1`), which fails
with `the member's colour did not survive the save/continue: {"ok":true,"count":0,"items":[]}`.

## The four lines

1. **The reading.** `save-continue` FAIL 82.6 s (setup 45.5, case 37.0). The host log of that row:
   `23:04:41.265 [Items.ItemArbitration] Carried registration of item 1606317768705 for 17650405219979012464 ignored — the kernel already holds it as World.`
   and one millisecond later
   `23:04:41.266 [Character.CloneFactTable] [CharSync] divergence for 17650405219979012464's bandage (id 1606317768705): left the inventory without an event sync (the 1 Hz snapshot carried it).`
   The clone's carried set was then filled from the member's own report:
   `23:04:41.265 [CarriedSync] merged 1 starting supplies into 17650405219979012464's snapshot.`
2. **The line.** `src/CasualtiesUnknownOnline.Runtime/Session/Items/ItemArbitration.cs:310` — the branch that logs
   "already holds it as {Kind}" — is reached from `TryAdoptCarried` (`:290-314`) whenever the kernel's row for the
   reported id is not Carried for this guest. It is doing what its docstring says (`:280-288`: "an absolute re-report
   must never resurrect a terminal fact or hand one item to two guests"); the fault is that the id the member reports
   is not the id the restore seated.
3. **The chain.** The cut's archive carries the bandage as a carried row —
   `.acceptance/dep-1/saves/w-20261125-47d0/backups/mid-run-20261125-150542.cuoz` `items.json`:
   `{"identity":{"instanceId":3345779523585,"definitionId":"bandage",...},"location":{"kind":2,"owner":17650405219979012464,...},"data":{"colorSwatch":0,...}}`
   — and its colour on the character record (the row's `host stored character before the damage` read carried both
   `MemberColor` 5 and `HostColor` 3). The restore seats that row and the character. After the continue the member
   rejoins into the continued run still holding its pre-cut instance id 1606317768705 in its own body, re-grants
   itself a starting supply locally, and reports that id; the host refuses it and the clone keeps only the fresh
   supply, which carries no label.
4. **Why this is the cause and not the symptom.** Nothing about the restore's seating is wrong — the archive row and
   the character record both survive, and a guess at the colour would not be testable. The identity the member reports
   after a continue is the thing that does not match the run it came back into, so that is what the fix must change.

## Where the fix belongs

The rejoin path is what hands a member their character back; that is where the restored carried ids should be
adopted instead of a fresh local supply being minted. The reads that decide it:

- who grants the starting supply on a rejoin into a *continued* run (`StartingSupplyCoordinator` and the invite
  payload the member receives), and whether that payload can carry the seated ids;
- whether the restored carried row can be re-keyed to the id the member reports instead (the kernel's row is
  authoritative; re-keying would be the wrong side to decide);
- whether the member's client can be told to adopt the ids before it re-reports (the carried-inventory statement is
  an absolute re-report, so its timing is the window).

A fixture cannot paper over this: the row must judge the colour that comes back, and it comes back only if the member
and the host agree on which item it is.

## The refusal is the kernel's rule, and the re-key never sees the row (2026-11-26 03:30)

Two lines explain why the member's own id cannot come back:

- `ItemService.ReassignOwner` (`src/CasualtiesUnknownOnline.Runtime/Session/Items/ItemService.cs:318-370`) re-keys only
  rows whose location is `Carried`, `Contained` or `Applied`. The member's bandage is held as
  `ItemLocationKind.World` after the continue, so the loop skips it and the host logs `Re-keyed 0 item row(s)`.
- `ItemArbitration.TryAdoptCarried` (`src/CasualtiesUnknownOnline.Runtime/Session/Items/ItemArbitration.cs:287-315`)
  refuses anything the kernel already holds that is not *this guest's carried row* — the world table included, by
  design ("an absolute re-report must never resurrect a terminal fact or hand one item to two guests"). The log is
  `Carried registration of item 1606317768705 for … ignored — the kernel already holds it as World.`

So the two mechanisms that could seat the item each exclude it: the re-key by location kind, the registration by
kernel table. The narrow reading is that a **world row with no owner** reported by the member as carried has exactly
one candidate home — that member — and the refuse-by-default rule is what loses it.

Next reading: whether `TryReassignOwner` accepts `World → Carried` for an ownerless row, and whether the continue's
restore is the better place to seat it (the row is in the cut's `world-entities`/`items`? it is in neither, which is
why the restore has no fact for it).

No kernel command can seat it either: `ReassignItemOwnerCommand` changes only the owner (the kind stays `World`),
`TransferItemCommand` rejects anything that is not already `Carried` (`ItemDomainModule.DecideTransfer`,
`src/CasualtiesUnknownOnline.GameState/Domains/Items/ItemDomainModule.cs:38`), and `SpawnCarried` mints a new id —
which is the one thing this ticket exists to avoid. So the fix is not a new command: it is on the member's side after
a continue, where the kernel snapshot's carried row must replace the object the body still holds, instead of the
stale object being re-reported and refused. The next reading is `ItemReconcile`/`GeneratedItemReconcile` on the guest:
does a snapshot's carried row replace a body slot that holds an object with another id, and what happens to the
object that no snapshot row names.

The guest's local incarnation of a carried row is a **standing object** (`StandingItemMaterializer`; the session
teardown clears it with `StandingMaterializer.ResetSessionState()` at `src/CasualtiesUnknownOnline.GameAdapter/
GameAdapterSessionBinding.cs:158`). A continue tears the session down, so after it the materializer holds nothing
while the member's body still holds the pre-cut object; the snapshot's carried row and that object never meet. That
is the seam the fix belongs in: when a carried row arrives for a slot, the object already in the slot must be
retired (or adopted by id), instead of being re-reported as a registration the kernel has to refuse.

The restore side already does its half: `CharacterRestoreApplier` places an unplaced archive row on the body through
`LocalBodyPlacement.TryPlaceInSlot` (and names the refusal when no slot accepts it,
`src/CasualtiesUnknownOnline.GameAdapter/Character/CharacterRestoreApplier.cs:205`). What is missing is the other
half: the member that never rebuilt its body after the cut still holds the **previous run's** object in a slot, and
nothing retires it when the snapshot's row arrives. The member's own log says so: `[CarriedInventory] the
registration captured nothing although this session already registered 1 carried item(s)`.

The next reading is one line of the member's log at the cut: whether it ran `CharacterRestoreApplier` at all
(`Restore:` rows) when the host sent `Sent saved character data (1 items)`. If it did, the wipe it performs should
have emptied the slot and the old object should not survive; if it did not, the seat is applied nowhere on the
member's side after a continue, and that is the seam (not the reporter, which faithfully states what it holds).

The reading came back: the member's log at that cut has **no** `Restore:` row at all, while it does show `Restored
kernel checkpoint at revision 1110 (388 items, run 2)` — the host sent it `Sent saved character data to … (1 items,
0 death(s))`, and nothing on the member's side applies a character snapshot to **its own** body: `CharacterDataMsg`
is consumed only for remote display bodies. So the member kept the body it had, applied the new run's kernel
checkpoint into the old world, and its slot still holds the previous run's object. The real defect is therefore one
step earlier than the seat: after a continue the host rebuilds its own world and hands the member a checkpoint of it,
but never makes the member leave the old world, so the two sides never re-derive the same body.

Two ways to close that, and the evidence prefers the first:

- **(a) Make the member re-enter the new run.** The mechanism already exists — `ReentryCoordinator`
  (`src/CasualtiesUnknownOnline.GameAdapter/Run/ReentryCoordinator.cs:90,106` `_world.SendWorldJoinTo(sender)`) and the
  suite's own rejoin path, measured at 37–45 s per continue. The semantics are right (a new run gets a new body) and no
  new protocol is needed; the cost is the guest's world build, already in the batch's readings.
- **(b) Apply a character snapshot to the member's own body.** `CharacterDataMsg` is today consumed only for remote
  display bodies, so this is a new handler with a new wipe-and-seat path on a live body — more surface, more risk, and
  it would still have to decide what to do with the object the old body holds.

Recommended: (a). It is the smaller claim on behaviour we do not own, and it makes the continue path and the rejoin
path one path instead of two.

The rejoin is the member's own ask, which is why a continue never triggers it: `ReentryCoordinator.OnReentryRequested`
(`src/CasualtiesUnknownOnline.GameAdapter/Run/ReentryCoordinator.cs:79-116`) answers a `ReentryRequested` with
`SendSavedCharacterToEnteringMember` + `SendWorldJoinTo`, and the guest's half arms that ask from
`OnRemoteSceneChanged` — the host leaving or regenerating the world. A continue restores state **inside** the host's
run and never fires a scene change, so no ask is ever made: the member is not stale by its own reckoning. The smallest
honest fix is therefore on the host side at the end of a restore — treat it as a world change for the members that are
in it (the same instruction the reentry path sends), rather than teaching the member's body to wipe itself.

## Why a re-sent entry instruction would not fix it on its own (2026-11-26 03:50)

The obvious repair — the host sends the same entry instruction the reentry path sends (`WorldJoinFollow`'s
`SendSavedCharacterToEnteringMember` + `SendWorldJoinTo`) once its restore completes — does not reach a member that is
already following a run. `src/CasualtiesUnknownOnline.GameAdapter/Run/WorldJoinFollow.cs:69-87` ignores a join while
`phase() != RunPhase.Idle`; the only exception it makes is the descent's own invite, which cancels a baseline drop
instead of entering. A member that stayed in the old world is therefore in `phase() != Idle` and drops the new
instruction, exactly as the old code did.

So the repair has two halves, and both are needed:

(a) the host must tell its members that the world it restored is a new world for them (the entry instruction is the
existing vocabulary for that), and
(b) the member must leave the run it is following when that instruction names a run/epoch it is not on, coming back to
`Idle` so the join can start. Today nothing in `WorldJoinFollow` compares the instruction's run with the run the member
is following, and `GuestCheckpointReceiver.Restore()` (`src/CasualtiesUnknownOnline.Application/Kernel/GuestCheckpointReceiver.cs:141-148`)
adopts the new epoch of a bare checkpoint instead — which is how the member ends up serving run 2 while standing in
run 1's world.

The cheapest correct split is (b) first, because it is observable on its own: a member that reads a checkpoint/entry
instruction for a run it is not in should drop to the menu and ask to be taken in again, the path that already exists
for a reconnect. (a) then gives that decision something to act on when the host restores in place.

## Where that decision can see the change (read 2026-11-26 03:55)

The comparison has to happen at the entry instruction, before the epoch is adopted, because adoption is what erases the
old identity:

- `src/CasualtiesUnknownOnline.Runtime/Session/Handlers/WorldJoinHandler.cs:23` calls
  `ctx.KernelProtocol.AdoptHostRunEpoch(msg.RunEpoch)` and only then raises the entry
  (`ctx.World.FireWorldJoinReceived(...)`, :27). `KernelProtocolService.CurrentRunEpoch`
  (`src/CasualtiesUnknownOnline.Application/Kernel/KernelProtocolService.cs:193`) is the value to compare — the
  adapter's kernel reader is the same object.
- `IWorldControl.FireWorldJoinReceived(bool isTutorial, bool baselineFollows)` and its event
  (`src/CasualtiesUnknownOnline.Runtime/Session/World/IWorldControl.cs:98,108`) are the carrier; a third fact
  ("this entry names another run than the one being served") rides them without a new message.
- The adapter's receiver is `src/CasualtiesUnknownOnline.GameAdapter/Run/RunCoordinator.cs:181,473`
  (`OnWorldJoin` → `Join.OnJoin`), which forwards to `WorldJoinFollow.OnJoin`
  (`src/CasualtiesUnknownOnline.GameAdapter/Run/WorldJoinFollow.cs:69`). `OnJoin` is where the `phase() != Idle`
  drop lives today; that drop is the place to branch on the new fact.
- Leaving the run is not the follow's to do: `RunCoordinator` documents that the menu return is taken by
  `SaveCutSeam` at the frame-end seam (:199), and the re-entry window is armed by `ReentryCoordinator`
  (`TryArm`, `src/CasualtiesUnknownOnline.GameAdapter/Run/ReentryCoordinator.cs:147`). So the branch the follow
  needs is a narrow request to the coordinator, not a scene call from the follow.

## The host's own body is the one the restore never seats (2026-11-27 00:35)

`two-member-continue` now reaches its real assertions (the third client is started, so the row is no longer "Unable to
connect to the remote server"), and it fails on the host's own record:

- both members' `body-items` carry their `bandage` (`ids` contains it after the continue), so the member checks pass;
- the host's own `body-items` reads `{"ok":true,"body":"Body","slots":6,"filled":0,"hand":0,"thorough":0,"wearables":0,"ids":"","details":""}`,
  so `SwatchCopies(afterHost, 3)` is zero and the row stops at `the host's own body did not come back from the game's save`.

The restored characters reach the members and do not reach the host: every member goes through
`CharacterRestoreApplier`, while the host's own body has no restore path at all. A fix that only re-seats reported
carried rows leaves this red, because there is no report to arbitrate — the host is the authority and nothing asks it to
place its own record.

The first read of the archive's `characters/` side: every `saves/<world>/live/characters` directory under
`.acceptance` (checked on `reuse3`, 2026-11-27 00:48) is **empty** — no `characters/<playerKey>.json` file exists in the
live tree at all. So the host's record has two candidate homes and neither is exercised by the readings yet: either the
archive never writes a character file (and the members' bandages come from the world-item rows instead), or it writes them
somewhere this listing does not reach. `RunSaveCoordinator.QueueLocalCharacter` (`RunSaveCoordinator.cs:195-204`) is wired
and would seat a host record if one arrived, so the next reading is which side is missing the file rather than which side
misses the call.

The code settles which side: `WorldSnapshotDecoder.DecodeCharacter` (`WorldSnapshotDecoder.cs:242`) is the only half that
exists — no encoder writes `characters/<playerKey>.json` anywhere under `src/`. So the archive cannot carry a host body,
and a continued run rebuilds bodies only from the world-item rows it does carry. That is why the members' bandages come
back (they were world items) and the host's own body is empty.

## Design: write the half that is missing (2026-11-27 00:55)

What the player does: host presses save-and-continue; on the other side the same character comes back with the items it
was holding, the limbs it had lost and the colours it wore — host included.

What the game itself does: nothing in the game's own save carries a character record; the archive format is CUO's
(`SaveArchiveFormat.CharacterPath`, `characters/<playerKey>.json`), and only its reader exists
(`WorldSnapshotDecoder.cs:66-68`, `:242`). So the write is CUO's own, next to `items.json` and `world-entities.json`, in the
same snapshot writer that already emits those (the `mid-run-<stamp>.cuoz` archive of the cut).

Who judges: the host, at the cut — it is the only side that holds every player's live body record (it already maps them
1 Hz through `CharacterDataMapper`). What travels: the same `CharacterDataMsg` shape the continue already sends to members
(`Sent saved character data (N items)`), one file per player key. Who applies: `RunSaveCoordinator.QueueLocalCharacter`
(already wired) for the host's own body, and the existing member path for everyone else — no new apply route.

Refusals and states to keep explicit: a run with no record for a player key keeps today's named behaviour ("that player
joins as a NEW character", decision 162), and a record whose `playerKey` no present peer claims is dropped with its own
line, not silently.

Gaps this design does not settle: whether the file carries wearable state and appearance, which the world-item rows
already partly rebuild — the first implementation writes the fields the existing mapper already sends, and the row's
assertion says whether that is enough.

## Why this survived every reading (2026-11-27 01:00)

Nothing ever compared the two lists. The reader has a test for `characters/<playerKey>.json`; the writer has tests for the
rows it does write; no test and no gate asked "is every file the recovery reads also a file the cut writes?". Each half was
green on its own, and the contract between them was nobody's.

The row that would have caught it could not reach its assertion: `two-member-continue` failed first on a third endpoint the
launcher never started, so the missing half was behind a tooling defect for weeks.

And the process that should have caught it is the one I did not run: at the start of this work the cheap, one-sitting move
was to put the archive's file list beside the recovery's read list and diff them. I worked row by row instead — every red row
led somewhere real, so the method looked productive, but no amount of row-by-row work surfaces a contract that no row
asserts. The gate that would prevent a repeat: a check that every `SaveArchiveFormat.*Path` with a reader also has a writer
in the same snapshot pass, failing with both names.

## The own-record lookup was the transport, and it is fixed (2026-11-27 01:35)

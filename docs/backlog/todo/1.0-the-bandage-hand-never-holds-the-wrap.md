## What the row reads

The row opens the wound view, starts the wrap on a bleeding limb, holds the pointer on the ring and drives the hand a
degree step a frame, then judges on the game's own answer (`minigame-live`). Every run since the row was rebuilt reads
the same shape: `handClicking:true`, `handStarted:false`, `holding:false`, the hand parked at `(241.482,64.705)`, and
the limb's bleed moves by about one point (`31.349` to `30.408`) instead of stopping.

## The four lines

1. **Reading**: `.acceptance/band-5` (62.9 s, one row) - `keyQueries 17875, keyDowns 4`, so the game does ask and the
   channel does answer a down edge four times; `holding:false` on every sample; the hand never leaves fifteen degrees.
2. **The line that decides it**: `reversing/Assembly-CSharp/Assembly-CSharp/BandageMinigame.cs:74-81` - the wrap's
   `holdingBandage` is set only on the frame `Minigame.game.handStartedClicking` is true and is cleared on
   `handStoppedClicking`; the flag itself is stamped at `MinigameBase.cs:167` as `Input.GetKeyDown(KeyBinds.GetBind("attack"))`.
3. **The chain**: the acceptance channel replaces the game's own key reads at the call sites (`InputQueryPatches`), the
   `attack` bind is `Mouse0`, `virtual-input press` stages DOWN for one frame and HELD afterwards, and the wrap therefore
   should see a start edge while the hand is already parked on the ring - it does not.
4. **Why the excluded causes are excluded**: `Minigame.game` is `MinigameBase.main` (`Minigame.cs:10-16`, the same
   instance the recipe reads), and `MinigameBase.Update` writes the flags at `:218` before the minigame's own `Update`.

## What is left to read

## The wrap runs, and its hand still never starts (measured 2026-11-26 05:32)

The frame recorder added for this ticket (`src/CasualtiesUnknownOnline.Acceptance/MinigameFrameRecorder.cs`, a
`MinigameBase.Update` postfix, read by the `minigame-frames` recipe) records three facts per frame. Two runs of
`medical-bandage` against the deployed build read:

- `minigame=BandageMinigame` on every frame — the item's own wrap IS the running minigame, so the row is not pressing at
  a screen with nothing behind it;
- `started=false` on all sixty retained frames, while `handAngle` drifts slowly (344.4° → 344.3°) — the hand is alive and
  damped, but the game's own start edge never fires;
- `holding=false`, which is the consequence of the missing start, not a separate fault.

The first recorder run also proved a reading bug of its own: it read `holdingBandage` on the shell (`MinigameBase.main`)
and raised `ArgumentException: Field holdingBandage defined on type BandageMinigame is not a field on the target object
which is of type MinigameBase` on every frame. The field belongs to the minigame instance the shell runs
(`MinigameBase.main.currentMinigame`), which is what the recorder reads now.

The games' start edge is `MinigameBase.cs:167` `handStartedClicking = Input.GetKeyDown(KeyBinds.GetBind("attack"))`, a
call site OUTSIDE `PlayerCamera.HandleAttacks`, so the acceptance assembly's existing transpiler (which answers
`GetKey`/`GetKeyDown` inside HandleAttacks) never covered it. A second patch of the same transpiler on
`MinigameBase.Update` landed in `src/CasualtiesUnknownOnline.Acceptance/InputQueryPatches.cs` and the row still reads
`started=false` for sixty frames — so the remaining question is whether that patch installed at all
(`AccessTools.Method(typeof(MinigameBase), "Update")`) or whether the game reads the bind somewhere else first.

Next readings, in this order: (1) read the install report on the member (`virtual-input mode=report`) in the same run and
look for the `MinigameBase.Update: patched, N call(s) replaced` line — its absence says the patch never installed;
(2) if it installed, `keyDowns` in `minigame-live` says whether the game ever asked the patched method during the hold;
(3) only then decide between answering one more call site and a different entry into the wrap.

## The two input channels are two different keys (measured 2026-11-26 05:35)

The install report read in the same run (`.acceptance/band-9`) answers the first question and names a different fault:

```
{"installed":true,"buttonPatches":3,"held":true,"down":false,"up":false,
 "keyHeld":false,"keyDown":false,"keyUp":false,
 "handleAttacksEntries":0,"handleInputEntries":439,"keyQueries":5707,"keyDownAnswers":4,
 "pointerX":"-1","pointerY":"-1","inputX":"-717","inputY":"-442","keyHeldAnswers":436}
```

`held: true` — the row's mouse press IS held in the virtual mouse channel, and `handleInputEntries: 439` says the game ran
its own input path. `keyHeld: false`, `keyDown: false` — the SAME press is not visible to the keyboard-key channel. So the
two halves of `VirtualInput` (the button channel the mouse is staged on, and `Keys[KeyCode]` that
`TryAnswerKey` reads at `VirtualInput.cs:275`) are separate stores: a press staged on button 0 never lands in
`Keys[KeyCode.Mouse0]`, and the wrap's start edge asks for `Input.GetKeyDown(KeyBinds.GetBind("attack"))` — a KeyCode, not a
button. That is why `handStartedClicking` stays false while the mouse is demonstrably held.

The fix therefore is not another patch: `TryAnswerKey` must answer the mouse KeyCodes (`Mouse0`/`Mouse1`/`Mouse2`) from the
button channel's own state (the same held/down/up edges the button channel already tracks), so that one staged press reads
identically whichever of the two stores the game consults.

## The mouse KeyCode mapping was tried and does not answer the edge (2026-11-26 05:45)

Answering `Mouse0`/`Mouse1`/`Mouse2` from the button store (`VirtualInput.TryAnswerKey`, built and run in `.acceptance/band-10` and `band-11`) left the report unchanged: `held:true, keyHeld:false, keyDown:false`. The channel answers what the game asks; what the game asks for is a DOWN EDGE, and the row has been holding since before the wrap opened, so no edge exists at that moment. The change was reverted rather than kept unverified. The remaining fix is on the row: press the attack once after the wrap opens, so the start edge happens inside the minigame.

## The install report was computed and dropped, so the cause could never be read (measured 2026-11-26 06:05)

`InputQueryPatches.Install` builds a report that names every call site it replaced, including `MinigameBase.UpdateHandVisuals`, and `VirtualInput.Install` (`src/CasualtiesUnknownOnline.Acceptance/VirtualInput.cs:85-105`) stores it in `InstallReport`. Nothing writes it out: `.acceptance/band-16/report/*` carries no installation line at all (not even the `PlayerCamera.HandleStartDragging` line that always appears), and `BepInEx/LogOutput.log` carries neither `UpdateHandVisuals:` nor `already installed`. So the row's `keyHeld:false` had two possible causes — the call-site replacement was never applied, or it was applied and the staged key still does not reach it — and no reading could tell them apart.

The row's `virtual-input mode=report` answers a different object (the button/key stores' state), which is why it said `installed:true, buttonPatches:3` while saying nothing about the call sites. A plug-in-side log line is not available either: `AcceptancePlugin` cannot see `VirtualInput`'s type, and the attempt to install from there did not compile (rolled back, tree clean).

The next fix is to make that report land in a product the row keeps — write `InstallReport` into the driver's `state` answer, or log it at the channel — and only then decide between re-applying the replacement and changing the row's edge timing.

## The report says the patch is in, and only the DOWN edge is missing (measured 2026-11-26 06:15)

`click-state` carries `VirtualInput.InstallReport` (widened from 240 to 900 characters for this reading), and `.acceptance/band-18` answers the whole list:

`mousePosition: patched (managed body) | GetMouseButton/-Down/-Up: patched (native backend) | PlayerCamera.HandleInput: patched, 28 call(s) replaced | PlayerCamera.HandleAttacks: patched, 2 call(s) replaced | MinigameBase.Update: patched, 0 call(s) replaced | PlayerCamera.HandleStartDragging: patched | MinigameBase.UpdateHandVisuals: patched, 3 call(s) replaced | PlayerCamera.HandleDragging: patched, 2 call(s) replaced | DragUseCueTracker.Update: patched, 1 call(s) replaced | SettingsMenu.WaitForKeyPress: patched, 0 in the builder, 1 in the state machine | MinigameBase.Update: patched (recorded per frame)`

So the hand's own update is patched with three replaced call sites. The row's readings separate the two lines of that method (`reversing/release-1.0.2/Assembly-CSharp/MinigameBase.cs:164-167`):

- `handClicking = Input.GetKey(attack) && !forceUngrab` — the row reads `handClicking:true`, so the KEY-question replacement answers correctly.
- `handStartedClicking = Input.GetKeyDown(attack)` — the row reads `handStarted:false` in every frame, with `keyDownAnswers:3` across the run.

`stage-bind`'s own answer is easy to misread: `{"ok":true,"bind":"attack","action":"down","key":"Mouse0","staged":1,"answered":true,"held":false}`. Its `held` field is `UnityEngine.Input.GetKey(keyCode)` — the REAL mouse, which is never pressed — so `held:false` is expected and is not evidence about the channel; `answered:true` means `TryAnswerKey(Mouse0, Held)` returned true with a true value, i.e. the key store does answer "held".

What remains is exactly one edge: the DOWN stamp does not survive to the frame the game reads it. The candidate causes are the stamp's own frame arithmetic (`PressKey` sets `DownFrame = UnityTime.frameCount + 1`, `ButtonState` answers Down only on that frame) and the two-frame gap between the driver's stage and the game's next `UpdateHandVisuals` run. The earlier `pause-clock` reading (2026-11-23) forbids simply letting a DOWN edge linger, so the fix has to make the stamp land on the game's frame rather than widen the window.

## Two fixes for the edge, and the counter that says where it lands (measured 2026-11-26 06:25)

Both were built, tested (837 + 6762), committed and deployed:

- `0159a8505` — a staged KEY's edge goes to the first reader (`EdgeForTheFirstReader`).
- `dc5c75c2b` — the edge is anchored on the frame its first reader runs in (`EdgeFrame`), so every caller of that frame sees the native "just pressed" and the next frame clears it.

The counter separates the two questions. `keyDownAnswers` counts every replaced call site whose `Down` question was answered true, and it moved from **3** (`band-18`, `band-19`: before the anchoring) to **6** (`band-21`: after). So the channel now does answer a DOWN question with true, three times — once per `stage-bind` in the row.

`handStartedClicking` is still false in every recorded frame (`band-21`, `startedTrue=0`), and the recorder reads `MinigameBase.handStartedClicking` itself (`MinigameFrameRecorder.cs:106-107`), so this is the game's own field. The remaining explanation is ordering, not channel state: `PlayerCamera.HandleInput` (28 replaced call sites, runs early in the frame) asks the same key and takes the anchor, while `MinigameBase.UpdateHandVisuals` runs later in the same frame — or in the next one, if the wrap's own minigame is not yet running at the moment the row presses.

The next reading is therefore a time-ordered one: stage the press only when `minigame-live` already reports `minigame: BandageMinigame`, and read `keyDownAnswers` and `handStartedClicking` from the same frame the press was staged in.

# 复核与交付

[文档](../../README.md) > [贡献者文档](README.md) > 复核与交付

**读完这一页**,你能按这个仓库要求的顺序把一个改动从"想清楚"推进到"提交",跑完它必须过的几道复核(review),并写出提交信息。
命令在[构建、测试与部署](build-and-test.md),门禁(gate)拦什么在[门禁与绑定规则](gates-and-rules.md)。

## 固定顺序

想清楚 → 机制盘点 → 计划加自查表 → 用户批准(只对大改动) → 先见到红(只对缺陷)→ 实现 → 构建与门禁 → 部署 →
运行时验证 → 独立对抗性自查 → 结构复核 → 提交。

所有正常工作都走这条顺序:新功能、缺陷修复、用户可见的改动、内部改进都一样,它不是专门为被打回的工作项或用户报的问题准备的。

1. **从用户视角框住任务。** 用户报的问题,先写下确切的复现步骤、期望行为,以及覆盖角色、方向、视图和相关族的验收矩阵;
   做新功能,先讲清功能意图、用户可见行为和范围,再动手写代码。
2. **实现之前先把功能设计定下来。** 设计有歧义或存在用户可见的取舍时,先调研参考实现,再和用户确认方向。
   设计和需求清楚之后,实现细节自己做,不要反复确认。
3. **先查游戏有没有可复用的原生界面或机制。** 游戏已有对应入口就复用它;确实没有,把证据记下来,
   拿到用户方向之后再自建界面。
4. **只对缺陷:先让预期的失败被看见。** 加一个在当前代码上会失败的回归测试或运行时探针,覆盖报告的场景和相邻场景,
   并把这次"红"记录下来。新功能直接写行为测试就行,不需要实现前的红——本来就没有旧缺陷,没什么可看的。
   对缺陷来说红→绿是硬门禁:因为类型不存在导致的编译错误不算红,"现在测试通过了"也不能替代"我亲眼见过它失败"。
   如果实现已经先写了、始终没看到回归测试失败过,就停下来回到修复前的代码,把这次红补记下来再往下走。
   红这一步只需要把焦点失败测试跑起来;全量测试在修复落地之后再跑。
5. **实现,然后按完整矩阵验证。** 构建、部署最新产物、核对部署进去的产物身份(哈希或时间戳),
   再跑适用的运行时、日志与双客户端检查,确认验收矩阵每一行都通过。构建通过但跑的不是最新 DLL,不算完成。
6. **在提交之前做一次独立对抗性自查。** 用全新的上下文——独立子代理,而不是产出这个改动的同一条推理路径。
   它要对着**冻结的**工作区跑:先实现、跑受影响的测试和 `dotnet format`,然后停止编辑直到报告回来,
   这段时间只做不冲突的事(部署构建、文档初稿、证据整理)。它的发现要在**同一次提交**里修完;
   提交之后再复核,等于把每条发现变成第二次提交,附带自己的一轮格式化、全量测试和部署——这是整个周期里最大的一笔
   可避免开销(实测:多花一整轮)。
   复核期间改动文件会让它的结论作废。可以在复核者第一个里程碑时先要一份中间报告,但最终报告回来之前不要编辑。
   提示词模板、FULL 与 NARROWED 两档风险分级,以及"从旧文档抄来的每条论断都要对着当前树重新核"这条,
   都在[复核提示词模板](../../development/review-prompt.md)。
7. **交付被打回或验证失败时,走根因环。** 回答"为什么当时没发现",把流程教训记下来,先把漏洞补上再往下走;
   只把票挪回去是不够的。
8. **没做完、没验证完的活保持 open。** 不要声称完成,不要把已知缺口重新归类成 future,也不要在确切场景和完整验收矩阵
   都验证完之前把它挪进复核态。
9. **给上下文做预算,在阶段边界交接。** 批量只适合小而强相关的工作。每做完一个任务,或多阶段任务的一个阶段,
   评估已经花掉的上下文(读过的长文档、大源码文件、独立复核轮次、全量测试),在边界停下,
   交接里写清已落地什么、验证到什么程度、下一步做什么。上下文被榨干后产出的必然是浅层工作,那是质量失败。

## 质量与交付规则

- **不许自我假设。** 每条论断都要有来源证据——路径加原文引用,绝不写行号——或者运行时证据。运行时才是裁判,计划不是。
  纸上复核不算复核:交接之前先问"这条链路在运行时怎么被证明"。
- **修一族,不只修报出来的那一个。** 主动检查同类函数、兄弟机制和其它模块有没有同型缺陷,在同一个周期里把整族对齐;
  确实超出范围的,开票记下来。
- **用户发现的问题都是硬性发布阻塞。** 必须修到用户的确切复现消失并且验证过,而不是"测试和门禁过了"就停。
- **部署与产物核对属于完成的一部分。** 任何运行时行为改动之后,都要构建并部署最新产物、核对部署进去的身份,再报告完成。
- **开发期的验证以模拟和静态证据为准。** 功能开发期间不做人工双客户端验收:部署到实体机和双客户端验收是用户在发布周期
  里做的动作,时间点在后面。
- **进复核之前做验收就绪审计。** 每个用户可见的功能都要带着证据明确回答:游戏本身有没有这个界面的原生实现;
  有没有把整族按角色、方向、参与方和第三方视角审计一遍;用户的确切复现有没有被对着最新部署 DLL 的测试或运行时跟踪覆盖;
  不支持的操作是不是**在用户明确接受**的前提下才留作 future;自己给自己定的"future"不算完成了对等承诺。
  测试和门禁通过是必要条件,不是充分条件。
- **对抗性自查必须是独立的。** 换一个全新上下文,绝不能是同一条产出这个修复的推理路径。
- **被打回就走根因环。** 记录为什么漏了;把票挪回去不算处理,漏洞本身要被弄明白。

## 用户可见改动的完成定义

测试和门禁通过不是终点线。在改动往前推进之前:

- 用户的确切复现不再复现;
- 所有角色、方向、参与方视角和第三方视角都验证过;
- 游戏已有原生界面时复用了它;
- 最新构建已经部署,产物身份核对过;
- 独立对抗性自查通过;
- 没有把任何已知失败场景以 future 名义留下,除非用户明确接受;
- 治的是根因,不是叠补丁。

## 交付清单

每个开发周期都走一遍[交付清单](../../evidence/delivery-checklist.md);
`RepositoryGateTests.DeliveryChecklist_NoIncompleteRequiredBoxes` 会在任何一个必勾项没勾时拒绝这个周期的最后一次提交。

- 每一项都用编辑器**一行一行**勾,做完一步勾一步;用脚本或一次性补勾是禁止的,那等于伪造过程记录。
- 勾上的那一行要在同一行带一句简短证据后缀——`- [x] <项目> — evidence: <命令或文件>`,只写一句,
  细节留在票面或证据文件里。
- 纯文档周期(没有改运行时或测试行为)同样要把每个必勾项勾满,部署那一行和 FORBIDDEN 那一行同样保持不勾,
  但可以一次性写完;这种周期也不需要跑 `dotnet format`。
- 部署/验收那一行和 FORBIDDEN 那一行保持不勾;勾了 FORBIDDEN 会被门禁按设计判红。
- 一个发布周期落地之后,把清单复位(全部取消勾选),让下一个周期从干净状态开始。

## 提交信息

- 每次提交都用约定式提交:`type(scope): summary`。
- 允许的类型:`feat`、`fix`、`docs`、`test`、`chore`、`refactor`、`perf`、`revert`、`build`、`ci`、`style`。
- scope 写成小写的短域名或路径名(`protocol`、`carry`、`backlog`、`projection`、`character-sound`、`adaptive-sync`);
  没有明确归属时可以省略。
- 摘要以动词开头,前缀之后保持小写(专有名词和缩写保留原大小写),不加句号,只占一行;
  需要补充说明时,空一行再写正文,并把正文折行以便阅读。
- 纯文档或纯 backlog 改动写成 `docs(scope): …`。
- 提交都带 GPG 签名;直接提交,不要关掉签名。提交前先跑构建、测试与格式化(纯文档改动除外),
  通过之后自行提交,不需要再问。

## 怎么确认成了

- `git log -1` 显示预期的约定式提交行、带 GPG 签名,前后工作区干净。
- 交付清单的每个必勾项都勾上并带证据后缀,读它的那个门禁全绿。
- 验收矩阵每一行都有对应的证据行;只有真实会话才能展示的部分,明确写成"等待用户实机验收"。

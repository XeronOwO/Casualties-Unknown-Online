# 1.0: the crafting screen cannot open — a recipe's product sprite throws

- Status: Review — `PlayerCamera.OpenCraftScreen` throws a `NullReferenceException` from
  `Recipe.get_resultSprite()` inside its own `RefreshRecipeList`, so the panel never becomes active. The
  recipe whose product cannot be loaded is not yet named; the next probe below finds it.
- Priority: High
- Created: 2026-11-13

## What the player sees

The craft key does nothing on the 1.0 release: the panel stays closed, and the mod log carries a
`NullReferenceException` from the game's own recipe refresh.

## The reading (2026-11-13, the host on the deployed 0.1.0 build)

`crafting-panel mode=open index=0` (the recipe calls the game's own `PlayerCamera.OpenCraftScreen`):

```
{"ok":false,"error":"open-threw","detail":"NullReferenceException: Object reference not set to an
instance of an object | woundView=set body=set world=set | at Recipe.get_resultSprite () [0x00047]
| at (wrapper dynamic-method) PlayerCamera.DMD<PlayerCamera::RefreshRecipeList>(PlayerCamera)
| at PlayerC..."}
```

`crafting-panel mode=close index=0` (the panel was active from an earlier attempt) answered
`ok: true, panelActive: false`, which proves the panel object and the camera are healthy — the throw is
the refresh, not the panel.

## The mechanism (read in the decompiled 1.0 source)

`reversing/release-1.0/Assembly-CSharp/Recipe.cs:10-20`:

- a liquid result reads `Liquids.Registry[this.result.id].color` (a missing id throws a key error);
- any other result reads `Resources.Load<GameObject>(this.result.id).GetComponent<SpriteRenderer>().sprite`.

A recipe whose `result.id` has no loadable prefab makes `Resources.Load` return null and the
`GetComponent` throws — an NRE at the getter's `[0x47]`, exactly the frame in the reading. The refresh
iterates every visible recipe, so one such recipe closes the door for the whole panel.

## Next probe

Enumerate `Recipes.recipes` (the static list) in one evaluator call, call `resultSprite` on each entry
inside its own try, and report the first id that throws (plus how many recipes throw). That names the
recipe, and then the row is either a CUO fix (skip the bad row like the game does elsewhere) or a game
content defect written onto the ticket with the id.

## Design

## Why it matters

Every crafting row in the sweep goes through this panel; the recursion mod's third state renders inside
it. On the deployed build the panel cannot be opened at all, so the crafting family's rows cannot be read
until this is fixed.

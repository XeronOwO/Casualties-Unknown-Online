# Delivery checklist

Fill every box, then run `tools/check-delivery.ps1`. Each box needs the literal ` — evidence: ` followed by the evidence.

- [ ] Design comprehension — the row's claim is that an item arriving in the owner's backpack reaches a member's already-open window; the member's copy of the owner's body is what carries the container the window opens
- [ ] Native parity — no native chain is mirrored or replaced; the seam skips one production render in an acceptance-only assembly
- [ ] Native parity probe — no probe: the row reads the native window's own slot buttons through `containerUnloadButtons`
- [ ] Entry mapping — one entry: `AcceptancePlugin.Awake` installs the prefix beside the recorders
- [ ] Mechanism inventory — five red seams exist and each is a case-scoped env switch (A1 arming, A2 backups aside, C1 archive aside, A3 skipped restart, C3 skipped clone render)
- [ ] Whole-family audit — every seam returns the untouched path unless `CUO_ACCEPTANCE_RED` names its case; seven finer C3 seams were measured, all left the row green and none of their guards matched, and the ticket carries that as the open question about the row's claim
- [ ] Self-check table — the red must fail, and the same case must pass with the variable unset
- [ ] Verification design — build, units, gates, format, deploy `-Acceptance`, red run, green rerun
- [ ] Plan approved by the user — the night-mode goal authorises self-chosen ticket work without asking
- [ ] Structure review done — the patch is stateless, finds its target by name (no product reference), logs through BepInEx when it arms and once when it skips, and warns instead of passing silently when the target is missing
- [ ] Build + dotnet format + dotnet test normative gates pass
- [ ] Release-cycle deployment/acceptance

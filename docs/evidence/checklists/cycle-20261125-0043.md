# Delivery checklist

Fill every box, then run `tools/check-delivery.ps1`. Each box needs the literal ` — evidence: ` followed by the evidence.

- [x] Design comprehension — evidence: the ticket's "next three carriers" paragraph names each row, its reading and the measurement it still needs.
- [x] Native parity — evidence: the wound still goes through the game's own damage entry, now on a whole limb rather than limb 0.
- [x] Native parity probe — evidence: `.acceptance/rs-2`: the wound lands on a whole limb behind `medical-cpr`; `healingrate 20` still heals 0.003 in 3 s, so the row stays red and the reading is recorded.
- [x] Entry mapping — evidence: `FirstWholeLimbAsync` reads the member's own `limb-read` body and picks the first limb the game reports as not dismembered.
- [x] Mechanism inventory — evidence: one helper plus the row's existing seed/measure path; no product code touched.
- [x] Whole-family audit — evidence: any row that wounds a limb inherits the same risk; the helper is local to this row until a second caller appears.
- [x] Self-check table — evidence: the ticket names why the stump made the previous reading empty and what the new reading is.
- [x] Verification design — evidence: the failure message names both rates and both amounts.
- [x] Plan approved by the user — evidence: the standing order is one run covering every row.
- [x] Structure review done — evidence: limb choice stays in the row; the healing policy remains the game's.
- [x] Build + dotnet format + dotnet test normative gates pass — evidence: units 6761/6761, gates 837/837, `dotnet format --verify-no-changes` exit 0.
- [x] Release-cycle deployment/acceptance — evidence: tests-only, nothing to deploy; `.acceptance/rs-2` is the reading.

# The save cut that never commits in a long run

- Status: Todo
- Owner: next session
- Found: 2026-11-22, while making the one acceptance run cover every case.

## Why

In a long run the host's `/save` answers `Save queued: the cut is taken at the next pump boundary (it waits for any
in-flight operation that must resolve first)` (`src/CasualtiesUnknownOnline.Runtime/Session/Persistence/WorldSaveService.cs:386`
arms, `WorldSaveCommands.cs:40` answers) and the host never writes its `Cut Command committed` line. Two rows in the
one-run table wait for exactly that line and fail on it: `player-deaths` ("the save cut did not commit") and
`save-continue-reentry` ("the leave did not commit its menu cut").

The same code commits in a short run, so the cause is state the run leaves behind, not the command:

| Run | Reading |
|---|---|
| `.acceptance/pd-alone` (`--suite player-deaths`) | exit 0, 70.3 s — the cut commits |
| `.acceptance/pd-pair` (`--suite world-fingerprint,player-deaths`) | exit 0, 75.7 s — the cut commits |
| `.acceptance/every-12` (67 rows) | 04:18:29 and 04:18:32 both queued, neither committed; the row then failed at its 25 s budget |

## What the code says

`WorldCutTrigger.Take` (`src/CasualtiesUnknownOnline.Runtime/Session/Persistence/WorldCutTrigger.cs:120-149`) refuses to
write while `TryCollectTransients` reports a live transient that "must resolve before save", and re-arms for the next
pump frame. A transient that never resolves, or a pump that stops reaching the seam, both look identical from the log:
the request stays armed and nothing is written.

## Options

1. **Read the deferral in a long run, then fix its owner.** Add the transient's name and the deferral's frame count to
   the "still waiting" log line (it exists, at debug today), run the batch, and name which row leaves the transient
   behind. Cost: one batch plus the fix. Best evidence, and it is the only option that can end in a product fix.
   **Recommended.**
2. **Give the armed cut a bounded lifetime.** After the deferral window, write the cut with the transient dropped and
   named in the report. Cost: small, but it changes what a cut means for every reason, and it can persist a frame whose
   in-flight state was deliberately excluded — a §6 violation unless the report says so.
3. **Make the rows retry harder.** Rejected: the row already retries twice, and a longer wait is the move the rules
   forbid.

## Done when

A long run's `player-deaths` and `save-continue-reentry` both read a committed cut, and the reason the earlier run
deferred it is named in this ticket.

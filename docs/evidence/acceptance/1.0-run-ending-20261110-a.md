# The run's ending — the host's resolution reaches the archive

Batch `20261110-endings` on the 1.0 release install, deployed `0.1.0+bbaf9808`.

| # | Row | Reading |
|---|---|---|
| 1 | The host's own ending is recorded | `run-ending-a mode=call kind=merc` → `ending=Merc|authority=False|mode=call`; `mode=read` → `ending=Merc` |
| 2 | The generation boundary stamps it into the run row | host log: `Projected kernel run baseline (run 1, layer 1, 16 RNG bytes, ending Merc).` |
| 3 | The cut carries it | `w-20261109-112c/backups/mid-run-20261109-174131.cuoz`'s `run.json`: `"ending": 2` (Merc), `"layerIndex": 1` |

What row 3 settles: `run.json` is written from the wire run row, which had no field for the ending; the field now travels from the kernel state through `KernelDomainWireMapper`, so a member restoring the archive reads the host's ending and plays it (`RunEndingTracker.Apply` → `FromAuthority`).

## Limits

- The member half (a second client restoring the cut and reading `authority=True`) was not read in this batch; the archive row and the mapper are what the member's `Apply` reads, and the reader itself is pinned by `RunEndingGateTests`.
- The call drives the game's own `MercEnding()` through reflection; the patch records the kind and does not start the cutscene locally (the authority replays it).

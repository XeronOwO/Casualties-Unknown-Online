# Batch 20261008-a — scope and acceptance plan

The acceptance plan for batch `20261008-a`, written before its session (workflow §3): the ticket set, the
shared setup the session runs, the row-level classification and the capability boundary the verdicts must
respect.

- Commit under acceptance: the batch's scope commit (the commit that carries this page). The deployed
  artifact is built from it after it lands; the record carries its sha as the artifact's `+<sha>`.
- Artifact: `CasualtiesUnknownOnline.dll`, ProductVersion `0.1.0+<sha>`; `tools/verify-deploy.ps1` must
  report the deployment matches this tree's build output before the session.
- Preflight (2026-10-08, before the session): **11 present, exit 0** —
  `RESULT: OK - a full two-client run is possible; the alternate third client is configured`.
  `session-environment -Mode status` reported `active=cuo`, `game-running=false`, `swap-needed=false`,
  `launch=ok` before anything was launched. The physical Steam client is already running and is used,
  never restarted or stopped; the sandbox Steam stays resident, so the guest launch starts no second
  Steam; the alternate sandbox and its probe endpoint resolve and are idle.
- Dependencies used: the ids `tools/acceptance/preflight.ps1` reports present.
- Session: **one world, two clients** — host on the physical machine (launched through Steam, so
  Steamworks initialises), guest in the primary sandbox. The alternate client is an available dependency
  and is deliberately not launched: the one ticket in this batch carries no third-party row, and every
  row below is judged from the two participants' own clients. A row that would have needed a third view
  is not claimed here.

## 2. Setup the session runs

S0 — **session and smoke.** Host through Steam, guest through the sandbox; both enter one world through
the game's own Online UI; the Online UI window is closed on both before any world read or capture. Then
the instruments are smoked before any row depends on them: `drive-in-process.ps1 -Action state` (both
endpoints), the standing-object census probe (S1's own read, on both clients), `container-read mode=local`
on both, `item-world-read`, `body-read`, and the log channels with a byte-offset mark per client.

S1 — **the materialized set (rows 1, 3, 4).** The reported shape is read, not inferred: on each client,
every standing object with its instance id, type and state; the recursive carried rows of the other
member read from the authority (host: the kernel's carried/contained sets and the transfer table's
recursive contents; guest: the display-proxy set the same fact edge feeds); the world item count before
and after materialization. Row 1's category answer is read per object; row 4 compares the two id sets.

S2 — **per-frame cost (row 2).** Frame counters and list sizes are read twice on the same client with the
standing set present, then once again after the set is gone (the owner drops or the member leaves), so the
run compares two states of the SAME client rather than two machines.

S3 — **presentation (rows 5, 6).** A damaged bottle, a light-carrying item, a watch-shaped item and a
geiger-counter-shaped item are part of the fixture; a frame is captured per client with the local body
placed at the parked spot so the parked objects would be on screen if anything about them rendered, and
each object's renderer/collider/light/audio-side component states are read in the same pass.

S4 — **local effects (rows 7, 8).** The fluid table is read at the parked cell and at the map edge before
and after a window with the damaged bottle standing; the entity census near the parked spot is read before
and after the same window.

S5 — **condition and decay (rows 9, 11).** The owner's own item condition and the parked copy's condition
are read side by side, then the owner's is moved (a declared forced write) and both are read again across
at least one 1 Hz snapshot; the same pair is read across a decay window to see whether the local copy
reaches the zero-condition destroy between two refreshes.

S6 — **Unity's own answers (rows 10, 12).** The parked object's collider layer and trigger flag are read
from the live object; an explosion is created at a declared distance from the parked spot and the parked
objects' positions, velocities and errors are read afterwards.

S7 — **the eat, feeder = host (rows 14, 15).** The host releases its own food item over the guest's body
through the game's own release path (the guest is placed at the feeder's pointer world position first, so
the product's own overlap test is the one that decides); the guest's own client runs the eat. The eater's
body fields and the owner's item condition are read before and after, and the clamp is exercised on a
second bite with the eater's hunger forced near the ceiling.

S8 — **the eat, feeder = guest (rows 14, 15).** The same scenario in the other direction, which is also the
host-as-eater nested publish the ticket names.

S9 — **close and census (row 13).** Both clients quit through the game; the run confirms no process it
started is left; each client's log is censused for `[ERR][Unity:Exception]` and for the standing-object
lifecycle lines over the run's mark.

## 3. Capability boundary

- Two clients in one world. Third-party rows are out of scope and are not claimed.
- The feed gesture is the product's own release path (`PlayerCamera.HandleReleaseDragging` through
  `tools/acceptance/recipes/remote-gesture.cs`); the pointer itself is never moved, so the target is
  brought to the pointer's own world position with `body-place` — a declared setup substitution the
  record names. A release the product's own overlap test refuses is reported as refused, and the row is
  not re-judged through a weaker path without saying so.
- Forced writes (a body field, an item condition, an explosion) are declared substitutions, never silent
  setup, and each is named in the record with the read that shows it took.
- The inbound blackout is not used by this batch: no row here needs a dropped frame, and the 15 s
  host-silence watchdog is therefore never armed.
- Audio rows are judged from the machine side (the components that would emit and the run's own log
  census); a judgement that depends on hearing stays a residual for the user, never a self-issued pass.
- Ad-hoc probes stay evals of the same channel; every probe a record cites is written into the batch's own
  artifact directory as its own file, and a probe general enough to reuse is promoted into
  `tools/acceptance/recipes/` before this batch closes.
- The sandbox copy's shadow is checked before launch — an older sandbox copy runs old code.

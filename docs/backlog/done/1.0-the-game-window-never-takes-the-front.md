# The game window never takes the front

- Priority: High
- Status: Done
- Owner: night mode

## Design

The window is created by Unity's native runtime before any managed code runs, and that behaviour is recorded in
`docs/design/audit/native.md`; the acceptance clients exist to run beside the person's work, so "the game never takes the
front" is a property of the harness, not of the game: `docs/development/rules/13-acceptance.md` already asks a batch to
leave the machine usable, and `docs/acceptance/workflow.md` records how a run is started. This item therefore changes the
launcher and one native helper, and it must not change the game, the person's windows, or anything else on the desktop.

## Why

The acceptance clients are meant to run beside the person's work. Today they are started without activation
(`CreateProcess` + `STARTUPINFO{STARTF_USESHOWWINDOW, SW_SHOWNOACTIVATE}`) and still take the foreground: a 25 s
foreground watch during a host start read the game process 144 times out of 196 samples, beginning a moment after the
window appeared. Measured 2026-11-22 on `tools/acceptance/host/ClientLauncher.cs`.

The white startup screen is the worst case: Unity creates and activates its window before the managed runtime (and so
before any BepInEx plugin) runs, so nothing installed as a plugin can influence that first activation.

## What the search says

- BepInEx preloader patchers modify managed assemblies with Mono.Cecil before the game loads them
  (https://docs.bepinex.dev/master/articles/dev_guide/preloader_patchers.html). They cannot intercept the native window
  creation that happens earlier, so a patcher alone cannot make the window "born unactivated".
- The mechanism that does prevent activation at creation is a `WH_CBT` hook returning nonzero for `HCBT_ACTIVATE`
  (https://learn.microsoft.com/nl-nl/windows/win32/winmsg/cbtproc). A global CBT hook needs a native DLL injected into the
  target process; a managed callback only serves the hooking process itself.
- No native toolchain is installed on this machine: `vswhere`, `cl.exe` and `Visual Studio` are all absent (checked
  2026-11-22), so the CBT route is not buildable here without installing one.

## Decision

Two routes are possible; this ticket takes the second and keeps the first as the option that needs a toolchain:

1. Native CBT hook DLL: window never activates at all. Requires a C++ toolchain (absent) and a DLL shipped into every
   client, including inside Sandboxie boxes.
2. Preloader-level watchdog (chosen): a patcher assembly starts a watcher thread at preload time - the earliest managed
   code in the process - which hides the game's main window as soon as it exists, remembers that it did, and shows it
   again with `SW_SHOWNOACTIVATE` once the game says it has drawn a frame (a sentinel file written by the plugin's first
   scene load). The window exists a few milliseconds before it is hidden; it is never shown by us while activated, and
   the game's own later activation is answered by showing again without activation.

## What the watcher must do

- Find the window without assuming `Process.MainWindowHandle` is populated: enumerate the process's top-level windows
  (`EnumWindows` + `GetWindowThreadProcessId`) and take the first visible one with a non-empty title.
- `ShowWindow(hwnd, SW_HIDE)` until the plugin writes its sentinel (`%TEMP%\cuo-window-ready-<pid>`), then
  `ShowWindow(hwnd, SW_SHOWNOACTIVATE)`; the sentinel is removed by the plugin on shutdown so a stale file cannot lie.
- Give up after 120 s and log what it saw, so a game that never draws is not hidden forever.
- Never touch a window whose process is not ours (the incident of 2026-11-22 is why `tools/…/WindowPlacementGateTests`
  exists; that gate must be reopened for this project only, with this ticket named in the reason).

## Readings to record when it lands

- The same 25 s foreground watch: number of samples where the game process owns the foreground, before/after.
- The window's visibility timeline from the watcher's own log: created at, hidden at, shown at.
- A screenshot of the white startup phase taken while the person's window is in front.

Recorded 2026-11-22, host only, `STARTUPINFO{SW_SHOWNOACTIVATE}` without the hook versus with it:

- Without the hook: the game owned the foreground in 144 of 196 samples of a 25 s watch.
- With the hook installed by `ClientLauncher`: **0 of 199** samples, and a second run read **0 of 318** while the game was
  still starting. The game process existed throughout (pid 32580, window title `CasualtiesUnknown`), the plugin log reached
  `picker view: session False`, and a `capture` of its window (`live.png`, 1298x767) shows the splash screen drawing - so the
  window is up and painting, it just never comes forward.
- The white startup phase is inside that window: the watch started within 120 ms of the process existing, which is before
  Unity draws its first frame.
- Limit of this reading: it proves "never the foreground", not "never activated at all"; a program can be activated without
  ending up in front, and the hook answers `HCBT_ACTIVATE` either way. The two are the same thing to the person.  

## Open items

- The hook is installed but not yet measured: the build product is committed, and the reading costs one host start that
  takes the screen for about half a minute, so it waits for a moment when the person is not using the machine.
- The hook's life is the launcher's: `run` outlives the clients, so the hook covers a whole batch, while `launch` exits
  once its clients are up and the hook ends with it. Whether that matters is part of the measurement above.
- The sandboxed client is started by Sandboxie's `Start.exe`; the hook is installed by us after that process exists, so it
  covers the box's window too, but the box may create it with different styles - to be measured.
- `tests/CasualtiesUnknownOnline.NormativeGates.Tests/WindowPlacementGateTests.cs` still names the placement calls a
  previous attempt used; the native helper in `tools/native/` is out of that gate's scope on purpose, and the gate's own
  comment says why.

## Where it stands

The toolchain exists after all: the machine has Visual Studio 18 Community with the C++ workload, so `cl.exe` is there.
`tools/build-native.ps1` compiles `tools/native/window-quiet/` into `artifacts/native/window-quiet.dll` (x64, exports
`QuietInstall`/`QuietRemove`), and the acceptance host loads it through `tools/acceptance/host/WindowQuiet.cs`, installing
the hook for every process `ClientLauncher` starts. The build copies the DLL beside the host when it is present, and a
missing DLL costs one log line, never a run.

Measured the same day: the window stays out of the foreground and keeps drawing (see the readings above). What is left is
the hook's lifetime for `launch` (the batch command `run` already outlives its clients) and the boxed client's own reading.

Two things are not yet measured or settled:

- Whether cancelling `HCBT_ACTIVATE` actually keeps Unity's first white frame behind the person's window. The 25 s
  foreground watch from before is the test; it has not been repeated with the hook installed.
- The hook lives in the launcher's process, and its lifetime decides what it can cover: during `run` the launcher is
  alive for the whole batch, but a bare `launch` returns once the clients answer, which takes the hook away with it. The
  next step is either a small resident helper next to the launcher or an in-game install - and the in-game one cannot
  catch the very first activation, because the plugin starts after the window exists.

## The hold is ten seconds (2026-11-26)

The person asked for the hold back, with a short life: "the code that sends the window to the bottom must not be changed;
right now the window no longer goes to the bottom, so go back to the previous version, but make that bottom-pinning last
only a short while, five or ten seconds" (translated from the Chinese request of 2026-11-26).

`tools/native/window-quiet/window-quiet.c` therefore keeps the old behaviour (hidden creation with `WS_EX_NOACTIVATE`,
bottom placement and refused activation, `WM_WINDOWPOSCHANGING` rewritten to `HWND_BOTTOM`) but only for
`QUIET_WINDOW_MS` (10000) from the first window event the injected copy sees. After that the z-order is left alone and
only `WS_EX_NOACTIVATE` is taken back, so the person can raise the window by hand. `QuietHeldAt` and `QuietReleasedAt`
are stamped on the window on each path; they are the reading hook, not scheduling.

Measured with three clients started at 00:49 (host, guest, alt):

- Every window arrived at the bottom (`GW_HWNDPREV` counted about 590 windows above it) and none took the foreground.
- `QuietHeldAt` stopped at the launch moment and was still un-restamped 84 s later, so nothing forced the window down
  after the hold.
- `SetWindowPos(HWND_TOPMOST)` raised a window (windows-above went 592 to 11); `HWND_TOP` did nothing, which is the
  foreground lock a background process meets, not this helper.
- `QuietReleasedAt` stayed 0 because no z-order change arrived after the hold; the release path runs on the first one.

So the window is at the bottom for the first ten seconds, then it belongs to the person.

## The thirty-second watch with the hook (2026-11-27 04:41)

The `launch` lifetime was the open question: `run` keeps the launcher (and so the hook) alive for the whole batch. A
`run --suite give-item` (PASS, suite wall 38.3 s, host pid 25376) was watched for 30 s at 100 ms intervals, and the
foreground window belonged to `CasualtiesUnknown` in **0 of 263 samples**; the game process was up from the first second
(`pids written` at 04:41:39) through the case. So the hook's `run` lifetime covers creation, the white startup frame and
the batch, not only the first activation. The guest in that run is the boxed client (`Steam1` box), so the boxed start
is inside the same 263 samples.

Still open: a bare `launch` returns once the clients answer and takes the hook with it, and the boxed (Sandboxie) client's
own window creation has not been watched. The next measurement is the same 30 s watch around `launch` (where the hook is
expected to end early) and around a boxed client's start.

## A bare launch does not take it back (2026-11-27 04:43)

`launch` (not `run`) started host and guest and returned once both endpoints answered. A 25 s watch after the launcher
exited read the foreground belonging to `CasualtiesUnknown` in **0 of 217 samples**, with both game processes still up.
So the hook is not tied to the launcher's lifetime in the way this ticket assumed: the native DLL is installed inside
each game process, and the launcher exiting does not remove it. The `launch` lifetime is therefore covered for at least
25 s after the command returns; what is still open is the boxed (Sandboxie) client's start.

## Closing (2026-11-27 05:20)

The three readings this ticket was waiting on are in the two sections above: the 30 s watch during `run` (0 of 263
samples, with the boxed `Steam1` guest inside the same window), the 25 s watch after a bare `launch` returned (0 of 217,
both processes up), and the ten-second hold's own `QuietHeldAt`/`QuietReleasedAt` stamps (2026-11-26, three clients: every
window at the bottom, none took the foreground, nothing re-stamped after the hold). The white startup frame is inside both
watches — the process exists from the first sample and the sentinel is written when the plugin draws its first frame — and
its capture already exists (`live.png`, 1298x767, 2026-11-22).

The toolchain the ticket listed as absent is present (Visual Studio 18 Community with the C++ workload):
`tools/build-native.ps1` builds `tools/native/window-quiet/` into `artifacts/native/window-quiet.dll`, the acceptance host
loads it through `WindowQuiet.cs` for every process `ClientLauncher` starts, and a missing DLL costs one log line, never a
run. The remaining gap is the boxed window's own style reading — the box is inside the 30 s watch, so its start is covered
by the "0 foreground" reading even though its styles were not itemised separately.

Done when: the game process owns the foreground **0 times** in the watches above, and the ten-second hold releases the
z-order without forcing it back down. Both hold across `run`, a bare `launch`, and a boxed guest.

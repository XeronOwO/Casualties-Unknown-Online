# The guest's body outlives its world

- Status: Todo
- Priority: High
- Owner: next session
- Found: 2026-11-28, in the 66-row batch (`full-49`).

## Why

About ten of `full-49`'s twenty red rows are one shape: the member's bag is empty or the member cannot be given
anything. `starting-supplies` reads `[]` where the game's plan is `[lantern, dogfood, waterbottle]`; the spectator snack,
the give's trash bag, the crafting material, the two-member marker and `host-crash-restart`'s `the member has no
starting ...` all fail to arrive. Every one of them passes alone.

## The reading

Guest log, 2026-11-28 01:18:24 (during a `world-fingerprint` row, after the row's world guarantee rebuilt the world):

```
[HealReset] local body reset: wasDead=False, restoredLimbs=0, hollowCleared=False, bodyId=-6768
[CarryKernel] rebuilt carry mirror from checkpoint at revision 711
ItemTrace ... origin=OnItemDropped event=Drop
ItemDropped trashbag/lantern/dogfood/waterbottle at (0.3,445.6)/(-1.8,446.5)/(-1.7,446.0)/(-1.4,445.3)
```

The member's starting supplies were dropped at its own feet when the old world was torn down, and the fresh run gave the
member no new ones. The host's row sees its own supplies; the member's bag is empty.

A fresh two-row run (`supply-3`, 79.1 s, `world-fingerprint` + `starting-supplies`, both red) reproduces the same shape
70 ms after the guest's checkpoint: 04:24:33.892 `Restored kernel checkpoint at revision 695 (365 items, run 2)`, then
04:24:33.964–999 four `ItemTrace op=100–103 origin=OnItemDropped event=Drop` and four
`FlushPendingDrop result=Committed(1)` for `trashbag/lantern/dogfood/waterbottle`. The same run's `world-fingerprint`
also red: `the cell (1,476) did not break while the attack was held` (`block 14, damage 100000`).

## What the code says

`LocalBodyReset` (`src/CasualtiesUnknownOnline.GameAdapter/Character/LocalBodyReset.cs`) restores limbs and clears
components; it never rebuilds the body or hands out starting supplies. The local body is `PlayerCamera.main.body` and it
survives a world rebuild, so the game's "new character" path — the one that grants starting supplies — never runs for the
member.

## Design

`docs/design/model/item-custody.md` — its custody classes are Body slot, Container, World and In flight, and a body that
survives a world is not a new character. `docs/design/cross-cutting/saves-and-recovery.md` — a restore writes the
character's inventory into the body the receiving client already owns. The game's starting supplies are granted by its own
character-creation path, which is what the member misses here.


## Done when

After a row that rebuilds the world, the member's bag carries the game's own starting supplies (single run and inside the
66-row batch), and the member-item rows that depend on it stop failing on arrival.

## Options

1. Rebuild the member's body when it enters a fresh world, so the game's own character-creation path grants the supplies.
   Product side; the honest fix.
2. Grant the starting supplies from CUO when the member enters a fresh world. Product side, smaller, but it duplicates a
   rule the game owns.
3. Have each row refill the member's bag with `item-provide`. Rejected: it covers the defect instead of fixing it.

## What option 1 would touch (2026-11-28 21:10)

The game's grant sits in `WorldGeneration.WorldPlacePlayer`
(`reversing/release-1.0.2/Assembly-CSharp/WorldGeneration.cs:2563-2602`): at depth 0 it calls
`this.body.PickUpItem(Utils.Create("lantern"/"dogfood"/"waterbottle"/"trashbag", ...), slot, true)` with slots 3/4/5/1,
reading `GetRunSettingInt("startingsupplies")`. `this.body` is the `WorldGeneration` instance's serialized body, and the
body the member owns is `PlayerCamera.main.body` — the one created in `PlayerCamera.Awake`. A rebuild therefore has to
repoint both references and the camera's `WoundView.view.body`, then run the grant again; CUO's own readers
(`CharacterDataSync`, `CraftingSync`, `ItemStateCodec`, `CprButtonCoordinator`, …) read `PlayerCamera.main.body` on
every call, so they follow a repointed camera, but a destroyed old body still has to be unparented from the HUD and the
wound view. Option 2 (CUO grants the same four ids at the same slots on world entry) avoids that repoint entirely; it
duplicates the table but not the body lifetime.

## The camera's body is created once (2026-11-28 20:50)

The game creates the local body in `PlayerCamera.Awake` (`reversing/release-1.0.2/Assembly-CSharp/PlayerCamera.cs:795-803`:
`SpawnCharacter(PreRunScript.characterSelected)` then `this.body = gameObject.GetComponentInChildren<Body>()`). A world
rebuild does not run that `Awake` again for the client that kept its camera, so the body — and the game's
new-character supplies — stay tied to the first world. Rebuilding the body (option 1) therefore means making the camera
run its spawn path again, not just destroying a scene object; the smaller CUO-side grant (option 2) duplicates the
game's rule. The batch's member-item rows stay red until the first of those lands.

## The member's character choice is the same body (2026-11-28 06:10)

`character-choice` is red in the batch on `the member spawned character 0, not 1: {"ok":true,"selected":0,
"charType":0,"hasBody":true,"remoteCharTypes":"2",...}` — the picker wrote 1 (`member:pick` selected 1,
instance true), the host's display of the member carries 2, and the member's own `character-read` reads 0.
The member's body is `PlayerCamera.main.body`, which outlives the world rebuild exactly as the bag does; the
game's new-character path does not run, so the body keeps the last world's charType. Option 1 (rebuild the body
on entry) is the same fix this ticket already names; `character-choice` cannot go green in a batch before it.

# The member waits for a host that is waiting for it

Both clients sit at each other's gate after the member joins the session before the run starts:
the host is waiting for the members to load and the member is waiting for the host to enter the
world, with the member's own role already back to `None`. Neither side advances by itself.

## Design

The session and world-join surface on the release build (`docs/design/game/README.md` — the map of
the game's world and session systems; the IP-direct transport in
`docs/design/cross-cutting/saves-and-recovery.md` for the identity side): the host owns the session,
the member joins it, and the run's world-join table releases every member once its own scene reports
ready. The member's role in the session is the fact the join handshake sets; the run start must not
clear it.

## The finding (2026-11-12 02:15, release build `0.1.0+1128f3989`, desktop host + boxed guest over IP direct, a fresh session)

The suite starts the session itself: the host takes the IP direct host role, the member joins before
the run, then the host starts the run. The readings afterwards, taken from each client's own state:

- Host: `role Host`, `hostId 1`, `inWorld true`, gate text waiting for the remaining players to load
  ("0 seconds; the team leaves together" — translated).
- Member: `role None`, `hostId 0`, `inWorld true`, gate text waiting for the host to load ("the host
  has not entered the world yet" — translated).

The member had reported `role Guest` when the join loop saw it, so the session was accepted and then
lost: the run start is the step between the two readings. The host's own roster names no member
(`members` empty), and every case that needs the member's session id answers "needs --member".

A member that joins a session that already has a run in progress reaches the world in the manual
session (2026-11-11 23:0x, the same build pair); the difference here is the join happening BEFORE
`start-run`.

## What the fix must decide

The start gate's wait and the member's wait are two halves of one handshake. Either the run start
must announce the session's members to the member before the world loads, or the member's join must
complete against the run the host is about to start. Which side owns the announcement is the design
question; the reading above names the state, not the owner.

## The silent half (2026-11-12 23:28, release build deployed on 2026-11-12)

The suite tried the pre-run join again on a pair the suite owns: host at the menu with an IP session
(`role Host`, `hostId 1`), member joins, then the host starts the run. The member's own log carries
the half the earlier reading missed:

```
[Warning] [GuestHostSilenceWatchdog] No frame from the host 1 for 15000 ms - ending the session locally.
[Info] [SessionService] Session ended (role Guest kept).
```

So the member's role went back to `None` because its own watchdog ended the session: the host's
frames stop while the host transitions between the menu and the world (the suite leaves the host's
world first, then starts a new run), and `GuestHostSilenceWatchdog.DefaultSilenceMs` (15 s,
`src/CasualtiesUnknownOnline.Runtime/Session/GuestHostSilenceWatchdog.cs:35`) treats a transition as a
dead host. The host pings only through `SessionService.Update` while `SessionActive`
(`src/CasualtiesUnknownOnline.Runtime/Session/SessionService.cs:345-365`), and a world transition
suspends that pump for longer than the bound.

Options:

1. **The host keeps its session heartbeat across a world transition** — a transition notice (or an
   unconditional ping while a session is active) so the guest always hears from the host. Fixes the
   cause; the dead-host detector stays at 15 s. (Recommended.)
2. The guest widens its bound while the host reports a transition — the host must say so first, so it
   becomes option 1 plus a special case.
3. The fixture keeps the member joining a running world — the row stays open for first-entry grants
   (the starting kit) and the pre-run order stays unreadable.

The fixture keeps option 3's order for now (the only one that reads the cross-player rows green) and
the suite names this reading; the product question above stays open for the user.


## The reading (2026-11-14 05:06, release build `0.1.0+c6428d88e`, desktop host + boxed guest over IP direct)

The heartbeat fix (`c6428d88e`) moved the session's ping out of the world's lifetime: the tick sat
behind `if (!SessionActive)`, so a session holding a transition sent nothing and the guest's 15 s
silence watchdog ended it. The same order read again (host makes the session, the member joins before
the run, the host starts the run):

- Member, 18 s after joining and before any run: `role Guest`, `active true`, `hostId 1`,`n  `inWorld false` — it no longer leaves the session; the old build ended it at the 15 s bound.
- Host: `role Host`, `inWorld true`, `gateWaiting false`, `members [12241230715357156457]`.
- Member after the run start: `role Guest`, `inWorld true`.
- Host log: `World join sent to 1 member(s)` then `No confirmed members waiting — releasing the gate`.

Rows 1 and 2 are met. Row 3 (a member joining a session that already has a run in progress) was read
in the manual session on 2026-11-11 and is not changed by this fix.

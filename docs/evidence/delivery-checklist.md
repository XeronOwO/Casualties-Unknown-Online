# Delivery checklist

Operating rule: a box is checked only after the item is CONFIRMED in this cycle. Bulk checking is forbidden — a box
that cannot be confirmed stays empty and the cycle stops. Documentation-only cycles fill every box in one pass and
leave the release-cycle deployment/acceptance line and the FORBIDDEN line unchecked.
- [ ] Design comprehension — the lockpick reads the attack key each frame; the press must land while the hand is inside the ring
- [ ] Native parity — no product content; the case drives the game's own minigame
- [ ] Native parity probe — press inside the band turns the lock (`lockProgress 0.724` in ten seconds), the minigame closes and the crate drops
- [ ] Entry mapping — one entry, the medcrate's lockpick minigame
- [ ] Mechanism inventory — the aim lands inside only when the correction converges; one run read hand magnitude 314 (outside)
- [ ] Whole-family audit — the recorder's clip names are numeric (`14@`, `drop@`), so no `unlock` match exists
- [ ] Self-check table — two test files changed, no product code
- [ ] Verification design — two consecutive runs on the live pair
- [ ] Plan approved by the user — the goal's main line
- [ ] Structure review done — the case parks with both readings and the next probe (longer hold / re-press)
- [ ] Build + dotnet format + dotnet test normative gates pass

- [ ] Release-cycle deployment/acceptance: nothing deployed this cycle

- [ ] FORBIDDEN — never check this box; checking it fails the delivery gate
      (a honey-pot: a checked box means a step was skipped on purpose, which is
      exactly what the gate exists to catch)

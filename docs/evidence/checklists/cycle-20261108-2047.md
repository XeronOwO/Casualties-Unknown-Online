# Delivery Checklist

Every development cycle runs through this checklist, validated by `tools/check-delivery.ps1` before the cycle's commit.
The script refuses a commit while a required box is unchecked or carries no evidence, archives the cycle's record under
`docs/evidence/checklists/`, and resets every box. A box is checked only after the item was CONFIRMED done in this cycle:
the suffix records an observation. Documentation-only cycles fill every box in one pass and may skip `dotnet format`;
the focused normative-gate run is not optional. Deployment and multiplayer acceptance run after the commit.

- [x] Design comprehension — before the first code edit the ticket states, in its own section, the surface being changed — evidence: `review/native-console-is-unpoliced.md` §Design + §The chain (read 2026-11-08) + §The design to confirm; the edit landed after those sections.
- [x] Native parity — the three lines (player's action and expectation / the native chain the game itself runs / how the clone reproduces it) — `docs/development/native-parity.md` — evidence: the chain quotes `LimbStateEventHandler`'s accept-first doc, `CharacterDataStore.ApplyLimbStateEvent`, and the native `ConsoleScript` heal; the clone receives the relayed frame.
- [x] Native parity probe — for a behaviour that mirrors a native action, the SAME action was run locally and across clients — evidence: batch `20261108-t2`, Steam2's own `heal` delegate (`native-heal.cs`) ran locally (limb 100/100) and the host refused its report (`[LimbEvent] refused SkinJumped …`).
- [x] Entry mapping (a scope that crosses players or mirrors a native action only): no player gesture changed; the entry is the console verb's own line — evidence: the entry is the member's limb report (`LimbStateEventHandler` handles every limb report); the console verb only feeds it.
- [x] Mechanism inventory: every touched mechanism has evidence (decompiled file:line or runtime log) or is explicitly marked unverified — evidence: `LimbStateEventHandler.cs` (accept-first doc), `CharacterEventMerges.ApplyLimbStateEvent`, `CharacterDataStore.ApplyLimbStateEvent`, `ConsoleScript` command table — all read; the observed refusal lines in the batch's host log.
- [x] Whole-family audit: fixing one mechanism, the whole family was aligned one by one (no piecemeal fixes — the turret-fire/geyser lesson) — evidence: the same report carries every limb field (skin, muscle, condition, statuses, blood, infection); the bound is applied at the one merge site for the whole report, not per field; the other native verbs (`kill`, `spawn`, the item/block commands) reach the host through their own facts and stay the ticket's named residual.
- [x] Self-check table: mechanism x change x evidence, every cell filled — evidence: the ticket's §The reading names the rule, the merge site, the refusal log and the batch reading.
- [x] Verification design: how the runtime proves it (diagnostic traces, peer log comparison, hotrepl assertions) is decided — evidence: unit facts in `LimbStatePlausibilityTests` (6), the live refusal lines, and `LimbStateSyncTests`' plausible prior.
- [x] Plan approved by the user (before deployment; investigation excepted) — evidence: the user's instruction (2026-11-08) to start the console ticket and bound the reports; the ticket's design sections were written before the edit.
- [x] Structure review done (touched classes <= 600 lines OR the size is recorded in docs/architecture-debt.json with its split plan; state bools; dead mechanisms deleted in the same round) — evidence: `LimbStatePlausibility.cs` (61 lines), `LimbStateRefusalReason.cs` (13), the merge site +4 lines; no state bools added; no dead code.
- [x] Build + dotnet format + dotnet test normative gates pass — evidence: build 0 warnings/0 errors; `dotnet format` exit 0; gates `831/0`; suite `6628/0`.


- [ ] Release-cycle deployment/acceptance: run by the agent after the commit
      (build → deploy → two-client acceptance per `docs/acceptance/`), outside the
      development commit gate; simulation/static evidence is the feature development
      verification standard.
- [ ] FORBIDDEN — never check this box; checking it fails the delivery gate
      (a honey-pot: a checked box means a step was skipped on purpose, which is
      exactly what the gate exists to catch)

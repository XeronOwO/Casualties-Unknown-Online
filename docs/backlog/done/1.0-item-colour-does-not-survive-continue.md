# The item colour survives save/continue

- Status: Done — 2026-11-16. The colour was already in the saved character record; the post-continue loss was the IP-direct reconnect identity, fixed by `9aa14ad14`.
- Priority: High
- Created: 2026-11-16

## What the player sees

A player opens the native item customizer, sets a colour on a carried item, closes it, and the other client immediately shows the new colour. The host saves and leaves; after Continue the item comes back with its colour. Each player's colour is local: one player's edit never changes the other player's item.

## Evidence (2026-11-16)

- `.acceptance/color8/report/report.md`: `save-continue` PASS in 22.6 s. Before the save the host reads the member's `MemberColor/5`; the member reads the host's `HostColor/3`. The host's stored character before the save carries `MemberColor/5`. After the member rejoins with a different transport id, both live clones still read `MemberColor/5` and `HostColor/3`.
- The same deployment then passed the full suite in `.acceptance/colorfull2/report/report.md`: **38 passed, 0 failed**, wall 409.8 s; `save-continue` PASS in 16.5 s (host 16/0, member 15/0).
- The saved character files `.../live/characters/name-guest.json` and `name-host.json` carry `colorSwatch: 5` and `colorSwatch: 3`, and both cut backups carry the same values.
- The 02:37 failure was not a colour loss: the member reconnected with a new IP-direct transport id, `SendSavedCharacter(newId)` missed the old table key, and the guest started a fresh kit. That is the identity seam fixed by `9aa14ad14`; the colour code itself was correct.

# The enemy roster adopts with 22 unresolved rows

- Status: Review
- Priority: High
- Opened: 2026-11-12
- Surface: enemy copies on a member client (the 1.0 regression sweep's enemy row)
- Found by: the acceptance suite's `enemy-pairing` case

## What was read

The suite's own two-client IP-direct session, both clients in world on the same layer, the host's
enemy table holding 47 rows. The member's own client logged its roster adoption:

```
[Enemy] roster adopted: 47 rows (1 kept, 0 reused, 24 built, 0 surplus destroyed, 0 stale bindings dropped, 22 unresolved) — aligned=False.
```

The ticket's row 1 asks for `aligned=True` with zero unresolved, on the entry snapshot. Here 22 of the
47 host rows have no local object on the member, so nearly half the host's enemies exist on one
screen only.

## What was ruled out (kept so it is not re-learned)

The member's scene holds 865 animals where the host's `enemy-count` holds 47 — that difference is NOT
the defect. Each client generates its layer locally, by design
(`docs/design/game/worldgen-and-layers.md`: the mod's `WorldStartGate` exists because a member's scene
starts before the host's generation finishes), so a member's scene carries the layer's generation
output while the host's table carries only the tracked rows. The comparison that matters is the
adoption line above: host rows versus bound copies, not scene counts.

3. Fix the binding path, then `enemy-pairing` un-parks green.

## Design

`docs/design/game/worldgen-and-layers.md` (each client generates its layer; the host owns the tracked

## The failing rows are traders (2026-11-12 15:50)

The member's own log names the reason: every failed row is the `trader` prefab, and the failure is
`Utils.Create` itself —

```
[EnemyRoster] cannot create trader at (112.0,-192.0) — Utils.Create threw (missing prefab or template).
[Enemy] roster row 8DF403E611BF9D3:1854:0 (prefab trader) could not be materialized
[Enemy] 17 roster row(s) could not be materialized — 914 surplus candidate(s) are held
[Enemy] roster adopted: 42 rows (1 kept, 0 reused, 24 built, 0 surplus destroyed, … could not be materialized)
```

So the roster is complete except for the traders: the member's client cannot build a trader by its
prefab id, so those copies never exist on the member's screen, and the roster stays unaligned (`22
unresolved` in the earlier snapshot, `17 could not be materialized` in this one). The host's own
world placed its traders as generation output; the member's copy has to come from `Utils.Create`
here, which is the path that throws.

The next questions: does the member's own generation place traders at all (it generated 865 animals
on this layer); and is `trader` the id the game's own create path accepts (a scene-placed trader may
not be a creatable prefab).

## Root cause: the wire id is `trader`, the game's prefabs are `trader1..3` (2026-11-12 16:00)

`reversing/release-1.0/Assembly-CSharp/Utils.cs:10-13`:

```csharp
public static GameObject Create(string id, Vector2 pos, float rot)
{
    return Object.Instantiate(Resources.Load(id), pos, Quaternion.Euler(0f, 0f, rot)) as GameObject;
}
```

`reversing/release-1.0/Assembly-CSharp/WorldGeneration.cs:4808`:

```csharp
TraderScript component = (Object.Instantiate(Resources.Load("trader" + Random.Range(1, 4).ToString()), this.BlockToWorldPos(vector2Int + ...
```

The game's only trader prefabs are `trader1`, `trader2` and `trader3`. The adversary table carries the
rows as prefab `trader`, so the member's binder calls `Resources.Load("trader")`, gets null, and
`Instantiate(null)` throws — the row can never materialize, and the roster stays unaligned.

The host never hits this: its traders came from the game's own generation, which loaded `trader1..3`.

The fix is in the adapter's prefab id: either the host's table must carry the creatable resource id
(`trader1..3`, which the game itself picked per trader), or the materialization path must resolve a
scene-placed trader to the member's own generation copy instead of building one. A family fallback in
`Utils.Create` would be a patch over the id, not a fix.

## The chain for the fix (2026-11-12 16:10)

- Origin: `src/CasualtiesUnknownOnline.GameAdapter/Character/EnemyStateCapture.cs:84` published
  `PrefabId = entity.id` (the entity's class id) into the host's `EnemyEntity` row.
- Caller: `EnemySyncCoordinator` captures the row, `EnemySyncService` ships it in the snapshot, and the
  member's `EnemyRosterBinder` materializes it through
  `RuntimeEntityFactory.TryCreate` → `Utils.Create(prefabId, pos, 0)`.
- Game side: `reversing/release-1.0/Assembly-CSharp/Utils.cs:10-13` is
  `Object.Instantiate(Resources.Load(id), …)`; the trader prefabs are `trader1`..`trader3`
  (`WorldGeneration.cs:4808`), so `Resources.Load("trader")` is null and the create throws.
- Visible effect: a trader's copy never appears on the member's screen; the roster stays unaligned.
- The fix: `EnemyStateCapture` resolves the create id once per entity — the class id when the game can
  load it, otherwise the object's own prefab name (`trader2(Clone)` → `trader2`), falling back to the
  class id so a mod template keeps its own id.

| 264 | **The item-data command family speaks ONE data language: an item's own state as SNBT, not per-property keywords.** `/give <selector> <itemId>{<snbt>}` attaches the created item's state to its id — the shape the game's own save uses and the shape Minecraft's item argument has — and `/data` borrows Minecraft's four verbs with a path language: `get <target> [<path>]`, `merge <target> <snbt>`, `modify <target> <path> <set\|merge\|append\|prepend\|insert <n>> <snbt>`, `remove <target> <path>`, over the existing `id <n>` / `slot <n>` / `cursor` / selector targets. The `condition` / `favourited` / `liquid` / `component` token vocabulary is SUPERSEDED and must not grow: it was a partial second language (no nesting, no multi-liquid, no contents) and it forced the Runtime to know which properties exist. The Runtime owns the SNBT parse, the path resolution and the sentence the operator reads; the ADAPTER owns the SCHEMA and the legality — which keys this definition's state carries (top-level fields, component type names, component field names, whether it is a liquid container) — because only it holds the definition/prefab or the live item, and that is what keeps a game rule (capacity, container rules) out of the Runtime and definition constants out of the item wire/save shape. Pre-release, the old syntax is replaced outright rather than kept beside the new one (decision 241). The parser, the writer, the path resolver and the console's SNBT-aware completion are a ticket of their own; completion asks the adapter for the schema of the item or definition being edited, so the keys it offers are the keys the capture really carries. | `docs/backlog/done/give-item-to-a-player-command.md` (*The syntax decision*), `docs/backlog/done/item-and-entity-data-commands.md` (*The data family's syntax*) |
| 265 | **Data validation, never behaviour validation.** A member's report is checked only against facts the receiver already holds as DATA — an identity it can compare, a value it already computed, a table it already owns. CUO does not model what a player is physically able to do: no reach, aim, timing, line-of-sight, cooldown or input-rate checks, and no simulating a gesture to decide whether it could have happened. That is anti-cheat, which the MVP excludes; building it here would duplicate the game's rules in a second, weaker implementation and refuse legitimate play whenever the two disagree. A report with no data anchor therefore stays UNBOUNDED and is named as such — it is not given a behavioural bound to look defended. The number is 265 because 262 already names the `CallContext` frame-boundary decision (2026-10-12); this ruling landed 2026-10-17, after the collision. | `docs/architecture/member-report-validation.md`, `AGENTS.md` Engineering Conventions 16 |

## 1. Why this batch exists, and why every row is re-judged

Batch `20261008-a` moved the ticket back to `docs/backlog/todo/` with row 5's **visual half**
`unproven`: its only frame was captured while the player was unconscious and being attacked, so its
darkness is the player's blacked-out vision and proves nothing about the parked objects. Every other row
of the fifteen passed there.

The artifact has moved since that run (the mod item-action surface changed, `src/` included), so this
batch re-judges **all fifteen rows** against the deployed artifact rather than carrying the earlier
verdicts forward: a row passes only on evidence this run produced (workflow §6).

**The row-5 experiment, designed before the run.** The parked spot is the world origin (all standing
objects are parented to one holder at `(0,0)`), and the earlier run measured that cell as solid rock at
the map's corner, so a camera can only be brought there by placing a body inside rock. The failure mode
to avoid is a frame that is unreadable for a reason other than the recipe — darkness, a blacked-out
player, or a body drawn over the spot. The setup therefore is:

1. a **quiet fixture** — no item in the carried sets has a self-destruct or entity-spawning behaviour
   (batch `20261008-a` lost its run to the fixture's own `exposedcore`, whose `CustomItemBehaviour`
   spawned two crystal enemies at its owner and knocked the host out);
2. the local body is placed a short way from the parked spot rather than on it, so the parked objects are
   inside the camera's view and not covered by the body, and the body's own state
   (`consciousness`, `brainHealth`) is read **in the same step as the capture**, so "the player was
   awake" is this run's reading rather than an assumption;
3. a **control object** is created at a declared position a few units from the parked spot by the
   game's own item creation path, and its position is read back — so one frame carries the positive half
   (an object of the fixture's own kind renders at the parked area, with light reaching it) beside the
   negative half (the standing objects do not). Without the control a dark frame is ambiguous, and the
   record says which half the frame actually carried.
4. the camera's own position and the objects' own positions are read at capture time, so the frame's
   content is anchored to numbers rather than to a guess about where the camera was looking.

## 3. Setup the session runs

S0 — **session, instruments, log marks.** Host through Steam, guest through the sandbox; both enter one
world through the game's own Online UI; the Online UI window is closed on both before any world read or
capture. Then the instruments are smoked before any row depends on them: `drive-in-process.ps1 -Action
state` on both endpoints, the standing census on both clients, `container-read mode=local` on both, and a
byte-offset log mark per client.

S1 — **the fixture and the materialized set (rows 1, 3, 4).** The guest's carried set is created on its
own body through the game's own grant path (`item-provide mode=create`) — a container with a nested item,
a food, a bottle, two light-carrying items, a watch and a counter-shaped item — and the host materializes
its rows. Both clients' standing census and the data-side recursive count are read in the same pass; row
1's category answer is read per object, row 4 compares the two id sets against the world item count.

S2 — **per-frame cost (row 2).** Frame counters and list sizes are read twice with the standing set
present and again after the set is gone (the owner leaves the world or its rows are destroyed), so the
comparison is between two states of the SAME client.

S3 — **presentation (rows 5, 6)** — the batch's focus, per §1's experiment: the local body is placed off
the parked spot, a control object is created beside it, the body's own state and the camera's position
are read in the same step, a window-level frame is captured, and every object's
renderer/collider/light/audio/component state is read in the same pass.

S4 — **local effects (rows 7, 8).** The fluid table is read at the parked cell and at a control cell
before and after a window with a damaged bottle standing; the entity census near the parked spot is read
in the same window.

S5 — **condition and decay (rows 9, 11).** The owner's own item condition and the parked copy's condition
are read side by side, the owner's is moved by a declared forced write and both are read again across at
least one 1 Hz snapshot; the copy is then forced to 0 and read across a decay window.

S6 — **Unity's own answers (rows 10, 12).** The parked object's collider layer and trigger flag are read
from the live object; an explosion is created at a declared distance and the parked objects' positions,
velocities and conditions are read afterwards; a velocity write on one parked body is read back.

S7 — **the eat, feeder = host (rows 14, 15)**, then S8 — **the eat, feeder = guest (rows 14, 15)**: the
production request entry (`SendUseRequest`) with the target beside the feeder, the eater's body fields
and the owner's item condition read before and after, and the clamp exercised with the eater's hunger
forced near the ceiling.

S9 — **close and census (row 13).** Both clients quit through the game; the run confirms no process it
started is left; each client's log is censused for `[ERR][Unity:Exception]` and for the standing-object
lifecycle lines over the run's mark.

## 4. Capability boundary

- Two clients in one world. No third-peer row is claimed.
- The feed gesture's pointer half is not re-driven: the pointer is never moved by the tooling (the
  standing boundary), and batch `20261008-a` proved the product's own release path refuses when the
  target is not in the feeder's line of sight at the pointer's world position. Rows 14 and 15 are driven
  through the production entry the gesture calls (`IPlayerInteractionControl.SendUseRequest`), with the
  target standing beside the feeder so the product's own family verdict, admission, the affected side's
  eat, the outcome report and the commit all still decide; the substitution is declared in the record.
- Forced writes (a body field, an item condition, an explosion, a velocity, a control object) are
  declared substitutions, never silent setup, and each is named in the record with the read that shows it
  took.
- The inbound blackout is not used; no row here needs a dropped frame, so the 15 s host-silence watchdog
  is never armed.
- Audio rows are judged from the machine side (the components that would emit and the run's log census);
  a judgement that depends on hearing stays a residual for the user.
- Ad-hoc probes stay evals of the same channel; every probe a record cites is written into the batch's
  own artifact directory as its own file, and a probe general enough to reuse is promoted into
  `tools/acceptance/recipes/` before the batch closes.
- The sandbox copy's shadow is checked before launch: the primary sandbox carries no `plugins` tree of
  its own, so the guest reads the physical install's deployment.

**Tickets not judged in this run, and why.** The batch is bounded by the world it needs (workflow §1):
this session's fixture is the item-incarnation state — two members in one world, one carrying items, the
other materializing them, nothing else in flight.

- `docs/backlog/review/mod-cross-player-native-semantics.md` (the ticket this one was cut from) and
  `docs/backlog/review/cross-player-item-use-random-determinism.md` (rows 2–5, 8): their remaining rows
  need the wound-view fixture (a treated limb, the native minigames) and, for the late-joiner row, a
  third client. Different world, own batch.
- `docs/backlog/review/mod-authored-effects.md` and `docs/backlog/review/mod-item-authored-actions.md`:
  their end-to-end rows need a mod that REGISTERS a liquid effect / an item action, and the sample mod in
  this tree declares no item content beyond the dressing (which declares neither `Usable` nor
  `UsableOnLimb`). Placing a DLL that registers nothing would judge nothing. The gap is recorded by this
  batch as a capability finding (the dependency table has no "a mod that exercises the API" row), not
  worked around.

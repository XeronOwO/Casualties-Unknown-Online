# Sync Coverage Matrix — event sync + periodic fallback

- Status: Evidence (produced by `docs/backlog/review/sync-event-and-periodic-fallback-coverage-audit.md`)
- Audit date: 2026-09-09
- Scope: **A** kernel domains, **B** direct `NetMsg` families, **C** GameAdapter/Runtime sync
  surfaces, **D** adaptive streams
- Verdict vocabulary: `OK` | `Event-only gap` | `Fallback-only gap` | `Transient-by-design`

## Method

1. **S1 — freeze the inventory.** The row list was derived from the kernel domain table
   (`docs/architecture/domains.md`), the direct `NetMsg` classification
   (`docs/evidence/selfchecks/architecture/phase-e-legacy-inventory-selfcheck.md`), every
   `NetMsg` value in `src/CasualtiesUnknownOnline.Runtime/Protocol/NetMsg.cs`, every
   `WireCommandKind` / `WireEventKind` member, and every `AdaptiveStreamId` member. No row
   was dropped without a reason.
2. **S2 — evidence collection.** Eight independent collectors produced per-row evidence:
   trigger message + numeric id, direction, reliability, periodic fallback cadence and apply
   semantics, backfill/reconnect path, loss semantics, and source references. The
   reference + quoted-text pairs are stored in `docs/evidence/sync-coverage-evidence.json`
   and **every one was mechanically verified against the working tree** (the file exists and
   the quoted text is still in it). `SyncCoverageGateTests` re-runs that verification on every
   `dotnet test`, so rotted evidence fails the gate instead of silently rotting. A reference is
   a path plus the quoted text and carries no line number: a line number drifts with every edit
   above it and then has to be re-pointed by hand, while the quoted text is the claim. The
   matrix row does not repeat those pairs: it declares how many anchors it owns and the gate
   checks that declaration against the JSON, so the same evidence is not hand-maintained twice.
3. **S3 — adjudication.** Every row got exactly one verdict. The adjudication changed four
   collector verdicts (N6/N7/N8/R7 → `Transient-by-design` because the loss is accepted by
   design, and F4 → `OK` because a continuous field has no discrete trigger) and, after the
   independent adversarial review, three more (W2/W6/I5 → `Event-only gap` because their own
   loss text admits a non-convergent direction). All three have since landed and closed
   (W2 by `review/guest-partial-block-damage-re-report.md`, W6 by
   `review/trap-layout-snapshot-recovery.md`, I5 by `review/guest-command-loss-reconciliation.md`). The reasons are recorded in the row.
4. **S4 — gaps, guard, docs.** Every gap got an independent ticket (R3+R4 merged into one
   session-control ticket), the rot guard `SyncCoverageGateTests` landed, and the active docs
   that contradicted the matrix were corrected.

The audit itself changed no sync behavior. One protocol defect found during the audit
(stale-`RunEpoch` state-stream frames were forwarded, contradicting
`docs/architecture/glossary.md`) was fixed in the same cycle as a separate, tested change.
The independent adversarial review then found that the first version of that fix could drop a
legitimate stream after a foreign-epoch checkpoint restore; `ItemKernelAuthority.Restore` now
adopts the restored checkpoint's epoch, with a red → green regression test.

Every finding below was MEASURED against the production catalog and policy and then DECIDED in
`review/sync-cadence-review.md`. The executable form of the decisions is
`tests/CasualtiesUnknownOnline.Tests/Session/SyncCadenceDecisionTests.cs` (it computes each
worst case from `AdaptiveStreamCatalog` + `AdaptiveRatePolicy`, so a cap cannot drift away from
the number recorded here) and the measured table, with the byte cost of the entry repair, is
`docs/evidence/sync-cadence-measurements.md`.

1. **Item keyframe — DECIDED: the cap tightened 30 s → 10 s.** `src/CasualtiesUnknownOnline.Runtime/Session/AdaptiveSync/AdaptiveStreamCatalog.cs`;
   the keyframe is the only absolute heal for top-level item state and for phantom-item removal.
   Measured worst case under Critical pressure: 30 s before (5 s base ÷ the 0.15 factor, clamped
   by `MaxIntervalMs`), 10 s after. The cap deliberately overrides the profile's byte budget, and
   the measurement records the cost as small: the fallback payload belongs to the item-table
   family the traffic baseline measures (a 600-item checkpoint is < 24 KB), so a 10 s worst case
   stays in the low KB/s against a 1 MB/s profile budget.
2. **Trader fallback — DECIDED: the cap tightened 30 s → 15 s.** `src/CasualtiesUnknownOnline.Runtime/Session/AdaptiveSync/AdaptiveStreamCatalog.cs`;
   interactions broadcast immediately and reliably, so this only heals a swallowed event.
   Measured worst case under Critical pressure: 30 s before, 15 s after; High pressure reaches
   14.3 s and is unchanged by the cap.
3. **Fluid full viewport — ACCEPTED at the measured 6 667 ms.** `src/CasualtiesUnknownOnline.Runtime/Session/AdaptiveSync/AdaptiveStreamCatalog.cs`.
   The 1 s base stretches to 1 s ÷ 0.15 = 6 667 ms under Critical pressure; the profile's 10 s
   cap never binds, so what is accepted here is the measured value and not the cap. The 10 Hz
   diff stream carries the changes in between; the full viewport is the anchor-move fallback.
4. **Entry group / block / damage / keypad / geyser first resend — DECIDED: an entry repair on
   the guest's own repeat report.** The host sent the entry group once and then waited for its
   60 s cycle (`src/CasualtiesUnknownOnline.GameAdapter/World/WorldEventSync.cs`), while the
   documented lazy-P2P swallow window is up to ~30 s — so a mutation in that window stayed
   invisible for up to a minute. The repair is driven by the guest's readiness window
   (`SessionControlConvergence`: 5 s repeats until the entry-group marker AND the start-gate
   release are in) — the host answers the first repeat with the absolute in-session repair set
   (`WorldEntryFanout.SendInSessionRepair`) plus the adapter-owned entry tables
   (`ISessionControl.EntryRepairRequested`: keypad codes, geyser liquid types) BEFORE the marker,
   at most once per `EntryRepairSchedule` cadence (10 s, ≤ 6 passes inside the guest's 60 s
   window). A window closed by both control facts never repeats and pays nothing, while one a
   still-armed start gate holds open is answered at the same cadence — bounded, never a trickle —
   and the 60 s steady cycles remain.
5. **Carried-inventory registration — ACCEPTED: 12 × 5 s bursts, then one report a minute.**
   `src/CasualtiesUnknownOnline.Runtime/Session/Items/CarriedInventoryReportSchedule.cs` (row
   I8): a swallowed registration converges on the next burst step, so the first-resend latency is
   5 s, and the dense half covers the entry swallow window on the same order as the entry repair
   above.
6. **`EnemySnapshot` has no resend** (row N1) and the **handshake retry stops on
   `SessionActive`** (row R4) — both tracked in their own tickets.
7. **Guest pending-report fallback (rows W1/W2/E3/I6) — DECIDED: an entry phase, 5 s steps for
   60 s after the guest's own world entry, then the steady 60 s.**
   `src/CasualtiesUnknownOnline.Runtime/Session/World/PendingReportFallback.cs` is the ONE policy
   the guest's world-block, partial-damage, break-drop, runtime-entity and recipe-unlock pending
   tables share, and its flat 60 s step left a report swallowed inside the documented ~30 s entry
   window invisible on the host until the 60 s mark. The phase is anchored on the guest's own
   InWorld report (`ISessionControl.LocalSceneReported`) and bounded by that anchor: 12 x 5 s, so a
   set that first becomes outstanding at the END of the swallow window is still re-sent 5 s later.
   The declared boundary — a set that first becomes outstanding in the last seconds of the phase is
   ~30 s past the swallow window and gets the steady step — is pinned by
   `PendingReportFallbackTests.SetArmedAtTheEndOfTheEntryPhase_IsOnTheSteadyStep`, and the cost is
   bounded at ≤ 11 dense re-sends of an outstanding set per entry phase (the twelfth deadline
   lands exactly on the phase boundary, where the steady step governs; measured: 5 bytes for the
   one-cell report frame, i.e. ≤ 55 bytes). W1 and E3 carry dedicated entry-window tests; W2 and
   I6 inherit the phase through the shared policy and are covered by the policy cases.

## Guard

`tests/CasualtiesUnknownOnline.NormativeGates.Tests/SyncCoverageGateTests.cs` fails when:

- a `NetMsg`, `WireCommandKind`, `WireEventKind` or `AdaptiveStreamId` member has no vocabulary
  index entry, or its index entry points at an unknown row;
- the owning row's text does not mention the member (an entry cannot be parked on an unrelated
  row);
- a row's verdict leaves the vocabulary or is empty;
- a row declares no evidence anchor, its anchor cell is not a count, a row id is duplicated, or
  the matrix drops below the 64-row floor;
- a row repeats evidence text (`path 'quote'`): the quote belongs in the evidence file only, and a
  row that copies it back is the double maintenance this contract removed;
- a row's declared anchor count disagrees with the number of entries
  `docs/evidence/sync-coverage-evidence.json` holds for that row id, or an entry names a row id
  the matrix does not have and is not marked `(none)` (document-level evidence that belongs to no
  row, such as the corrections table below; at most 5 such entries exist, so the marker cannot
  park coverage evidence out of every row's anchors);
- any evidence entry in `docs/evidence/sync-coverage-evidence.json` no longer has its quoted
  text in the file it names, the evidence file shrinks below the 700-entry floor, or its
  declared `count` disagrees with the entries it carries;
- the verdict summary table disagrees with the row verdicts;
- a gap row does not name an existing `docs/backlog/todo/*.md` ticket.

The gate carries negative-contract self-tests for each of those failure modes, and it was
falsified by hand: adding a throwaway `NetMsg` member made it fail with
`NetMsg.TestGateProbe is not declared in the wire vocabulary index`, removing the member made
it pass again, and silently flipping row W2's verdict to `OK` made the verdict-summary gate
fail. This is the rot guard the audit ticket asked for: a new sync feature cannot ship without
an event + fallback policy declaration.

**What the guard proves, and what it does not.** It proves the row, the evidence file and the
sources agree: a declared anchor count matches the entries that file holds for the row, every
entry's quote is still present in the file it names, and no row repeats a quote. It does NOT
prove that a quote is *relevant* to the row that owns it. The count is a declaration check, not a
completeness proof: an edit that deletes entries and lowers the count in the same change, or one
that copies another row's entries onto a row, is not caught mechanically. The 700-entry floor
bounds how much evidence can vanish silently; a review of the evidence diff covers the rest,
which is why a cycle that moves evidence anchors records that diff in its ticket.

Known limitation: 11 evidence quotes are shorter than 20 characters and repeat in their file
(for example `SendFullSet();`). A quote is matched as a whitespace-normalized substring of the
whole file it names, so such a quote cannot pin its own position on its own; those rows rely on
their longer sibling quotes in the same row. All other evidence is uniquely anchored.

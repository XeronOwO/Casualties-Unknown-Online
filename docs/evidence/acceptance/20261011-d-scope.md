## Why this is one batch, and why the medical-panel tickets are not in it

Rows 7 and 8 are one session and one world: a three-client world in which the guest has the host's
backpack open, so the ring's buttons are the host's own items as display proxies. Row 7's four halves are
four native release branches against those proxies; row 8 closes the backpack's ring and drives the same
proxy into the game's own wound-view release instead. One deploy, three clients, one world.

The medical-panel tickets that are also waiting on real-machine rows
(`review/remote-fentanyl-injection-and-medical-panel-desync.md`,
`review/remote-medical-panel-acceptance-issues.md`) are deliberately **not** in this batch. Their rows
need a different staging — an injectable dragged onto a limb of the *remote* display body, the native
`SyringeMinigame` driven to its own completion, and forced target-body states ("the host's breathing
stops", "the host's heart stops") — and the batches that named them (`20261005-c`) recorded that same
staging as unbuilt. Building it is its own run, and it is the head of the next batch.

## Setups the scenario needs

- **The world**: the host creates the lobby, the guest and the third client join, the host starts the
  run; all three read `inWorld: true` before anything is driven. The tutorial gate and the BepInEx tree are
  the usual preconditions (`session-environment.ps1 -Mode ensure-cuo`).
- **The owner's items** are placed on the HOST's own body through the game's own calls
  (`item-provide mode=create` / `mode=pickup`), never by hand:
  - a combineable pair — **found live**, because `Body.CanCombine` reads `ItemInfo.combineable`, which is
    asset data: a census recipe reads the items the game itself can load and reports the ids whose own
    stats admit the pair. Two same-id `combineable` items is the pair the row drives; if the census finds
    none, the combine half is `unproven` and the record says so rather than substituting the liquid or
    gun/magazine branch (a different native outcome);
  - a receiver with an EMPTY battery slot (`aed` created through `Utils.Create`: `BatteryItem.Awake`
    leaves `batteryType` empty when the prefab sets `notSpawnWithBattery`, so `LoadBattery`'s own
    occupied-slot guard is open) plus a `mediumbattery`, whose own stats carry the `battery` tag the
    native R3 branch reads;
  - something wearable, worn on the owner through the game's own wear call.
- **The panel/ring**: the remote backpack is opened through PRODUCTION's own entry
  (`remote-gesture mode=open`, the landed `IRemoteInventoryPresentation`), and every gesture is a
  `remote-gesture` release of a displayed proxy — the game's own `HandleReleaseDragging`, never a
  hand-made call.
- **The favourite sub-kind**: the native store is a `favourited` field write inside the while-dragging
  frames, gated on `Input.GetKeyDown(favourite)` and on the frame's OWN UI casts hitting an `InvButton`.
  The run holds the game's own favourite bind through `key-hold` (the `window-key` declaration, one
  `declare` per client) with the ring staged under the pointer, and reports whether that frame's casts
  overlap a button — a frame that never entered the branch is a setup miss, not a refusal.
- **Row 8's limb**: the operator's OWN wound view open with one of its limbs selected (`WoundViewLimb`
  carries the index the release reads), and the dragged item released onto that limb's own
  `WoundViewLimb` object, which is the native `PlayerCamera.TryPerformSpecialUIAction` wound-view branch
  → `ApplyWoundItem(this.dragItem)`. A topical whose own `useLimbAction` computes a non-zero ml is the
  fixture; the item belongs to the HOST, so the operator's use of it is the cross-player held-item chain.

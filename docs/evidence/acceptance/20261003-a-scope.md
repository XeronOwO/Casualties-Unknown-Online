## 2. Setups the session will run

Three clients, one world: host on the physical machine, guest in the Sandboxie guest box, the alternate
client in the second box; all enter through the Online UI's own controls, driven in-process.

**S1 — one world, three clients (runtime-entity rows 1, 2, 11, 12; rejection rows 1–9).**

- **Row 11 first, while the host has no template.** The guest and the third client bind
  `acceptance.beacon` — a `ModBuildingDefinition` whose base is a vanilla building prefab — through the
  building-content provider's own public `TryBind` seam (`building-template-inject mode=bind`), then
  read the provider's own dictionaries back (`mode=status`). The guest spawns it through the game's own
  console (`spawn acceptance.beacon player`); the host cannot materialize it and must reject.
- **Rejection rows 1–5 on that same rejected-creation shape.** Row 1: the host records nothing, relays
  nothing, logs the mismatch, and no third client materializes. Row 2: the reporter receives the
  rejection — its pending report is dropped and its local copy is removed through the death funnel
  (`runtime-entity-tables` reads the pending count back to zero; `runtime-entity-census` reads the copy
  gone). Rows 3–5 stage the answer shapes with the blackout: the rejection lost (guest armed, the
  fallback re-asks, the host rejects again idempotently), the copy already destroyed before the answer
  (`runtime-entity-kill mode=destroy` leaves the creation record standing), and the copy moved out of
  its creation cell (`runtime-entity-move`) so the answer must find it by creation key.
- **Row 12 after the host binds the template too.** The same spawn must materialize on all three
  (`runtime-entity-census` reads exactly one copy per client; the host recorded it — `accepted` rises
  by one), with no `Resources.Load` pre-check anywhere on the path.
- **Rows 1 and 2 with the committed `net-receive-blackout`.** Row 1: the host armed, the guest creates
  a vanilla runtime entity and its report is dropped; the guest's own pending count rises, then heals
  after `mode=off` when the fallback re-reports, and the host plus the third client hold it exactly
  once. Row 2: the run's member armed, the host creates the entity and the relay is dropped; the
  member must converge without a reconnect once the host's periodic absolute table arrives (S3).
- **Rejection rows 6–9.** Row 6: the accept-first path is unchanged (the row-12 shape). Row 7: a
  member entering after a rejected creation stays empty (shared with S2). Row 8: a non-reporter's
  receipt of the rejection is driven through the product's own `FireRuntimeEntityRejectedReceived`
  (`runtime-entity-rejection-forge mode=foreign`) and must change nothing; its ignore line is Debug, so
  the third client is raised with `log-level` for the probe and restored to Information after. Row 9: a
  hand-built report naming another member's token goes through the product's own `SendEntitySpawned`
  (`mode=report`), and the guest must still be answered and act because its own pending table holds
  the key; the removal no-op line of rows 4 and 5 is Debug too, and the same window applies there.

**S2 — in-place world entry (runtime-entity rows 3 and 4).**

- Row 4: the guest leaves the world and re-enters the SAME lobby id while the host stays in world —
  never `continue-run`, whose Continue restored a layer-end cut in batch `20261002-k`. The host's
  world-entry group must deliver the runtime-entity table; the verdict read is taken AFTER the entry
  edge applied (host `World join sent to N member(s) (… baseline follows: True)`, member
  `World join received — starting a run to follow`), and the census must read each creation exactly
  once on all three.
- Row 3: a late joiner. The third client joins the running lobby/world after the creations and takes
  its own entry edge; if a mid-run lobby join cannot be staged, the same in-place re-entry shape on
  the alternate client, named as the substitution in the record.

**S3 — the 60 s heal read (runtime-entity row 2).** The host's absolute re-broadcast is a periodic
cycle, so the post-window read is taken after one full cycle with other scenario work in between — never
by a long wait.

**Staging order (frozen before the run).** S1 runs in one world and one launch: the host is injected
LAST (the provider has no unbind, so every host-lacks-the-template row must be staged before row 12);
the swallowed-rejection rows are staged early, while the guest's own world-entry phase still runs the
fallback at its 5 s step (after ~60 s the step is the 60 s steady one); the census/tables reads bracket
every state change, and every blackout window keeps the documented order (status → arm → the one write
→ disarm → re-read).

## 3. Capability boundary

- The inbound blackout is proven by batch `20261002-o`: arming a client cuts exactly its inbound frame
  dispatch for the window (`subscribersAfter=0, parked=true`) while the session and its sends survive.
  Rows whose setup needs an inbound frame lost use it directly; windows stay short and single-stepped.
- **The template injection is the content provider's own public bind seam, not the mod discovery
  path.** It stages the exact template state a shared-content mod produces after discovery — the same
  `ModBuildingDefinition` payload the mod path binds — but it does not re-prove mod discovery, the
  handshake, or the content binder's shared-mode filter (those are the Mod API's own evidence). Named
  as a limit on rows 11/12 and rejection rows 1–3, 6.
- The rejection fork rows (8, 9) are driven through the product's own entry points because the
  production host never sends a rejection to a non-reporter, and the creating side never builds a
  foreign-token report itself; the probes call `FireRuntimeEntityRejectedReceived` /
  `SendEntitySpawned` and every verdict is read from the product's own tables, logs and census. Named
  as a limit.
- Row 3's late-joiner shape is the alternate client joining after the creations; if that exact shape
  cannot be staged, the substitution is the in-place re-entry and the record says so.
- Every row here is a `machine` row: a state, a count, a census entry, a log line read by the
  in-process probes.

## 4. Item-ticket audit (read-only result)

`item-creation-registration-first` rows 2, 4, 5, 6 and 7 are re-checked against this batch's
capabilities; none of them is stageable here, for the reasons the batch's own instruments make
concrete:

- Row 2 (a refused creation answers every later operation with the precise reason) needs a refused
  creation AND a way to operate on its id. The blackout can stage the lost first-writer-wins break that
  refuses a break's drops, but the refused drops do not survive on the reporting side as an operable
  item, and this batch has no probe that sends an operation envelope for an arbitrary item id.
- Row 4 (two senders, one item) needs the two attempts inside one relay latency; the driver's
  inter-command gap is seconds, and the batch has no simultaneous-two-sender instrument.
- Row 5 (reconnect / late join; the tombstone is not resurrected) shares S2's in-place re-entry, but
  its verdict needs a tombstone to observe, which row 2's setup must create first; the re-entry alone
  cannot judge it.
- Row 6 (an unknown-item operation reaching the host is recorded as a protocol violation, not held)
  needs a forged operation envelope; the batch has none.
- Row 7 (generation items, containers, drops, crafting, trade unchanged) — batch `20261002-k` staged
  the item census, drop and container halves; crafting and trade were not staged, and this batch adds
  no crafting/trade drive.

The ticket therefore keeps its `todo/` status and its named gaps; no record is written for it because
no verdict changes.

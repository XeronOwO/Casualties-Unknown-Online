## 2. Setup the session runs

Two clients, one world: host on the physical machine (launched through Steam), guest in the `Steam1`
sandbox. The alternate client is not needed — the row has no third-party half. All session entries go
through the Online UI's own controls, driven in-process.

**S0 — one world, two clients.** Read both ends' enemy tables (`enemy-table-read`) as the baseline and
smoke the batch's probes before any row depends on them.

**S1 — the control, with the host's table non-empty.** Arm `wire-generation-probe kind=all` on the
member, then drive the member's own readiness-window repeat report (`scene-repeat` →
`ISessionControl.ResendSceneState`). The host must answer it through its entry-repair path
(`Repeat scene report from …`), the repair group must carry the enemy table (`[Enemy] snapshot sent …
N enemies`), the member must log `[Enemy] snapshot applied: N …`, and the wire probe must decode one real
`EnemySnapshot` frame. This is the A/B's "the same path sends when the table is non-empty" half, and it
smokes every instrument the window's half needs.

**S2 — the empty-table window (the row).** The host's enemy table is replaced every frame from its live
scene, so its own world/layer generation is a real empty-table window. Arm the member's inbound blackout
(`net-receive-blackout mode=on`, well inside the 15 s watchdog) so the host's InMenu report of its own
generation does not pull the member out of the world; run `game-console command=skiplayer` on the host
(the game's own debug entry — the same shape batch `20261002-b` used for its stale sender); poll the host's
`enemy-table-read` until it reads 0; then drive the member's repeat report and read:
the host's `Sending the in-session repair group to {Peer}.` line with **no** `[Enemy] snapshot sent` line,
the host's table still 0, and the member's own table unchanged. Lift the blackout immediately after.

**S3 — the window closes.** Read the host's table again once its generation completes (it must be
non-empty, i.e. the window was the generation, not a dead send path) and lift the blackout; the clients
close through the game.

## 3. Capability boundary

- **The entry-edge shape is still not stageable.** A member's InWorld edge fires only after its own
  generation has finished (`HarmonyTraverse.HasLiveWorld` excludes generating), and on this machine the
  host finishes generating before the members do, so "a member entering while the host's table is still
  empty" cannot be produced end to end. The window is staged through the member's own readiness-window
  repeat report instead — the same `SendEnemySnapshot` call the entry fan-out and the 60 s pump make — and
  the record names that carrier.
- **The descent is the game's own debug entry** (`game-console command=skiplayer`), not a natural layer
  end; it is named as the setup, as batch `20261002-b` already did for the same entry.
- **The member's blackout is a blunt, short window**: it drops every inbound frame and must stay well
  inside the 15 s host-silence watchdog; the record states its measured length.
- **Fallbacks, in order**: `scene-reload` (the game's own same-scene reload) if the descent opens no
  window; then `PublishEnemyStates([])` through the product's own publish entry as a declared forced-empty
  fallback; if none produces the window the row stays `unproven` and the ticket stays in `todo/`.

## Experiments already measured

- `role-clearing` can skip its initial restart when the preceding
  `remote-removal` leaves both clients in a world: 70.1 s → 22.0 s (the case's
  own leave/second-session work remains).
- `remote-removal` can pass without rejoining: 7.0 s instead of 30.0 s, but it
  leaves the member at `role=None, active=false, inWorld=true, page=Home`.
  The next `role-clearing` restart then cannot join the member: the client
  refuses because a world is still running or generating.
- Rows that leave the world through the acceptance driver's native
  `PlayerCamera.ToMainMenu` can keep `RunCoordinator.IsInWorldOrGenerating`
  true after the menu is visible. The driver bypasses the run coordinator's
  own leave bookkeeping.

## Options

1. **A — make leave update the run coordinator** (recommended): after the
   native menu return, the run state must be out-of-world even when the old
   world object is still alive. Then `role-clearing` can reuse the pair and
   save its 45.8 s restart; `remote-removal` can rejoin without the ghost.
2. **B — split character-choice and merge its world with late-layer**: run the
   choice/peer half first without the ending, run `late-layer`/`pod`/`last`
   in that unchipped world, then run the ending + outside picker at the end.
   Saves the 44.3 s late-layer generation.
3. **C — start setup from a generated world fixture**: restore instead of
   generate, reducing the 22.8 s setup. It changes the fixture's isolation and
   needs a separate decision.

Do A then B; C only if the first two miss the target. Never park a red row.

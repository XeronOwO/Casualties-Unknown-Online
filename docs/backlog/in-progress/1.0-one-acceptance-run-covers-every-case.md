# One acceptance run covers every case

- Status: In progress (2026-11-21) — the split is gone; the runner owns the world's lifetime; the hang and the journal
  loop are fixed, and the one run now completes (47 of 67) — the rows still fail on the session's own shape: a second
  member row left behind, and a member body with no free slot.
- Priority: High
- Created: 2026-11-21

## Why

Acceptance had grown two tiers: a "batch" of 39 rows whose `RunsInBatch` was true, and 28 rows that ran "by name" and
were left out of `--suite all`. The split was mine, not the user's. It came from a five-minute wall-time figure I had
derived myself (from the user's much older complaint that a run took "half a day"), and the figure then hardened into
"five minutes is the ceiling" in the rules and in a handoff prompt that later rounds read as an instruction from the
user.

The user's requirement, restated on 2026-11-21:

- Acceptance is **one complete run at the end of the work**, not a fast batch plus a closing batch.
- Five minutes was **the wall time at that point**; when a case is added, the added time must be as small as possible.
  It was never a ceiling, and it never decides which rows run.
- Every row that can run, runs. A row that genuinely cannot run on this machine is named, not silently dropped.

## What changes

- `tests/CasualtiesUnknownOnline.AcceptanceSuite/Suite.cs`: `RunsInBatch` is deleted; `--suite all` selects every
  registered case; `--list` prints name/launch/cost; the report names the registered cases the selection did **not**
  run (so a partial run states its own gap).
- Registry order is the run order, and it now carries the constraints: `world-fingerprint` first (before anything moves
  the world); then the rows that need state the rest of the run consumes (`starting-supplies`, `crafting`, `lockpick`,
  `capability-report`); then the shared-world rows in their existing order; then the three pair-shaping rows last —
  `net-conditions` (lossy link), `host-rule-toggles` (writes host rules), `host-crash-restart` (kills the host).
- The run launches all three clients (`run --all`); two-member-continue reads Steam2 and fails naming the missing
  client when the launch did not start it.
- Rules: `docs/acceptance/AGENTS.md` rule 14 rewritten; `docs/acceptance/workflow.md` "the wall-time reading" rewritten;
  `docs/development/game-update-runbook.md` §6 wording; `docs/backlog/README.md` index row; a lesson in
  `docs/acceptance/lessons.md`.

- `medical-tourniquet` — the row scanned the member's limbs without waiting for the body and without healing a body an

Still failing on their own readings: `medical-bandage` and `medical-shrapnel`.

`medical-bandage` is now measured to the game's own numbers rather than guessed at. The row arms the wrap
(`.acceptance/bandage8`: `handStarted true`, `handClicking true`, hand 19 degrees off the roll, so `dot > 0.9` holds) and
the roll still does not turn: `angle 0`, `lastActionAngle 0`, `fill 0` for the whole budget while the bleed only drifts
with the wound's own tick (35.9 → 9.5 over 40 s). It is driven by the game's own input now: `GetMousePos` adds a pain
shake (`MinigameBase.cs:160`) that wanders the hand's direction by up to ~16 degrees a frame at this body's pain, and
`BandageMinigame.PhysicsUpdate` advances only on `< 20` degree steps past `lastActionAngle`
(`BandageMinigame.cs:104-126`), so a staged pointer still does not reproduce the sweep a hand makes. That is a row
defect, not a product one — no player-visible claim is contradicted, the row cannot yet drive the gesture.
`medical-shrapnel` is the same family (seeded 3, remaining 3).

The grip itself is now the measured part, and two of the row's own bugs are fixed. `minigame-live` reports the game's
`holdingBandage` and the hand's own angle, which says exactly which of the two ways a wrap stalls it is:
`holding: false` means the key went down while the hand was outside the roll (the game stamps the grip only on that
frame, `BandageMinigame.cs:74-80`), and `holding: true` with a still ring means the hand is not walking the ring. Measured
2026-11-21 on a fresh pair (`.acceptance/med-bandage7`): the old code pressed with the hand at 152 degrees and read
`holding: false, handClicking: true, angle 0` for the whole run — the press was the first line of the failure, not the
sweep. The row now installs the pointer patches first (`pointer-circle` only stages a position; without the patches the
game reads the real cursor, measured as `pointerX -160, pointerY -491, handMagnitude 741`), waits for the hand to pass
the roll's start, and only then puts the key down. The remaining wall is the sweep: even one step per frame at 0.8
degrees the hand hovers near 200 degrees instead of carrying the ring (`handAngle 217, 218, 200` over 40 s,
`.acceptance/med-bandage11`), so the roll never reaches `holding: true` for long enough to wrap.

Options for the next attempt, in the order they are worth trying: (a) drive the hand with the game's own velocity input
instead of a pointer path — hold a fixed pointer just outside the ring so `handVelocity` keeps a tangential component,
which is what a mouse held against the ring does; (b) lower the body's pain first (the shake is the thing that keeps
kicking the hand off the ring) and then sweep; (c) accept the two gesture rows as blocked on the input seam and record
the measured wall in this ticket, the way `host-crash-restart` was recorded before its launcher bug was found.


`save-continue` passes alone but failed in the 67-case run with "6 geyser type(s) applied (the archive carried 97) … 91
row(s) not taken", because the live world had drifted from the cut by the time the row ran — that belongs to
`1.0-the-batch-compares-live-world-state`.

### The row that hung the run: a restore dropped the adopted row (2026-11-21)

The second single run (`.acceptance/every-3`, 67 cases, three clients) stopped at row 128, `remote-backpack-refresh`,
with no progress for seven minutes. The field said why: the guest's `latest.log` had grown to 970 MB with

`Batch from 1 creates a revision gap: expected 8, received 9..N` and
`Applying batch from 1 failed: carried item 150959648765 references unknown player 2518207895626860263`

and the host was re-sending the same journal from revision 8 forever (`Sent N journal batch(es) 8..M`).

The chain, from the host's own log: the guest reconnected under a new transport id and adopted the saved character
(`Re-keyed 2 item row(s)`); the cut it then restored carried the player row under the id the character was saved with;
the restore replaced the kernel with those rows, so the adopted id disappeared from the players table while the member
kept its new id and re-reported its carried items under it every 5 s. The item batch then named a player no peer had,
every peer refused that revision (`PlayerDomainModule`'s unknown-player invariant; the guest cannot resume past a gap),
and the host re-sent it forever. `CharacterDataStore` now hears `ItemKernelAuthority.CheckpointRestored` and re-runs the
adoption it recorded — the adopted row is committed from the saved snapshot, then the items still owned by the id it came
from are re-keyed (`ReestablishAdoptions`).

Verification: the focused test is red with the subscription removed and green with it (6749/6749 units, 836/836 gates);
deployed as `0.1.0+4af714e94`; the three save rows over a fresh pair (`.acceptance/adopt-fix1`) are **3 passed, 0 failed**
— `save-continue` PASS 52.4 s, `save-write-interrupted` PASS 69.3 s, `save-continue-reentry` PASS 111.6 s (suite wall
269.3 s), with no `unknown player` or `revision gap` line in either log.

### The roster half is done (2026-11-22 00:10)

`SessionDriver.EnsureSingleMemberAsync` runs inside the existing `EnsureLiveWorldAsync` guarantee: it reads the guest's
own id and, for every roster entry that is not it, asks the host to kick that member (`SessionService.KickMember`,
exposed to the batch as the `kick-member` recipe), re-reading the roster until only the guest is named. Cases that bring
a second client in do it after this point as their own step. The first attempt failed as `eval 'kick-member' returned
no value` — a recipe file ends with the invoked cast (`}))()`), and the missing call parentheses were the whole defect
(`.acceptance/shape1`).

Verification, `.acceptance/shape2` on the fixed build: `two-member-continue`, `remote-backpack-refresh`, `net-conditions`
and `host-rule-toggles` together read **4 passed, 0 failed** (three of them failed on the two-member roster minutes
before). The remaining family is the member's body: `give-item` reads `slots 6, filled 0` — the guest's own inventory is
empty in its client even though the session holds its carried items — while other rows read "every body slot is
occupied". The two readings point at the same seam (the guest's client and the session disagree about what it carries),
so the next measurement is one row run alone against a full run's prefix, reading `body-items` before the give.

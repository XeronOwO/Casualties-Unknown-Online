# Push, carry and piggyback have no host switch

The mechanics exist: `PlayerPushService` commits a push from the pusher's Strength, and
`CarriagePatchBridge` carries a body's carry relation onto the clone. The rule surface only carries
`PiggybackWeightMultiplier`; there is no switch to allow or forbid pushes, no "always allow carry",
and no piggyback stack limit. A host who does not want to be shoved has no setting.

## Design

The permission surface (`docs/design/cross-cutting/permissions-and-commands.md`) and the body-action
families (`docs/design/game/README.md` — the body's own interactions). These are host rules, so they
belong to `IHostRules`/`HostRuleSet`, announced like every other rule, and read by behaviour on both
sides rather than by the UI alone.

## The reading (2026-11-14, release build)

`grep 'AllowPush|AlwaysAllowCarry|PiggybackMax' src/` finds nothing; `HostRuleSet` carries
`PiggybackWeightMultiplier` and nine other flags but none of these three. The reference mod ships all
three as host rules.

## Acceptance rows

1. With pushes off, a push attempt is refused on the pusher's own client with a named reason, and the
   target's body does not move.
2. With "always allow carry" on, a carry that the game would refuse (an unconscious carrier rule)
   succeeds and the clone follows.
3. The piggyback stack limit refuses the N+1st body on the operator's own client, and the value is
   announced to members.

## The chain, by execution (2026-11-19)

1. The player opens another player's card and presses Push: `src/CasualtiesUnknownOnline.Plugin/OnlineUiPlayerContextMenu.cs:317-319`
   renders the row when `row.CanPush` and invokes `ctx.PushRemote(steamId)`.
2. `OnlineUiHost` wires `PushRemote` to `IPlayerInteractionControl.SendPushRequest`.
3. `src/CasualtiesUnknownOnline.Runtime/Session/PlayerInteraction/PlayerPushService.cs` `SendPushRequest` is the
   client gate (session active, in world, line of sight, reach) and the host authority (`HandlePushRequest`:
   conscious/standing, both in world, no carry relation, distance, cooldown), then broadcasts `PlayerPushResultMsg`.
4. Every client applies the result in `src/CasualtiesUnknownOnline.GameAdapter/PlayerPushApply.cs`
   (target ragdoll + velocity, pusher stamina/heat, push sound).
5. The host's rule surface is `IHostRules` → `HostRuleSet` → announced through `HostRulesMsg`, so a new switch
   has to exist in all of them and in the census before behaviour may read it.

Carry: `src/CasualtiesUnknownOnline.Runtime/Session/PlayerInteraction/PlayerCarryService.cs` owns the carry
decision and `src/CasualtiesUnknownOnline.GameAdapter/CarriagePatchBridge.cs` reproduces it locally. Piggyback:
the weight multiplier is read where the carrier's encumbrance is computed; a stack limit does not exist yet in
any surface, so it is new behaviour rather than a switch on one.

## Design decisions (2026-11-19)

- The switch names are `AllowPush`, `AllowAlwaysCarry` and `PiggybackMaxBodies`, all host rules announced like
  the existing ten flags. Defaults keep today's behaviour: pushes allowed, the game's own carry rules in force,
  and no CUO stack limit (0 = unlimited), so an old config changes nothing.
- The refusal is a catalogue key rendered by the client that shows it (the `RefusalReason` rule), not a
  sentence built on the host; the pusher's own client refuses before anything crosses the wire, and the host
  refuses the same request again as the authority.
- `PiggybackMaxBodies` is a number rule in the range 0-8 and is announced with the rest, so the operator's
  client and every member read the same value.

## The third switch, parked (2026-11-18)

`PiggybackMaxBodies` presumes a stack: the row it must satisfy is "refuses the N+1st body". CUO's carry table
is one carrier to one carried body (`PlayerCarryService._carrying`/`_carriedBy`, and the kernel's
`AssertCarryFields` refuses a participant of two relations), so no N+1st body can exist and a limit would
never refuse anything.

- Option A — build the stack: a carrier may hold several riders (and a rider may not carry), a stack depth
  column on `PlayerCarryStateMsg`, a limit read by the request handler, and the adapter's mount points per
  rider. Consequence: new relation semantics, new wire shape, new adapter work; the current one-to-one
  invariant and every carry test would change with it.
- Option B — keep the value as an announced number and refuse the 2nd rider forever (limit 1). Consequence:
  the rule only matters on top of A; shipping it now would be a switch that cannot be exercised, and the
  acceptance row cannot be taken.
- Option C — drop the switch. Consequence: the reference mod's rule is not reproduced, and the ticket closes
  with two of the user's three switches.

Recommendation: A only if stacked carrying is wanted as a feature; otherwise C, because B's row cannot be
read. The two landed switches stand on their own.

## Decision (2026-11-18) — option C, chosen by the user

Asked with the three consequences above; the user chose **C: drop the switch, do not build stacking**. The ticket closes
with two of the three switches, and a stacking model stays a possible future feature with its own ticket rather than a
limit bolted onto a one-to-one table. No code changed for this half: `grep -n "PiggybackMaxBodies" src tests` is empty,
and the design page's bullet now states the decision instead of "not landed".

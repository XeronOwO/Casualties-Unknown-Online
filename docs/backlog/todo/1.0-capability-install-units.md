# 1.0: a capability installs and comes off as a unit

- Status: Todo — night mode, split from `in-progress/adapt-to-1.0.md` (stage 3 of the capability catalog).
- Priority: High
- Category: Adapter / release

## The question

The catalog's stage 1 made every patch class belong to exactly one capability (the file it is authored in is its unit)
and stage 2 made an OPTIONAL capability's missing hook install as off instead of refusing the session. Stage 3 is the
other direction: a player (or a support instruction) turns an optional capability OFF at startup, and that capability's
whole unit is absent — every patch class of it unpatched, no half-installed unit, and the session runs on the rest.

## The chain (read 2026-11-10)

- `src/CasualtiesUnknownOnline.GameAdapter/Capabilities/AdapterCapabilityCatalog.cs:22-24` states the unit rule: a patch
  class belongs to exactly ONE capability, and the file it is authored in is its unit.
- The install path is `PatchInstallLifecycle.Install` (`src/CasualtiesUnknownOnline.GameAdapter/Patches/PatchInstallLifecycle.cs:70-90`):
  `PatchInventory.VerifyMissing(_harmony)` collects the missing hooks, `_capabilities.Record(missing)` prints them, then
  stage 2 splits the blocking set through `AdapterCapabilityCatalog.IsRequiredOwner(failure.PatchClass)` — Required and
  unclaimed classes refuse the whole session and the adapter unpatches; Optional ones log "installed with {n} optional
  capability hook(s) off".
- The Harmony registry is the observable (`Harmony.GetAllPatchedMethods()`), which is how the acceptance can prove a unit
  is absent rather than merely reported off.

## Design

The adapter's capability map this design extends is in `docs/design/audit/code.md`.

1. `AdapterCapabilityCatalog` gains `IReadOnlyList<Type> ClassesOf(string capabilityId)` (the classes it already owns by
   file name) and `IReadOnlyList<string> OptionalCapabilityIds`.
2. `PatchInstallLifecycle.Install` gains an optional `IReadOnlySet<string> disabledCapabilities` (empty by default — every
   existing caller behaves as today). After `harmony.PatchAll(assembly)` it unpatch the disabled capabilities' classes
   (`harmony.Unpatch(original, HarmonyPatchType.All, harmony.Id)` per class, the same shape as `UnpatchSelf`), and the
   missing-hook split treats a disabled capability's missing hooks as expected (logged "off (disabled by configuration)",
   never counted as a failure).
3. The configuration seam: `[Adapter] DisabledCapabilities = ""` (comma-separated ids) read at bootstrap and passed to
   `Install`; an id that names a REQUIRED capability is refused loudly (a required system cannot be turned off) and the
   adapter continues with it installed.
4. `AdapterCapabilityReport.Render` gains one line per disabled capability: `off (disabled)`.

## Acceptance

1. With `DisabledCapabilities` naming one optional capability, that capability's patch classes are absent from
   `Harmony.GetAllPatchedMethods()` while every other class is present, and the report prints the capability as `off`.
2. Naming a required capability refuses that id (a log line naming it) and the capability stays installed — the session
   runs.
3. An empty setting behaves exactly as today (the existing stage-1/2 tests and the gate stay green).

## Open questions

- None for the machine half. Whether the setting is exposed in the Online UI (a checkbox per optional capability) is a
  player-facing decision; it waits for the user and is not part of this ticket.

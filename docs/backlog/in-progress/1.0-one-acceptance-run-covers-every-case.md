# One acceptance run covers every case

- Status: In progress (2026-11-21) — the split is gone; the runner owns the world's lifetime; the hang and the journal
  loop are fixed, and the one run now completes (47 of 67) — the rows still fail on the session's own shape: a second
  member row left behind, and a member body with no free slot.
- Priority: High
- Created: 2026-11-21

## Why

Acceptance had grown two tiers: a "batch" of 39 rows whose `RunsInBatch` was true, and 28 rows that ran "by name" and
were left out of `--suite all`. The split was mine, not the user's. It came from a five-minute wall-time figure I had
derived myself (from the user's much older complaint that a run took "half a day"), and the figure then hardened into
"five minutes is the ceiling" in the rules and in a handoff prompt that later rounds read as an instruction from the
user.

The user's requirement, restated on 2026-11-21:

- Acceptance is **one complete run at the end of the work**, not a fast batch plus a closing batch.
- Five minutes was **the wall time at that point**; when a case is added, the added time must be as small as possible.
  It was never a ceiling, and it never decides which rows run.
- Every row that can run, runs. A row that genuinely cannot run on this machine is named, not silently dropped.

## What changes

- `tests/CasualtiesUnknownOnline.AcceptanceSuite/Suite.cs`: `RunsInBatch` is deleted; `--suite all` selects every
  registered case; `--list` prints name/launch/cost; the report names the registered cases the selection did **not**
  run (so a partial run states its own gap).
- Registry order is the run order, and it now carries the constraints: `world-fingerprint` first (before anything moves
  the world); then the rows that need state the rest of the run consumes (`starting-supplies`, `crafting`, `lockpick`,
  `capability-report`); then the shared-world rows in their existing order; then the three pair-shaping rows last —
  `net-conditions` (lossy link), `host-rule-toggles` (writes host rules), `host-crash-restart` (kills the host).
- The run launches all three clients (`run --all`); two-member-continue reads Steam2 and fails naming the missing
  client when the launch did not start it.
- Rules: `docs/acceptance/AGENTS.md` rule 14 rewritten; `docs/acceptance/workflow.md` "the wall-time reading" rewritten;
  `docs/development/game-update-runbook.md` §6 wording; `docs/backlog/README.md` index row; a lesson in
  `docs/acceptance/lessons.md`.

### The row that hung the run: a restore dropped the adopted row (2026-11-21)

The second single run (`.acceptance/every-3`, 67 cases, three clients) stopped at row 128, `remote-backpack-refresh`,
with no progress for seven minutes. The field said why: the guest's `latest.log` had grown to 970 MB with

`Batch from 1 creates a revision gap: expected 8, received 9..N` and
`Applying batch from 1 failed: carried item 150959648765 references unknown player 2518207895626860263`

and the host was re-sending the same journal from revision 8 forever (`Sent N journal batch(es) 8..M`).

The chain, from the host's own log: the guest reconnected under a new transport id and adopted the saved character
(`Re-keyed 2 item row(s)`); the cut it then restored carried the player row under the id the character was saved with;
the restore replaced the kernel with those rows, so the adopted id disappeared from the players table while the member
kept its new id and re-reported its carried items under it every 5 s. The item batch then named a player no peer had,
every peer refused that revision (`PlayerDomainModule`'s unknown-player invariant; the guest cannot resume past a gap),
and the host re-sent it forever. `CharacterDataStore` now hears `ItemKernelAuthority.CheckpointRestored` and re-runs the
adoption it recorded — the adopted row is committed from the saved snapshot, then the items still owned by the id it came
from are re-keyed (`ReestablishAdoptions`).

Verification: the focused test is red with the subscription removed and green with it (6749/6749 units, 836/836 gates);
deployed as `0.1.0+4af714e94`; the three save rows over a fresh pair (`.acceptance/adopt-fix1`) are **3 passed, 0 failed**
— `save-continue` PASS 52.4 s, `save-write-interrupted` PASS 69.3 s, `save-continue-reentry` PASS 111.6 s (suite wall
269.3 s), with no `unknown player` or `revision gap` line in either log.

### The bandage row: our own panel read the press (2026-11-22 00:40)

`medical-bandage` could not advance the wrap: the hand was staged on the roll, the key went down
(`posted: true`, `handStarted true`, `handClicking true`, `dot 0.944`), and `bandageAngle` stayed at
0 with `fill 0` and `holdingBandage false`, so the bleed only decayed on its own (35.9 → 9.5 over
the row's 44 s). Four theories were written down and each died on a reading: the hand lags the
pointer (no — the mapping is exact), the window is not in the foreground (no — the patch drives
`Input.mousePosition`), the patch does not intercept `mousePosition` (no — the staged point is what
the game reads), and the point sat off the circle (no — it sat on it).

The cause is our own Online panel. The batch opens it to read the session's state and leaves it open;
it is centred on screen, it carries buttons, and it ate the press the minigame was waiting for. The
`CUO Example` box at the top right only draws. The ledger has written this twice, on 2026-10-06:
"A key swallowed by an open Online UI window reads as `posted: true, heldAtEnd: true` … close the
window and read the toggle back" (`docs/acceptance/lessons.md:268`) and "the Online UI window is
closed before driving the game's own keys" (`:276`). Neither page was opened before this row was
rewritten for a day; the cost of not reading was the whole night's first half.

What changed: the driver gained `close-window` (`tools/acceptance/driver/InProcessDriver.cs`, after
`open-window`; it toggles `OnlineUiOverlay` when `windowState.Visible`, and answers
`ok/command/visible/page`), `SessionDriver.CloseWindowAsync` wraps it, and the row closes the panel
after `select-limb` and requires `visible: false` before it opens the minigame. `PointerCircle` also
learned to be driven by saying where to point (`start-point`/`point`, radius inferred from the
circle's centre to the first point) instead of approximating the circle from outside.

The acceptance workflow now makes the reading a step rather than an intention: `tools/knowledge.ps1
-Query "<the player's words>"` prints the design, architecture, decision and lesson pages that carry
a topic, and `-Changed` prints the pages each changed file's words live on so they are updated in
the same commit (`docs/acceptance/workflow.md`, "Before a row is written, the docs answer first").

Next: deploy this harness and read the row's own frames — the roll must turn, the fill must advance,
and the bleed must fall in seconds rather than tens of seconds.

which inventory, which host-rule defaults. Rows that need a different state say so; rows that cannot run rather than
report a false red.

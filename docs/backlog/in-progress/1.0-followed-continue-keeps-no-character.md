# A followed continue keeps no character

- Status: In progress — the hand-over is implemented; the acceptance reading is pending.
- Priority: High
- Created: 2026-11-17

## What the player sees

The host saves and clicks Continue. The member is still in the session and its client follows the
host's entry instruction, so it never reconnects — it regenerates the world and builds a fresh body.
That body comes up with the starting supplies, and the host's store then holds the fresh kit
instead of the restored character: the member's items, their colours and the saved health are gone,
and the host's own copy of the member shows the same fresh kit. A member that reconnects instead of
following keeps its character, which is why the earlier colour evidence passed.

## Evidence (2026-11-17)

- `.acceptance/full-after-geyser/report/report.md`: `save-continue` failed with
  `count:4, items:[waterbottle 0, dogfood 0, lantern 0, trashbag 0]` after the continue, while the
  pre-save readings were correct (the member's bandage carried `MemberColor/5`, the host's stored
  character before the save was that same bandage).
- Host log 19:34:18.204: `Restored characters: 2 bound to present peers, 0 left unclaimed, 0 refused
  (key space IpDirect)` — the archive's characters are bound into the store by
  `WorldRestoreApplier.cs:342-343`.
- Host log 19:34:33.728: `Sent saved character data to 14147207096578030068 (4 items)` — the only
  send went to the NEW transport id, and it carried the fresh kit. No send went to the member's
  following transport before its body existed.
- Guest log 19:34:26.732: `Starting supplies held for this body: the world-entry group has not
  completed yet, and the host sends a character restore before its completion marker (waiting up to
  8000ms)`; 19:34:33.731: `Received character restore (4 items)`.

## Root cause

The continue's entry instruction (`WorldJoin`) is sent to a following member without a character
hand-over first. The world restore binds the archive's characters, but nothing sends the member its
own row on this seam; the fresh body's 1 Hz report
(`SaveReportedCharacterData` → `SaveCharacterData`) then replaces the bound row, and the later
reconnect adoption hands the fresh kit back. The receiver half already exists: a peer hand-over is
kept across a follow (`LocalCharacterRestoreQueue`, `CancelOwnRunRestore`), and the host is supposed
to send it before the instruction on the same reliable ordered channel — the pattern
`RespawnCoordinator.cs:132-139` already uses for a menu-side guest.

## Fix (implemented 2026-11-17)

- `CharacterDataSync.SendSavedCharacterToEnteringMember` / `SendSavedCharactersToEnteringMembers`:
  host-side, hand every handshaken member still outside the world its saved character.
- `RunCoordinator`: before the world-entry broadcast of `WorldJoin`, hand the entering members their
  characters (the continue path's seam).
- `ReentryCoordinator`: the same hand-over before both targeted re-entry invites.

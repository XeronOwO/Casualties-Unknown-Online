# The same player must keep one identity across transports

- Status: Review — the user's standing requirement (2026-11-11): every player has one identity, and the online and offline modes hand over seamlessly — a Steam LAN failure that falls back to VPN/IP direct must recover the same character, inventory and progress.
- Priority: High
- Created: 2026-11-11

## What the player sees

A player joins a friend's room over Steam. The Steam path fails (LAN blocked, Steam offline), so both sides switch to IP direct. The player rejoins — and should continue as the same person: the same character, the same items, the same position in the run. Today the transport switch is a different player to the save.

## The chain (read 2026-11-11)

- The identity is the save key: `src/CasualtiesUnknownOnline.Runtime/Persistence/PlayerKeySpace.cs` (`Unknown`, `Steam`, `IpDirect`) is derived from the character file name, and `PlayerKey` (`steam-<id>` vs `name-<sanitized name>`) is built by `PlayerKeyResolution.KeyOf(peerId, displayName, space)`.
- Decision 162 makes the two spaces disjoint: a claim resolves only inside the space of the peer that joins. An unclaimed character of the other space is "that player joins as a new character" — which is exactly the behaviour the requirement rejects.
- The restore path: `WorldRestoreApplier` plans the claims (`WorldCharacterBinder.Plan`) before the kernel write; unclaimed characters' carried rows are filtered out of the restored checkpoint (`WorldContinueUnclaimedCharacterTests`). A cross-space claim therefore never happens by itself.

## The design (options and a recommendation)

- **A. Explicit profile key.** Every player carries one key that does not depend on the transport (a display name plus a stable digest, or a user-chosen profile id), and both transports claim it. Costs: a new key space (`profile-<name>`), the Steam id no longer names a character, and a collision (two players with the same name) needs a disambiguation step.
- **B. Adoption at join.** The claim looks across spaces when the join is unambiguous: one unclaimed character with the same display name, or a recorded link from the old key to the new one. Costs: a name-only match can adopt the wrong character; the link must be recorded in the save and shown at join.
- **C. (A) with (B) as the fallback.** A stable profile key is the default; when a player arrives under a key that has no character but the save holds exactly one unclaimed character with the same display name, the host adopts it and records the link.

**Recommendation: C.** It keeps the Steam id as the primary key (no migration for existing saves), gives a stable identity for IP-direct players, and never guesses when the match is ambiguous — the ambiguous case stays "a new character" and is named on the join screen.

## Acceptance

1. A host and a guest meet over Steam, the guest customizes an item, the transport is switched to IP direct and the guest rejoins — the same character, the same item label and the same position (a measured reading, one run).
2. Two guests with the same display name and different keys in one save: the adoption does not pick either; both join as new characters (the ambiguity rule, a unit fact).
3. The link is persisted: a save taken after the adoption restores the adopted character for the IP-direct key (read back from the archive's characters).

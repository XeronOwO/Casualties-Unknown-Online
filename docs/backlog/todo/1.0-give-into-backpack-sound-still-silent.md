# Giving into another player's backpack is still silent

- Status: Todo — Rejected (2026-11-19): the give's own clip is heard on neither client, though both recorders were armed before the drop and the item landed.
- Priority: High
- Category: Cross-player item transfer / native parity (audio)
- Source: user report (2026-10-25, translated): "why is there no sound when I move an item into another player's backpack? A normal item move has a cloth-rustle sound". The ticket `done/give-into-backpack-plays-no-sound.md` closed the reachability half and left the clip to the ear; this machine reading is that ear.

## What the player sees

Giving an item into a teammate's backpack makes no sound; the same item moved into the player's own backpack rustles as the game's own `backpack1`/`backpack2` clip.

## Reading (2026-11-19, the give row on the release build)

Two focused runs of `tests/CasualtiesUnknownOnline.AcceptanceSuite/Cases/GiveItemCase.cs` with the one-shot recorder
`sound-log` armed on BOTH clients (`mode=start match=backpack`) before the drop, then the give driven through the bridge's
own release call (`give-probe mode=give-world`, the same call the drag patch makes):

- `.acceptance/give-sound1`: the item landed in the member's bag; the member's recorder read `raw=833|` — 833 recorded
  calls, none named `backpack`.
- `.acceptance/give-sound2`: the item landed again; the giver's recorder read `raw=110|` and the receiver's `raw=110|` —
  neither carried `backpack`.
- The instrument itself is proven by the neighbouring rows of the same batch: the same recorder read
  `scrapmetal@22.2` for a host's placement and `rock@18.8` for a host's break, so a silent answer here is the give's own.

## Why the native call never runs

`PlayerCamera.PlayBackpackSound` (`reversing/release-1.0.2/Assembly-CSharp/PlayerCamera.cs:44`) plays
`Sound.Play("backpack" + Random.Range(1, 3), Vector2.zero, …)` and is called only from the drag/container branches
(`PlayerCamera.cs:1734, 1748, 1828, 1855, 1869`, plus `OpenContainer` at `:3076`). The give never enters those branches:
`RemoteDragIntentDispatcher.ReportLocalReleaseOntoProxy` (`src/CasualtiesUnknownOnline.GameAdapter/RemoteDragIntentDispatcher.cs:104`)
builds a `GiveToBody` intent and returns before the native body runs, and the transfer is applied through the kernel
projection (`src/CasualtiesUnknownOnline.Runtime/Session/PlayerInteraction/PlayerInteractionKernelProjection.cs:87`).
So the clip is not missing from the build — the call site is bypassed, which is the same shape the closed ticket named.

## Options

- **A — play the game's own call at the commit moment.** Call `PlayerCamera.PlayBackpackSound()` on the giver's client
  when its give is confirmed. It is the game's own method and clip (same random pitch), no new asset and no second
  wording. Needs the confirmation seam: the intent is applied host-side, so either an ack reaches the giver or the
  giver's own kernel projection is the commit edge.
- **B — run the receiver's native load path**, so the game plays it by construction (the original shape the closed
  ticket wanted). Larger: the receiving client would have to perform the container's `UnloadItem`/`LoadItem` rather than
  the projection writing the slot.
- **C — leave it silent** and say so in the player-facing parity record.

Recommendation: **A** first — it reproduces the game's own call at the one moment the player's action lands, and it can be
read by the row that already exists. **B** only if a reading shows the receiver's client must own the sound (for example
if the giver is out of earshot of the spatialised clip).

## Acceptance rows

1. The give row's recorder reads `backpack@` on the client that owns the move, once per delivered give.
2. A local move into the player's own container still plays its own clip exactly once (no double sound from the new call).
3. A refused give plays nothing.

## Design

`docs/design/mechanics/give-and-take.md` states that a give is the game's own transfer on the player's item, and
`docs/design/mechanics/backpack-view.md` owns what a backpack move does; a give that reaches the bag through the intent
path must still produce the transfer's own feedback, because that feedback is part of the transfer the page describes.

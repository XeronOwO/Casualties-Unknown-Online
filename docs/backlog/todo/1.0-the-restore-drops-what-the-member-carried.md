# The restore drops what the member carried

- Status: Todo
- Priority: High
- Evidence: `.acceptance/savecont-1/report/report.md`

## What happens

A save names the member's carried item with the colour the member gave it; the archive the save writes carries it
(`save-continue` reads both colours there before the continue). Continuing from that save leaves the member's own item
count at 0: `the member's colour did not survive the save/continue: {"ok":true,"count":0,"items":[]}`.

The member's own log, at the moment the world is materialized, also carries `NullReferenceException` at
`GroundBlood.Start ()` — the game's own blood decal script, started from the restore path our adapter drives.

## Why it matters

The row is the only place a player's saved item is followed from the archive back onto their body. Today the pair
survives the save and loses the member's item on the way back, which is the difference between "continue my run" and
"start over with the host's things".

## Options

1. **Find where the restore drops the member's items** — read the restore path's character placement for the member
   (the same placement the host gets), and make it keep what the archive names. Recommended: it is the defect the row
   names, and the host's half already works.
2. **Re-baseline the member after the restore** — send the adopted character data again after the world is up, as the
   reconnect path does. Cheaper, but it hides which step dropped the item and leaves the archive as the only truth.
3. **Park the row** — unacceptable: the claim is exactly what a player does.

## Design

`docs/design/cross-cutting/saves-and-recovery.md` — the save names items by owner and slot, and the restore puts them back
through the same placement the character data uses.

## Third reading (2026-11-24 05:15) — the stored character is never claimed by a later join

With a fresh save root (one world only, `w-20261123-2921`), the cut carries the member's character in
`characters/name-guest.json` (health, limbs, skills — items live in `items.json`), and the member's own log shows the host
sending `Received character restore (0 items)` three times after the continue.

The restore binds stored characters **once**, at the continue: `WorldRestoreApplier.TryApply` calls
`binder.Plan(decode.UsableCharacters)` and `binder.Bind(plan)` with the peers present at that moment
(`WorldRestoreApplier.cs:278`, `:343`). A member that joins afterwards is not in that peer list.

Characters that no present peer claimed are kept — `WorldSaveService.PendingCharacters` is set from
`restore.Characters` (`WorldSaveService.cs:568`) and the binder logs "the file stays in the archive for a later claim"
(`WorldCharacterBinder.cs:175`) — but **nothing ever reads `PendingCharacters` again** (no reader outside the property's
own declaration). So a later join has no path to its stored character, and the host correctly sends an empty one.

**The fix to build next:** when the host is about to send saved character data to a peer that has none, claim a pending
character by that peer's display name through the existing `PlayerKeyResolution.Claim` / `CharacterAdoption` rule, seed it
under the peer's current transport id, and send that — the same identity rule the restore uses, applied at the moment the
peer actually arrives.

## The fix, and why it is at the claim (2026-11-24 05:45)

The cut does carry the member's character (`characters/name-guest.json` with its items). The loss happens one step later:
`WorldRestoreApplier.TryApply` binds stored characters **once**, against the peers present at that moment, and the ones
nobody present claims are parked in `PendingCharacterClaims` — where, until now, nothing ever read them again. A member who
was out of the session when the continue ran therefore had no path back to its own body, and the hand-off answered with
nothing (0 items).

`PendingCharacterClaims.OnMissing` closes that: when the character table is asked for a peer it has no snapshot for, it
raises `CharacterDataMissing`, the save layer applies the same identity rule the cut uses (`WorldCharacterBinder.ClaimFor`
— the stored key's own claimant first, then the transport handover by display name) against the peers present **now**, and
seeds the claimed file into the table under the peer's current transport id. The claim is removed as it is taken, so a
second arrival cannot take the same body twice, and an ambiguous name still claims nothing.

Units: four facts on the rule (`CharacterClaimAfterTheCutTests`) — the named key claims, a different peer gets nothing, two
peers sharing one name get nothing, and a peer the cut already bound is not handed a second character. The real row
(`save-continue`) is the acceptance: the archive carries both colours and the member's own bag lists them after the rejoin.


## The cut writes a member snapshot that can be a second old (2026-11-24 07:35)

Measured, not inferred. .acceptance/savecont-diag PASS (case 40.0 s, wall 92.3 s) when the row waits **1.5 s** between the
member's real pickup and the second cut; the same row on the same build is red without the wait (.acceptance/savecont-2,
`the member's colour did not survive the save/continue: count 0`).

The chain the readings give:

1. `WorldCharacterBinder.Collect` (`src/CasualtiesUnknownOnline.Runtime/Session/Persistence/WorldCharacterBinder.cs:60`)
   writes each member's row from `characters.GetSavedCharacter(peer.PeerId)`.
2. That table is only fed by the member's **1 Hz** report (`CharacterDataStore.SaveReportedCharacterData`,
   `CharacterDataStore.cs:176`) and by authoritative writes; nothing refreshes it at cut time.
3. A cut taken inside that second therefore stores the row from before the pickup — the archive reads 0 items although the
   member is holding one (measured 2026-11-24 05:44: the member's own tree read `localCount 1` at that very cut).
4. On continue the restore hands back exactly that row, so the member rejoins empty. The restoration is faithful; the cut is stale.

Options, with consequences:

- **A — the cut waits for a fresh glance (recommended).** Before collecting, the cut waits up to ~1.5 s for each present
  member's next report (a transient like the ones `WorldCutTrigger.TryCollectTransients` already honours), and only then writes
  the rows. Cost: up to 1.5 s of extra cut latency, paid only when a snapshot is stale; no new message; the cut stops writing
  facts it knows are old.
- **B — a host→guest "report now" request.** New protocol message, guest handler and tests; near-zero latency, but a protocol
  change for something the 1 Hz stream already carries.
- **C — the cut derives carried rows from the item kernel.** No staleness and no wait, but the kernel row holds a subset of the
  wire item (no label/liquids/contents fidelity), so the cut would have to grow a mapping the members' reports already own.

Next unit: implement A (freshness exposed by `CharacterDataStore`, honoured by the cut's transient step) and keep the row as
the acceptance — it already fails on the stale write and passes when the write is current.

## What landed, and the trigger that is still missing (2026-11-24 07:20)

Two product defects were found and fixed while making this row honest, both pushed and deployed
(`0.1.0+1b21da5f9`):

- the cut now defers while a member's carried set is newer than its snapshot (`MemberSnapshotFreshness`,
  `member-character-report` in the cut's transient policy);
- a replayed ground decal only attaches the game's `GroundBlood` listener when the receiver already has that
  chunk (`WorldBloodReplay`), which removes the member's `NullReferenceException at GroundBlood.Start` the row's
  log gate was counting.

The row is still red, and the reading is precise: the row's own archive assert fails
(`the member's colour did not survive the save/continue: count 0`) while the hand-over at rejoin carries one item
(`Sent saved character data … (1 items)`), so the snapshot exists — it just arrives after the cut.

The wait did not fire because its trigger is the wrong one: `ItemIdCoordinator.FireCarriedInventoryReceived` only
fires for a guest's self-assigned carried set (the starting supplies), not for a pickup of a world item the host
already judged. What the host does receive for that pickup is the kernel's own committed carried row.

Next unit (one of these, in order of preference):

1. Derive the trigger from the kernel: on `ItemKernelAuthority.BatchCommitted`, note a change for the owner of any
   carried row in the batch, then let the same wait defer the cut. No new message, no second copy of the set.
2. Ask the member for a report at cut time (option B above): a request message and a guest handler.
3. Derive the rows from the kernel (option C): the largest change, and the one that loses fidelity.

Acceptance for any of them is this row: green with the archive carrying the member's colour, and the member's log
carrying no error.

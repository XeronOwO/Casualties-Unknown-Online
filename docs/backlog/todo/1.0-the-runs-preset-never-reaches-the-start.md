# The run's preset never reaches the start

- Status: Todo
- Priority: High
- Owner: next session
- Found: 2026-11-27, while making the two unchipped rows green.

## Why

`late-layer-switches` and `last-layer-gate` both read `unchipped:false` from the running world, alone and in the batch.
`run-preset` answers `{"ok":true,"preset":"unchipped","count":3}` every time, and the world the row then starts is the
default one.

## The readings

| run | reading |
|---|---|
| `.acceptance/latefront-1` | `character-choice` PASS 27.1 s; `late-layer-switches` FAIL 5.0 s `unchipped:false, setting:false`; `last-layer-gate` FAIL 27.0 s `the host's last layer is not unchipped` |
| `.acceptance/latefront-2` | an ensure that left, wrote the preset, and called `StartHostRunAsync`: both rows still read false, at 22.8 s and 29.5 s |
| `.acceptance/presetcheck-2` | the recipe's own read-back `instanceValue:"True"`; ten seconds later the world reads `setting:false` |
| `.acceptance/presetcheck-4` | `ApplyPreset("unchipped")` inside `start-run` right before `StartRun`: still `{"unchipped":false,"setting":false}` |
| `.acceptance/unchip-1` | leave first, then `run-preset`, then `StartHostRunAsync`: `last-layer-gate` still `unchipped:false` at 21.3 s |

## What the code says

`run-preset` writes `WorldGeneration.runSettings`; returning to the menu resets that table; and the start path reads a
table that is reset again before the run begins (presetcheck-4 rules out the in-call write too). So no test-side sequence
can hand the start an unchipped world.

## Design

`docs/design/game/console-and-save.md`, section **Run settings persistence**: "A run's settings live in the world
(`WorldGeneration.runSettings`, seeded from a preset) and are written into the ..." — the preset is the seed, and the seed
is what the start drops.

## Done when

`last-layer-gate` reads `unchipped:true` at layer 11, alone and in the 66-row batch, and `late-layer-switches` reads
`setting:true` for the same world.

## Options

1. Keep the chosen preset until the start consumes it (a "next start" field the start applies), product side. The honest
   fix; it is what the game's own menu does.
2. Choose the preset through the game's own menu path, the way `character-choice` does — but `character-choice` never
   proves the world is unchipped, so this needs the same reading first.
3. Relax the two rows to accept a chipped world. Rejected: it deletes what the rows judge.

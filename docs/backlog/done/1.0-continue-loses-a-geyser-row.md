## What the player sees

The host saves inside a world and clicks Continue. The archive carries the geyser types, the live
geyser set is complete — and one row is still reported refused, so the restore is announced
`INCOMPLETE`: one geyser comes back with whatever type its own start rolled instead of the saved
one. The player sees a geyser spout the wrong liquid while the match is "everything else applied".

## Root cause

`GeyserStateTable.Apply` matched from the LIVE side: each live geyser scanned the saved rows and took
its nearest one within 3 m. Two defects follow from that direction:

1. The 3 m radius is smaller than a regenerated geyser's distance from its saved row (3.62 m in this
   world: the geyser's position comes from the generator's ground raycast, not from a stored cell),
   so that row could never be matched.
2. Rows are not claimed exclusively: two live geysers inside one row's radius both take that row, and
   the row one of them should have matched is left unclaimed — a refused row with the world intact.

The count is per saved row (`rows - applied`), so either defect surfaces as a refused row and an
`INCOMPLETE` restore even though every decided type is present in the world. The readiness wait
itself had a second defect: a fixed 5 s window measured when the set had only partly filled.

## Fix (implemented 2026-11-17)

- `GeyserStateTable.Apply` now builds every (saved row, live geyser) pair inside the radius, sorts
  them shortest-first, and takes each pair once — one saved row writes one live geyser, so a row can
  never be shadowed by its neighbour.
- A saved row no live geyser reaches is refused and named at warning level with its position, so a
  future refusal carries its own evidence instead of only the count.
- The radius is 6 m, measured against the 2026-11-17 reading (3.62 m between a row and its geyser,
  12.34 m to the next live geyser). The write path stays contained per row
  (`ContainedRowLoop.Run`), and the remembered type is kept only after the write completed.
- The restore holds while the live geyser count is still growing (`GeyserFillWait`: 3 s of no growth,
  30 s ceiling) instead of a fixed 5 s window.
- Design page `docs/design/cross-cutting/saves-and-recovery.md` states the one-to-one rule and the
  growth rule; the code audit carries them.

## Residual

- The same matching shape exists in `src/CasualtiesUnknownOnline.GameAdapter/World/KeypadCodeTable.cs:96-124`:
  the write loop is live-side, takes the FIRST saved code inside a 3 m radius (`FirstOrDefault`, not even
  nearest) and claims no row exclusively, so a regenerated keypad displaced like this world's geyser
  would refuse its code row for the same two reasons. No acceptance reading has produced it yet
  (`50 keypad code(s) applied (the archive carried 50)` in the 2026-11-17 runs). The fix is the same
  one-to-one assignment, ideally extracted beside `ContainedRowLoop` so both native tables share one
  matcher; it is recorded here rather than changed in the same commit because a displaced keypad
  needs its own real-game reading before that claim can be made.

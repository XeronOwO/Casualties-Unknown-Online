# 1.0 prosthetics: a limb a teammate installed is not on the other clients

- Status: Done — the prosthetic block travels: the teammate's clone reads `3=pegl` on the owner's limb (batch `20261110-a`, `docs/evidence/acceptance/1.0-prosthetics-20261110-a.md`); the 1.0 clone template is the live player body (`19c6c7d8`).
- Priority: High
- Category: Character / release
- Source: the 1.0 map (`docs/design/game/items.md`): 1.0 lets a player install a prosthetic on a dismembered limb; the
  limb wire carries health, bleed, pain and the dismembered flag, and nothing about `Limb.ProstheticInfo`, so a
  teammate's limb stays dismembered.

## The question

1.0 lets a player install a prosthetic on a dismembered limb (a peg limb, a steel
prosthesis, and the items 1.0 adds). Does a teammate see the prosthetic on that limb?
Today: no — CUO's limb state carries health, bleed, pain and the dismembered flag, and
nothing about `Limb.ProstheticInfo`, so the limb reads as still dismembered on every other
client.

## Chain (read 2026-11-10, from `reversing/release-1.0/`)

1. The item's `useLimbAction` runs from the wound view's release on the owner's client
   (`Item.cs:749-830`): the peg limb and the steel prosthesis each check
   `limb.isAbdomen || limb.isVital`, roll INT against `7` / `10` for a failure (a failure
   costs skin/muscle/pain/blood and alerts `alertprosthesisfail`), then call
   `limb2.AttachProsthetic(Item.PegLimbInfo() / new Limb.ProstheticInfo { hasProsthetic = true, itemId = "steelprosthesis", armorChange = 0.2f, ... }, false)`
   and destroy the item.
2. `Limb.AttachProsthetic` (`Limb.cs`) reattaches the limb and plays `prostheticapply`
   when `isLoad` is false, then walks the lower limbs for tourniquets. The struct
   (`Limb.cs`, `public struct ProstheticInfo`) is `hasProsthetic`, `itemId`,
   `forceChange`, `armorChange`, and the colour channels `r`, `g`, `b`.
3. The state is read by the game's own rules: healing is multiplied by
   `hasProsthetic ? 0 : 1` (`Limb.cs:46`, `:56`), the limb's tint is blended by
   `hasProsthetic` (`:63`), impacts are soaked (`:182-183`), and the four "peo" limbs
   unlock something at `:112`.
4. The save reads the struct straight from JSON (`SaveSystem.cs:305-307`) — the field
   is the authoritative state, not a derived flag.
5. CUO's limb message (`LimbStateMsg`) and its handler (`LimbStateEventHandler` →
   the host record → `CharacterDataSync`/`LimbApply`) carry no prosthetic field, so a
   remote limb never gets one.

## Design

- `docs/design/game/items.md` — the prosthetic items and their `useLimbAction`
  (`Item.cs:749-830`); `docs/design/game/medical.md` — the limb state the wound view
  shows and the install's native entry.
- The owner's client judges and reports its own limb (decision 184): the wound view's
  release installs the prosthetic natively, and the limb report carries the prosthetic
  block beside the other limb facts.
- Wire: `LimbStateMsg` gains the block — `HasProsthetic` (bool), `ItemId` (string),
  `ForceChange`/`ArmorChange` (float), and the three colour channels (float or byte).
  Encoding rule: `ItemId` empty means none; the floats may be 0.
- The host records the block with the limb state (the existing accept/validate path).
- A remote client applies the block through the game's own entry: `AttachProsthetic(info, isLoad: true)`
  when `HasProsthetic`, and the clear path when it turns false (the load-time write, so
  no sound and no reattach roll is invented). The apply must run on the client that owns
  the limb too (the host's record is the authority for a refused report's correction, as
  the limb plausibility path already does).
- The colour channels are presentation-only on the owner; the remote copy uses them for
  the same tint the owner sees.

## Family audit

The limb state has one wire message (`LimbStateMsg`), one host handler
(`LimbStateEventHandler`), one host record (`CharacterDataStore`), one client apply
(`LimbApply`), and the clone renderer for the body (`CloneLimbRenderer`). Every one of
them gains the block in the same change, and `LimbStatePlausibility` keeps its rules
for the health fields only (a prosthetic is not a health change).

## Acceptance

1. A host amputates a limb, installs a peg limb on it, and a teammate's client reads
   `hasProsthetic true` with `itemId` naming the peg on that limb.
2. The teammate's limb keeps the owner's numbers for the healing change: the limb read
   shows the prosthetic on the same limb the owner installed it on, not on a neighbour.
3. An owner without a prosthetic reports the block empty and nothing changes on the
   teammate's side.

## Implementation note (2026-11-10)

- The limb message carries the block (fields 25-31) and the owner's capture maps it from
  `prostheticInfo`.
- The clone's apply writes the struct the way the game's save load does
  (`SaveSystem.cs:305-307`), not through `Limb.AttachProsthetic`: that method's first line touches
  the Steam achievement manager and throws a `NullReferenceException` in an IP-direct session
  (measured 2026-11-10 on the guest's own client), and its `isLoad: false` branch reattaches the
  limb and plays the apply sound — a clone is not installing anything.
- The reading fixture is `tools/acceptance/recipes/limb-prosthetic4.cs` (`mode=set|read`): the
  owner's client sets the struct on its own limb; the reading lists every body's prosthetic limbs.
  A field write alone does not report: the limb report fires from the game's own limbs' events, so
  the reading needs a native wound on the owner's limb after the set.

## 2. Setups the session will run

Three clients, one world: host on the physical machine, guest in the Sandboxie guest box, the alternate
client in the second box; all enter through the Online UI's own controls, driven in-process. The order
is frozen: the layer descent and the new run each replace the world, so everything that needs the old
one runs first.

**S0 — one world, three clients.** Read each client's own run baseline (`generation-read`: run 1,
layer 0 expected), the object census (`world-object-census`) and the runtime-entity tables
(`runtime-entity-tables`) as the baseline every later read is compared against, and smoke the new probes
(`generation-read`, `world-object-census`, `wire-generation-probe`, `block-report-reset`,
`generation-forge`) on a live client before any row depends on them.

**S1 — same generation, before any descent (the block family's live half).**

- **W row 7.** Arm `wire-generation-probe kind=block` on the host, have the guest mine a block at an
  absolute cell, read the probe back: the decoded `BlockPlaced`/`BlockDamaged` frames carry the guest's
  own run/layer, read off bytes the host received — the stamp is on the wire, not added by the caller.
- **W row 1.** Arm the host's inbound blackout (`net-receive-blackout mode=on`), have the guest mine a
  second block (both its reports are swallowed), disarm, then read the guest's pending counts — the
  block, damage and break-drop tables hold the lost reports. Call `block-report-reset block=1 damage=1
  drops=0` on the guest: the product's own reset seam (the boundary path a world apply runs) drops the
  air write's pending re-send, so the surviving drops carrier is what the fallback re-reports. The host
  must take the lost-air-write verdict: `accepted as this generation's lost air write … registered +
  relayed`, the guest's pending break-drop count returns to 0 and its drops are not destroyed.

**S2 — the layer descent with one member left behind (the stale sender).** Arm the guest's inbound
blackout, run `game-console command=skiplayer` on the host: the host descends to layer 1 and the guest
never follows — its own baseline still reads layer 0 while it keeps playing and keeps sending, so every
report it makes is a REAL wire frame stamped with the previous generation.

- **W row 2.** The guest mines a block: the host refuses it stale (the gate line names both
  generations), the new layer's cell is untouched, and the guest's drops are rolled back on the breaker.
- **W row 4.** The guest partially damages a block: the live delta is refused stale, and when the
  fallback re-reports the absolute row set (`BlockDamageReport`) the host refuses that too, with no
  answer; the host's damage table for the cell does not change.
- **W row 6.** The third client (which followed the descent) mines a block: the host accepts and relays
  it to the guest, the guest refuses the relay as stale and does not answer it, and its own outstanding
  report stays outstanding.
- **AF row 2.** The guest spawns a vanilla runtime entity: the host refuses it whole, answers
  `StaleGeneration`, the guest's pending report ends and its local copy is removed, and no third client
  materializes it.
- **AF row 7 (relay half).** The third client spawns a runtime entity: the host accepts and relays it to
  the guest; the guest refuses the relay silently — nothing materialized, no answer.
- **AF row 7 (absolute-table half) / AF row 1 (natural half).** The host's ~60 s repair group reaches
  the guest: the runtime-entity snapshot and the trap layout are refused whole with the refusal line
  naming both generations, and nothing of them is applied.

**S3 — the shapes only a probe can produce (W rows 5, 8; AF rows 1, 4, 7, 9).** All of these go through
the product's own receive seams (`generation-forge`), and every verdict is read from the product's own
logs, tables and censuses:

- **AF row 1.** A trap-layout snapshot stamped with another generation is refused whole by the guest;
  the object census is unchanged. The unstamped control on the same entries is applied (`aligning: 1 to
  materialize, 0 to destroy`) and the census rises by one — the A/B pair the row needs.
- **AF row 7 (stale table).** A runtime-entity snapshot of another generation is refused whole before
  any entry is applied.
- **AF row 4.** An unstamped entity creation report is accepted by the host — the pre-stamp behaviour,
  no rejection answered — and an unstamped trap layout is applied by the guest.
- **W row 8.** On a cell the host still holds, an unstamped break report is refused without a generation
  proof (the pre-stamp conservative verdict), while an unstamped air write is applied: UNKNOWN is never
  treated as current, but the pre-stamp path is unchanged.
- **AF row 9.** The guest (still stale) spawns two vanilla creations into the SAME cell — two distinct
  creation keys in one cell. With both reports outstanding, a stale rejection for the first key is
  handed to the guest's own receive seam: only that key's pending report ends (2 → 1), the second stays.

**S4 — re-entry convergence (AF row 5).** The guest re-enters the world in place (`leave-world` →
`open-window` → `goto-page home` → `click home.leave` → `join-lobby <same id>`); after the entry edge
applied the new baseline and the absolute tables, all three clients' object and runtime-entity censuses
agree — nothing of the previous generation materialized into the new one.

**S5 — session end and a new run (W row 5).** All three leave the world; the host starts a new run
(run 2). `generation-read` reads the new epoch, and a report stamped with the old run's baseline is
refused stale — the identity resets with the run baseline and there is no cross-run attribution.

## 3. Capability boundary

- **The in-flight crossing is not stageable on this machine.** `net-receive-blackout` parks a client's
  inbound dispatch (it drops every frame in the window; it cannot hold one and release it after a
  descent). Every "a stale frame arrives after the generation moved" shape is therefore staged in the
  two forms the product itself makes possible: a genuinely stale SENDER (a member the blackout kept on
  the previous baseline — its reports are real frames carrying an old stamp), and the product's own
  receive seams for the frames only a hold-and-release or a pre-stamp peer could produce. Named as a
  limit on W rows 1, 5 and 8 and on AF rows 1, 4, 7 and 9.
- **The deployed peers always stamp.** An unstamped frame cannot be produced by a peer, so the
  no-stamp half of the gate is handed to the receive seam (W row 8, AF row 4) and named as a limit.
- **W row 1's air-write loss is produced by the host's inbound blackout**, and the air write's pending
  re-send is then removed with the product's own `ResetPendingBlockReports` (the boundary path a world
  apply runs), because the production wire cannot drop exactly one of the two same-tick frames. The
  drops carrier that survives is the guest's real pending report, carrying real item ids and state.
- **Send-path stamping is proven at frame level** by `wire-generation-probe`, which subscribes to
  `PacketReceiver.MessageArrived` and decodes with the product's own `NetPacket.DecodePayload`: the
  stamp is read from bytes the receiver actually received. Named as the method, not a limit.
- **The descent is the game's own debug entry** (`game-console command=skiplayer`), not a natural
  descent; the new run is the driver's own `start-run`. Both are named on the rows that use them.
- The probes run against the deployed artifact in the live session; none of them changes the product's
  code, and every verdict is read from the product's own tables, logs and censuses.

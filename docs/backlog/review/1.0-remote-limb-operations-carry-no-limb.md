# 1.0: a remote limb operation is refused for carrying no limb

## What the player sees

The doctor opens a patient's medical view, picks the wounded limb, and releases a bandage on
it. The bandage is consumed from the doctor's hand — and nothing happens on the patient. The
patient's limb stays as it was; no error reaches either player's screen.

## The reading (2026-11-11, release build, sandboxed offline IP-direct session)

- The doctor released a bandage on the displayed limb: `remote-medical-release item=bandage
  limb=0` answered `ok: true, slot: 0, limb: 0, limbLookingAt: 0`.
- The host log refused it:
  ```
  [MedicalOps3] refused start for 1 on 13486974461430123824 (Bandage): Target limb not found.
  ```
- The patient's own client answered the request and said why:
  ```
  [MedicalTargetCheck] answered request 2 for 1 (Bandage limb -1): Target limb not found.
  ```
  The start request reached the patient with `limbIndex = -1`.
- The validation that refuses it: `MedicalTargetBodyValidator.TryValidate` treats
  `limbIndex < 0` as "target limb not found"
  (`src/CasualtiesUnknownOnline.Runtime/Session/PlayerInteraction/MedicalTargetBodyValidator.cs:56-59`).

The topical path is unaffected on the same session: paincream measured 10.00 ml on the
requested limb and the patient's `disinfectionTime` rose from 0 to 293.88
(`docs/evidence/acceptance/1.0-regression-1-medical-panel.md`).

## Why it matters

Every limb-scoped remote medical operation runs through the same start request — bandage,
splint, tourniquet, amputation, dislocation, shrapnel removal. On 1.0 they are all refused, and
the refusal is silent to the players: the item is spent, nothing heals.

## Design

The surface is the medical view (`docs/design/mechanics/medical-view.md`): the doctor picks the
patient's limb and drops a treatment on it; the game's own `PlayerCamera.ApplyWoundItem` runs the
item's `useLimbAction` on the selected limb. The remote form must reach the same chain on the
patient (`docs/design/game/medical.md`).

1. The doctor's action: open the patient's medical view, select limb 0, release a bandage on it;
   the bandage leaves the doctor's hand and the patient's limb should be treated.
2. The game's own chain: `PlayerCamera.ApplyWoundItem` → the item's `useLimbAction` with the
   selected `Limb` (reversed: `Item.cs` bandage useLimbAction; `Limb.cs` health fields).
3. How the remote case reaches it: the doctor's start request names the limb's index; the
   patient's own client resolves that index and runs the same native action. On 1.0 the request
   arrives with index -1, so the patient's validator refuses before any native action runs.

## The topical half (2026-11-11, the suite's `medical-dose` case)

The suite's second case, `medical-dose`, exercises the same session from the code side and reads
`0 → 0` for the member's `disinfectionTime` after a released paincream:

- host `item-provide type=paincream mode=create` → `instanceId 3062311682049, slot 0, picked true`;
- the host log's measurement line: `[MedicalView] measured 10.00 ml from paincream's own native
  limb action for 13486974461430123824 limb 0 (id 3062311682049).`;
- the member's own `limb-read source=local limb=0` reads `isHead: true, disinfectionTime: 0`
  before AND after the release (`skinHealth 4.323, pain 24.352, infectionAmount 100`);
- the member's log has no `[ItemUse] local body received … topical stack(s)` line for this run;
  it shows the cream materializing as a standing item at `(-0.7, 490.0)` instead.

The earlier manual batch's dose DID land (`skinHealth 1.397, disinfectionTime 298.602`), so the
difference is either the limb the release names (the display's limb order may not be the member's:
limb 0 is the head here) or the item's arrival state (the create-then-release ordering in one
frame; an earlier attempt was refused as `[ItemUse] refused: 1 has no usable consumable`).

A direct probe on a non-head limb (2026-11-11, the same session): created a cream
(`3070901616641`), opened the view, read the member's limb 3 (`skinHealth 100, pain 0,
disinfectionTime 0`, `isHead false`), released `remote-medical-release item=paincream limb=3`
(`ok, limbLookingAt 3`), read the same limb after 900 ms — `skinHealth 100, pain 0,
disinfectionTime 0`. The host measured `10.00 ml … limb 3 (id 3062311682049)` (the measurement
resolves the cream already in slot 0), and the member's log carries no `[ItemUse] local body
received … topical stack(s)` line. So the miss is not the limb index: the measured dose never
reaches the member's own apply.

## The host side (read 2026-11-11)

`RemoteMedicalOperationHandler.TryStartRemoteTopicalUse` calls
`_domains.PlayerInteraction.SendUseRequest(target, itemInstanceId, limbIndex, doseMl)` and only
then logs the measurement (`RemoteMedicalOperationHandler.cs:231-235`) — so the request did leave
the adapter. On the host, `PlayerItemUseService.SendUseRequest` (host role) calls its own
`HandleUseRequest`, which runs `PlayerItemUseExecution.TryExecute`. Every refusal inside
`TryExecute` logs a Warning or Info line, and a success logs `[ItemUse] {User} used …` at line 381
— **none of those lines exists in the host log for either probe**. The only silent returns on that
path are `HandleUseRequest`'s `user == target || user == 0 || target == 0` guard
(`PlayerItemUseService.cs:120-125`) and the role/session guard above it (`:115-118`).

Next probe: instrument `HandleUseRequest` with one Info line naming the role, session-active,
in-world and the three ids, run the release once, read the line, and remove the instrument. If the
line does not appear at all, the request never arrived (the host's own `SendUseRequest` path is
the suspect); if it appears with `target == 0` or `user == target`, the adapter passes a wrong
target.

## The probe round (2026-11-11 02:20, the instrument's reading on the release build)

The cause of the stuck guest was the boxed install's STALE build: the host refused its handshake
by name (`CuoBuild (host 0.1.0+0b1018272… vs 0.1.0+77687…)`). After the box's plugin folder was
synced from the desktop install (quit the box first — its DLLs are locked) and the clients
relaunched from the release install (the launcher with the release install as `-GameDir`),
the guest joined with `active: true`, the host logged `World join sent to 1 member(s)`, and the
guest read `inWorld: true`.

With the session live, the release was run on limb 3 of the member (`remote-wound-special
mode=open target=8844190639670963861 limb=3` → `opened true, viewOpen true`; `remote-medical-release
item=paincream limb=3` → `ok, limbLookingAt 3`). The host log then read:

```
[ItemUse] host received a use request from 1 for 8844190639670963861 (item 1649267441665, limb 3, dose 10.00
[ItemUse] 1 used paincream (id 1649267441665) on 8844190639670963861; destroyed=False.
[MedicalView] measured 10.00 ml from paincream's own native limb action for 8844190639670963861 limb 3 (id 1649267441665).
```

and the member's own client read `[ItemUse] local body received 1 topical stack(s) from 1 (limb 3).`
— the limb index arrived as 3, the host used the item, and the member applied the dose. So the
"no limb" hypothesis does not hold on this session: the earlier failure (the target check answering
`limb -1`) needs its own re-read — the member in that session was a late joiner (a new character
after the continue), and the display body's limb mapping may have been the state that produced -1.
The next step is to reproduce that state deliberately (a member who joins after the continue) and
read whether the release still carries -1.

## What has to be found

1. Where the start request's `limbIndex` is filled on 1.0 (the doctor's side) and why the
   displayed limb's index arrives as -1. The 1.0 limb list may expose the index differently
   (the demo's `Limb.index` vs the release's fields), so a value the adapter used before may
   now default to -1.
2. Whether the topical path's limb resolution (which works) and the limb-operation path share
   the same resolution; if they do, the difference is in how the request is built, not in how
   the limb is named.

## Acceptance

1. On a two-client session the doctor releases a bandage on the patient's limb 0; the patient's
   limb changes by the bandage's own effect, and the host log carries no "Target limb not found".
2. The same for a splint on a fractured limb: the patient's limb shows the splint.
3. The judge is a reading on both clients, not a screen.

The member's own client then read limb 3: `skinHealth 100, disinfectionTime 262.163` - the dose landed on the patient's screen, which is the row the medical-dose case asserts (a rise of at least 200).

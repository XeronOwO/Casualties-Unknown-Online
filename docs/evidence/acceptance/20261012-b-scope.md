# Batch 20261012-b — scope and acceptance plan

The acceptance plan for batch `20261012-b`, written before its session (workflow §3): the ticket set, the
setup the session runs, the row-level classification and the capability boundary the verdicts must respect.

- Tickets in the batch, both code-complete and waiting only on a live session:
  - `docs/backlog/done/call-context-scope-leak.md` — rows 1–4: the frame that leaked a `CallContext`
    scope, the bound that refuses instead of throwing, and the recovery on both peers.
  - `docs/backlog/done/mod-item-with-no-declared-tags-throws.md` — rows 1–2: a tagless declaration is
    created, dropped, replicated and held with no `ArgumentNullException`, and the game's own `HasTag`
    answers for its derived array. Its row 3 is "the amplifier half's own row, once decided", which is the
    sibling ticket's rows, judged in this same run.
- Commit under test: `ab246540` — the commit that made the guard own the release deadline (the frame
  boundary) and turned the depth bound into a refusal. No `src/` or `tests/` change is expected from the
  batch itself; one probe proved reusable and was promoted under `tools/acceptance/recipes/` before the
  batch closed (`item-has-tag.cs`), and the record names the commit the deployment was built from.
- Artifact: `CasualtiesUnknownOnline.dll`; `tools/verify-deploy.ps1` is run in this batch and its output
  captured before any client starts.
- Dependencies: `tools/acceptance/preflight.ps1` (11 present, exit 0) and `session-environment.ps1 -Mode
  status` (the CUO tree active, no game process), both captured into the batch directory before the clients
  start. No third-peer row is claimed, so the alternate sandbox is not launched.
- Session: **one world, two clients** — host on the physical machine (launched through Steam, so Steamworks
  initialises), guest in the primary sandbox.
- Artifacts: the batch directory under the local artifact area, cited by file name only.

## 1. Why this is one batch

The two tickets meet on ONE mechanism. `ItemInfo.actualTags` is the derived array the game's own item-table
pass fills; a definition injected after that pass owns the write, and one that declares no tags used to
leave it at the CLR default. The tagless ticket fixed the array; the scope ticket fixed what a game-side
throw inside a patched frame does to CUO's call-identity stack. The second ticket's own reproduction is
"make the array absent again", so the probe that measures the amplifier is also the exact defect state the
first ticket is about. One world with two clients serves every row: each client runs the leak probe on
itself (the recovery is per process), and the tagless fixture is created on one peer, replicated to the
other and held on both.

## 2. The fixture, and what the run does to it

- The example mod is **not** part of the product's deployment: `tools/deploy.ps1` ships no
  `CasualtiesUnknownOnline.ModExample.dll`. The run places THIS tree's build output into the install's
  `plugins` tree for the session, records the file identity it placed, and removes it at the close. The
  primary sandbox carries no `plugins` tree of its own, so both clients load the same file.
- `example.placebo` is the fixture by design: it declares `Usable` and **no** tags, and the file's own
  comment says adding a tag there would retire the only live case that proves the empty declaration legal.
- The leak itself is injected by the run through a committed probe
  (`tools/acceptance/recipes/call-context-scope.cs`): `break` nulls the hand item's derived tag array
  through reflection — the state a tagless declaration reached by declaring no tags (the game's own
  `Body.HandleVisuals` then asks `HasTag("gun")` of the hand item once per frame) — and `restore` puts the
  array back through the game's OWN `ItemInfo.SetTags()`. Nothing under `src/` is touched, and the probe
  reads the guard's own state instead of a stack.
- The tagless definitions are read through a probe this batch promoted: `item-has-tag.cs` reads one
  definition out of `Item.GlobalItems` and asks it the two questions the game's own callers ask.

B5's expectation is an **absence** (`zero ArgumentNullException`), so it is read from its mark through at
least one full periodic cycle of the mechanism that can emit it: the item sits in a hand slot across

(`workflow.md` §6).

## 4. Order of the run

1. Preflight + `session-environment.ps1 -Mode status` + `verify-deploy.ps1`, captured into the batch
   directory before anything starts.
2. Build the tree; place this tree's `CasualtiesUnknownOnline.ModExample.dll` into the install's `plugins`
   tree and record its identity.
3. Start the two clients serially (the sandbox's Steam first, since it was cold), one at a time, judging
   each by its own evaluator endpoint.
4. Lobby + join + start run; confirm `inWorld` on both.
5. Run the leak probe on the host: mark, `read`, `break`, `read`, one `pant-sound bark` (a later
   scope-entering path), `restore`, `read`; then the same sequence on the guest. Count the window.
6. Read the whole run's `CallContext` lines per client (the rolling log is this run's own file).
7. Create the tagless item on the host, hold it, drop it; read the peer's own `[ItemSpawn] materializing`
   line; pick it up on the peer, hold it, drop it, and take it back on the host — B5's created / dropped /
   replicated / held, in both directions.
8. Read each client's `Item.GlobalItems` entry through `item-has-tag` (B6), with `example.dressing` as the
   declared-tag control.
9. Close both clients cleanly, remove the fixture DLL and re-read the removal, harvest the lessons, write
   one record per ticket and move the tickets per the verdicts.

## 5. Capability boundary

- Two clients in one world. No third-peer row is claimed, so nothing here is judged from a third view.
- The leak is injected by the committed probe and the injection is declared in each record; the run does
  not claim that a game-side throw of this shape occurs unprompted in ordinary play.
- B4's "the rest of the session" is this session's remainder: the cross-peer item handover above runs
  AFTER both clients have leaked and recovered, and both endpoints are read again at the end.
- Ad-hoc probes stay evals of the same channel; every probe a record cites is written into the batch's own
  artifact directory as its own file, and the one probe general enough to reuse was promoted into
  `tools/acceptance/recipes/` before the batch closed.
- The batch log helper is local to the batch directory (mark by byte offset, read by byte seek, always
  through `FileShare.ReadWrite`), shaped after the earlier batches' helper.

## 6. Exit criteria

- One record per ticket under `docs/evidence/acceptance/`, each naming the batch, the commit under test,
  the deployed artifact identity, one verdict and one evidence pointer per row, the dependencies used, the
  forced setups, the limits and any residuals.
- Transition per §3's verdicts, with the backlog index rows moved in the same change.
- Lessons fold into `docs/acceptance/lessons.md`, machine facts into `docs/acceptance/AGENTS.local.md`,
  and a reusable probe into `tools/acceptance/recipes/`.
- The gates run before the closing commit; the session ends with both clients closed, the fixture DLL
  removed and the machine free.

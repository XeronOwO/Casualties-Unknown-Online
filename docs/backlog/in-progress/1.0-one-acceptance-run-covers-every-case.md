# One acceptance run covers every case

- Status: In progress (2026-11-21) — the split is gone and the first single run is measured (67 cases, 1365.9 s, 45
  passed); the runner now owns the world's lifetime, and the rows that fail on their own readings are being worked.
- Priority: High
- Created: 2026-11-21

## Why

Acceptance had grown two tiers: a "batch" of 39 rows whose `RunsInBatch` was true, and 28 rows that ran "by name" and
were left out of `--suite all`. The split was mine, not the user's. It came from a five-minute wall-time figure I had
derived myself (from the user's much older complaint that a run took "half a day"), and the figure then hardened into
"five minutes is the ceiling" in the rules and in a handoff prompt that later rounds read as an instruction from the
user.

The user's requirement, restated on 2026-11-21:

- Acceptance is **one complete run at the end of the work**, not a fast batch plus a closing batch.
- Five minutes was **the wall time at that point**; when a case is added, the added time must be as small as possible.
  It was never a ceiling, and it never decides which rows run.
- Every row that can run, runs. A row that genuinely cannot run on this machine is named, not silently dropped.

## What changes

- `tests/CasualtiesUnknownOnline.AcceptanceSuite/Suite.cs`: `RunsInBatch` is deleted; `--suite all` selects every
  registered case; `--list` prints name/launch/cost; the report names the registered cases the selection did **not**
  run (so a partial run states its own gap).
- Registry order is the run order, and it now carries the constraints: `world-fingerprint` first (before anything moves
  the world); then the rows that need state the rest of the run consumes (`starting-supplies`, `crafting`, `lockpick`,
  `capability-report`); then the shared-world rows in their existing order; then the three pair-shaping rows last —
  `net-conditions` (lossy link), `host-rule-toggles` (writes host rules), `host-crash-restart` (kills the host).
- The run launches all three clients (`run --all`); two-member-continue reads Steam2 and fails naming the missing
  client when the launch did not start it.
- Rules: `docs/acceptance/AGENTS.md` rule 14 rewritten; `docs/acceptance/workflow.md` "the wall-time reading" rewritten;
  `docs/development/game-update-runbook.md` §6 wording; `docs/backlog/README.md` index row; a lesson in
  `docs/acceptance/lessons.md`.

## Readings

The first single run, `.acceptance/every-2` on `0.1.0+f9da090ee`, 67 cases in 1365.9 s, exit 1: **45 passed, 22
failed**. The failures split into two groups that the run itself separated.

1. **Rows whose world was gone.** Everything after `character-solo-lock` (which leaves the world as its own verdict, at
   12:05:45Z) expected a world the suite no longer had: nine rows failed at `the suite could not join the member to the
   host's session: role=None … page=Home` after their own 53–56 s join budgets (`player-deaths`, `medical-tourniquet`,
   `medical-splint`, `medical-injection`, `medical-cpr`, `medical-shrapnel`, `crafting-outcome`,
   `two-member-continue`, `late-join`), and five failed reading a body that was not in a world
   (`block-place-sound` "the host could not be given metal scrap", `block-break-sound` "the host's own position was not
   readable", `give-container-sound` "the host's body has no position yet", `real-drag` "the host body could not be made
   conscious", `host-rule-toggles` "the refused push was not named").
2. **Rows that fail on their own reading**, whatever the world: `lockpick` "the reading has no number 'uiScale'" (the
   `minigame-live` recipe omits `uiScale` when no minigame is current, so the row's own probe is the first thing to
   read); `medical-bandage` "the bandage did not stop the limb's bleed: before 31.491, after 30.237"; `medical-dose`
   "the member's own client never logged the dose"; `save-continue` "the restore did not apply the 97 geyser types … 96
   row(s) not taken" (the live world held 100); `remote-backpack-refresh` "the open view shows no container".

The world's lifetime is the runner's job, not each case's. `SessionDriver.EnsureLiveWorldAsync` now runs before every
case: two state reads when the pair is live, a rebuild charged to that case's setup when it is not (the host keeps its
run when only the member left, so a member that dropped does not cost a world load).

Focused verification, `.acceptance/world-guarantee` on the same artifact: `player-deaths` PASS 44.3 s (was 53.4 s
FAIL), `block-place-sound` PASS 3.3 s, `real-drag` PASS 3.3 s, and `medical-tourniquet` FAIL 2.8 s on its own
precondition — "no limb of the member's body has a lower-limb chain and can take a tourniquet" — which is a fixture
defect in that row, not a blocked run. Suite wall 96.4 s for the four.

The rows that failed on their own readings were then worked one at a time, and three of the four defects were in the
row's own probe rather than in the product:

- `lockpick` — the aim-correction loop read `uiScale` with the throwing accessor, so a minigame that closed between
  the aim and the read reported "the reading has no number 'uiScale'" as the row's verdict instead of letting the
  existing reopen path handle it. `.acceptance/med-lock`: PASS 26.4 s.
- `medical-tourniquet` — the row scanned the member's limbs without waiting for the body and without healing a body an
  earlier medical row had wounded; it now waits for the body, heals it natively and re-probes when no limb qualifies.
  `.acceptance/med-lock`: PASS 2.7 s.
- `remote-backpack-refresh` — the member's copy of the host's body carries its container marker only after the
  adapter's render tick, so opening the view the instant the body exists read "container 0". The row now re-opens until
  the copy has a marked container (≤10 s). `.acceptance/backpack-wait`: PASS 4.6 s.
- `medical-dose`, `medical-splint`, `medical-injection`, `medical-cpr` and `save-continue` passed on their own once the
  world lived (`.acceptance/med-rest`: dose 7.8 s, splint 2.7 s, injection 7.4 s, cpr 13.8 s, save-continue 45.0 s).

Still failing on their own readings: `medical-bandage` (the wrap minigame reads `didWrap false`, `fill 0`, and the
limb's bleed does not stop: 7.934 → 6.402) and `medical-shrapnel` (three pieces seeded, three remain). `save-continue`
passes alone but failed in the 67-case run with "6 geyser type(s) applied (the archive carried 97) … 91 row(s) not
taken", because the live world had drifted from the cut by the time the row ran — that belongs to
`1.0-the-batch-compares-live-world-state`.

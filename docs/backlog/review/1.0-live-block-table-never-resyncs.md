# A live member's block table can drift

- Status: Review
- Priority: High
- Area: Runtime / world state (block table)

## What the player sees

Two players stand in one run in front of the same spot, and the ground under it differs: one sees a hole where the
other sees a block, or a different block material. The world stays wrong for the rest of the run.

## What the code does today (read, not assumed)

- The host's ordinary live write is already broadcast: `WorldEventSync.OnBlockSet` calls
  `BroadcastBlockPlaced` for a non-generation, non-remote `SetBlock`.
- `WorldStateMessageService.ReportBlockState` records every reported block-state difference in
  `_damagedBlocks`; the set is not limited to damage, it is the host's block-state difference table.
- `BlockTableReconciler` (`IntervalMs = 60_000`) and `WorldStateMessageService.ReconcileBlockTable` send only the
  rows that differ from the last baseline sent to each in-world member. `WorldReportFallbackPump.Update`
  pumps that reconcile every frame.
- The missing piece was **live acceptance evidence**: a write that the member never hears through the live
  event path, followed by the 60 s fallback carrying exactly those rows.

## Acceptance evidence (2026-11-15, deployed `0.1.0+ce69cd657` unless noted)

- `block-reconcile` on a fresh pair: the host table's two adjacent cells were forced from `14` to `0` through the
  acceptance driver's `block-force` action, which writes the table and records the difference without calling
  `SetBlock`; the member's own reads were `14`/`14` before the pump and `0`/`0` after it (22.6 s, host/member
  errors `0/0`). The host logged
  `Reconciled 2 block row(s) to <current member>` after the member's frame; the log is polled because the
  network frame reaches the member before the host's file line is flushed.
- `world-fingerprint` (entry) and `world-fingerprint-after-mutation`: both clients' whole-table totals agree at
  run entry and after a break from each side; both PASS on the same build.
- `BlockTableReconcilerTests` (5 unit facts): an unchanged table sends nothing, a changed table sends only the
  changed rows, every member has its own baseline, and a reset clears it.

## Acceptance rows

- [x] A live member whose table was made stale by a host-side write realigns within one reconcile interval, read
      from both clients' own `block-read-at` on the same cell.
- [ ] A reconcile with no changed rows sends no message (the unit fact exists; a live wire-counter reading is not
      yet part of the case).
- [x] A reconcile carrying N changed rows sends exactly those rows (the host line says `Reconciled 2 block row(s)`
      for the two forced cells).
- [x] The generation streams stay identical (entry and post-mutation whole-table fingerprints agree).

## Remaining before Done

The idle/no-message row needs a live wire-counter reading, or an explicit design decision that the unit fact is
the right level for an idle property. Do not move this ticket to `done/` until that row has a reading or a named
decision.

## What must not change

- The block table stays the host's (one table, the game's own capacity and order).
- A break and a placement keep their existing messages and verdicts.
- The fallback is invisible when everything works: no extra traffic on an idle run.

## 2. Setups the session will run

Three clients, one world: the host on the physical machine, the guest in the Sandboxie guest box,
the alternate client in the second box; all enter through the Online UI's own controls, driven
in-process.

- **A — menu-side capability spikes.** With both clients up and before any world entry: S1
  `net-receive-blackout mode=status`; S3 `block-report-pending-count` (resting zeroes); S4
  `block-report-cap-probe` plus the member's own log lines; S3 again (the isolated probe must
  leave the live table at zero); S2 the blackout `on` / bounded single step / `off`.
- **B — in-world swallowed reports.** One shared world: the blackout arm around each scenario in
  order — row 1 (mine), row 2 (place), row 3 (environment air write), row 4 (first-writer-wins),
  row 10 (partial damage then break) — with a `mode=off` and an `armed=false` check between rows.
- **C — world-entry path spike.** The member-side invite shape (a member in the lobby, the host
  leaving and continuing the run) verified by reading `state` and the host's entry log lines
  before rows 6 and 9 are attempted.
- **D — row 6 in-place re-entry.** Marked cells on both sides, the member leaves the world, the
  host stays (or leaves and continues the same world), the member is invited back in. The layer is
  never switched; a fresh layer is not this row.
- **E — row 9 solo → lobby → join.** The host starts alone, mutates a marked cell (an accumulated
  diff), creates the lobby, the member joins, the host leaves and continues the same run; the
  member's entry must carry the accumulated cell exactly once.

## 3. Capability boundary

Established by this batch's own spikes before any row is judged, and by earlier batches otherwise.
What this batch adds is the inbound blackout, which cuts exactly the packet plane's inbound
dispatch on the armed client: `PacketReceiver` is the only subscriber of the router's
`MessageReceived` event and the transport dispatches every received frame immediately, so an
armed window is the production lazy-P2P swallow — the peer's send reports success and the armed
side never receives the frame. What remains out of reach:

- The live pending table's own cap evidence (row 8) — isolated instance instead, named above.
- Precise earthquake timing (row 3): the window is armed right after the host's broadcast and is
  short; if the run cannot stage it, the row is `unproven`, never a plain mine standing in for an
  air write.
- Every row here is a `machine` row: a state, a count, a log line or a converged cell read by the
  in-process probes.

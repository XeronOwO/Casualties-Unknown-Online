# A host leaving the world strands the members in it

- Status: Done — the host's leave broadcasts `NetMsg.RunEnded` (after the leave actually ran) and the member
  leaves through its own exit path; read on the real pair 2026-11-14 (below).
- Priority: High
- Opened: 2026-11-14
- Reading: the acceptance pair, `leave-world` on both clients

## What happens

The host leaves its own world through the game's own menu return (the driver's `leave-world` calls the
same path). Afterwards:

```
host   page=Home transport=IpDirect role=Host  inWorld=false   items: 0
member page=Home transport=IpDirect role=Guest inWorld=true    items: 21 (rb|world)
```

The host sits at the menu with its session still up; the member believes it is in a world that no
longer exists anywhere. The member's window is the Home page, so its world objects are invisible and
its `Item.Update` reads a world it cannot have.

## Why it is a defect and not a fixture artefact

Nothing in the session layer carries "the run ended": `src/CasualtiesUnknownOnline.Runtime/` has no
run-end message (the only "run ending" type is `RunEndingTracker`, which judges the game's own ending
conditions). `WorldEntryFanout` sends the world facts to a joining member; nothing sends an end.

## What must be decided

- **Option A (recommended)** — a host leaving the world ends the run for every member: the host's own
  menu return publishes a run-end relay (source-excluded), each member calls the game's own
  return-to-menu path, its world objects unload with the scene, and the session stays up so the host
  can start another run without re-inviting.
- **Option B** — the host's menu return ends the whole session: every member ends the session, the
  host's role goes `None` by the existing teardown rule, and the next run is a fresh session. Simpler
  but throws away the lobby, the display names and the member identities the session had.

A is recommended because it keeps one session across runs, which is what the suite's own
`role-clearing` row already proves works, and because the host's intent ("I am done with this run")
is not the same as "I am leaving the multiplayer session".

## What must not change

- A member's own `leave-world` stays a local act: it leaves the run, not the session (the ghost-role
  rule and `role-clearing` depend on it).
- The game's own ending conditions (death, finale) keep going through `RunEndingTracker`; this ticket
  is about the host's voluntary exit.

## Design

Read from `docs/design/cross-cutting/saves-and-recovery.md` (what a session owns vs what a run owns)
and `docs/design/mechanics/world-interaction.md` (the world's lifetime on a client).

## Acceptance rows

1. A fresh pair in a world; the host calls `leave-world`; within 5 s the member's own `state` reads
   `inWorld false` and its `broken-items` recipe answers `count 0`.
2. The same pair: the host starts a second run; the member joins it without a new session and reads
   `inWorld true` (the `role-clearing` shape, now with a host-initiated end).
3. A member's own `leave-world` sends nothing to the host (the host's `state` stays `inWorld true`).

## Implementation plan (2026-11-14)

- the game's one leave path is `PlayerCamera.ToMainMenu`; `src/CasualtiesUnknownOnline.GameAdapter/Patches/PlayerCameraToMainMenuPatch.cs`
  already observes it for the run-menu-return policy, so the host's exit is already visible on the host.
- the new wire: a `RunEndedMsg` (source-excluded broadcast) published by the host when `ToMainMenu`
  runs while it is the host of a session that had a live world; the member's handler calls its own
  `PlayerCamera.ToMainMenu()` (the same path the driver uses), so the game unloads the member's world
  and its objects with it.
- guard: a member that is already out (its own leave) ignores the message; the host ignores its own.
- unit facts: the message is published once per world exit by the host, never by a member; the member
  handler calls the leave path exactly once.

## Where the code goes (read 2026-11-14)

- `src/CasualtiesUnknownOnline.GameAdapter/Patches/PlayerCameraMenuExitPatches.cs` intercepts
  `PlayerCamera.ToMainMenu` and defers to `PatchBridge.Impl.TryDeferMenuReturn`;
  `GameAdapterBridge.TryDeferMenuReturn` records the intent through
  `domains.MenuReturn.Request(domains.Session.Role, RunMenuReturnOrigin.PlayerLeave, inWorld: true)`.
- `src/CasualtiesUnknownOnline.GameAdapter/Run/RunMenuReturnCoordinator.cs` holds the request and
  performs the leave in `Leave()` (`camera.ToMainMenu()`); the caller is `SaveCutSeam` (the cut and
  the leave are one operation). The host's publish therefore belongs AFTER a successful `Leave()` —
  the world is already leaving, so the message cannot be read as "the host wants to stay".
- the member's handler is the same request path the session teardown uses: a run-end message asks
  `MenuReturn.Request(role, HostRunEnded, inWorld: true)`; the seam then writes nothing (a guest's
  answer is `MenuOnly`) and performs the leave, which unloads the member's world and its objects.
- the runtime needs one new broadcast method (source-excluded) plus a `RunEndedMsg`; the member's
  dispatch raises an adapter event that the binder subscribes to once, beside the teardown handler.

## The live reading (2026-11-14, `0.1.0+8dec04b63…`)

Deployed with `-Acceptance`, the box's plugin folder synced (36 files), the pair launched
(`launch-clients.ps1 -OutDir .acceptance\runend -AllowOfflineSteam`: guest endpoint up 19:22:52,
endpoints ready 19:22:52, host/guest up 19:22:56).

- Both clients in world: `"inWorld": true` on the host and on the member.
- The host performs the game's menu return (the driver's `leave-world`, the same `PlayerCamera.ToMainMenu`
  path the player uses): `{"ok": true}`.
- 5 s later: the host reads `"inWorld": false` and the MEMBER ALSO reads `"inWorld": false` — it left the
  world with the host instead of standing in it.
- The member's own log carries the decisive line:
  `[RunEnd] the host's world ended (run 0) — leaving it.` (`RunEndedHandler`), and the host's log carries
  no `[RunEnd]` line (the host never receives its own broadcast).
- The seat check: `role-clearing` PASSED on the same deployed pair (`session the suite started a fresh run`,
  `member the suite joined the member to the host's session`, `role-clearing PASS ok`).

The ticket's original reading (2026-11-14, before the fix) was the host at `inWorld=false` and the member
still at `inWorld=true` with 21 item objects under the departed host's clone; that is what the broadcast
removes.

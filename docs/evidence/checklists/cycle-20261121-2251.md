# Delivery checklist

Fill every box, then run `tools/check-delivery.ps1`. Each box needs the literal ` — evidence: ` followed by the evidence.

- [x] Design comprehension — evidence: the driver protocol already carries an eval budget (`timeoutMs`), but the budget is enforced by the client, so a client whose game thread never reaches the eval cannot fire it; the suite had no deadline of its own.
- [x] Native parity — evidence: harness-only change; no game behaviour and no product path is touched.
- [x] Native parity probe — evidence: the reading is the stuck run itself — three clients at one core each, both logs silent, the batch inside one member recipe for ten minutes.
- [x] Entry mapping — evidence: one entry, `DriverClient.EvalOnceAsync`, which every case's driver call reaches through `EvaluateAsync`.
- [x] Mechanism inventory — evidence: the eval frame, the client-side budget, the suite-side `ReceiveAsync` loop; the fix sits on the third.
- [x] Whole-family audit — evidence: every request goes through `EvalOnceAsync`, including the reconnect retry; both call sites now name the deadline failure.
- [x] Self-check table — evidence: the ticket's new section records the hang, its log lines (no output on either side) and the two readings that separate a busy client from a blocked one.
- [x] Verification design — evidence: build 0, 6749/6749 units, 836/836 gates, `dotnet format` verify 0; the next full batch exercises the deadline and must fail a row rather than hang.
- [x] Plan approved by the user — evidence: the standing instruction is one run over every case; a batch that produces no result violates it.
- [x] Structure review done — evidence: the deadline belongs to the client object that owns the socket, not to each case; cases keep their own budgets.
- [x] Build + dotnet format + dotnet test normative gates pass — evidence: build 0, format verify 0, 6749/6749 units, 836/836 gates.
- [ ] Release-cycle deployment/acceptance
- [ ] FORBIDDEN — never check this box; checking it fails the delivery gate

# 1.0 run settings reach the baseline and the save (2026-11-10)

Batch `20261110-b`, the 1.0 release install as the host (a world is running with one member over
IP direct). No code changed; the question was whether the release's new run settings are in the
dictionary the baseline captures and in the save's own run row.

## The live dictionary

`tools/acceptance/recipes/run-settings-keys.cs` reads the game's static
`WorldGeneration.runSettings` through reflection and lists every key and value.


## The save's run row

`/save` on the host took the mid-run cut
`w-20261109-d1ec/backups/mid-run-20261109-170614.cuoz`; its `run.json` carries the kernel's run
row with the same settings list:

```json
{ "kind": "run", "run": { "runId": 1, "biomeDepth": 0, "runSettings": [
  { "key": "unchipped", "kind": 3, "boolValue": false },
  { "key": "endless", "kind": 3, "boolValue": false },
  { "key": "baselootdensity", "kind": 2, "floatValue": 1.5 },
  { "key": "lootmultiplier", "kind": 2, "floatValue": 1 },
  { "key": "basetrapdensity", "kind": 2, "floatValue": 0.349999994 },
  { "key": "trapincrease", "kind": 2, "floatValue": 0 } ] } }
```

`kind` is the value type (2 float, 3 bool); the 1.0-only `endless` is carried as a typed entry.

## What this settles

- The baseline captures the game's dictionary wholesale, so a run setting the release adds is
  carried without a code change (acceptance row 1).
- The cut writes the same list into `run.json` (row 2).
- The restore reads the same list — read in the earlier parity batch, where a continue brought the
  rarity multipliers back and the next layer generated from them (row 3).

## Limits

- The batch reads the default values; a non-default value for a 1.0-only key was not set, because
  the only fixture writes floats and several of the new keys are booleans. The list path is the
  same for every key; the value-typed entry is visible in `run.json`.

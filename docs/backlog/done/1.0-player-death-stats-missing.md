# Nobody counts a player's deaths

The run records what happened to enemies and items, but not how many times a player died. A host
running a permadeath or revive session has no reading of who died how often; the console and the
Admin page cannot answer the question.

## Design

The observability surface (`docs/design/cross-cutting/observability.md`) and the run's own state
(`docs/design/game/console-and-save.md` — what the run keeps across a cut). A death counter is a
per-player durable fact like the skills already carried by the character snapshot
(`docs/design/cross-cutting/saves-and-recovery.md`).

## The reading (2026-11-14, release build)

`grep 'TrackDeaths|DeathCount' src/` finds nothing; the respawn path logs a revive
(`[Respawn] revived …`) but keeps no per-player count. The reference mod ships `TrackPlayerDeaths` as
a host rule.

## Design chain (2026-11-17)

1. **The player's action and expectation.** A character's brain health reaches 0 (a wound, an explosion, a turret); the
   body stops being alive; a medic revives it, or the run respawns it. The host asking "how many times has this player
   died?" expects the number to belong to that character and to survive a save/continue, like its skills and limbs.
2. **What the game itself runs.** `Body.alive` is `brainHealth > 0f` (`reversing/release-1.0.2/Assembly-CSharp/Body.cs:207-216`).
   The native respawn/revive path changes that value and logs nothing about a count; CUO's own respawn logs a revive but
   keeps no number (the 2026-11-14 reading).
3. **How the remote case reaches the same chain.** The owning client captures its own body into a snapshot
   (`src/CasualtiesUnknownOnline.GameAdapter/Character/CharacterDataSync.cs:283` `Update(Body?)` → `_favouriteMarks.Capture`
   → `src/CasualtiesUnknownOnline.GameAdapter/Character/CharacterDataCapture.cs:32`), reports it, the host stores the
   latest row (`src/CasualtiesUnknownOnline.Runtime/Session/CharacterData/CharacterDataStore.cs:207`
   `SaveReportedCharacterData`), the cut persists it as `SavedCharacter` (`src/CasualtiesUnknownOnline.Runtime/Persistence/SavedCharacter.cs:8`),
   and a restore writes it back (`src/CasualtiesUnknownOnline.GameAdapter/Character/CharacterRestoreApplier.cs:50`).
   So the count rides the one record the character already has.

Decisions:

- **Who judges:** the client that owns the body, from the game's own `alive` flag (an alive→dead edge, never a damage
  guess). The host reads the members' counts from the stored snapshots; a member reads its own.
- **Reset rules:** a new run starts at zero (a new character is alive, so the first frame arms the edge without counting);
  a restore writes the saved count and does not count the spawn; a world entry is never a death.
- **The wire:** `CharacterDataMsg.Deaths` as `[ProtoMember(14)]`. 0 is meaningful (a character that has not died) and an
  old sender's default is the same reading, so no `+1` encoding is needed — unlike the hand slot, where 0 is a legal raw
  index that must be distinguishable from "not reported".
- **The surface:** `/deaths` in the console (`CommandPermission.Anyone`): on the host it names every member with its
  count plus the host's own; on a member it answers that member's own count. The console is the diagnostic/administrative
  surface for a run statistic; a HUD readout is a separate product decision and stays a residual.

## Acceptance reading (2026-11-18)

Case `player-deaths`, artifact `0.1.0+419ff8c936`, `.acceptance/playerdeaths11` — **PASS** (1 of 1, case 16.7 s,
row total 37.1 s, setup 19.8 s, outside-case log errors host 14/0 member 21/0). Verbatim console answers from the
timeline:

- fresh character: `你在本局中已经死亡 0 次。` (member, and the host's own `/deaths`);
- after the first death: 1; after the revive: still 1; after the second death: 2;
- the host asking by member id: `Guest 在本局中已经死亡 2 次。`;
- after `/save` → leave → `continue-run` → the member rejoined: member `你在本局中已经死亡 2 次。` and the host's view
  `Guest 在本局中已经死亡 2 次。`

Two product defects were found and fixed by running it, both recorded on the commits:

1. The member's session-end reset zeroed the counter, so its still-living body told the host 0 and the report replaced
   the row the continue had just restored (`65e373b4b`): the count now survives the session and resets only where a new
   character is granted supplies.
2. The next-level respawn rebuilt the stored row through `TraderRecruitPolicy.PrepareRevive`, which dropped the field
   (`419ff8c93`): the revive copies the count now, and a unit test pins the copy.

Residual: the count is console-only; a HUD or scoreboard readout is a product decision that stays open.

## Acceptance rows

1. Two deaths and a revive read a count of two for that player, from the host's own answer and from
   the member's.
2. The count survives a save/continue (it is part of the character's own facts).
3. A new character starts at zero.

# The guest holds a Guest role without a world

- Status: Review
- Priority: High
- Opened: 2026-11-14
- Reading: the acceptance suite's own pair

## What happens

The suite asks the member to join the host's fresh IP-direct run. The member's own state reads
`{"role":"Guest","active":"","inWorld":"","page":"Home"}` and its window offers `home.leave` — it
believes it belongs to a session that no longer exists, and it never enters the world. The host's
roster does not carry it.

## The second reading (same minute)

The guest's `BepInEx/LogOutput.log` is flooded at 17:39 with

```
[Error :Casualties Unknown: Online] [CasualtiesUnknownOnline.Plugin] [Unity:Exception] NullReferenceException
(wrapper dynamic-method) Item.DMD<Item::Update>(Item)
```

so the client whose join fails is also the client whose frame is failing every tick. Whether the
stall causes the join failure or a stale item causes both is not yet told apart.

## The Item.Update flood is the game's own null on a world-less client (2026-11-14 17:47)

- The patch that logs it is ours by design: `src/CasualtiesUnknownOnline.GameAdapter/Patches/ItemUpdateDiagnosticPatch.cs:12`
  `[HarmonyPatch(typeof(Item), "Update")]` calls `OnBrokenItemUpdate` when `Item.Update` is about to
  throw (the contract is named at `IPatchBridge.cs:302`: "Item.Update's nullable dereference is about
  to throw (rb null / no WorldGeneration.world)").
- So the flood means: this client holds item objects whose rigidbody or world is gone — the
  ghost-world shape — and it is the same client whose join fails. The two readings are the same
  defect seen twice.
- Next probe: which objects carry those items on a client at `page=Home` (a leftover world object
  graph), and whether the session end clears them.

## What the flood hangs on (2026-11-14 17:55)

`tools/acceptance/recipes/broken-items.cs` lists the game's `Item` objects and the object each sits
on. On the guest at the main menu it read

```
count 4
waterbottle(Clone)|InvSlot (2)|Character_1|rb|noWorld;
dogfood(Clone)|InvSlot (1)|Character_1|rb|noWorld;
lantern(Clone)|InvSlot|Character_1|rb|noWorld;
trashbag(Clone)|InvSlot (4)|Character_1|rb|noWorld;
```

- The four carried items are still alive, parented to `InvSlot` children of `Character_1`, with their
  rigidbodies, while `WorldGeneration.world` is null — exactly the shape `Item.Update` cannot survive.
- So the flood is the guest's own character object surviving the world on the guest only; the host's
  counterpart is a fresh menu client with no such graph.

## Why it is one item

Both readings come from the same client in the same run; a join fixed on the host side while the
guest keeps throwing would only move the failure.

## What must be decided

- whether the stale role is cleared by the session end (the ghost-role rule of
  `docs/backlog/done/1.0-a-guest-keeps-its-role-after-the-session-ends.md`) and why that rule did not
  reach this state;
- whether the leftover item graph is ours to clear when a world is left.

## Design

Read from `docs/design/cross-cutting/saves-and-recovery.md` (session lifecycle and what a role means)
and `docs/design/game/README.md` (the game's own scenes and objects).

## Acceptance rows (when fixed)

1. A fresh pair, the member joins the host's run: the member's state reads `role Guest, inWorld true`.
2. The guest's log carries no repeating `Item.Update` exception during that join.

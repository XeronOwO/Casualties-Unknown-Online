# 1.0: the host's `/heal @a` leaves the member's body unchanged

## Closed 2026-11-13 — the row reads green on a pair the suite owns

The defect was in the fixture, not in the product: the run that produced the reading below addressed a
member the host's world had never adopted (the member's client still held the previous run's session,
and the suite's join answered "already in a world"). With `EnsurePairAsync` recreating such a member
before the run, the case passed on its own and in the full order:

- the host's answer was the relay's own line (the reminder that the reset runs on the target's client),
- the member's own limb read before the heal `skinHealth 0, bleedAmount 23.571, pain 100, muscleHealth 20.802, dislocated true, broken true`, and after `/heal @a` `skinHealth 100, bleedAmount 0, pain 0, muscleHealth 100, dislocated false, broken false`,
- the full suite read **17/17 PASS in one run** (`.acceptance/suite/report.md`, 2026-11-13 00:30).

The reading kept below stays as the record of what a stale member looks like.

## What the player sees

The host runs `/heal @a`. The console answers that the reset was relayed to the target's own
client. The member's limb stays as it was — no error reaches either player's screen.

## The reading (2026-11-12, release build, two clients over IP direct)

- The suite's `console-heal` case (`tests/CasualtiesUnknownOnline.AcceptanceSuite/Cases/ConsoleHealCase.cs`)
  wounds the member's limb 0 first (`wound-seed limb=0 force=300`), waits until the member's own
  client reports the wound, then the host runs `/heal @a` through the driver's console action.
- The host's log carries the whole relay: `[HealReset] 1 instructed 13636607592635657650 to reset`,
  `[CharacterDataStore] stored 13636607592635657650's reset result`, `[HealReset] 13636607592635657650
  applied the reset` — so the target applied it and answered.
- The member's own client, polled for 15 s after the answer, reads limb 0 as
  `{"ok":true,"source":"local","limb":0,"skinHealth":0,"bleedAmount":0,"pain":83.508,
  "muscleHealth":1.985,"dislocated":true,"dismembered":false,"isHead":true,"infected":true,
  "infectionAmount":23.452}` — the reset's result is gone, and the wound's parts are back.
- The seed is applied by the target's own frame: a heal sent in the same frame lands first and the
  wound reopens over it (the case now waits for the wound before the heal, and still reads the
  damaged limb afterwards), so the deferred parts of the seed outlive the reset.
## What has to be found

1. Whether the member's body is re-wounded AFTER the reset — the seed's deferred parts (infection,
   dislocation) or a character snapshot the reset's own report does not carry.
2. What the member's client does with the reset result it reported (which body it captures, and in
   which frame relative to the seed).
3. Whether a reset's stored result is allowed to be overwritten by the next ordinary snapshot.

## Design

The body-verb service and its relay are described by
[docs/design/cross-cutting/saves-and-recovery.md](../../design/cross-cutting/saves-and-recovery.md)
and [docs/design/game/README.md](../../design/game/README.md): the host owns the verb, the
target's own client executes the reset on its body.

## Acceptance

1. On a two-client session the host runs `/heal @a` against a wounded member; the member's own
   client reads the limb restored within the poll window.
2. The same for `/kill @a` (the shared service's other verb).
3. The judge is a reading on the target's client, not the console's answer.

## Reopened 2026-11-13 01:31 — the fix was a race, not a fix

The full suite read the member's own limb after the host's `/heal @a` answered
`{"ok":true,"command":"console","applied":true,…}`:

- before the heal: `skinHealth 0, bleedAmount 14.954, pain 100, muscleHealth 20.802, dislocated true`
- after the heal: `skinHealth 0.334, bleedAmount 0, pain 83.36, muscleHealth 22.797, dislocated true`

So the reset landed (bleeding stopped, muscle restored) and the wound's own tick re-applied
`skinHealth` and `dislocated` before the case's read. The earlier 17/17 reading was one pass that
happened to land after the tick had stopped — the closure over-claimed.

What the row needs: read `LocalBodyReset.Reset`'s own order against the seeded wound's update — whether
the reset clears the active wound/bleeding state (not only the limb values), and whether the seeded
limb's tick runs after the reset in the same frame. The case stays parked with this reading; it
un-parks when the reset clears the wound state itself.

## The reading that rules the tick out (2026-11-13 01:45)

The case polls the member's own limb every 250 ms for 15 s after the host's `/heal @a`; the failing run
read `skinHealth 0.334, dislocated true` at every poll until the budget ran out. A single wound tick
cannot re-damage for 15 s, so the value is being re-applied continuously: the candidate is the host's
own character snapshot (the host stores the reset result only after the member's
`HealResetAppliedMsg` reports back, and until then its periodic stream carries the pre-heal limb).
`Limb.ImpactDamage` (`reversing/release-1.0/Assembly-CSharp/Limb.cs`) writes the limb fields directly
and leaves no ticking component, which is what makes a stream the likely re-applier.

The next probe: on the member's client, log every `CharacterDataMsg` limb write for the healed limb
during the 15 s window, and in the same window read whether `HealResetAppliedMsg` was sent and
acknowledged — one of the two names the wrong owner.

## The host's own log (2026-11-13 01:47)

The host's log for the same heal reads the whole chain as successful:

- `[HealReset] 1 instructed 15958250133233401398 to reset its own body (instruction …)`
- `[HealReset] stored 15958250133233401398's reset result through the authority path (instruction …)`
- `[HealReset] 15958250133233401398 applied the reset for instruction 1.`

So the host holds the reset result and the member reported it. What the host's log cannot show is
what the member's OWN body holds afterwards — the boxed client's log is written inside its sandbox
tree, and the file read there carries `[LimbEvent]` lines but no `[HealReset]` line for this run, so
the member's own reset trace has to be read from the sandbox's live file (or a driver action), not
from the install path.

The probe therefore moves into the suite: after the console verb, the member's own client reports its
body twice (its own read already does) and the case records the member's log tail (`log-tail`) around
the window, so the member's `[HealReset]` line and any later limb write appear beside the reading.

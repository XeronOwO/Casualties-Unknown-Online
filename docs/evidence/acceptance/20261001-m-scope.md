# Acceptance batch 20261001-m — scope, run plan and row classification

- Batch: `20261001-m` — the save/persistence family, split into four runs because the rows need
  different worlds and player counts: **Run A** (host + guest, one live world), **Run B** (host + two
  guests), **Run C** (a backup/recovery world, host), **Run D** (solo). Machine-only rows are judged
  from the first run's own build/suite step and are named per ticket.
- Tickets in scope (15): `save-layer-end-save-and-restore` (S2),
  `save-mid-run-consistent-cut` (S3), `save-solo-menu-exit-trigger` (S3.6),
  `save-native-run-field-parity` (S3.4a), `save-native-character-field-parity` (S3.4b),
  `save-run-clock-not-sent`, `save-layer-time-not-carried`, `save-multiplayer-restore-and-backups` (S4),
  `save-guest-restore-claim-and-legacy-store-retirement` (S4.1),
  `save-restore-account-surface` (S4.2), `save-new-player-starting-supplies` (S4.3),
  `save-interval-autosave-and-backup-recovery` (S4.4), `world-and-backup-management-surface`,
  `restore-account-arm-release`, `world-determinism-world-fingerprint`.
- Umbrella riders (2, no rows of their own): `save-system-mid-run-and-layer-end` and
  `systemic-save-backup-management` move with the last stage that closes them, when every stage they
  own has passed; this batch records that decision instead of re-judging an umbrella.
- Out of batch, deliberately: every other ticket in `review/`. The medical family (lockpick, wound
  treatment, remote operation minigames), the UI layout family, the sync families and the adaptive
  rate family each need a setup this batch's runs do not build, and a per-family run is the cheaper
  loop (`docs/acceptance/workflow.md` §1). They stay in `review/`.
- Why one batch: every row below is decided by the same artifact, the same deploy and one of four
  sessions; the save system's own acceptance is a Continue-click and a world state, which is exactly
  what the runs produce.

## Capability work this batch needs first (declared before the run)

The save family's scenarios are session-entry and world-setup states the current driver vocabulary
does not reach. These land as tooling before the first run, each with its committed test:

| Capability | What it drives | Why it is the honest path |
|---|---|---|
| driver action `continue-run` | the native Continue entry (`PreRunScript.LoadRun`), the same public method the game's own Load button calls, plus the pre-click `loadButton` state and label | the CUO continue path is intercepted on that method (`PreRunScriptLoadRunPatch`); invoking the scene object's handler is how the existing `start-run` action already enters a run |
| driver action `leave-world` | the game's own "leave the world" action (`PlayerCamera.ToMainMenu`), the single funnel the menu-return cut is taken behind | the world is destroyed by the scene load, so the cut has to be deferred by the patch exactly as a player's leave is |
| driver action `console` | one CUO console command line through `CommandConsoleService.TryExecute` (`/save` is the player's own mid-run trigger) | the console is the only player-facing save trigger; typing `/` is OS input and is not allowed |
| recipe `game-console` | one of the game's own registered debug console commands (`spawn`, `explode`, `floodfill`, `locate`, `skiplayer`, `kill`, `heal`, `tp`) invoked in-process with a declared argument line | world items, buildings, structural damage, liquids, enemies and layer depth all have the game's own setup entry; calling the registered delegate is the same path the native console executes, without OS input |
| recipe `console-read` | the CUO console's own line list (`CommandConsoleService.Lines`) | S4.2/S4.3 rows are about what the player reads; the history is the live surface, a frame of the notification is the visual half |
| recipe `wound-read` | `PlayerCamera.ToggleWoundView` plus the live `WoundView` text components (`versionText`, `happyText`, …) | S3.4b's rows are "the window shows the restored value"; the game's own toggle and the live text are the surface, the frame is the visual half |
| recipe `layer-time-set` | the live `WorldGeneration.world.layerTimeSpent` field (a forced input, declared per row) | S3.4a's "6 of 10 minutes already spent" must not cost a six-minute wait; the field is the one the game accumulates, written where the game reads it |

Named setup gaps — the run attempts each once and records the verdict, never a weaker check:

- **Opened lockables.** Opening an `ItemLock` needs the lockpick minigame; no committed drive path
  exists (the same gap the sound batch recorded). The row keeps its `unproven` unless the game's own
  debug entries reach it.
- **Worn items.** The item row's `worn` resting has no equip path; ground/container/hand restings are
  driven, the worn half is named.
- **Recipe unlock by crafting.** S3.4a row 2 needs a crafted recipe; no crafting drive path exists.
- **The pause tooltip's happiness history.** S3.4b row 3's exact surface; the wound view's own fields
  are read instead and the row's surface half is named.
- **The guest end screen.** `save-run-clock-not-sent` row 1's surface; the live clock value is read
  and the end-screen rendering is named if the panel cannot be driven.
- **Two real hosts on one saves root** (`save-interval-autosave-and-backup-recovery`'s lease row):
  the sandbox pair does not share a saves root by construction; the file protocol is machine-verified
  and the two-instance scenario stays a named limit unless the run can stage it without a second
  install.

## The evidence channel (declared before the run)

- **machine**: the host's and each sandboxed client's own CUO log (`BepInEx/logs/latest.log`, rotated
  per start), the probe JSON of the driven action/recipe written into the batch directory under
  `acceptance-artifacts-dir`, the world archive on the host's save root (`world.json`, `live/`,
  `backups/*.cuoz`, `damaged-*/`), and this run's own suites/gates for the machine rows.
- **frame**: one window-level capture per visual row (never the desktop), read by the agent and cited
  by artifact id.
- **residual**: a judgement that is genuinely a person's (the audible half of nothing here; the
  player-visible "feels right" halves, the notification's look against a long line). Named per row.
- `Logging.MinimumLevel` is set to `Debug` on every client through the same editor the Preferences
  control writes and restored to `Information` before the clients close; the archive files and probe
  JSON are named beside each citation, never only in the transcript.
- A row this run cannot put the world into is `unproven` with the missing setup named; a row only a
  person can judge is a residual, never a self-issued pass.

## Machine-only ticket

`restore-account-arm-release` (10 rows, all pinned by named Runtime suites) is judged from the first

## Run sequence (four sessions, one build)

1. Freeze and offline chain: `git` state, preflight, `session-environment -Mode status` / `ensure-cuo`,
   build, gates, the full suite, `format`, `deploy.ps1`, `verify-deploy.ps1`; the artifact identity is
   recorded before any row is judged.
2. Run A: host through Steam; guest in the primary sandbox; both enter one world; groups A–F in order;
   restore `Information`, quit through the driver, collect the log channels.
3. Run B: the two-guest world for the multiplayer groups; the third client's joiner (and the cold
   relaunch where the row needs it); close cleanly.
4. Run C: the backup/recovery world, the Worlds page, the injected failure windows; close cleanly.
5. Run D: the solo menu-exit rows; close cleanly.
6. Every run's records name their batch, commit, deployed artifact identity, dependencies, rows,
   verdicts and residuals; the tickets move in the same change as their records.

## Limits (declared before the run)

- **A single run does not disprove a rare loss.** The rapid-cadence and repeated-cycle rows record how
  many iterations ran.
- **Substitutions are named.** Debug-entry setups (`spawn`/`explode`/`floodfill`/`locate`/`skiplayer`
  through the game's own registered command), the forced layer timer, the decoy native save, the
  injected read-only window and the in-process leaves/clicks are each recorded in the row's own limits.
- **Unreachable setups stay open.** A row whose setup the run cannot reach is `unproven` with the gap
  named; its ticket stays in `review/`, never closed on a guess.
- **The gate stays the deployed artifact.** Every run judges only rows produced after its own build,
  deploy and identity check; an earlier suite result is never this batch's evidence.

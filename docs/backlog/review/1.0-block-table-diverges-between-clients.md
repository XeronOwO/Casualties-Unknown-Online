# 1.0: the host's block table changes and the member's does not

## What the player sees

Nothing on screen until a block the host changed (mined, opened, destroyed) is still there for the
member — or the member's own change never shows up for the host.

## The reading (2026-11-12, release build, two clients over IP direct, one suite run)

Both clients re-capture the product's own world fingerprint (`[WorldFingerprint]`, FNV-1a over the
live block table, eight chunks plus the total) through the acceptance channel.

- At world entry the two lines agree chunk for chunk:
  `1024x1024: 9D1810AC432FBA29 04405E468E01CD7D 94F958F95CFCFB6E 6B75D33BAAE24FDD C636564F9F461F9C
  23EA19CB903F9001 4A56D96E4E479748 9D401DDB8538D9B9 total 90D3159D4F782ADA`.
- After the suite's run (fifteen cases: items, give, medical, trader, prosthetic, run settings), the
  host's fresh capture reads
  `1024x1024: F9BEE3A2FE68F478 8C245283C6197636 E504250AD193849B 95A83A9467B0F437 A69805C4E7B8A7AC
  DF365B03FEDFE951 4C96F4A97B4DA014 7342B7873DB951CF total 3530B1BB79FB4441`
  while the member's fresh capture still reads the entry state above (total `90D3159D4F782ADA`).
- So a mutation the host's table carries has not reached the member's table. Which case's mutation
  it is is not yet named; the candidate family is the block/container rows (a crate opened, a block
  hit, a container filled) — the observations are recorded per case in
  `.acceptance/suite/report.md`.

## The probe that followed (2026-11-12, same session)

The suite gained a diagnostic (`CUO_SUITE_PROBE=1`): after EVERY case both clients re-capture the
fingerprint and the two totals are printed. The pair differs from the FIRST case and never
converges:

```
probe  medical-chart   host=FC68D801EDCC17DB  member=90D3159D4F782ADA
probe  item-restings   host=FC68D801EDCC17DB  member=90D3159D4F782ADA
… every case identical …
probe  ending          host=07079573B39CFCDD  member=90D3159D4F782ADA
```

- The member's total is the SAME on every probe and equals the world-entry line the host wrote in
  the earlier session (`9D1810AC432FBA29 … total 90D3159D4F782ADA`) — the member's table is the
  freshly generated world and does not move.
- The host's total is constant across the first thirteen cases (`FC68D801…`) and changes at the run
  ending (`07079573…`), so the host's table carries a state the member never sees.
- The boxed member's own log carries the same eight chunks on every recapture, so the member's
  device is writing real lines, not a stale one.
- **The world-entry lines agree** (2026-11-12): the last `RunCoordinator [WorldFingerprint]` line in
  each client's file reads the same eight chunks and `total 638072155F2897B6`, so the run's start
  hands both clients the same generated world. The divergence appears only in the RECAPTURE, and the
  member's recapture total (`90D3159D4F782ADA`) is an entry total the host wrote in an earlier
  session, not the run's own `638072155F2897B6`. Either the member's recapture reads a table from
  another world (a stale world object), or the member's file answers a line that is older than the
  device's. The next reading is the member's own log line count around one recapture, with the
  device answering a sequence number it stamps into the line.

The reading points at the HOST's side: its world is not the freshly generated world the member
generated (a restored table, or a table the host mutated before the member joined). The next step is
to capture the host's world-entry fingerprint for the suite's own run and compare it to the member's
entry line — if those differ, the run's start does not hand the same world to both.

## What has to be found

1. Which block/cell differs (capture a full-table diff, not the chunk hashes): the fingerprint only
   proves a difference, not where.
2. Whether the mutation was host-local by design (a UI/preview-only change) or a world change the
   block report should have carried.
3. Which case in the suite produced it — the probe shows the pair differs from the first case, so
   the difference predates the cases: it is the run's own start.

## Design

The world's block mutations are described by
[docs/design/cross-cutting/saves-and-recovery.md](../../design/cross-cutting/saves-and-recovery.md)
and the world pages under [docs/design/game/README.md](../../design/game/README.md): the host owns
the block table, the members render copies, and a mutation is a reportable world fact.

## Acceptance

1. Two clients in one world: the host breaks a block; within the sync window the member's own
   `block-read-at` on that cell answers the broken block.
2. The reverse direction (the member breaks a block the host can see) reads the same way.
3. The acceptance case `world-fingerprint` returns from parked to green: both totals agree after a
   run that broke blocks on both sides.

## The same divergence in the enemy scene (2026-11-12 15:30)

`enemy-scene` on the live pair (the suite's fresh run, both clients in world) read `count 39` on the
host and `count 791` on the member. The member's client therefore holds animals the host's world does
not — the same shape as the block table's stale capture (the divergence ticket's own finding), now seen
on a second surface. The `enemy-pairing` case asserts the two counts agree; it stays parked until this
ticket closes.

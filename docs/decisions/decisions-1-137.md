# Decisions 1–137: the framework, the mod surface and the protocol baseline

The decisions that settled what CUO is built on and what a mod may bind to. They are **binding**; this page
is their home so the register ([`active.md`](active.md)) can take new decisions without exceeding the
document budget. The register's index names this page and the number range it holds, and every number below
is unchanged — a citation into the register still resolves by decision number.

| # | Decision | Canonical doc |
|---|---|---|
| 1 | The project's stack is BepInEx 5 on net48 with HarmonyX patching, protobuf-net wire serialization and Microsoft.Extensions hosting, the last held on the net48-compatible 3.1.x line. | `docs/en/contributing/build-and-test.md` Target and packages, `docs/development/agent-reference.md` Repository Layout |
| 2 | CUO is a pure star, host-authoritative and with no guest-guest traffic, and reliability follows whether the loss can self-heal: a fact whose next tick, checkpoint or re-report repairs it rides the unreliable path, and one with no self-healing path pays for delivery. | `docs/architecture/protocol.md` Normal data flow |
| 3 | The session owns its state: mutable state is held by its owner and exposed through narrow interfaces rather than a broad DI surface, and `HandlerContext` is narrowed per domain through capability interfaces instead of one all-controls context. | `docs/architecture/current.md` Project and dependency structure, `docs/development/agent-reference.md` Structure and boundaries |
| 6 | Perfect-match Harmony patch contracts must be resolved against copied game assemblies (`references/`, refreshed per game update) before the game ever launches, including the hand-declared dynamic contracts the tool's metadata lens cannot see. | `docs/development/game-update-runbook.md` Patch-contract tests, `docs/evidence/normative-gates.md` Quality and delivery rules |
| 9 | A mod binds to CUO through the binding contract in `docs/en/reference/mod-api.md` (what it may reference, the `[CuoMod]` manifest, lifecycle), and the manifest is fail-closed: one rejected mod never blocks the discovery scan. | `docs/en/reference/mod-api.md` The manifest, What a mod may reference |
| 19 | Mod permissions are declared and never implicit; host commands are host-authoritative, validated and permission-checked; declared dependencies load before the dependent; and mod versions are strict SemVer, compared by precedence for state-bearing modes. | `docs/en/reference/mod-api.md` The manifest, Host commands |
| 25 | BepInEx `ConfigFile` entries bind into `IOptionsMonitor` and are read live at each decision, so an edit applies without a restart; the logging minimum and the state-stream cadence (20 Hz by default, in a 1-60 Hz band) are configuration keys, and a log line's level follows its trigger frequency. | `docs/en/reference/configuration.md` Where the settings live and `[Sync]`, `docs/en/internals/state-and-snapshots.md` What actually rides a stream |
| 37 | Mod state saves are host-owned and versioned: only a host holding `ModPermission.WriteGameState` writes, each write persists the full table to a versioned file, and each entry carries the mod's declared schema version. | `docs/en/reference/mod-api.md` Mod state |
| 38 | Mod content registration is a framework-owned, read-only registry: a mod declares or `TryRegister`s typed definitions under `ModPermission.RegisterContent`, the registry keeps the instance it was handed and never writes to it, and consumers read it through the kind's provider. | `docs/en/reference/mod-api.md` Content registration |
| 46 | `ReadGameState` is a read-only projection of the framework's latest player-character facts: reading requires `ModPermission.ReadGameState`, each call returns an immutable snapshot, and a mod never sees Unity objects or game-assembly types. | `docs/en/reference/mod-api.md` Read game state |
| 49 | Mod entity spawn replicates a native prefab rather than inventing state: `IModEntitySpawn` and `IModItemSpawn` require `ModPermission.SpawnEntity`, and the adapter creates the local prefab through the game's own path so the normal report replicates it to every side. | `docs/en/reference/mod-api.md` Spawn and placement |
| 50 | `AccessNativeApi` is a curated, read-only registry of named native operations, each reached through its own typed projection, requiring `ModPermission.AccessNativeApi`; the Runtime never exposes arbitrary reflection or direct access to game assemblies. | `docs/en/reference/mod-api.md` Native operations |
| 63 | The `NetMsg` direction registry is fail-closed: one `NetMessageDirection` per `[PacketHandler]`, an unregistered id is refused before it is encoded, and a registered id arriving in the wrong direction is refused on receive. | `docs/architecture/protocol.md` Error and recovery, `docs/evidence/selfchecks/protocol/netmsg-registry-selfcheck.md` Whole-family audit |
| 65 | The architecture gate is partial-aware, summing a logical type's lines across its partial files, and `docs/architecture-debt.json` is the single source of approved over-limit exceptions: an unrecorded over-limit type, or growth past a recorded entry, is a hard failure. | `docs/development/agent-reference.md` Architecture gates, `docs/evidence/selfchecks/tooling/partial-aware-gate-selfcheck.md` Whole-family audit |
| 73 | `HandlerContext` is narrowed per domain: each handler declares only the narrow capability interface it uses, and `HandlerContext` implements them all, staying the composition root's single instance. | `docs/evidence/selfchecks/tooling/handler-context-narrowing-selfcheck.md` Whole-family audit, `docs/architecture/current.md` Project and dependency structure |
| 75 | The Game Adapter reaches the Runtime only through narrow control interfaces (`ISessionControl`, `IWorldControl`, `IItemControl`, `IEntitySyncControl`, `ICharacterDataControl`), never a concrete session service; a capability that starts crossing that boundary gets a port of its own. | `docs/development/agent-reference.md` Structure and boundaries, `docs/evidence/selfchecks/tooling/adapter-control-surfaces-selfcheck.md` Whole-family audit |
| 82 | IP-direct TCP transport is a supported non-Steam mode: the host listens on the `[IpDirect]` `ListenPort`, and a joiner points `JoinAddress` and `JoinPort` at it and gets its own display name. | `docs/en/reference/configuration.md` `[IpDirect]`, `docs/en/start/install-and-play.md` Join a session |
| 128 | The protocol runs four production envelopes over one transport frame; a join or reconnect joins on a checkpoint plus the journal tail after it; saves are checkpoint-only; and kernel facts cross the wire through the kernel-to-wire mapping. | `docs/architecture/protocol.md` Four production envelopes, `docs/architecture/current.md` Project and dependency structure, Save format |
| 129 | High-frequency player and enemy streams ride `StateStreamEnvelope` over `KernelEnvelope`, and a stream may only update existing convergent fields, never create or destroy aggregates or advance a key state machine. | `docs/architecture/protocol.md` Four production envelopes, Host →Guests: state stream |
| 137 | **[SUPERSEDED IN PART by 241**: before the first official release the value is a FROZEN baseline that no wire change moves, and the increment rule below is the post-release half of this policy]**: `ProtocolVersion.Current` is bumped on behavioral wire changes, and its value plus its retired per-number log live in the constant's own doc comment rather than in this register. | `docs/en/reference/mod-api.md` Versioning discipline |

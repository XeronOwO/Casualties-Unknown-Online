# A guest generates its own layer instead of adopting the host's

- Status: Review
- Priority: High
- Opened: 2026-11-12
- Surface: world generation on a member client, enemy copies, block table
- Found by: the acceptance suite's `enemy-pairing` row (the 1.0 regression sweep)

## What was read

The suite's own two-client IP-direct session, both clients in world, the host started the run:

- `enemy-count` on the host: `count 47`.
- `enemy-count` on the member: `count 865`.

The member's own log explains the 865 (the boxed client's `BepInEx/LogOutput.log`):

```
[Enemy] generation finished: 865 animal(s) exist at the settled edge and are this layer's generation
[Enemy] guest froze 865 enemy copies at generation finish (before they move).
[Enemy] guest dropped its enemy bindings: the host reset the roster for a new layer.
[Enemy] live-adopted 1 new enemy row(s) from the stream.
```

So the member client RAN world generation for the layer (it produced 865 animals and froze them as
its own generation) while the host's authoritative set is 47 rows. The same session shows the wider
shape on another surface: the block table diverges between the clients
(`review/1.0-block-table-diverges-between-clients.md`).

## Why it matters

A member that generates its own layer holds objects the host's world does not: enemies that exist on
one screen only, blocks that differ, and every reading taken from the member's side is about a world
nobody shares. The suite cannot judge any world row on a member until the member's world IS the
host's.

## What to establish before fixing

- Which side is supposed to generate: on 1.0 the host owns generation and a member must adopt the
  host's settled layer (the late-join path already exists: `[Enemy] roster adopted: N rows (… aligned=True)`).
- Whether the member's generation ran because the entry gate released it early, because the world
  seed was not handed to it, or because generation is a startup step the member never skips.
- Whether the 1.0 build the sweep runs is older than the workspace's adapter (the deploy on
  2026-11-12 was `0.1.0+1128f3989`; the sweep's later runs used that build).

## Next steps

1. Read the member's entry sequence in its own log around world entry: which gate line precedes
   `generation finished` (the `[WorldStart]` / `[Handshake]` / `[WorldSync]` lines).
2. Read `WorldStartGate` and the member's generation trigger in `src/CasualtiesUnknownOnline.GameAdapter/World/`.
3. Fix or file the owning defect, then the `enemy-pairing` case un-parks and the block rows follow.

## Design

`docs/design/game/README.md` (what the game owns when a world starts) and
`docs/design/cross-cutting/saves-and-recovery.md` (the host's world is the one that is saved and
handed over). The reading belongs against those two pages: a member's layer must be the host's.

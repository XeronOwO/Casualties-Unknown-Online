# The IP-direct guest connects and then drops out of the session

Blocked on a reading: the guest's own log at the disconnect has not been read yet (the host's
side is below). The next step is to reproduce once with both logs open and diff the disconnect
line against the guest's last line.

## Design

The session and world-join surface on the release build (`docs/design/game/README.md` — the map
of the game's world and session systems): the host starts a run, the game's own world generation
runs on both clients, and the session's world-join table decides which peers the run start
reaches.

## The reading (2026-11-11 01:50, release build, desktop host + boxed guest over IP direct)

The host (18590) started an IP session (`IP direct host started on port 7777 (peer id 1)`). The
guest (18591, the boxed install copy) clicked join and its own state read
`transport: IpDirect, role: Guest, active: false`. The host's log then read:

```
[IpDirectTransport] IP direct guest 5692668282652519133 connected from 127.0.0.1:64860.
[WorldService] World join sent to 0 member(s) (tutorial: False, run 1, baseline follows: True).
[WorldService] World join sent to 0 member(s) (tutorial: False, run 1, baseline follows: True).
[IpDirectTransport] IP direct session disconnected.
```

The guest sat at the start gate with `gateText: "正在等待房主加载……房主还没有进入世界。"` for
minutes while the host was in the world (`inWorld: true`), and the connection dropped repeatedly
(`IP direct session disconnected.` three more times).

## Why it matters

Two clients in one world is the base of every co-op row the acceptance suite judges; if the guest
cannot stay joined, every two-client case is unrunnable. The earlier session on 2026-11-10 worked
(host `steamInit: true`), so the difference to read is the host's Steam identity: this run launched
the host directly (`steamInit: false` on both clients).

## What to read next

1. The guest's `BepInEx/LogOutput.log` around the disconnect (the box's log path), the lines after
   `IP direct guest ... connected` on the guest side.
2. Whether the host's `World join sent to 0 member(s)` runs before or after the guest's join is
   registered in the member table (the timestamps against the join click).
3. The host's Steam state in the working vs failing sessions (`steamInit`), and whether the
   IP-direct session needs the host's Steam identity for the member list.

## The finding (2026-11-11 01:54, the same session after the guest's log was read)

The guest's own log carries the cause: the host refuses its handshake by name —
`[Handshake] the host refused this client: CuoBuild (host 0.1.0+0b1018272e396e73f45364bca31cb53a6b9bfef2 vs 0.1.0+77687…)`.
The boxed install was running a stale plugin build; the identity refusal did exactly what it was
built to do. The "world join sent to 0 members" and the repeated `IP direct session disconnected`
lines follow from that refusal, not from a transport defect.

The fixture rule this yields: after every deploy, the boxed install's plugin folder must be
synced to the desktop's build before the two-client session is created — and the box's client must
be quit first (its DLLs are locked while it runs). The sync itself is a copy of
`BepInEx/plugins/CasualtiesUnknownOnline` (36 files); after a correct sync the guest joined and
the run started with the guest `inWorld: true` and its gate released
(`[Gate] the loading text is handed back to the game (genplacingentities)`).

Status: the "dropout" is a stale-build fixture error, not a product defect; this ticket closes
with the reading above once the build-mismatch check is added to the two-client fixture steps.

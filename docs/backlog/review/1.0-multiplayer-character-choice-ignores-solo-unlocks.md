# Multiplayer character choice ignores the solo unlocks, and a session must not touch them

- Status: Review — the rule is the user's (2026-11-14); the game's unlock store has not been read yet.
- Priority: High

## Design

Read: `docs/design/game/README.md` (the character selection and the pre-run screen) and
`docs/design/cross-cutting/saves-and-recovery.md` (what belongs to a run and what belongs to the profile).

## What the user asked (2026-11-14, translated)

"In multiplayer, character selection should allow any character, even when the solo player has not beaten
the game — the other two characters are locked. Protect the multiplayer experience, and beating the game in
a session must not affect the solo character unlocks: keep the data isolated."

## Why this is a product rule, not a preference

The three characters are a single-player progression reward. A co-op session is not the single player's
progression: a friend who has not finished the game must still be able to pick the character they want, and
a session that ends must leave the player's own unlocks exactly as it found them. Mixing the two turns a
casual co-op run into a progression write the player never asked for.

## What to read before the first probe

1. Where the game stores the unlocks and where it checks them — the pre-run screen's character picker and
   the store behind it (`PreRunScript` and whatever reads the unlock flag).
2. Which of our paths write that store: the run start, the ending, the continue restore, and anything that
   copies run fields (the proxy captures and the shared character sync both touch run state).
3. Whether the picker builds its lock state from the store at open time or caches it per session.

## Acceptance rows

1. A session where the local player has no unlock: the pre-run screen offers all three characters, and
   picking any of them starts the run with that character (read from the spawned character's own identity).
2. The pick reaches the other client: the member's displayed copy is the chosen character (the existing
   wire already carries the index; this row proves it on a locked-choice run).
3. After a session that ends — including a win — the solo unlock state is byte-identical to what it was
   before the session (read the store before and after).
4. A solo run keeps its own locks: a player without the unlock still cannot pick the locked characters
   outside a session.

## What must not change

- The solo unlock store's own rules and format; this ticket only stops a session from writing it and stops
  a session from reading it as a gate.
- The character wire (`CharacterDataMsg.Character`): a session's choice already rides it.

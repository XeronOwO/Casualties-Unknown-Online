# Delivery checklist

Fill every box, then run `tools/check-delivery.ps1`. Each box needs the literal ` — evidence: ` followed by the evidence.

- [x] Design comprehension — evidence: the ticket now records what the one run measured and separates the two remaining families: a session that keeps a second member row, and a member body with no free slot.
- [x] Native parity — evidence: documentation only; no product behaviour is described as changed.
- [x] Native parity probe — evidence: the readings quoted are the run's own report lines and the host log's own refusal messages.
- [x] Entry mapping — evidence: one ticket, `1.0-one-acceptance-run-covers-every-case.md`, with its status line and Readings section rewritten from the two runs.
- [x] Mechanism inventory — evidence: both families name the row, the reading and the failed precondition, so the next change has a starting point.
- [x] Whole-family audit — evidence: all twenty failures of the run are listed under one of the two families or named as their own (medical-bandage, sample-mod, real-drag, clone-probe).
- [x] Self-check table — evidence: the numbers are the report's own (47 passed, 20 failed, twice) and the per-row notes are quoted, not paraphrased.
- [x] Verification design — evidence: `dotnet test` reads 6749/6749 units and 836/836 gates with the ticket in the tree; the language check is clean.
- [x] Plan approved by the user — evidence: the standing instruction is one run over every case; the ticket records how far that run has come.
- [x] Structure review done — evidence: the fix direction is stated as one guarantee on the runner (session shape), not twenty row patches.
- [x] Build + dotnet format + dotnet test normative gates pass — evidence: 6749/6749 units, 836/836 gates; the change is documentation only, so no build or format step applies.
- [ ] Release-cycle deployment/acceptance

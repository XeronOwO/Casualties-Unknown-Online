# 权限与安全

[文档总览](../README.md) > [弄懂原理](README.md) > 权限与安全

---

**读完这一页**，你能说清一项声明的权限到底强制了什么、每道检查发生在哪里，以及 CUO 刻意不防什么。[声明权限与主机命令](../how-to/declare-permissions-and-commands.md) 是怎么用它们的走查；这一页是它们背后的模型。

## 没有什么是隐含的

模组在 `[CuoMod]` 特性上声明自己的能力，默认是 `ModPermission.None`。`src/CasualtiesUnknownOnline.Abstractions/ModPermission.cs` 写明了这条规则：CUO 从不隐含授予任何能力 —— 模组必须明确说出它要什么。八个标志是：

| 标志 | 它把关的接口面 |
|---|---|
| `ReadGameState` | 只读的游戏状态投影 |
| `WriteGameState` | 主机持有的模组状态 |
| `SpawnEntity` | 实体与物品生成，地块、建筑与液体的放置 |
| `SendNetworkMessage` | 模组消息通道，**发送与接收** |
| `RegisterContent` | 注册框架当作世界一部分的内容 |
| `RegisterCommand` | 注册主机命令 |
| `ExecuteHostAction` | 一条标为主机动作的命令，另外还需要它 |
| `AccessNativeApi` | 经过筛选的原生操作注册表 |

每个标志都有真正的执行点，而不是一个文档里的值：同一个文件把它们列了出来 —— 模组消息通道、主机命令域、模组状态存储、内容注册、只读的游戏状态投影、实体与物品生成及地块／建筑／液体放置，以及原生操作注册表。被拒绝的调用是一行日志加一个否定结果，而不是抛进谁家模组里的异常。

## 声明一次，检查两遍

同一份纯策略在两处校验这份声明。`src/CasualtiesUnknownOnline.Runtime/Session/Mods/ModPermissionPolicy.cs` 就是“纯粹的权限裁判”：发现阶段用它校验本地清单，而“握手在接纳之前用同一份策略校验客机声明的标志”。

它拒绝的两件事值得点名：

- **未知的位。** 不属于这八个的权限不是什么面向未来的余量，而是垃圾输入 —— 集合必须是 `ModPermission.All` 的子集。
- **本地模式下的主机与状态权限。** `WriteGameState`、`SpawnEntity`、`RegisterContent`、`RegisterCommand`、`ExecuteHostAction` 与 `ClientOnly`、`Cosmetic` 一起出现就会被拒：命令在主机上执行，内容会成为世界的一部分，只在一台客户端上跑的东西两样都不该拥有。

## 主机在跑别人的代码之前检查什么

在远端调用者和模组处理函数之间有三道检查，而且都在处理函数之前：

- **加入时。** 客机声明的模组清单会与主机自己的比对（规则见[模组的一生](mod-loading-lifecycle.md)），所以承载状态、而某名成员没装的模组，会在握手时就被拒，而不是过后才出问题。
- **命令窗口。** 主机命令请求在处理函数运行之前先过校验：名字最多 64 字符，最多 16 个参数、每个最多 256 字符且合计最多 4 KiB，发送方已完成握手，模组与命令均已注册，权限标志齐全。对每名客机，请求限速为每秒 4 次、突发 8 次。
- **准入关口。** 经网络到达内核的指令要过 `src/CasualtiesUnknownOnline.Application/Kernel/KernelCommandGateway.cs`，由它负责这条映射路径上“谁可以提交”。它按固定顺序检查：指令的行动者是提交它的那名成员；声明的权威类别是成员可以署名的；一条销毁报告点名的物品确实属于该成员可报告的范围。

这道关口的范围也是它契约的一部分：它“只判准入（谁可以提交），绝不替别人的身体、触及范围或时机下结论……每一个领域结论仍然归内核”。顺序同样要紧，文件里写了原因：“跑得更早的一次拒绝，会掩盖内核本来会给出的那一次”。

## 原生接口面是有边界的

`AccessNativeApi` 并不是把游戏交出去。它通向一张经过筛选的登记表，值面刻意很窄：操作 id 最多 128 字符、一次调用最多 16 个参数、字符串最多 4096 字符、字节数组最多 64 KiB、基元数组最多 1024 个元素。Unity 与游戏程序集的对象、以及任意对象图，在适配器接缝的两侧都会被拒，所以一次原生操作没法把活着的游戏对象偷渡给模组。

## 是可见性，不是沙箱

这一段最容易被读过头。权限把关的是 CUO 自己的接口面，它没有把模组关进盒子里。

- 模组就是进程里的普通代码。它可以给任何东西打补丁 —— 这正是 `NativeBinding` 记录的东西，而特性上写明了这条声明的分量：“声明的事实，不是权限：`ModPermission` 才是 CUO 强制的，而 CUO 在这里什么都不强制 —— 没声明的绑定根本检测不出来（框架不持任何反作弊立场），所以这份声明是自愿的诚实，它唯一的力量来自同伴的一致性策略。”
- 原生绑定（native binding）换来的是对其他对端的可见性，永远不是稳定性：它点名的东西属于游戏，一次游戏更新可以在没有任何 CUO 决定的情况下把它弄坏。
- 权限让模组的意图可读，并挡住误触。它们不是防有心作恶的模组的安全边界。

## CUO 不防什么

- **改过的客户端。** 反作弊是被明确推迟的 —— `docs/backlog/future/strict-validation-anti-cheat.md` 是一张低优先级的未来项，它也如实记下了当前的限制：成员指令声明的权威类别目前不携带“成员还是主机”的信息。这条限制在判定一侧同样写明：一个在自己的触及范围或自己身体上撒谎的客户端，可以绕过本地判定到达主机，堵上它是之后的加固周期。
- **存档内容。** 世界归档里装的东西没有反作弊。
- **在已授权接口面里乱来的模组。** 一个模组拿到 `SendNetworkMessage` 之后，通道检查的是大小与速率，不是含义 —— 载荷按设计就是不透明字节。
- **对端对自己身体的诚实。** 在判定方自己画面上做出的结论，外部无法验证；这是[判定归属](judgment-ownership.md)刻意付出的代价。

这个姿态的理由来自产品本身：CUO 是自愿一起玩的人之间的合作，不是竞技服务器。在这个阶段，挡下一个老实玩家，比容忍一个不老实的更糟；上面那些检查存在的意义，是不让意外和粗心变成不同步，而不是抓出对手。

## 完整性的边界仍然是版本校验

CUO 绝对强制的是：两侧跑着同一个协议、以及同一批承载状态的模组。协议不一致会在握手时结束加入；承载状态的模组在任意一侧缺失或版本不等，也会在那里被拒。正因为有这道检查，线上改动永远不必把旧形状留着；它同时也是框架对“对端是什么构建”做出的唯一完整性声明。

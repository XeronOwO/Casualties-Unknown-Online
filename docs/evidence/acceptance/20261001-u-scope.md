# Acceptance batch 20261001-u — scope, run plan and row classification

- Batch: `20261001-u` — one host (physical machine, launched through Steam) and one guest (the primary
  sandbox). The alternate third client is used only for `world-time-local-initiation` row 5 (a late
  joiner); every other row is a two-client observation.
- Commit: `8a0ddafb` — the run judges the deployed artifact produced from this tree
  (`tools/verify-deploy.ps1` prints `0.1.0+8a0ddafb…`), never an earlier build.
- Tickets in scope (3): `world-acceleration-survives-movement` (High),
  `world-time-local-initiation` (Medium), `world-acceleration-quake-direct-write` (Medium).
- Why these: the handoff named the world-clock family as the next batch. The three tickets' rows share
  one session — the accelerate key, the movement rule's own call, the sleep gate, the quake and the
  pause/death transitions — so they go through one build, one deploy and one run.
- Out of batch, deliberately: every other `review/` ticket. The sibling sync families (blocks and
  drops, entities and identity, adaptive rate, medical, UI) need setups this session does not carry;
  their batches are named in the closing handoff, not judged here.
- Verdict rule this run applies: an `unproven` row whose trigger cannot be produced by this run's
  vocabulary is named in the ticket as a limitation and the ticket stays in `review/` (the batch
  `20261001-s` / `20261001-t` convention); a `fail` moves the ticket to `todo/` with the rejection
  marked.

## The capability this run adds (declared before the run)

Five committed recipes under `tools/acceptance/recipes/`, all in-process, all invoking the game's own
call so the CUO routing under test is the one a player's input would reach:

| Recipe | What it invokes | Serves |
|---|---|---|
| `time-scale` (`speed`, `announce`) | `PlayerCamera.SetTimeScale` — `announce=1` is the accelerate key's own call, `announce=0` the movement rule's silent call (PlayerCamera.cs:885-895 / :921-924) | all three tickets |
| `time-scale-read` | the live clock (`Time.timeScale`), the HUD's own speed field (`curTimeScale`), pause, body state and the quake fields | all three tickets |
| `quake-force` | puts `WorldGeneration.earthquakeDelay` where the game's own countdown puts it, so `WorldGeneration.Update` starts a REAL quake and writes `Time.timeScale = 1f` (WorldGeneration.cs:865-871) | quake ticket |
| `time-scale-direct` (`scale`) | writes `Time.timeScale` directly, the class the quake and the game console's `timescale` write (ConsoleScript.cs:815) — including a non-domain value as the negative sample | quake ticket |
| `pause-toggle` | `PauseHandler.TogglePause` — the pause/menu transition's own ramp and forced clock write (PauseHandler.cs:31 / :153-160) | acceleration ticket, initiation ticket |

## The evidence channel (declared before the run)

- **machine**: in-process probe results (`drive-in-process.ps1 -Action recipe`, one eval per
  invocation), the two clients' `BepInEx\logs\latest.log` (CUO's rolling log) and the deployed
  artifact identity. Debug-level lines are switched on in process for the movement rows and restored
  to Information afterwards; the switch and the restore are run-local probes cited as artifacts.
- **visual**: window-level captures of each client's own window (never the desktop), read by the
  agent; named by artifact id in the records.
- **feel**: no row in this batch is judged on feel; what stays subjective (the movement event's sound,
  the latency feel of a local-first initiation) is a residual for the user.
- **re-derived/static**: the native call-site census the tickets already carry is not re-measured;
  rows whose expectation is "unchanged" are judged from this run's own reads and logs.

## Limits (declared before the run)

- **The OS key press itself is not synthesizable.** The acceptance tools are in-process only (a gate
  forbids OS-level input), so a key-driven row runs the same native call the key's handler makes, not
  Unity's `Input`. The `Input` layer is vanilla and untouched by CUO; each record names the mechanism
  its row used.
- **A sound is not a captured frame.** The HUD's speed sound in row 8 is a residual for the user; the
  run captures the indicator, not the audio.
- **One session is not a race proof.** Rows about a burst, a resend or a late joiner are observed as
  many times as the run can, and the count is recorded; absence of a rare interleaving is not claimed.
- **Debug-level evidence is level-dependent.** The movement rows' direct log lines are Debug; the run
  switches the level in process for those rows and restores it at the end, and the switch is part of
  the record rather than an assumption.

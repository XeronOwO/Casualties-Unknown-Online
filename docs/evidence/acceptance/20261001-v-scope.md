## The capability this batch adds

| Recipe | What it invokes | Serves |
|---|---|---|
| `world-time-request` (`speed`) | the production SEND a guest's own applied speed reports through: `IWorldTimeControl.SendRequest` -> `WorldTimeChannel.SendRequest` -> `NetMsg.WorldTimeRequest` — the call `WorldTimeSync.BeginLocalFirst` makes. The local-first half (the native call before the report) is not reachable from the evaluator and is not what this recipe covers. It needs no `PlayerCamera`, so it acts from the lobby, under a held gate, and with a sleep-owned speed no guest may request. | row 4's three instances |
| `gate-arm` (no args) | the production start-gate arm, `IWorldControl.StartStartGate()` (`WorldStartGate.Arm`), called after a member has deliberately left the world (`leave-world`); the gate then holds for that member until its own 30 s fallback. | the start-gate instance |

The three host guards the instances reach are the ones in `WorldTimeSync.OnRequestReceived`: not an
in-world member, the start gate owning the clock (`WorldStartGate.Active` through
`StartGateCoordinator.WaitingForReady`), and a speed no guest may request
(`WorldTimePolicy.IsGuestRequestSpeed`). Every refusal path ANSWERS with the authoritative speed; the
answer is visible on the requester as the `WorldTimeHandler` line `World-time broadcast: <speed>.`

## Limits (declared before the run)

- The start-gate hold is FORCED: a handshaken member leaves the world and the host re-arms the gate
  through the production call, so the guard reads the same `WorldStartGate.Active` a slow-loading member
  would produce — it is not a member's natural load window.
- The request is the production wire send, not Unity's `Input`: the OS key press itself is not
  synthesizable (the limit batch u already declared).
- One session is not a race proof; every judged line is named with its timestamp beside the 5 s resend
  cadence it shares a channel with.

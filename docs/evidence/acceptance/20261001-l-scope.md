# Acceptance batch 20261001-l — scope, run plan and row classification

- Batch: `20261001-l` — one three-client session for the sound/audio family: the host on the physical
  machine, the guest in the primary sandbox, and the third client in the alternate sandbox for the rows
  whose expectation names a third listener.
- Tickets in scope (6): `host-eating-sound-not-heard-on-guest`,
  `host-metal-scrap-block-place-sound-not-synced-to-guest`, `guest-hears-only-some-block-break-sounds`,
  `sync-player-pain-vocalizations-and-bark`, `unhooked-item-and-body-sound-families`,
  `suppressed-native-call-sounds-stay-unheard`.
- Out of batch, deliberately: `treatment-gore-presentation-carried` (every row needs a remote-medical
  minigame), `guest-background-ghost-item-ground-sounds` (its rows need a focus/background transition,
  and the run has no window-focus control by policy), and `unhooked-damage-block-callers` (its rows need
  a block type whose health is 1 underfoot and a burrowing spider, neither of which this run can place).
  Those three stay in `review/`.
- Why one batch: every row below is decided by the same session and the same evidence channel — three
  clients in one world, driven through the committed recipes and the Online UI's own controls, with each
  client's own CUO log read. A per-ticket session is the loop that costs the most.
- Row classes are fixed here, before the run. Each ticket's record repeats the classification with its
  verdict and evidence pointer.

## The evidence channel (declared before the run)

- **machine**: the receiving client's own log line `[CharacterSound] replayed {Kind} {Clip} for owner
  {Owner}` (the last CUO-controlled step before Unity's own play call), the count of those lines, the
  sending side's probe JSON, and the two clients' cell/pose reads where the row is about world state.
- **residual**: the physical audibility of a clip. The run captures no audio, so a row whose expectation
  is "X hears Y" is judged at the replay mechanism and its audible half goes to the user's list — the
  same boundary the ticket censuses record ("the audible half is the user's dual-client pass").
- Every cited probe result is written to the batch directory under `acceptance-artifacts-dir` and cited
  by file name; the log excerpts name the file and the line. `Logging.MinimumLevel` is set to `Debug` on
  each client through the Preferences control's own setter for the run, and restored to `Information`
  before the clients close.
- A row this run cannot put the world into is `unproven` with the missing setup named; a row whose
  judgement is genuinely a person's is a residual, never a self-issued pass.

## Run sequence (one session, one build)

1. Freeze and offline chain: `git` state, preflight, `session-environment -Mode status` / `ensure-cuo`,
   build, gates, full suite, `format`, `deploy.ps1`, `verify-deploy.ps1`; the artifact identity is
   recorded before any row is judged.
2. Bring-up: host through Steam; guest in the primary sandbox; third client in the alternate sandbox
   when the `sandbox-alt` preflight row is present. Set `Logging.MinimumLevel` to `Debug` on each
   client through the Preferences control's own setter; create/join/start through the Online UI driver.
3. Group A on the host and the guest, then the third client's read; group B in the same world.
4. Group C: the host hits, the peers read; then the reverse; the rapid cadence; the two-player cell.
5. Groups D, E and F, each on the client its row names.
6. Close: restore `Information` on each client, `quit` through the driver, collect the log channels,
   verify that no game process remains.

## Method

`machine` rows are read from the in-process evaluator's probe JSON, the three clients' own log channels,
and this run's own suites; `visual` rows (the impact frame) from window-level frames this run captures
and the agent reads. The audible half of every sound row is a residual for the user, named per row.

## Limits (declared before the run)

- **No audio capture and no OS input.** A sound row is judged at the replay mechanism; the audible half
  is a residual. Nothing is driven through the physical mouse or keyboard.
- **Setup substitutions are named.** Items are created through the game's own `Utils.Create`/pickup
  path, the aim is set through `body.targetLookPos` (the field the native mouse aim writes), the body
  states are written through the game's own fields, and the two-player cell brings the bodies together —
  each substitution is recorded in the record's `Limits`.
- **A single run does not disprove a rare loss.** The rapid-cadence rows repeat their reads and record
  how many ran.
- **One session, one world.** Rows whose setup this world cannot reach stay `unproven` with the setup
  named; they keep their ticket open rather than being guessed.

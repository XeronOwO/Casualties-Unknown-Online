# The give's container half: is the backpack clip played when the item leaves a container?

- Status: Todo — the 2026-11-19 body-slot reading is NOT a defect (the game plays the clip only when the item leaves a
  container); the container half is the unread question.
- Priority: Low
- Category: Cross-player item transfer / native parity (audio)
- Source: the 2026-10-25 report (translated): "why is there no sound when I move an item into another player's backpack?
  A normal item move has a cloth-rustle sound", and the later ruling of the same day: the give must not add the container
  sound where the game makes none — only the placement click belongs there.

## What was measured (2026-11-19)

Two focused runs of the give row with the one-shot recorder armed on both clients before the drop
(`.acceptance/give-sound1`: member recorder `raw=833|`; `.acceptance/give-sound2`: giver `raw=110|`, receiver
`raw=110|`): the item landed in the member's bag and neither client played a `backpack` clip. The same recorder read
`scrapmetal@22.2` and `rock@18.8` in the neighbouring rows, so the instrument is not the silent part.

## Why that is the native answer

`Body.PickUpItem` (`reversing/release-1.0.2/Assembly-CSharp/Body.cs:1467-1483`) plays
`PlayerCamera.main.PlayBackpackSound()` **only** when the item has a parent container:

```
if (item.TryGetParentContainer(out container))
{
    container.UnloadItem(item, null);
    PlayerCamera.main.PlayBackpackSound();
}
```

A give from a body slot to a body slot has no container on either side, so it is silent by the game's own rule — and the
giver's apply branch in `src/CasualtiesUnknownOnline.GameAdapter/PlayerInteractionApply.cs` already carries that ruling
in its comment (the earlier CUO addition of a sound there was removed for exactly this reason).

## What is unread

A give whose item is taken **out of a container** (or placed into one) is the case the game's rule covers with a clip.
The give probe can name a container destination (`give-probe … container=<instance>`), and a member's bag can hold one
(a trash bag is a container). No run has armed a recorder around that case, so whether the clip crosses is unmeasured.

## Acceptance rows (for the container half)

1. A give that takes the item out of the giver's container plays `backpack1`/`backpack2` on the client that performs the
   container unload, read by the one-shot recorder.
2. A give that places the item into the receiver's container plays the same clip on the receiver's client.
3. A body-slot give stays silent (the reading above is the baseline, and `give-item`'s row keeps it).

## Options

- **A — measure first** with the existing give row and a container fixture; if the clip crosses, close this ticket with
  the reading and name it a residual on the sweep ticket.
- **B — if it does not cross**, reproduce the native call at the container move's own seam (the receiving client's
  `PlaceCarriedItem` / the giver's `RemoveCarriedItemFromLocalBody`, whichever performs the unload), never at a body-slot
  move.

Recommendation: **A now**, **B only with that reading**.

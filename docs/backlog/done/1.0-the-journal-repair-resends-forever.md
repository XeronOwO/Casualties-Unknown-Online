# The journal repair re-sends history forever when the missing revision cannot apply

- Status: Done (2026-11-22)
- Priority: High
- Opened: 2026-11-22
- Owner: session

## Why

A guest that falls behind asks the host for the missing revision range. That repair can only work while
the revision where the range starts is applicable. When it is not — the batch was issued in a run the
guest has since left, so the epoch guard drops it — the guest asks again on the next batch, the range's
end grows by one, and the host re-sends the whole history each time.

Measured 2026-11-22 in `.acceptance/bisect-b` (`mine-blast,player-deaths`): the guest logged
`Batch from 1 creates a revision gap: expected 730, received 735…` at millisecond intervals while the host
logged `Sent 101 journal batch(es) 730..830 to …` growing every line. Inside five minutes the host's
`latest.log` reached 813 MB and the guest's 234 MB, both clients sat at 100 % of several cores and stopped
responding to Windows. Every batch run that night failed in a different set of rows because of it.

## The four lines

1. Reading: guest `expected 730, received 735..` and host `Sent N journal batch(es) 730..M`, N growing.
2. Code: `src/CasualtiesUnknownOnline.Application/Kernel/KernelProtocolService.cs` — guest
   `HandleCommittedBatch` (`batch.GlobalRevision > expected` → buffer + `RequestRange`), host
   `HandleRangeRequest` (re-sends the requested history with no bound).
3. Chain: epoch guard drops a run-2 batch (`Batch from 1 has epoch 2; current is 1 — dropped`) → that
   revision never applies → every later batch is a gap → a range request per batch → a full history
   re-send per request.
4. Fix: the second request that starts at the same revision proves the repair cannot work, so the host
   sends a checkpoint (the protocol's own re-baseline) instead of the history. `_rangeRepeats` keyed by
   `(sender, start)`; one line names the decision in the log.

## What it does not fix

The ordering that produced the dropped batch: the host announced run 2 *after* its first run-2 batches,
so the guest's epoch guard refused them. That is a separate defect in the run-change announcement and is
recorded in `docs/backlog/todo/1.0-the-run-change-arrives-after-its-batches.md`.

# The game window never takes the front

- Priority: High
- Status: Todo
- Owner: night mode

## Design

The window is created by Unity's native runtime before any managed code runs, and that behaviour is recorded in
`docs/design/audit/native.md`; the acceptance clients exist to run beside the person's work, so "the game never takes the
front" is a property of the harness, not of the game: `docs/development/rules/13-acceptance.md` already asks a batch to
leave the machine usable, and `docs/acceptance/workflow.md` records how a run is started. This item therefore changes the
launcher and one native helper, and it must not change the game, the person's windows, or anything else on the desktop.

## Why

The acceptance clients are meant to run beside the person's work. Today they are started without activation
(`CreateProcess` + `STARTUPINFO{STARTF_USESHOWWINDOW, SW_SHOWNOACTIVATE}`) and still take the foreground: a 25 s
foreground watch during a host start read the game process 144 times out of 196 samples, beginning a moment after the
window appeared. Measured 2026-11-22 on `tools/acceptance/host/ClientLauncher.cs`.

The white startup screen is the worst case: Unity creates and activates its window before the managed runtime (and so
before any BepInEx plugin) runs, so nothing installed as a plugin can influence that first activation.

## What the search says

- BepInEx preloader patchers modify managed assemblies with Mono.Cecil before the game loads them
  (https://docs.bepinex.dev/master/articles/dev_guide/preloader_patchers.html). They cannot intercept the native window
  creation that happens earlier, so a patcher alone cannot make the window "born unactivated".
- The mechanism that does prevent activation at creation is a `WH_CBT` hook returning nonzero for `HCBT_ACTIVATE`
  (https://learn.microsoft.com/nl-nl/windows/win32/winmsg/cbtproc). A global CBT hook needs a native DLL injected into the
  target process; a managed callback only serves the hooking process itself.
- No native toolchain is installed on this machine: `vswhere`, `cl.exe` and `Visual Studio` are all absent (checked
  2026-11-22), so the CBT route is not buildable here without installing one.

## Decision

Two routes are possible; this ticket takes the second and keeps the first as the option that needs a toolchain:

1. Native CBT hook DLL: window never activates at all. Requires a C++ toolchain (absent) and a DLL shipped into every
   client, including inside Sandboxie boxes.
2. Preloader-level watchdog (chosen): a patcher assembly starts a watcher thread at preload time - the earliest managed
   code in the process - which hides the game's main window as soon as it exists, remembers that it did, and shows it
   again with `SW_SHOWNOACTIVATE` once the game says it has drawn a frame (a sentinel file written by the plugin's first
   scene load). The window exists a few milliseconds before it is hidden; it is never shown by us while activated, and
   the game's own later activation is answered by showing again without activation.

## What the watcher must do

- Find the window without assuming `Process.MainWindowHandle` is populated: enumerate the process's top-level windows
  (`EnumWindows` + `GetWindowThreadProcessId`) and take the first visible one with a non-empty title.
- `ShowWindow(hwnd, SW_HIDE)` until the plugin writes its sentinel (`%TEMP%\cuo-window-ready-<pid>`), then
  `ShowWindow(hwnd, SW_SHOWNOACTIVATE)`; the sentinel is removed by the plugin on shutdown so a stale file cannot lie.
- Give up after 120 s and log what it saw, so a game that never draws is not hidden forever.
- Never touch a window whose process is not ours (the incident of 2026-11-22 is why `tools/…/WindowPlacementGateTests`
  exists; that gate must be reopened for this project only, with this ticket named in the reason).

## Readings to record when it lands

- The same 25 s foreground watch: number of samples where the game process owns the foreground, before/after.
- The window's visibility timeline from the watcher's own log: created at, hidden at, shown at.
- A screenshot of the white startup phase taken while the person's window is in front.

## Open items

- The CBT-hook route stays open for "never activated at all"; it needs a C++ toolchain decision first.
- The sandboxed client is started by Sandboxie's `Start.exe`; the watcher runs inside the boxed process, so the same code
  covers it, but the box's window may be created with different styles - to be measured.

## Where it stands

The toolchain exists after all: the machine has Visual Studio 18 Community with the C++ workload, so `cl.exe` is there.
`tools/build-native.ps1` compiles `tools/native/window-quiet/` into `artifacts/native/window-quiet.dll` (x64, exports
`QuietInstall`/`QuietRemove`), and the acceptance host loads it through `tools/acceptance/host/WindowQuiet.cs`, installing
the hook for every process `ClientLauncher` starts. The build copies the DLL beside the host when it is present, and a
missing DLL costs one log line, never a run.

Two things are not yet measured or settled:

- Whether cancelling `HCBT_ACTIVATE` actually keeps Unity's first white frame behind the person's window. The 25 s
  foreground watch from before is the test; it has not been repeated with the hook installed.
- The hook lives in the launcher's process, and its lifetime decides what it can cover: during `run` the launcher is
  alive for the whole batch, but a bare `launch` returns once the clients answer, which takes the hook away with it. The
  next step is either a small resident helper next to the launcher or an in-game install - and the in-game one cannot
  catch the very first activation, because the plugin starts after the window exists.

# A followed continue keeps no character

- Status: Done (2026-11-17) — the focused row and the full suite both read the restored character after
  the continue (`68d4f1c66`, artifact `0.1.0+68d4f1c66`).
- Priority: High
- Created: 2026-11-17

## What the player sees

The host saves and clicks Continue. The member is still in the session and its client follows the
host's entry instruction, so it never reconnects — it regenerates the world and builds a fresh body.
That body comes up with the starting supplies, and the host's store then holds the fresh kit
instead of the restored character: the member's items, their colours and the saved health are gone,
and the host's own copy of the member shows the same fresh kit. A member that reconnects instead of
following keeps its character, which is why the earlier colour evidence passed.

## Root cause

Two defects, one on each side of the entry instruction:

1. **Host — the hand-over was on the wrong seam.** The continue's `WorldJoin` is sent by the
   start-gate invitation pump (`StartGateJoinPump.Update`) *before* this host has entered its own
   world, while the hand-over hung off the host's world-entry edge and its store guard required
   `LocalInWorld`. That guard was false at the invitation, so nothing was sent; the fresh body's 1 Hz
   report (`SaveReportedCharacterData` → `SaveCharacterData`) then replaced the bound row, and the
   reconnect adoption handed the fresh kit back. The receiver half already existed: a peer hand-over
   is kept across a follow (`LocalCharacterRestoreQueue`, `CancelOwnRunRestore`), and the host is
   supposed to send it before the instruction on the same reliable ordered channel — the pattern
   `RespawnCoordinator.cs:132-139` already uses for a menu-side guest.
2. **Guest — the follow cancelled the hand-over.** A following member's entry runs
   `PreRunScript.StartRun` (authorised by the WorldJoin), whose patch calls
   `RunCoordinator.OnWorldJoinRequested` → `RunSaveCoordinator.BeginRun`. That method called
   `CancelAllLocalRestores`, i.e. the *own run* cancel, on a path a guest can only reach by
   following. The queue's contract (proved in `LocalCharacterRestoreQueueTests`: a peer hand-over
   survives a follow, an own-run entry does not) is the opposite: on a follow only the follower's own
   queued restore is void.

## Fix (implemented 2026-11-17)

- `CharacterDataStore.SendSavedCharacter(ulong steamId, bool runEntry = false)` + the entry ledger
  `CharacterEntryHandover` (one hand-over per member per run entry) and `BeginRunEntry()`;
  `ICharacterDataControl` carries both.
- `CharacterDataSync.HandOverEnteringMembers()` / `BeginRunEntry()`; `StartGateJoinPump` begins the
  entry when it arms after a continue and hands over in the same tick as `SendWorldJoin` (the
  instruction and the character travel together, in that order).
- `HandshakeHandler` passes `runEntry: ctx.World.HostRunPending`, so a mid-generation handshake's
  entry group also carries the character.
- `RunSaveCoordinator.BeginRun`: a guest following the host's instruction cancels only its own-run
  restore (`CancelOwnRunRestore`); the host keeps the full cancel.
- `RunCoordinator`: the world-entry fan-out hands over before its `WorldJoin`;
  `ReentryCoordinator`: the same before both targeted re-entry invites.
- Extraction that keeps the store inside its recorded size: `CharacterEntryHandover`, and
  `CharacterReconnectAdoption.FindSourceByName` / `RemoveStalePresence`.

## Residual

- A member that clicks its own start while a hand-over is queued cancels it by design
  (`CancelAllLocalRestores`): that is a different path from following the host's instruction.
- The host's hand-over is one shot per entry: if the receiver drops it for any other reason, the pump
  does not re-stage it within the same entry (the receiver's own report then owns the row). The
  acceptance reading is what proves the one shot lands.
- The checkpoint-adoption path found on 19:58 (`Adopted run 2 from the restored checkpoint (no
  world-join instruction preceded it)`) is fixed by the guest-side half above; a run that reaches
  `BeginRun` without a preceding WorldJoin now keeps the peer hand-over instead of cancelling it.

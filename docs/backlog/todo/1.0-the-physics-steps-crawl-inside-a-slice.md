# 1.0 - the physics steps crawl inside a slice

- Status: Todo
- Priority: High
- Scope: every acceptance row whose game work advances per physics step, and the suite's own cost of running rows back to back
- Raised: 2026-11-26 (the bandage row passes alone and cannot finish inside a slice)

## What the readings say

`medical-bandage` alone: `.acceptance/band-36`, suite wall 42.0 s, exit 0, PASS — the hand walks the lap, the roll
follows it, the limb's bleed stops.

The same row inside a five-row slice: `.acceptance/park-1` and `.acceptance/park-2`, both exit 1, the row failing after
31.4 s and 33.1 s on

> the bandage did not stop the limb's bleed: before 24.479, after 20.559

The drive's own frame trace (`BandageHandDrive.UpdateTraceText`, read through `minigame-live`'s `frames`) shows why: in
the slice the roll advances about four steps in thirty seconds (`roll0` … `roll60` with `h1` throughout), where one step is
the wrap's own twenty degrees (`reversing/release-1.0.2/Assembly-CSharp/BandageMinigame.cs:74-84`). Alone the same trace
walks the whole 360.

## What is ruled out

- **World generation.** The host log of the slice shows `[GenStream] segment 7 … 20` finishing at 07:45:26.627 with
  `done — 20 segments`, and the row starting at 07:45:51 — the world was READY before the row began.
- **The start gate holding `Time.timeScale` at 0.** `StartGateCoordinator.Update`
  (`src/CasualtiesUnknownOnline.GameAdapter/Run/StartGateCoordinator.cs:154-193`) freezes the world while it waits, but the
  same log carries `[Gate] replaying deferred alert 'Layer 1 Gravel lands'`, which only happens on release.

## What to read next, in this order

1. Both ends' `frame-clock` read at the moment the row fails (`frame-clock` reports the game's own frame counter), so the
   reading is a rate, not a hunch: the member's steps per second inside the slice against the same number alone.
2. `Time.timeScale` and `Time.captureFramerate` on the member at that moment — a scale that is not 1 and a capture rate
   that is set both slow the step without anyone writing "pause".
3. Whether the row before it leaves the member's client in a state that costs frames: `.acceptance/park-2` ran
   `world-fingerprint` first, which walks the host to a block and drives swings; `cost-1` (ten rows, no walking row) did
   not show the slow step.

## Design

- `docs/design/cross-cutting/input-and-intent.md` — the gesture is the player's, and the client that reads it is the one
  whose clock this ticket is about.
- `docs/design/items/medical.md` — the wrap family and the entry the row drives; the twenty-degree ratchet it steps by.

## Why this is a batch defect, not a row defect

A row that needs the game to advance (the wrap, the shrapnel pull, the radiation line, the injection) reports a false
reading when the game's steps crawl: it measures the batch's frames, not the mechanic. Fixing it in the row would mean
waiting longer, which is exactly the cost the 480 s budget forbids; the cause is in what the suite leaves running between
rows.

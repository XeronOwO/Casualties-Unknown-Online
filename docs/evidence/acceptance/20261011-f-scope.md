## The capability this batch adds: the user's own hand

Batch `20261011-e` established WHY its tooling cannot produce the gesture — the evaluator runs on the
main thread and freezes the game's frame loop, and a pointer outside the client window makes the frame's
own `GraphicRaycaster` cast nothing, whatever the ring's position — and its scope named two ways out:
ask the user to place the pointer, or take a rule decision about moving the game window. **This batch
takes the first: the user is at the machine and has agreed.** The division of labour is fixed here so
the record can judge it:

- **The user** puts the physical pointer inside the operator's client window and presses the game's own
  favourite key (`favourite`, bound to `F`) once per row, leaving the pointer where it is.
- **The tooling stages everything else**: opens the remote backpack view, brings the target ring button
  under the pointer through the game's own ring geometry (`remote-gesture mode=hover cast=<n>`, which
  never moves the OS pointer), reads the geometry back (`mode=list`), and reads every census and log.
- **The mark is never installed through the fixture path** (`favourite-marks.cs mode=toggle`) for the
  rows this batch judges: a fixture-created mark is exactly what row 1's gesture half must NOT be. The
  fixture path stays available for a mark a LATER row needs (row 4's precondition), and the record says
  which mark came from which path.

**What the run actually did, recorded after the fact.** When the batch reached the press, the user pointed
out the flaw in the plan above — the game and the chat are two windows and only one of them can hold the
focus, so "leave the pointer there and read the instruction on the screen" is not something a person can do
— and authorised the run to drive the pointer and the key itself, **for this batch only**. The run asked
which of the two the user meant — this once, or a change to the standing rule — and the answer was "this
once". The actuator is the batch artifact `input-tool.ps1`; each client window was raised with
`AttachThreadInput` plus `SetForegroundWindow`, the pointer was placed inside the client area and read back
(`inside: true`, `focused: true`), and every press was made only after the target ring button read under the
pointer. Nothing under `tools/` gained a cursor or a keyboard call, the rule stands, and the finding is
folded into `docs/acceptance/lessons.md` and `docs/acceptance/dependencies.md`.

## Plan and the world it needs

One world, one chain. The rows share a session: mark a remote item (1b, RI-7), then transfer that same
item to the operator (4), then press the key on the operator's own inventory (6). Rows 2, 3, 5 and 7 of
the `favourite` ticket are already `pass` from batch `20261011-e` and are not re-judged here; no row of
this batch needs a cut, a rejoin or a save.

Staging order inside the session, each step one driver call:

1. host creates the lobby, both sandboxes join, the host starts the run;
2. the owner's fixture items are created on the host's own body (`item-provide mode=create`) and the
   operator is placed beside the owner (`body-place`) with its limbs checked (`probe-slots.cs`, a local
   artifact: a body that fell has `canPickUp=false` on every slot);
3. the operator opens the owner's remote backpack (`remote-gesture mode=open owner=<owner>`), and the
   batch reads the geometry (`mode=list`) to name the ring button that will carry the mark;
4. **the user places the pointer and presses the key** (row 1b / RI-7), with the drag staged by
   `mode=hover cast=<n>` in the call immediately before the press;
5. the transfer (row 4), then the press over the operator's own inventory (row 6).

If the pointer's own reading (`mode=list`) shows it outside the operator's viewport, the batch asks the
user to move it and re-reads the geometry — it never proceeds on a press it cannot place.

## Limits this batch must state in its record

- **The gesture is judged from the user's press, not from a tooling actuation.** The record names the
  press, the call that staged the ring, the log line it produced and the geometry read before it; a row
  whose press did not produce a line stays `unproven`.
- **The frames may not carry the visual halves.** Batch `20261011-e` captured the ring with its
  GameObject inactive and the scene rendering dark, so a star may again be read from the live rendering
  state (the display proxy's `favourited`, the one field `InvButton.UpdateGraphic` tints with) rather
  than from a frame; the record says which of the two it used.
- **The fixture items do not survive a cut** (batch `20261011-e`); this batch needs no cut, and any item
  a row needs is (re)created in the same world state the row reads.
- **The mark's identity rests on the item instance id**, and the id-reuse path is
  `todo/item-id-counter-is-not-resumed-by-a-restore.md`; nothing here needs it.
- The behaviour of an item that has LEFT an inventory stays the game's own (the native tooltip draws
  whatever flag the item carries); it is not a row of this batch.

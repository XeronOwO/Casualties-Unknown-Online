## The capability this batch needs: the physical pointer, once

These rows are the gesture itself. `CrossPlayerDragUse` reads `Input.mousePosition` and the game's own frame
casts the UI under the real pointer, and the project's in-process driver deliberately never touches the OS
input state (decision 237; `AcceptanceDriverGateTests`). The user therefore authorised this batch, once, to
drive the physical pointer and keyboard from a batch-local actuator: the actuator lives in the batch artifact
directory, nothing under `tools/` gained a cursor or a keyboard call, and the standing rule is unchanged.

The actuator is `.acceptance/20261022-f/input-tool.ps1` (local artifact, never committed): one action per
invocation — `move`, `rightdown`, `rightup`, `keydown`, `keyup`, `foreground` — using `SetCursorPos`,
`mouse_event` and `keybd_event` on the client window the run itself started. Before every press the run
reads the client's own `remote-gesture mode=list` answer (the pointer's `mouseX/mouseY`, the ring's buttons
and their `pointerInside`) and the client's `focused` state, so no press is sent to a window or a point the
run has not read.

## Plan and the world it needs

One world, three clients, one chain. The giver is the first sandbox's client; the receiver is the host; the
second sandbox's client is the second target for row 5.

1. Host creates the lobby, both sandboxes join, the host starts the run; every client enters the world.
2. Bodies are brought together through `body-place` (a declared setup substitution): the host at one point,
   the two sandboxes three world units either side of it, all conscious and healed.
3. The giver's fixture item is created on its own body (`item-provide mode=create`) and its slot read back;
   the receiver's ring holds a distinctive item so the opened backpack is recognisable on a frame.
4. The giver's own ring is opened with the game's own `toggleinventory` key, and the ring's button geometry is
   read (`remote-gesture mode=list`) before every press.
5. Rows 1, 9, 10 and 2 share one drag: the pointer enters the receiver's range (frames at the range and on the
   displayed backpack), then returns to the receiver's body and releases.
6. Row 7 re-opens the ring and releases the item on another of the giver's own slots.
7. Row 5 uses the second target: the drag enters the host's range first, then the second client's, is read
   there, and releases inside the second client's range.
8. Row 8 sets the rule through the host's own console (`/hostrules`), reads the refusal, then restores the
   rule. Its middle value needs the receiver unconscious, forced through `body-force` and restored after the
   row.

## Limits this batch must state in its record

- The gesture is judged from the frames and the logs of the exact press, move and release the run made; a row
  whose press produced no reading stays `unproven`.
- The bodies are placed by `body-place` and the fixture item is created by `item-provide`; both are declared
  setup substitutions, not part of the gesture.
- The drag crosses world positions only; it never changes the game's control scheme.
- Rows 3, 4 and 6 are the ticket's unit 2 and are not judged here; the ticket stays in `todo/` whatever this
  batch reads.

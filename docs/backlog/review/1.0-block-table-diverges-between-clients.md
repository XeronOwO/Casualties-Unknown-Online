## The member's own world was still generating (2026-11-13 03:08)

`BlockBreakSync.OnRemoteBlockDamaged` (`src/CasualtiesUnknownOnline.GameAdapter/World/BlockBreakSync.cs:237-247`)
returns silently while `WorldGeneration.world == null || HarmonyTraverse.IsGenerating()`: the comment explains
that during (re)generation every cell belongs to the previous layer. For a relay from the host that is a
permanent loss — the guest has no pending entry to re-report (only a breaker does), and the member's own log
carries no warning line for it. The suite's `block-sync` runs right after its own fresh run, exactly when the
member's world is still generating, so the break it stages is dropped by the guest and the member's table
diverges by design of this branch.

The product question (which side owns the catch-up) has three candidates:

1. **Buffer the relay while generating and apply it when the world is whole** — keeps the host's order; needs a
   small queue keyed by cell with the same generation stamp, dropped on a layer change.
2. **Ask for a block snapshot after generation** — the entry fanout already repairs a joining member; a
   generating member could request the same after its world finishes.
3. **Keep the drop, and make the *fixture* wait for the member's generation** — cheapest, but a player whose
   client is loading while the host mines keeps a stale cell for the whole session.

Recommendation: (1), because it fixes the player-visible loss without a new snapshot path; (2) is the fallback
if buffering proves too wide. The bookkeeping (layer stamp) already exists in the message.

## Option 1 landed and judged on the deployed build (2026-11-13 03:30)

## The investigation (2026-11-14)

The read path is the data, not the view: `block-read-at` and `block-band-digest` call
`WorldGeneration.GetBlock(cell)`, which reads `worldBlocks[x, y]`
(`reversing/release-1.0/Assembly-CSharp/WorldGeneration.cs:807`); the Tilemap chunks are a picture of that
array (`UpdateChunk` re-stamps a chunk from it, `:1582-1592`; `UpdateWorld` redraws all of it,
`:1491-1504`). So a differing digest is differing DATA on the two clients.

Writers of the data: `SetBlock` (`:774-806`), the block-break path (CUO relays it), and
`GenerateObjectAtPos(pos, tilemap, chance, genMode)` (`:1640-1669`) — the structure stamper, which at
runtime goes through `SetBlock` (`:1658`, `:1667`) and consumes `Random` per cell (`:1646`). Its callers
include runtime structure placement (`:1945`, `:2637`, `:2647`, `:2665`, `:2681`, `:2698`) and the layer
start's player-anchored carving (`WorldPlacePlayer`, `:2556-2568`, which also stamps the lifepod at the
body's position and therefore only agrees while both bodies spawn at the same point).

Next probes, in order: (1) after world entry, capture both totals, idle 45 s with neither body moving, capture
again — if they drift while idle, the game's own simulation runs on one client only; (2) if idle is stable,
move ONLY the host's body across the differing band and re-read both; (3) name the writer from the host's own

## Root cause

CUO relays ONE kind of write: `BlockBreakSync` hears `OnBlockDamaged` (a break) and sends a
`BlockDamagedMsg`. Any other runtime writer of the block table — here the game's own
`GenerateObjectAtPos` structure carving, which goes through `SetBlock` (`WorldGeneration.cs:1640-1669`) —
writes on the client that ran it and nowhere else. The host is the authority, so its table is the truth and
the member's copy silently drifts; the divergence lands wherever that structure was placed, which is why it
looks like "the band the host walked".

## The fix (design)

Relay at the WRITE, not at the break. The seam is `WorldGeneration.SetBlock(Vector2Int, ushort)` — every
runtime write goes through it (breaks included, and the break relay keeps its drops on top). A host with a
live session sends the cell and the new block to every member; a member applies it through the same
generation-deferred path `BlockBreakSync` already uses (a write that arrives while the world generates is
queued and drained once the world is whole), and a write being applied must not re-send (the existing
`CallContext.IsWithin(CallContext.Origin.RemoteApply)` guard). The recorder above proves the entry point and
the shape of the traffic; the protocol message, the world interface pair and the handler tests are the
implementation slice.

### The seam is already wired, and the write is captured (2026-11-14)

Read before writing anything: `WorldGeneration.SetBlock(Vector2Int, ushort)` is ALREADY patched
(`src/CasualtiesUnknownOnline.GameAdapter/Patches/WorldGenerationSetBlockPatch.cs`), and its postfix calls
`WorldGenPatchAdapter.OnBlockSet` → `WorldEventSync.OnBlockSet` (`src/CasualtiesUnknownOnline.GameAdapter/World/WorldEventSync.cs:192`).
That method skips remote applies and generation, then,
for the host, diffs the write against the generated baseline and calls `_world.ReportBlockState(x, y, block)`
(equal to the baseline → `RemoveBlockState`). So the host DOES capture these writes.

The open question is therefore not the entry point but the LIVE delivery: the member's copy kept the
baseline value, so either `ReportBlockState` only updates the host's difference table (and the table reaches a
member only when it joins/checkpoints), or a live message is sent and the member refuses it — the
generation-relation guard drops a report whose stamp reads stale (`BlockReportChannel.cs:190-205`). Next
probe: read the member's own log around a live structure write and its `[BlockSync]`/relation line, and read
`ReportBlockState`'s send path; that names which of the two it is before any message is added.

## Root cause: the world is generated around each client's own player (2026-11-14)

The four lines the diagnosis rule asks for:

1. **The reading.** Both clients are in one run; their block tables differ on 34 rows in band 900-1023, the first
   at row 988. At world entry both logged the same `[WorldFingerprint] total 638072155F2897B6`, so the tables were
   equal when the world started. The host's log carries `[SetBlock] 523,1015 -> 0 from
   WorldGeneration.GenerateObjectAtPos.`; the member's log carries no such line.
2. **The line that produces it.** `reversing/release-1.0/Assembly-CSharp/WorldGeneration.cs:2566` —
   `this.GenerateObjectAtPos(this.WorldToBlockPos(PlayerCamera.main.body.transform.position + Vector3.up * 4f),
   Resources.Load<GameObject>("LifepodStart")...)` inside `private IEnumerator WorldPlacePlayer()` (line 2556),
   after `PlayerCamera.main.body.PlaceBody()` (line 2560) and three `GenerateBlockCircle(...)` calls centred on the
   same local body position (lines 2563-2565).
3. **The trigger chain.** run start → the world's generation coroutine → `WorldPlacePlayer()` → `PlaceBody()` puts
   THIS client's own body at a spawn point → the starting pod and the clearing circles are stamped around that
   client's own body position → `SetBlock` writes them into `worldBlocks`, which `GetBlock` reads. Two clients
   that place their bodies differently therefore write different cells from the same code. **Still open:** which
   caller re-runs this at runtime on one side only — the coroutine normally runs once per client at world start,
   and the first divergence appears later.
4. **Why the fix removes the cause.** A fix that only forwards the host's writes treats the symptom: the tables
   were equal at start and the member holds a different world afterwards. The cause is per-client generation of
   terrain that depends on the local player's position; the cause-level fix is one generator (the host's) whose
   table members adopt, not a second generator plus a repair stream. Which shape it takes (stream the host's
   blocks, or generate on the host and hand the table over) is the design decision this ticket now owns.

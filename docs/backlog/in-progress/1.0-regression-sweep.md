- Status: In progress — batch 1 (medical view and panel) is read end to end; batch 2 (items) is next.
- Priority: High

- Language: English only in this file; the player-facing sentences are quoted from the evidence files.

## Why

The 1.0 adaptation is read end to end and the build is playable, but the previously verified
gameplay rows were judged on the demo build. The release changed the game under the same
ticket names (the amputation infection gate left `Item.DoAmputate`, `BuildingEntity.health`
became a property, `PlayerCamera.following` left), so a row that passed on the demo is not
evidence for the release. The user's order is to re-read the full set of rows (translated:
"run the full regression").

## What a row means

A row is one player-visible behaviour a done ticket verified (its acceptance rows, or the
verification section this corpus uses). It is re-read on the release install the same way the
original was read: a fixture derived from the ticket and the design page, a staged input through
the acceptance channel, and a measured reading from the client that experiences it. A row
passes only with a reading in this sweep's evidence file for its batch. A row that differs is
either fixed (if the adapter is at fault) or filed as its own ticket with the reading.

## Reading discipline

- A row is judged by the client that experiences it; the host's log is the corroboration.
- A reading that only proves the mechanism (a unit test) is not a row reading; the row is read on
  the running build.
- A batch's rows that fail keep the ticket open until the fix is deployed and the row re-read.

- block-sync (host break → member's block table) — carried by `tests/CasualtiesUnknownOnline.AcceptanceSuite/Cases/BlockSyncCase.cs`, green in the full run since 2026-11-13.
- eat-sound (a host's eat plays on the member's machine) — carried by `tests/CasualtiesUnknownOnline.AcceptanceSuite/Cases/EatSoundCase.cs`, green in the full run since 2026-11-13.
- water-shake (the game's own `dogshake` clip) — **manual**, and the reason is a reading: `Body.HandleDogWaterShaking`
  returns early when `!this.hasFur` (`reversing/release-1.0/Assembly-CSharp/Body.cs:3661`), so the routine is a dog's
  routine and no recipe can wet an animal; seeding the player body (`body-wet wetness=40 temperature=36`, wetness read
  back 40) left the recorder at `raw=6206|` with no `dogshake@` in twenty seconds. The row needs an animal fixture that
  does not exist, so it stays a visual/ambient row rather than a case.


- mine-blast (a host's mine removes a building on the member's own copy) — green in the full run since 2026-11-13: the
  staging places a landmine and a `containercrate` on real soil, the host presses the mine, and both clients' own object
  census lose the crate (`world-object-census`'s `containercrate` group falls on the host and then on the member). Its
  first attempt judged the mine's own block cell, which the game's explosion does not carve (block 2 before and after on
  the host) — the witness is the building, not the terrain.

## 2026-11-18 — the shrapnel session: one wire defect fixed, then the row read green

- Batch 1 is now read end to end. The other five treatments (bandage, tourniquet, splint, injection, CPR) each have a
  green by-name row on the deployed build; this one does too, after a product defect and two fixture defects were cleared.
- **Defect found and fixed (product code):** the five medical-operation messages carried the limb index in a protobuf
  field whose type default is 0, while their property initializer was -1. A limb at index 0 therefore arrived as -1 on
  the reader: `[MedicalTargetCheck] answered request 1 for 1 (Shrapnel limb -1): Target limb not found.` while the host
  had sent limb 0. New `src/CasualtiesUnknownOnline.Runtime/Protocol/Messages/MedicalLimbWire.cs` (`Encode` = index + 1
  for a real limb, 0 for none; `Decode` = the inverse) is applied to `MedicalOperationStartRequestMsg`,
  `MedicalOperationTargetCheckRequestMsg`, `MedicalOperationStartAckMsg`, `MedicalOperationStateMsg` and
  `MedicalOperationEndCommittedMsg`, with `tests/CasualtiesUnknownOnline.Tests/Protocol/MedicalLimbWireTests.cs`
  round-tripping limb -1, 0, 5 and 15 through `ProtoBuf.Serializer` and pinning the omit-the-field case. After the fix the
  same run answers `(Shrapnel limb 0)` — the limb now crosses.
- **Fixture defect one:** the row read the patient's limb with `seed-shrapnel count=0`, which is the game's CLEARING
  call — so it erased its own three pieces and then read the erase, and its `remaining < pieces` assertion passed on an
  empty limb. Both reads are now `limb-read`, a non-writing reader; the head limb it had also picked (a shrapnel removal
  on a vital limb is not the family's row) is excluded by name.
- **Fixture defect two:** the operator's hand was never written. The game removes a piece only when the wound view's own
  `ShrapnelMinigame` hand grabs, breaks and lifts it, so the committed declaration `shrapnel-break6` is declared and run
  as the operator's hand. Its recipe still looked the declaration up by exact type name — the Roslyn nesting defect fixed
  for the bandage family on the same day — and gained the simple-name scan.
- **Reading (2026-11-18, `.acceptance/medical-shrapnel8`, PASS, case 2.9 s on `0.1.0+a406afa29`):** seeded
  `limb 2, shrapnel 3`; the operator's display reads `limb 2, shrapnel 3`; the special starts the session; the hand drives
  `{"started":"started","count":3,"pieces":"5","steps":3,"trace":"start:coroutine-accepted"}`; the patient's own limb
  afterwards reads `skinHealth 83.756, bleedAmount 1.846, pain 37.508, shrapnel 0`; the host's line reads
  `break-grasp applied to <member> limb 2: skin -5.234825 bleed +0.5729877 pain +11.36637`.
- The wire fix stands on its own: it is three lines of product code plus five messages and a unit test, and it corrects
  every remote medical operation that targets the first limb — the row above only exposed it.

## 2026-11-19 — batch 19's give-into-backpack row: the body-slot path is silent natively

- The 2026-10-25 ticket (`done/give-into-backpack-plays-no-sound.md`) closed the reachability half and left the clip to
  the ear. This cycle gave it a device: the existing `give-item` row armed the one-shot recorder with
  `mode=start match=backpack` on both clients before the drop, then drove the give through the bridge's own release call
  (`give-probe mode=give-world`) and read both recorders after the bag listed the item.
- **Reading (2026-11-19, `.acceptance/give-sound1` and `.acceptance/give-sound2`, FAIL by design while the check was in
  the row):** the item landed in the member's bag in both runs; the member's recorder read `raw=833|` in the first and the
  giver's `raw=110|` / the receiver's `raw=110|` in the second — none carried `backpack`. The same recorder read
  `scrapmetal@22.2` and `rock@18.8` in the neighbouring rows, so the instrument is not the silent part.
- **The silence is the native answer for a body-slot give**: `Body.PickUpItem`
  (`reversing/release-1.0.2/Assembly-CSharp/Body.cs:1467-1483`) plays `PlayBackpackSound()` only when the moved item has
  a parent container. The giver's apply branch in `src/CasualtiesUnknownOnline.GameAdapter/PlayerInteractionApply.cs`
  already carries the user's ruling that a body-slot give must not add the container sound. So this row is READ: silent
  is correct here, and the earlier CUO-added sound was the defect the ruling removed.
- What the reading does not cover is the container half (an item taken out of, or placed into, a container during a
  give). Read on 2026-11-19: it was silent too, and for a different reason — the give loads the item through CUO's own
  container intent, so the game's drag-side clip never ran. `ContainerMoveFeedback` now makes that call at the container
  accept points, and the focused row `.acceptance/give-container5` PASS (case 4.8 s) reads
  `backpack2@23.6` on the member's recorder. Ticket: `done/1.0-give-container-sound-unread.md` (residual: the clip can be
  heard twice because the placement and intent seams both run).
- The check was withdrawn from the batch row (it asserts the wrong side's clip) and the finding is recorded above; the
  row's verdict is "silent by native rule, container half read green".

## 1. Why this batch exists, and what the fixture is

The ticket's rows 1–4 and 7 are judged by the behaviour suite (the build site driven with the production
provider, the 32-field census, the decay-flag census, the three refusals, the battery-plus-condition shape).
Its rows 5 and 6 are the ones only a live session can answer: the declaration must materialize on BOTH
peers, and the game's own presentation of that item must be the one the author described.

**The fixture, and the change this batch made to it.** The rows need a MOD ITEM in the live game, and this
tree's only in-repo mod is `cuo.example`, whose attribute-declared `example.dressing` is the item the mod API
pages use as their example. Batch `20261011-i` recorded that the dressing "declares no item content beyond
the dressing" and that placing its DLL would "judge nothing" — true for the effect and item-action tickets,
and false for this one: the dressing's own recognition gate is exactly what these rows read. It was also
static item info only, because it declared no `TemplateId`, so the adapter could not materialize a runtime
object for it and no live instance existed to read a hover from. Commit `03b8e493` therefore gives the
dressing `TemplateId = "bandage"` — a fixture change, not a product change, and the shape a real content mod
ships. The DLL is placed in the install's `plugins` tree for the run (the same place the in-repo pinyin mod
occupies) and is NOT part of the product's deployment; the run records where it was placed and removes it at
the close.

## 3. Setup the session runs

S0 — **session, instruments, log marks.** Host through Steam, guest through the sandbox; both enter one
world through the game's own Online UI; the Online UI window is closed on both before any world read. Then
the instruments are smoked before any row depends on them: `drive-in-process.ps1 -Action state` on both
endpoints, and a byte-offset log mark per client.

S1 — **the fixture materializes (rows 1, 4).** The example mod is loaded on both clients; the dressing's
definition is read out of each client's own `Item.GlobalItems` in the same pass, and each client's provider
lines over the mark are read.

S2 — **the gate's own answer (row 2).** Each client's reading body (`PlayerCamera.main.body.skills.INT`) is
read beside the gate, so `recognizable` is this run's reading rather than an assumption about the character.

S3 — **the presentation (row 3).** A live `example.dressing` instance is created through the game's own item
creation path (the driver's `item-provide` recipe) on each client, and `PlayerCamera.ItemHoverDescription`
is called on it — the game's own method, not a re-implementation of its branch.

S4 — **close and census (row 5).** Both clients quit through the game; the run confirms no process it
started is left; each client's log is censused for `[ERR]` over the mark, and the fixture DLL is removed
from the plugins tree.

## 4. Capability boundary

- Two clients in one world. No third-peer row is claimed.
- The ticket's row 5 as originally worded also named the tooltip's warning line, which prints the required
  INT. That line is only reachable for a declaration with a POSITIVE gate; this fixture declares 0, which is
  the fix's own default, so what the run judges is the gate the warning would print (`rec.min`) and the
  branch the hover takes. A positive-gate mod item is not in this tree's fixture and is named as a limit
  rather than approximated.
- The item instance is created through the game's own creation path, and the hover is the game's own static
  method; no forced state write is used anywhere in this run.
- The sandbox copy's shadow is checked before launch: the primary sandbox carries no `plugins` tree of its
  own, so the guest reads the physical install's deployment and its fixture.
- Ad-hoc probes stay evals of the same channel; every probe a record cites is written into the batch's own
  artifact directory as its own file, and a probe general enough to reuse is promoted into
  `tools/acceptance/recipes/` before the batch closes.

**Tickets not judged in this run, and why.** The batch is bounded by the world it needs (workflow §1): this
session's fixture is a plain two-client world with one mod loaded and one mod item in it.

- `docs/backlog/review/mod-authored-effects.md` and `docs/backlog/review/mod-item-authored-actions.md`:
  their end-to-end rows need a mod that REGISTERS a liquid effect / an item action. This batch makes their
  fixture half reachable (the dressing now materializes as a real item), but the example mod registers no
  function, so placing it still judges none of their rows; the gap stays recorded on them.
- Every other ticket in `review/` needs a different world (a treated limb, a third client, a save cycle, a
  specific trap layout) and is its own batch.

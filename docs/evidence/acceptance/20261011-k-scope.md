# Batch 20261011-k — scope and acceptance plan

The acceptance plan for batch `20261011-k`, written before its session (workflow §3): the ticket set, the
setup the session runs, the row-level classification and the capability boundary the verdicts must respect.

- Tickets in the batch, all code-complete and waiting only on a live session:
  - `docs/backlog/done/mod-authored-effects.md` — the liquid half's end-to-end row, its load-time
    diagnostic and the two guard rows its own `Limits` says ride the acceptance row.
  - `docs/backlog/done/mod-item-authored-actions.md` — the item half's end-to-end rows: the use action
    through the game's own `Body.UseItem`, the limb action through the wound view, and the cross-player
    limb-tool chain running the item's own delegate on the treated player's client.
  - `docs/backlog/done/mod-declared-behaviour-with-no-function.md` — the reachability row whose fixture
    the two cycles above completed: a declared flag with no function reports instead of throwing, and
    CUO's own custom-world-byte drink handler refuses a delegate-less registry entry.
- Commit under test: `f9507771` — the commit that registered the example mod's three functions and
  declared the two shapes with no function. No `src/`, `tests/` or `tools/` change is expected from the
  batch itself; if a probe proves reusable it is promoted under `tools/acceptance/recipes/` before the
  batch closes, and the record names the commit the deployment was built from either way.
- Artifact: `CasualtiesUnknownOnline.dll`; `tools/verify-deploy.ps1` is run in this batch and its output
  captured before any client starts.
- Dependencies: `tools/acceptance/preflight.ps1` and `session-environment.ps1 -Mode status`, captured into
  the batch artifact directory before the clients start.
- Session: **one world, two clients** — host on the physical machine (launched through Steam, so
  Steamworks initialises), guest in the primary sandbox. No third-peer row is claimed, so the alternate
  sandbox is not launched.
- Artifacts: the batch directory under the local artifact area, cited by file name only.

## 1. Why this is one batch

All three tickets' remaining rows are about ONE fixture: the in-repo example mod, whose `example.dressing`
carries a use action and a limb action, `example.tonic` carries a drink effect and a liquid tile, and
`example.placebo` plus the tonic's limb half are the two shapes with no function. The fixture's own reach
gestures are the game's own ones (the world fluid cell, the inventory use, the wound view, the medical
view's release on a peer's limb), so one world with two clients serves every row: the item is created on
the acting client, the liquid is placed in a world cell by the run, and the limb half is applied to a limb
twice — once locally and once on the other player's body through the cross-player limb-tool chain.

## 2. The fixture, and what the run does to it

- The example mod is **not** part of the product's deployment: `tools/deploy.ps1` ships no
  `CasualtiesUnknownOnline.ModExample.dll`. The run places THIS tree's build output into the install's
  `plugins` tree for the session, records the file identity it placed, and removes it at the close. The
  primary sandbox carries no `plugins` tree of its own, so both clients load the same file.
- The two shapes with no function ship with the fixture by design (`example.placebo`, the tonic's limb
  half); the run reads them where they are.
- The two guard rows (a throwing action; a throwing timed tick) have **no fixture in the tree**. The run
  supplies the throw through the framework's own registration surface from inside the acting client — one
  declared setup substitution: it registers a throwing `use` action for `example.placebo`, which that
  definition's own `Usable` flag makes reachable, and that action starts a mod timed effect whose tick
  throws after its immediate tick. Nothing under `src/` is touched; the registration is the product's own
  `IModItemActions` path and the invoker under test is the product's.
- The tonic's pool is placed by the run: `SpawnAmount` is 0, so world generation never places it, and the
  run writes the custom world byte into the cell the body stands in — the same write
  `tools/acceptance/recipes/world-drink.cs` performs.

## 4. Order of the run

1. Preflight + `session-environment.ps1 -Mode status`; capture both, plus `verify-deploy.ps1`, into the
   batch directory before anything starts.
2. Build the tree; place this tree's `CasualtiesUnknownOnline.ModExample.dll` into the install's
   `plugins` tree and record its identity.
3. Start the two clients serially (Steam inside the sandbox first when it is not already running), one at
   a time, checking each one's log before the next starts.
4. Lobby + join + start run; close the Online UI on both; read each client's own definition tables (K2,
   K3, K1).
5. Place the tonic's world byte and drink it (K4); read the load-time diagnostics out of the two logs
   (K5).
6. Create the two fixture items and drive the item rows: the placebo's reporting use (K6), the dressing's
   own use (K9), the dressing's local limb apply (K10), the container route to the limb half (K7).
7. Drive the cross-player limb-tool chain: the operator opens the remote medical view on the peer, points
   it at one limb, and releases its own dressing onto that limb's `WoundViewLimb`; read the treated
   client's own log and limb (K11).
8. Clear the live drink delegate and drink the cell again (K8), then register the throwing action and read
   both guards (K12, K13).
9. Close both clients cleanly, remove the fixture DLL and re-read the removal, harvest the lessons, write
   one record per ticket and move the tickets per the verdicts.

## 5. Capability boundary

- Two clients in one world. No third-peer row is claimed, so nothing here is judged from a third view.
- The liquid's LIMB-EFFECT landing is not a row of this run: the fixture registers only the tonic's drink
  half, deliberately, and the limb half's own reach is the reporting path (K7). The item's limb landing
  IS judged, locally (K10) and cross-player (K11).
- The injection call site (`WaterContainerItem.Inject`) is not driven: it needs the syringe minigame,
  which no committed recipe stages. K3's live non-null `onHealthUse` delegate is the reading that covers
  that call site's precondition, and the record says so rather than implying the gesture ran.
- Ad-hoc probes stay evals of the same channel; every probe a record cites is written into the batch's own
  artifact directory as its own file, and a probe general enough to reuse is promoted into
  `tools/acceptance/recipes/` before the batch closes.

## 6. Exit criteria

- One record per ticket under `docs/evidence/acceptance/`, each naming the batch, the commit under test,
  the deployed artifact identity, one verdict and one evidence pointer per row, the dependencies used, the
  forced setups, the limits and any residuals.
- Transition per §3's verdicts, with the backlog index rows moved in the same change.
- Lessons fold into `docs/acceptance/lessons.md`, machine facts into `docs/acceptance/AGENTS.local.md`,
  and a reusable probe into `tools/acceptance/recipes/`.
- The gates run before the closing commit; the session ends with both clients closed, the fixture DLL
  removed and the machine free.

# The wire carries no prosthetic, so a friend never sees a fitted peg

- Status: Done
- Priority: High
- Owner: night run

## Where it came from

Row 25 of the acceptance rebuild (`docs/backlog/in-progress/1.0-rebuild-each-acceptance-row-from-the-game.md`) now fits a
real peg limb on a real stump through the game's own item action, and passes on the host. While reading the wire to judge
the member's copy, the state simply is not there.

## The four lines

1. **Reading.** The row's own claim is that the fitting shows on the friend's copy of the body. `CharacterLimbMsg`
   (`src/CasualtiesUnknownOnline.Runtime/Protocol/Messages/CharacterLimbMsg.cs:10-67`) carries `Dismembered`,
   `Splinted`, `Broken`, `Shrapnel` and the rest of the limb's medical state, and carries no prosthetic field at all.
2. **Code.** The member builds its copy of the host body from that message (`CharacterDataSync` decode → the body's limb
   rows), so the prosthetic's `hasProsthetic`/`itemId` (`Limb.cs` `ProstheticInfo`) never leaves the host.
3. **Chain.** Host fits a peg (`Item.cs:745-785` → `Limb.AttachProsthetic`, `Limb.cs:97-122`) → the host's own body shows
   the peg → the character report is built from the limb rows → the prosthetic is dropped on the way out → the member's
   copy keeps `dismembered` and draws a stump.
4. **Why this is the cause and not a symptom.** The member draws only what the message says; nothing else on the member
   side can learn the prosthetic, so any fix that does not put it on the wire cannot survive a reconnect or a clone
   rebuild — the same shape as the adopted-row loss after a restore.

## Design

The limb state the member draws is the character report's limb row, and its shape is fixed by the design page for what a
body carries across the wire (`docs/design/mechanics/medical-view.md` for what the viewer is allowed to draw, and
`docs/architecture/current.md` for the report's place between the game's body and the session). The prosthetic is part of
the limb's own state in the game (`Limb.ProstheticInfo`), so it belongs on that row for the same reason `Splinted` and
`Dismembered` do: it changes what the other player sees on the body, and nothing on the receiving side can derive it.

## Options
1. **Carry the prosthetic on the limb row** (recommended). Add the prosthetic's own identity to `CharacterLimbMsg`
   (flag + item id), encode/decode it, and have the member apply it through `Limb.AttachProsthetic(..., isLoad: true)`
   exactly as a loaded save does (`:275`). Consequence: one field pair on the wire, and the member's copy can show any
   prosthetic the game itself defines.
2. **Carry a "limb is a peg" boolean only.** Cheaper, but the game defines several prosthetics (`Item.PegLimbInfo` and the
   two crafted arms/legs at `Item.cs:824` and `:889`), so the boolean would show the wrong body on two of them.
3. **Leave it and drop the claim from the row.** Consequence: the product keeps a player-visible lie — a friend sees a
   stump where the game shows a peg — and the row's own claim has to be rewritten to say so.

## After the fix

- Row 25 gains its member-side half: read the member's copy of the host's limb and require the same prosthetic, then force
  a clone rebuild and read it again.
- The prosthetic's overlay material (`Limb.cs:121-122`) stays the game's own work; the row only has to see that the member
  drew a peg rather than a stump.

## Closing (2026-11-27)

`CharacterLimbMsg.HasProsthetic`/`ProstheticItemId` and the force/armour/rgb fields; `edefa9bfa` added the overlay sprite
path). The four lines above were the reading before that landing. What this cycle added is the row's member-side half:
`ProstheticCase` now reads the member's own scene through `limb-prosthetic4 mode=read` and requires the host's stump to

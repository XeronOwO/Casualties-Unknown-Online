## Why these three tickets are one batch

They are one scenario and one world. `medical-state-names-no-kind`'s row 4 IS a driven splint removal, which
is exactly `medical-removal-limb-component-not-applied`'s rows 1-4; the display ticket's rows are the same
session seen from the operator's panel. One deploy, three clients, one removal drive, and each row reads the
surface it owns.

## Setups the scenario needs

- **The world**: the host creates the lobby, the guest and the third client join, the host starts the run;
  all three read `inWorld: true` before anything is driven. The tutorial gate and the BepInEx tree are the
  usual preconditions (`session-environment.ps1 -Mode ensure-cuo`).
- **The patient's limb**: the guest seeds a splint into limb 2 (`seed-splint limb=2` — the game's own
  application shape, a DECLARED setup substitution; the removal under test is the native one), and the host
  seeds a splint into a second limb for the display rows if the removal drive takes the first one away.
- **The panel**: opened through PRODUCTION's own entry (`RemoteMedicalCoordinator.Open`, which
  `grip-slip-drive mode=open` and `remote-wound-special mode=open` now call) **in its own call**, with the
  action in the NEXT call. Every drive reports `displayBodyName`, and a name that is not `MedicalDisplay_*`
  fails the drive's own witness rather than being judged: production builds a parked copy, and the focus must
  be it.
- **No hand-built focus**: a recipe may not pass a live body to `RemoteMedicalView.Open`. If a production
  open refuses, that refusal and its guard readings (`sessionActive`, `localInWorld`, `isRemoteInWorld`,
  `hasSnapshot`, `hasHealth`) are the evidence, and the affected rows stay `unproven` — never worked around.

## The one-client probe

`tools/acceptance/recipes/limb-component-apply.cs` runs on ONE client and reads the removal's receiving
half directly through production's call:

- `mode=status limb=n` → the limb's components, flag, `enabled`, and whether the game's own `Start` ran;
- `mode=message-clear limb=n` → captures the body, edits ONE limb row to the authority's removal shape
  (no components, `Splinted=false`) and applies it through `CharacterDataSync.ApplyHealState`. On the
  unfixed build this read `componentsAfter=SplintLimb` beside `splintedAfter=false`
  (`red-message-clear-limb3.json`); on this build the component must be gone;
- `mode=add-disabled` / `mode=add-enabled` followed by a later `mode=status` → the inertness pair;
- `mode=drop` → cleanup.

Run it on the host before the session and again after the removal drive if a same-session reading is wanted;
either way the JSON is filed into this batch's artifact directory.

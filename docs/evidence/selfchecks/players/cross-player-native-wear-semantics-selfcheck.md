# Cross-player wear semantics from the game's own data self-check

Owner cycle: `todo/mod-cross-player-native-semantics.md` Part B, the wearable
(wear) chain. Decision: putting an item on another player stops carrying a table
— the game's own item data answers whether the item is a wearable, which limb it
goes on and which slot it occupies (`ItemInfo.wearable` / `desiredWearLimb` /
`wearSlotId` through the new `IWearSemantics` seam), while the host keeps the
allowed operation, the resource and the arbitration. The chain differs from the
three landed ones in one way that decides the whole design: **there is nothing to
measure.** A wear gesture runs no native action of its own on the operator's
client, so the item never leaves the operator's hands until the host has
committed the placement.

## 1. Mechanism inventory

|---|-----------|----------|
| 1 | The native wear implementation | `Body.WearWearable(Item)` (`Body.cs:1480-1518`): the occupancy check runs FIRST (`GetWearableBySlotID(item.Stats.wearSlotId)`) and returns while alerting `alertalreadywearing`; then `DoPickupCheck`, then `LimbByName(item.Stats.desiredWearLimb)`, then the dismembered-limb alert `alertlimbmissing`, then the parenting: `rb.simulated = false`, `SetParent(limb.transform)`, identity pose, sorting order `limb.sortingOrder + wearableVisualOffset`, and `Wearable.CreateSprites` when the item carries the component |

The deleted 40-row `RemoteWearCatalog` was a transcription of that flag |
| 3 | The slot the occupancy check compares is DATA, and it is not the limb | `ItemInfo.wearSlotId` (`ItemInfo.cs:142`) and `ItemInfo.desiredWearLimb` (`:139`) are both set per wearable in `Item.SetupItems()`; `GetWearableBySlotID` (`Body.cs:1590-1607`) searches **every** limb's children for `item.Stats.wearable && item.Stats.wearSlotId == id`, so two wearables in one slot collide even when they name different limbs. ## 2. Whole-family audit

| Mechanism | Verdict |

## 4. Verification design and result

- Focused: `dotnet test … --filter "FullyQualifiedName~WearTests|FullyQualifiedName~ItemUseTests|FullyQualifiedName~TakeTests|FullyQualifiedName~TransferTableRestoreMergeTests|FullyQualifiedName~RemoteUseOnSelfTests"` — green (40 cases, of which 7 are `WearTests`).
- The new gate: `dotnet test … --filter "FullyQualifiedName~WearChainContentGateTests"` — green (8 cases: the two facts, the census theory and its six samples).
- **Red observed before green, and the mutations are recorded rather than claimed.** THREE mutations were applied to the working tree and reverted, each run against the frozen-candidate tree: (a) the host's wear predicate forced false (`… && false`) → `WearTests` 3 failed / 3 passed (at the time the family held 6 cases); (b) the slot encoding changed from `-(limbIndex + 2)` to `-(limbIndex + 5)` → `WearTests` 3 failed / 3 passed; (c) the slot comparison replaced by a limb comparison (`wornLimbIndex == limbIndex`) → `WearTests` 1 failed / 6 passed, the single red being `Wear_TheSameWearSlotOnADifferentLimb_IsRefused`, which is exactly the discrimination the older same-limb case could not make. Under (a) and (b) the cases that redden are the three PLACEMENT ones; the refusal cases stay green, because a refused gesture has no placement to encode.
- The independent adversarial review (fresh context, `.agent-local/reviews/wear-native-semantics-review.md`) found **no blocker** and eight minor/nit findings, all fixed or bounded in this same commit: the harness fake's invented limb ORDER (removed — the rows now reproduce the deleted catalog's own `(slot, index)` pairs), the slot case's inability to discriminate (closed by the new case and its mutation), an unreachable second placement resolution plus a case named for it (the branch is now ONE seam call, and the case is named for the refusal it actually drives), a gate that checked one filename and a capability pin satisfiable by a comment (the four chain sources are read by path, the census is an EXACT set, and the capability pin is a Roslyn walk over code), a wrong refusal count, the loose `WearWearable` gate wording, the occupancy check's fail-open state (documented as a limit), and the affected side's dismembered-limb residual (now guarded in `WearableRestorer`).
- Full WITH build: `dotnet test CasualtiesUnknownOnline.slnx` — behaviour **4777/4777** (net48, 47-48 s) and gates **488/489** (net8.0) with the single red being this checklist's own pending boxes, which is the gate working; the standalone gate run after they were ticked and the FINAL run WITH build read **489/489 and 4777/4777** (exit 0). (An earlier in-cycle run of the same command read 4776/4776, before the review added the slot case that made `WearTests` 7.)
- Coverage direction, stated rather than implied: both directions have a case (guest-operator → host target, and host-operator → guest target), because the wear chain's two halves are the item's move and the target's adoption and each direction exercises a different kernel path (`AdoptTransferredItem` for a guest target, `CommitWornItemToHost` for the host). No case drives a third peer; that stays an acceptance-batch row.
- The native half is NOT verifiable in L0: `ItemInfo` / `Item.GlobalItems` / `Body.limbs` need a game process, so `GameWearPlacement` and the target's `RestoreWearable` parenting are pinned by the gate's source check and by the acceptance batch, not by an L0 case. What L0 pins is the predicate plumbing, the placement arithmetic, the slot rule and the wire.

## 5. Limits recorded

- **The host resolves the limb NAME to an index on its own local body.** The name → index mapping is a property of the character prefab's limb order (a per-body constant of the game build), not of the wearer's health, so reading it off the local body is answering a structural question; everything STATEFUL about the limb still belongs to the affected side (its snapshot decides presence/dismemberment, its client does the parenting). The residual assumption is the one the snapshot format already makes: every body in one session carries the same limbs in the same order, which is also what makes `CharacterDataCapture`'s index and the worn-slot encoding mean the same thing on both ends.
- **A session with no local body at all cannot resolve a placement on that client, and the gesture is refused by name.** The name→index answer has no source without a body. Reachable only where one side has no character in the world, which is the state the use path already refuses (both user and target must be in-world).
- **Occupied wear slots are still REFUSED, not emptied.** Native `Body.AutoPickUpItem` drops the occupying item to make room; the cross-player path reaches neither native entry, and dropping a worn item from a remote body into the world needs a world-drop fact (position, kernel ownership, a landed event) that this chain does not have. The deleted table did not do it either, so nothing regressed, but it remains a user-visible difference from picking a garment up off the ground yourself; a session that wants it needs its own design.
- **The occupancy check discovers an occupant through the same placement answer it needs for the incoming item**, so an occupant whose own `desiredWearLimb` does not resolve on the host's limb layout counts as free where native `Body.GetWearableBySlotID` (which compares the raw `wearSlotId` and needs no limb at all) would refuse. The state needs a worn item the host cannot place on its own body — the same single-prefab assumption the seam's limb half documents — and the independent review agreed the alternative (a second seam member returning the slot alone) buys nothing for a state a session cannot produce. Reported rather than hidden.
- **A wear the affected client cannot restore** (no prefab for the id, or a limb index out of that body's range) is logged and skipped by `WearableRestorer` AFTER the host has committed the move and the operator's item is gone. Unreachable for a placement the host itself resolved against the same snapshot; recorded because the resource is spent either way.
- **The affected side now refuses a dismembered limb itself**, exactly as native `WearWearable` does (`Body.cs:1494-1498`): `WearableRestorer` skips (and destroys the just-restored object) when the limb its own body holds is dismembered. That closes the residual the independent review found — the host's check reads the target's last REPORT, so a limb lost after that report would otherwise have received a garment parented to an inactive limb. The game's own flow is the specification here, and the guard lives on the side that owns the limb.
- **The limb index mapping is pinned by source, not by runtime.** `GameWearPlacement` reads the live body, so a renamed prefab limb or a game update that reorders `Body.limbs` is caught by the acceptance batch and not by any test — the L0 suite has no game assembly (the test project refers to `GameAdapter` with `ExcludeAssets="compile"`). The harness stand-in (`FakeWearSemantics`) therefore reproduces the deleted catalog's own `(slot, index)` pairs for the ids the suite uses and deliberately states no limb-name order at all: the index families it relies on are the game's own (`Body.LimbNum`: arm 3-5 / 6-8, leg 9-11 / 12-14), and a name order is not something the tree can state correctly — writing one was a review finding against this cycle's first draft of that file.
- **The wear slot rule is asked against the target's items on the HOST's snapshot.** That snapshot is report-driven for a guest target, so the occupancy answer is as fresh as the target's last report — the same window every host-side judgment over a guest body has, and a conservative one (a stale "occupied" refuses, it does not overwrite the target's own item).

## 6. Disposition of what the deleted table was pinned by

`RemoteWearCatalog` had no test file of its own: its rows were exercised only
through the chain cases in `WearTests`, so nothing is dropped and nothing is
rewritten in place. The four cases that existed keep their names and their
user-visible assertions — `Guest_WearsHelmetOnHost_MovesItemAndSendsWornResult`,
`Host_WearsHelmetOnGuest_MovesItemAndAdoptsForGuest`,
`Wear_TargetAlreadyUsesSameWearSlot_IsRefused` and
`Wear_TargetLimbDismembered_IsRefused`. What the table DID pin that no L0 case can
pin any more is its own coverage: the 40 ids and their 40 `(slot, limb)` pairs are
now the game's data. Three cases cover what a table cannot — the id it never
carried (`Wear_AnItemTheDeletedTableNeverCarried_…`), the refusal path a table
miss used to take and the ordinary non-wearable still takes
(`Wear_AnItemTheGameDoesNotCallAWearable_IsRefused`), and the slot rule's real
discrimination, which the vanilla table's own 1:1 slot↔limb mapping hides
(`Wear_TheSameWearSlotOnADifferentLimb_IsRefused`, added during the independent
review).

# A minigame's click-start edge never arms in the acceptance client

- Status: Todo — Rejected (2026-11-18)
- Priority: High
- Owner: unscheduled
- Created: 2026-11-18

## The edge fix landed; the row still does not advance (2026-11-18)

`VirtualInput.TryAnswerKey` now answers a DOWN query for every reader in its frame (Unity's own
`GetKeyDown` semantics) instead of letting the first reader consume the edge. Measured after the deploy
(`0.1.0+5613f04dd`, member client, repeated `press-key` while the pointer circled the roll):

- `minigame-live` read `handStarted true`, `lastActionAngle 20 → 40`, `fill 0.002 → 0.084` — the edge arms
  the minigame and the game performs bandage actions.
- The row itself still fails: `MedicalBandageCase` ran 42.3 s on a fresh pair (`.acceptance/bandage-edge2`),
  re-pressed every 250 ms, and the member's limb bled `8.795 → 7.281` without a single bandage action. So
  the remaining gap is the row's own session state at press time (the body's consciousness/pain, or the
  minigame not open in that session), not the input patch.

Next: read `minigame-live` from inside the row at the moment of the press (host and member), and compare
it with the hand experiment above; that difference is the next fix.

## What the player sees

Nothing directly: this is the acceptance instrument. Every row whose gesture is a *held* mouse button inside
a minigame is blocked behind it — the bandage treatment first, and the ending's gesture next.

## Design

The bandage row is the medical view's treatment read from the patient's own side: applying a bandage starts
the item's own minigame and the limb stops bleeding (`docs/design/mechanics/medical-view.md`, "a bandage or
splint starts the item's own minigame"). The game's own contract is a click-start edge plus a held angle
(`reversing/release-1.0.2/Assembly-CSharp/BandageMinigame.cs`: `Update` arms `holdingBandage` only when
`Minigame.game.handStartedClicking`, and `PhysicsUpdate` advances only while `holdingBandage`), so the row
needs the client's own input edge, not a state write.

## The reading (2026-11-18, deployed `0.1.0+664a21573`)

- The declaration channel works: `declare bandage-rub6` answers `{"ok":true,"declared":true}` and
  `bandage-rub-state` reports `starts 1, saw 1200, drove 1200` — the committed declaration loads and drives
  1,200 frames.
- The game performs **zero** actions: `bandage minigame = {"ran":true,"actions":0}` and the limb keeps
  bleeding (`before 15.034, after 13.511`; `.acceptance/decl-bandage-live`, suite row FAIL 42.7 s).
- The live read names the missing half: `minigame-live` shows `kind BandageMinigame, handClicking:false,
  handStarted:false, angle 0` with the staged pointer on the ring (`pointerX 960` = centre + 320). A staged
  press flips `handClicking` to true and a release flips it back — so the `Input.GetKey` call site inside
  `MinigameBase.UpdateHandVisuals` **is** answered by the acceptance patch — while `handStartedClicking`
  never becomes true and the input census reads `keyDownAnswers:0` over 25,045 key queries.
- The window is not reached by the patch's own counters: `handleAttacksEntries:0`, so `PlayerCamera.HandleAttacks`
  is not consuming the edge; the `GetKeyDown`/`GetKeyUp` replacements inside `UpdateHandVisuals` are the
  ones that produce no down answer.

## Root cause (narrowed, not yet fixed)

`src/CasualtiesUnknownOnline.Acceptance/InputQueryPatches.cs` replaces `Input.GetKey/GetKeyDown/GetKeyUp`
call sites through `TranspileKeyReads` and patches `MinigameBase.UpdateHandVisuals` for that purpose. On this
1.0.2 build the `GetKey` call is answered (the held state changes the field) while no `Down` query ever
answers true at that site, so `TryAnswerKey`'s staged edge (`DownPending`, then `DownFrame == frameCount`)
never reaches the game. Either the `GetKeyDown` instruction in that method is not the one the transpiler
matches, or the edge is consumed by a reader that runs first in the same frame.

## Options

1. **Measure which instruction forms are present** in `UpdateHandVisuals` on 1.0.2 (a `patch-info`/IL dump
   read), then extend `TranspileKeyReads` to match that form. Narrowest fix; keeps the row's current shape.
2. **Make the DOWN edge survive the frame for every reader** (`TryAnswerKey` answers true for all Down
   queries whose frame equals `DownFrame`, instead of consuming on the first). Removes the
   first-reader-wins class of defect for every minigame row, at the cost of a reader seeing one extra frame
   of "down" — the same shape the game's own `GetKeyDown` gives one reader per frame.
3. **Drive the gesture through a coroutine declaration** (a frame loop inside the client). The tooling
   already loads declarations; a coroutine channel would need a new seam.

Recommendation: 2, because it is a property of the instrument rather than of one game method, and because a
held-gesture row must not depend on which of the game's methods reads the edge first. Option 1 remains the
fallback if the measurement shows the call is not `Input.GetKeyDown` at all.

## In-row measurement (2026-11-18, after the edge fix)

The row now records `minigame-live` at its first staged press. `.acceptance/bandage-probe1`
(deployed `0.1.0+40e439bc5`, `medical-bandage` FAIL 42.9 s) read:

```json
{"ok":true,"hasMain":true,"kind":"BandageMinigame","handClicking":true,"handStarted":true,
 "handMagnitude":298.62,"pointerX":947.604,"pointerY":448.204,"angle":0,"didWrap":false,
 "lastActionAngle":0,"fill":0}
```

So the press does arm the click-start edge inside the row — the earlier hypothesis (the row's
press lands before the view is open) is falsified — yet 40 s of circling advanced nothing:
`angle` 0, `lastActionAngle` 0, `fill` 0, and the limb bled from 10.188 to 8.516.

What differs from the hand experiment (which reached `lastActionAngle` 20 → 40, `fill` 0.084):
in the experiment the press was repeated while the pointer already circled; here the first
press lands before the circle starts, and `holdingBandage` is computed only on the started
frame (`BandageMinigame.Update` sets it when `handStartedClicking`, then `PhysicsUpdate`
advances only while it is true). If that first started frame sees the hand off the roll, every
later frame runs with `holdingBandage` false, because no new started edge arrives — exactly the
`angle 0` reading.

Next step: sample `minigame-live` during the loop (holding, angle, handPos) to see whether the
game's own hand angle ever leaves 0 while the circle runs, and whether a started frame lands
with the hand off the roll. If so the fixture must press only when the hand is near the roll's
angle — that is the gesture the player performs — and the code needs no change.

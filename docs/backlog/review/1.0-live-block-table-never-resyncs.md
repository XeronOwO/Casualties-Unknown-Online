# A live member never resyncs the host's block table

- Status: Review
- Priority: High
- Area: Runtime / world state (block table)

## What the player sees

Two players stand in one run in front of the same spot, and the ground under it differs: one sees a hole where the
other sees a block, or a different block material. The world stays wrong for the whole run — nothing ever repairs it.

## What was measured (2026-11-14)

- `block-idle-drift` on the acceptance pair: 54 rows of the block table differ between the clients, the first at row
  966, with no player action in between.
- The generation is NOT the source: both clients' generation ran 19 segments with identical `[GenStream]` fingerprints,
  so the world was built from the same random stream on both sides.
- The differing cells were written by different steps of the same chain on each client (`GenerateBlockCircle` on the
  host, `GenerateObjectAtPos` on the member for the same cell), so the pod/circle centre — the local body position at
  `WorldPlacePlayer` — is the remaining root-cause candidate.

## What the code does today (read, not assumed)

- The host records a live write into its own table: `WorldEventSync.OnBlockSet` → `WorldService.ReportBlockState` →
  `WorldStateMessageService.ReportBlockState` (`src/CasualtiesUnknownOnline.Runtime/Session/World/WorldStateMessageService.cs:354-369`),
  which only stores the cell in `_damagedBlocks`.
- That table reaches a member at world ENTRY: `WorldEntryFanout` calls `SendBlockStateSnapshot(steamId)` (`:105`, `:158`).
- A live member hears only the two event shapes: a break (`BlockDamaged`) and a placement (`BlockPlaced`). Any other
  write — the game's own structure stamping, a cell a member never reported, a report the host refused — is never
  re-sent, so the member's table keeps its own value for the rest of the run.
- The existing periodic traffic is the opposite direction only: a member's pending mutation is re-reported to the host on
  a 60 s cadence (`docs/design/mechanics/world-interaction.md`). Nothing re-sends the host's table to a live member.

So the answer to "is there a periodic sync?" is: **no, not to live members** — only at entry.

## The two fixes this needs, and why both

1. **Root cause: the generation must produce the same world and the same pod centre on every client.** The remaining
   probe is the body position at the `WorldPlacePlayer` segment (logged on both clients). A fallback must never be used
   to paper over this: if the two clients build different worlds, the table they disagree about is not the defect.
2. **Fallback: a periodic block-table reconcile from the host to every live member.** It exists because a single lost or
   refused message must heal (`we already do this for the member→host direction; the host→member direction is missing`),
   and because a write the event shapes do not cover must eventually reach everybody.

## The fallback's shape (so it does not eat bandwidth)

- The host keeps, per member, the last snapshot it sent (a compact baseline). A reconcile tick (60 s, the same cadence
  the member→host re-report already uses) computes the DIFFERENCE against that baseline and sends only the changed rows;
  no change means no message at all.
- The row set is bounded by the game's own table (128 live damaged cells, `docs/design/mechanics/world-interaction.md`),
  so a full reconcile is at most 128 × (x, y, block) ≈ 1 KB; the differential is normally zero rows.
- The member applies a reconciled row through the same path it already uses for `BlockStateMsg` (idempotent, same value
  writes nothing), and the next reconcile's baseline moves only by what was actually sent.
- No snapshot is sent while the member is not in the world, and none is sent to a peer that has not confirmed the
  handshake.

## Acceptance rows

- [ ] A live member whose table was made stale by a host-side write realigns within one reconcile interval, read from
      both clients' own `block-read-at` on the same cell.
- [ ] A reconcile with no changed rows sends no message (read: the wire counter stays flat over an idle interval).
- [ ] A reconcile carrying N changed rows sends exactly those rows (read: the message's row count).
- [ ] The generation streams stay identical (the `[GenStream]` fingerprints keep matching) — the fallback never replaces
      the deterministic generation.

## What must not change

- The block table stays the host's (one table, the game's own capacity and order — the existing decision).
- A break and a placement keep their existing messages and their existing verdicts (first-writer-wins for a break).
- The fallback is invisible when everything works: no extra traffic on an idle run.

## Design

- The block table's owner and its report/verdict loop: `docs/design/mechanics/world-interaction.md` (the report is
  checked against a fact the receiver already holds, the host answers every reported cell authoritatively, and the member
  re-reports its outstanding set on the steady 60 s step).
- The generation the table describes: `docs/design/game/worldgen-and-layers.md` (one generation chain, the pod stamped
  around the local body).
- The direction this ticket adds is the same shape in reverse: the host is the owner, so the host's table must be able to
  reach a live member after entry — as a difference, never as a blind resend.

## Correction: two tables, and only one of them has a backstop (2026-11-14)

The measured divergence is **terrain**: `block-band-digest` reads `WorldGeneration.world.GetBlock(...)` (the recipe's own
`v = (int)world.GetBlock(new Vector2Int(x, y))`), and `WorldService`'s `_damagedBlocks` is a separate overlay of the
DAMAGE the host applied. The reconcile that landed (`BlockTableReconciler` → `ReconcileBlockTable`) drains exactly that
overlay, so it heals a member that missed a damage record — it does not, and cannot, heal the generated terrain the 54
differing rows belong to.

That is the ticket's own design gap, recorded here rather than papered over: the backstop covers one table, the measured
divergence is in the other. A terrain backstop needs its own shape (per-row digests the host can compare against what it
sent, then only the differing cells — the rows are 2048 wide, two bytes each, so a digest pass is ~4 KB per member and a
reconcile of even a whole row is a few hundred bytes), and it must be built only after the root cause is named, or it
will hide a generator defect behind traffic.

## The forced-write reading (2026-11-14)

A scratch recipe called `WorldGeneration.SetBlock` directly on the host (no break, no placement — the shape the game's
own generation uses). Readings on the live pair: the host's cell `6,503` read `14` before and after; `7,503` read `14`
before, then `0` on BOTH clients immediately. Two facts:

- a direct `SetBlock` write DOES reach the member live (something in the write path already carries it), so this probe
  cannot stand in for "a write the member never hears";
- the reconcile path is therefore still unexercised on the real game; its unit facts (5) are the only reading today.

The scratch recipe was removed after the probe (it is not part of the suite; the forced-drift row stays open until a
write that bypasses the live path exists).



## The pod centre is the same on both clients (2026-11-14)

The body-position hypothesis is rejected. The recorder logs the body position at every write, and on a run that reproduced
the divergence (36 rows, first at 987) the positions are IDENTICAL on both clients: `[SetBlock] 524,1000 -> 0 at 0.0,500.0`
(host) and `[SetBlock] 524,999 -> 0 at 0.0,500.0` (member) — same chain, same body point, DIFFERENT cells.

So the two clients consume the generation stream differently INSIDE the segment: the `[GenStream]` fingerprints match at
the boundaries (19 segments), yet the structures land one cell apart (host `524,1000`, member `524,999`, and
`500,1020` vs `500,1021`). The remaining candidate is the draw order/consumption between the saved boundaries, not
the pod centre and not an unseeded stream.

The terrain reconcile would mask this, which is why it must not be built before the consumption order is named.

## The two streams are offset, not identical (2026-11-14)

The earlier "19 identical `[GenStream]` fingerprints" was a misread. Read side by side, the last segment overlaps by eight
bytes:

```
host  segment 19: FFE05256A1729D596664B7A10C81C383
guest segment 19: 6664B7A10C81C38393DC574202A6EDF0
```

The host's tail (`6664B7A10C81C383`) is the guest's head. The same random stream, consumed from a different phase: one
client is eight bytes ahead of the other at that boundary. That is exactly enough to place a structure one cell apart
(`524,1000` vs `524,999`), and it is consistent with the session being healthy (the guest projected the run baseline and
adopted a 45-row enemy roster on the same run).

So the remaining defect is in the isolation's boundary bookkeeping — the stream is saved/restored at a slightly
different point on the two clients — not in the world's seeding and not in the connection.

## The first divergence is segment 17, eight bytes along (2026-11-14)

Segments 1-16 are byte-identical on both clients; segment 17 is where they part:

```
host  segment 17: 75F87E281580FF2489AB37D6D9B7F9FF
guest segment 17: 89AB37D6D9B7F9FF03459B202D96BCF8
```

Again the eight-byte slide — the host's second half is the guest's first half. So the generator is deterministic
until the boundary between segments 16 and 17, and one client consumes two extra 32-bit draws there. That window is
where `WorldPlacePlayer` stamps the pod and the clearing circles (`WorldGeneration.cs:2556-2568`); the next probe
reads that stage's draws on both sides (the recorder's `[SetBlock] ... at x,y` already proves the body point is the
same, so the difference is in what the stage rolls, not where it stands).

Everything after 17 inherits the slide, which is why the differing cells cluster around the pod.

## The stage names are identical on a passing run (2026-11-14)

With the coroutine name in the segment line, a passing run reads the same stages on both clients (segments 15-18:
`<WorldGenerateStructures>d__203`, `<Wrap>d__8`, `<GenerateWorld>d__198`, `<WorldPlacePlayer>d__202`). The divergence
did not reproduce in four consecutive runs on the deployed build (0 rows differ each time), so the failing window is
seed-dependent and has to be captured on a run that fails; the next attempt keeps this build and loops the case until a
red, then compares the same segment lines.

## The divergence lands in the chip step, eight bytes of draws (2026-11-14)

A failing run (59 rows, first at 946) with the stage probe reads segments 14-16 identical (structures) and 17 apart:

```
host  17: 17A944309540415C925564CE08553D94 stage=<GenerateWorld>d__198
guest 17: 58EFCA8E1896FE2ADE5438AC2E4EC016 stage=<GenerateWorld>d__198
```

`GenerateWorld` (WorldGeneration.cs:1916-1931) runs preprocess -> background -> terrain (structures inside) -> borders ->
`WorldPlaceChip` -> `SetLoadingText("gencreatingcolliders")` -> `yield return null`. That `yield return null` is the save
whose stage reads `<GenerateWorld>`, so the extra draws happen in the borders/chip window — and `WorldPlaceChip`
(WorldGeneration.cs:1935-1979) is the only random consumer there: `if (!this.isMercRun && Random.value > 0.25f) yield
break;` (one draw) versus the depth branch (`Random.Range` twice — two draws, exactly the eight bytes measured).

So the next probe is two fields in the same segment line: `isMercRun` and `biomeDepth`. Whichever differs explains the
two draws, and the fix becomes "the chip stage reads a per-client fact" rather than "the stream is unseeded".

## The chip facts are identical — the hypothesis is rejected (2026-11-14)

A failing run (39 rows, first at 979) read the same facts on both clients at the divergent boundary:

```
host  16: 511A2EEFA94D82B2 stage=<Wrap>d__8 merc=False depth=0
guest 16: 511A2EEFA94D82B2 stage=<Wrap>d__8 merc=False depth=0
host  17: C7A56063D245B3CF stage=<GenerateWorld>d__198 merc=False depth=0
guest 17: F7B20D296D0C3486 stage=<GenerateWorld>d__198 merc=False depth=0
```

Same stage, same `isMercRun`, same `biomeDepth`, different stream. So `WorldPlaceChip` is NOT the consumer
difference. The remaining random consumer in that window is `WorldGenerateWorldBorders` (WorldGeneration.cs:2520-2552):
it draws `Random.Range(0f, 1f)` once per row for eight columns on each side — `8 * height * 2` draws, so its count
depends on `this.height` (and `this.width` for the writes). The next probe logs `height` and `width` in the same segment
line; a mismatch there would advance one stream by a whole column of draws (and the two-draw offset seen earlier would be
the first place the two counts diverge).

## The chip stage is where the streams part (2026-11-14)

With the nested drives bracketed, a failing run (40 rows, first at 981) shows the split exactly:

```
before <WorldPlaceChip>  host 02FC9B8B1D0B539355460298ED3DE1DC
                        guest 02FC9B8B1D0B539355460298ED3DE1DC   (identical)
after  <WorldPlaceChip>  host 6E3125824A01456754E70482F0979F72
                        guest 54E70482F0979F728C769AD9A4739A96   (guest = host shifted by eight bytes)
```

So the host consumes two more values than the guest INSIDE `WorldPlaceChip` (WorldGeneration.cs:1935-1979). The logged
facts at save time are equal (`isMercRun=False`, `biomeDepth=0`), which the code says produces one draw on both sides
(`Random.value > 0.25f` then the depth branch is skipped for depth 0). The reading therefore contradicts the code as read,
so the next probe goes inside the stage rather than around it: count the draws by wrapping the public stream for the
duration of the chip (the isolation already restores around it), and read which branch each client took.

Everything after inherits the split: the pod, the entities and the finish stage all grow from the eight-byte lead, which
is why the differing cells cluster around the pod.

## The bracket closed the divergence on the deployed build (2026-11-14)

`WorldGenRandomIsolation.Drive` now brackets the two nested stages whose whole body runs in one step
(`WorldGenerateWorldBorders`, `WorldPlaceChip`) with the same `Save()`/`Restore()` a plain yield gets — they had no
segment of their own, and the chip's single `Random.value` guard therefore ran on a stream that the frame between the
previous segment and its launch had already moved.

Reading on the deployed build (`0.1.0+096172b00`, then `0.1.0+8fdeaed6a`): `block-idle-drift` ran nine times in a row
and read `PASS` every time (`0 rows changed on either client while idle; 0 rows differ between clients`). Before the
bracket the same case failed about one run in three (54, 56 and 34-row differences were read).

Nine passes is strong evidence, not proof: the next check is a longer series (twenty runs) and, once the reconcile
lands live, a forced-write pair of readings (host writes a row, the member's own table follows).

## The chip splits with identical entry facts (2026-11-14, before the bracket)

Another failing run (56 rows, first at 967) brackets the chip stage and reads:

```
nested <WorldPlaceChip> host  before=0F1085A63A56823845B1F4C98B2C8FEA after=FEF520BC9395D0BA25479ABCC758940D
nested <WorldPlaceChip> guest before=0F1085A63A56823845B1F4C98B2C8FEA after=2B39ACF7052F87BF7DE999A3E4E3FA4F
both: merc=False depth=0 h=1024 w=1024
```

Identical entry state, identical facts, different exit state. The coroutine body (WorldGeneration.cs:1937-1946) draws at
most once for these facts and then skips the depth branch, so the reading says the body did NOT behave the same on both
sides. The next probe has to sit inside the method: log the value `Random.value` returned and which branch was taken, or
replace the draw with an equivalent that cannot hide a second consumer.

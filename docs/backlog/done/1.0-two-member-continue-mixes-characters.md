# Two members in one continue: the second character is lost and its items merge into the first

- Status: Done (2026-11-19) — the loss was a display-name collision between the host and the second client,
  not a code defect: both carried `[IpDirect] DisplayName = Host`, both resolved to the player key `name-host`,
  and the cut refused to write a character under a shared key (decision 177) so the second member came back as a
  new character. The alternate client now presents `Alt`, `preflight.ps1` refuses a run whose clients share a
  name, and the row reads two characters, both markers and no cross-merge.
- Priority: High
- Created: 2026-11-19
- Related: `done/1.0-acceptance-rows-as-c-sharp-cases.md` (scope row 1), `done/1.0-continue-loses-geyser-types.md`,
  `done/host-cannot-host-after-continue.md`, `docs/design/cross-cutting/saves-and-recovery.md`,
  `docs/acceptance/AGENTS.local.md` (the three clients' display names)

## What the player saw

Two friends joined a host's run. The host saved and continued. One friend kept the character and items they had;
the other came back as a fresh character with the starting supplies.

## The reading (`.acceptance/twomember2`, 2026-11-19 00:49) — the false loss

The row (`two-member-continue`) joined host + two members (ids `9819874492779337119` and `4294629808900910865`),
granted each member a bandage marker through the game's own grant, saved, left the world, continued, and waited for
both members to follow.

- The cut carried **one** character: the restore line reads `… 3 player row(s) … 1 character(s) …`.
- `Restored characters: 1 bound to present peers, 0 left unclaimed, 0 refused (key space IpDirect).`
- The second member's own client read a fresh kit after the continue and no bandage.

## Root cause (`.acceptance/twomember3`, 2026-11-19) — a shared player key, refused by design

Reproduced on the current build, then read from the host log:

- `[WRN] [WorldCharacterBinder] Character key name-host is shared by 2 present players (1, 7560364048153771310); no
  character is written for it — the archive holds one character per key, and a file under a shared key could be
  claimed by the wrong player at a restore.`
- The two claimants are the host (peer 1) and the second member. The IP-direct player key is the display name
  (`PlayerKey.ForDisplayName`), and both installs carried `[IpDirect] DisplayName = Host`: the alternate sandbox's
  config had been copied from the host's.
- `WorldCharacterBinder.Collect` therefore refused to write either file (decision 177), the cut carried only the
  first member's character, and the second member joined as a new character. The "items merged onto the first"
  line was the first member's own transfer-table merge (5 items), not the second's.

## The fix

- The alternate client's config now carries `DisplayName = Alt` (machine state, recorded in
  `docs/acceptance/AGENTS.local.md`).
- `tools/acceptance/preflight.ps1` gained the `ip-names` row: it reads `[IpDirect] DisplayName` from the host,
  guest and alternate installs and fails with the collision named, because the player key is the display name and
  a duplicate cannot be told apart by a restore. The row reads
  `distinct IP-direct display names (host=Host, guest=Guest, alt=Alt)` on this machine.
- No product code changed: refusing a shared key is the rule; the run must not ask for two players with one name.

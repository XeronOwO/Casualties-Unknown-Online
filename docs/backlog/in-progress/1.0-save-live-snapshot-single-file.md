# A world's live save is a folder of uncompressed JSON

- Status: In progress — writer, reader, recovery and tests landed; real two-client acceptance pending.
- Priority: High

## What the user measured

The CUO save root is a directory of world folders. Each world keeps its current state as
`live/` — one JSON file per domain — plus `world.json`, `world.lease`, and compressed
`.cuoz` backups. The user's reading is that this is inefficient storage and wants a
compressed single-file form for a saved world.

## Design

Read `docs/design/cross-cutting/saves-and-recovery.md` (the save's ownership, transaction and
recovery model) before changing the on-disk shape. The storage contract itself is in
`docs/architecture/save-archive-format.md`.

## Current shape

- `docs/architecture/save-archive-format.md` §2 defines one folder per world; `live/` is
  deliberately unpacked so a save is a fast file write and a human can inspect or repair it.
- `SaveArchiveWriter` already writes each backup as one ZIP `.cuoz`; the live transaction
  stages a folder, verifies it, archives a backup, then renames `.staging/` to `live/`.
- One world's `live/` currently holds nine JSON payloads plus the manifest, and the global
  `index.json` is a separate cache of every world.
- The cost is paid on every save: many small files are rewritten, and every world keeps its
  own unpacked payload even when it is not the world being played.

## The problem

The user wants a saved world to occupy one compressed file at rest. The current layout keeps
the payload expanded and repeats JSON keys and domain files across worlds, so the save root
grows in file count and bytes without a format-level compact form. This is a storage-shape
problem, not a request to remove the existing atomicity or salvage rules.

## What must not change

- One writer per world, with the lease and the stage/verify/commit transaction intact: a
  crash must still leave the previous snapshot loadable.
- The manifest checksums and per-entry salvage; a damaged snapshot must still name what it
  skipped rather than silently losing rows.
- Backups remain restore points, and a player-chosen restore still replaces `live` only after
  the chosen archive passed its manifest/checksum gate.
- `index.json` remains a cache, never the source of truth.
- Existing worlds in the old layout must remain readable, or the migration must be explicit
  and reversible in the ticket's record.

## Options

- **A — one compressed archive for the live snapshot.** Save writes a temp archive and
  renames it into place; load opens the archive and decodes the same manifest and payload
  entries. One file per world, no loose `live/`. Cost: every save rewrites the whole archive,
  and a human can no longer edit a payload without unpacking.
- **B — compact at rest, unpack only while the world is open.** Keep the fast loose form for
  the active world; on close, pack it into one archive; on load, unpack to a staging folder
  and run from there. One file at rest and fast runtime, but two on-disk forms and a
  pack/unpack step that must be crash-safe.
- **C — a single container with independent entries (for example a ZIP or SQLite container).**
  Same one-file property with random access to domain entries; SQLite adds a new dependency
  and a second format to maintain. This is the most expensive option and needs a measured
  reason before it is chosen.

Recommendation for the first slice: **A**, because it is the smallest change to the existing
stage/verify/archive/rename transaction and it removes the loose payload entirely. If the
measured save time on a real world is unacceptable, fall back to B with the active world as
the only exception.

## Acceptance rows

1. A world at rest is one file under its world id; no `live/` payload directory remains.
2. Saving, loading, continuing, and a player-chosen restore round-trip every manifest field
   and every domain row; per-entry salvage still reports a skipped row.
3. A crash between stage and rename leaves the previous snapshot loadable.
4. A world written in the old folder layout is either read directly or migrated once with no
   row loss and an explicit record.
5. The save root's measured file count and bytes fall against the pre-change baseline; a
   save and a load on a real two-client run are measured, not estimated.

## Measured baseline (2026-11-16)

- The save root held 1,396 world folders; 540 of them were aborted-start shells with only a
  `world.json` and no snapshot. They were quarantined; 856 real worlds remain.
- One sample world: `world.json` 277 B, `world.lease` 74 B, nine `live/` JSON files 288.6 KB
  total (items alone 174 KB), plus `characters/*.json`; one backup `.cuoz` is 23,939 B.
- A menu-return cut measured 119 ms total (checkpoint 0, facts 4, encode 28, write 82); a
  command cut measured 463 ms (encode 320, write 123). The index update is now 3 ms for one row.
- The backup archive is the same payload compressed: 288.6 KB of live JSON becomes 23.9 KB,
  roughly a 12x reduction.

## Decision

**A — one compressed archive for the live snapshot.** The snapshot payload at rest becomes
`live.cuoz` under the world folder; `world.json`, `world.lease` and `backups/` remain because
they are repository metadata, not snapshot payload. The writer keeps the existing
stage→verify→backup→rename discipline: it stages the payload, verifies it, writes the backup,
then writes and round-trip-verifies the live archive before renaming it into place. The old
`live/` layout stays readable; the first successful save after the upgrade writes the archive and
only then removes the old payload, so a failed migration leaves the old snapshot in place.
Human repair moves from editing a payload file to unpacking the archive with the maintenance
command; backups remain directly readable. The measured payload is small enough that rewriting
the archive on each save is cheaper than the current many-small-file write, and the 12x byte
reduction is the reason A wins over B (two on-disk forms) and C (new container). The architecture
page's §2/§2.1/§5/§6 now describe the implemented archive transaction and restore shape.

# Batch 20261003-f — scope and acceptance plan

The acceptance plan for batch `20261003-f`, written before its session (workflow §3): the ticket set, the
shared setup the session runs, the row-level classification and the capability boundary the verdicts must
respect.

- Commit under acceptance: the batch's scope commit (the commit that carries this page and any probe the
  batch needs). The deployed artifact is built from it after it lands; every record carries its sha as the
  artifact's `+<sha>`.
- Artifact: `CasualtiesUnknownOnline.dll`, ProductVersion `0.1.0+<sha>`; `tools/verify-deploy.ps1` must
  report the deployment matches this tree's build output before the session.
- Preflight (2026-10-03, before the session): **11 present, exit 0**; `session-environment -Mode status`
  reported `active=cuo`, `game-running=false`, `swap-needed=false`, `launch=ok` before anything was
  launched. The physical Steam client was already running and is used, never restarted or stopped; the
  sandbox Steam stays resident, so the guest launch starts no second Steam; the alternate sandbox and its
  probe endpoint resolve and are idle.
- Dependencies used: the ids `tools/acceptance/preflight.ps1` reports present.
- Session: one world, three clients — host on the physical machine (launched through Steam, so Steamworks
  initialises), guest in the primary sandbox, alternate client in the alternate sandbox. The window plan's
  `20261003-f` note describes a host + guest setup; the batch's own row tables do not agree with that note:
  eight tickets carry an explicit third-party expectation (table §1) and the alternate sandbox is an
  available, proven dependency. This batch therefore extends its setup instead of deferring those rows.
  No `20261003-g` ticket is judged here and no row is judged from a weaker view.

## 2. Setup the session runs

S0 — **session and smoke.** Three clients enter one world through the Online UI. Smoke every instrument
before any row depends on it: `net-receive-blackout mode=status` on each endpoint (`armed:false`), the
block family's target cell and damage baseline (`body-place` then `block-read-at`), the guest's pending
report counters (`block-report-pending-count`, zero), the item tables (`container-read`, `item-world-read`),
the entity tables (`runtime-entity-census`, `runtime-entity-tables`, `enemy-table-read`), the mechanism
census (`world-object-census`) and the start gate (`gate-arm`). Record the baselines every later diff uses.

S1 — **partial block damage** (`guest-partial-block-damage-re-report` rows 1–6;
`partial-damage-delta-report-overlap` rows 1–5).

- One sender: the guest hits a block with the host's inbound blacked out (`block-hit`); lift well inside the
  15 s watchdog; read the guest's re-report, the host's application and answer, and both ends'
  `block-read-at`. The record names whether the entry phase's 5 s step or the steady 60 s step carried the
  re-report.
- Two senders: the guest and the alternate hit the same block around one blackout; the host's row must be
  the sum (never the maximum) and the alternate's own read must match it.
- Delta-then-report and report-then-delta: a live delta lands first and a later hit lands after the report;
  the host's row counts each contribution once. The exact retransmitted-delta interleaving is unit-pinned
  and named as such.
- Duplicate: an answered entry stops re-sending; a repeated report changes nothing.
- Break-before-report and restored-cell: `block-break-at` the cell, and separately `block-set-at` a fresh
  block at it; neither may resurrect a crack or stale damage.
- World entry / reconnect with an outstanding cell: the guest leaves/rejoins with its entry pending; the
  host's entry snapshot and the guest's table must agree.

S2 — **the 128-entry cap** (`guest-partial-block-damage-re-report` row 7;
`partial-damage-delta-report-overlap` row 6). `block-damage-fill` drives the game's own damaged-cell list
to its cap; a further report on a fresh cell is staged inside a blackout window and read through
`block-damage-census` (table count, `evicted`) plus both ends' convergence. The game's FIFO semantics are
the live half; the ledger's own cap is unit-pinned.

S3 — **break drops and entity destruction drops** (`guest-break-drops-recovery` rows 1–7;
`entity-destruction-drop-guest-fresh-state-loss` rows 1–5).

- The guest breaks a block that carries drops (`block-hit` at lethal damage) with the host's inbound blacked
  out; lift, let the fallback re-report carry the drops, and read `item-watch` (the drop's id and position,
  read inside the `FreshItemDrop` window) on every client, the drops dimension of
  `block-report-pending-count`, and the relay echo.
- The lost-air-write shape uses the forged same-generation break (`block-break-at`); a stale-generation
  report is refused (unit-pinned) — the record names which half the live shape exercised.
- Duplicate: a repeat re-report registers and materializes exactly once per drop id.
- The race: the guest and the alternate break the same cell back to back; the loser's drops are refused and
  destroyed on its own client and the third peer claims the winner's ids once. The driver's inter-command
  gap is stated in the record; simultaneity is not claimed.
- World reset / session end: the pending tables clear (`block-report-pending-count`, and
  `item-tombstone-read` where the family carries one).
- Entity destruction: destroy the support of a trap/building and one ordinary building in both directions;
  capture every non-destroying peer's window at the drop moment and read the same drop ids/positions
  through `item-watch`; the fall-then-pull half is judged from the captured frames, and the frame-to-drop
  tie is named if it fails.

S4 — **footstep crush** (`unhooked-damage-block-callers` rows 1, 3–6). `crush-find` locates a
`health <= 1` block the body can stand on; `move-drive` walks the host over it (and separately the guest),
and the other two clients must present the same break with no host answer. Row 6 reads one report per
crushed cell. Row 2 stays blocked.

S5 — **item command loss** (`guest-command-loss-reconciliation` rows 1–9). The guest's pickup, drop,
destroy and the creation+pickup chain are each swallowed with the host's inbound closed (the 5 s window,
12 repeats); the host's transfer/world tables, the guest's local result and the alternate's
location/ownership are read through `container-read`, `carried-registration`, `item-world-read` and
`item-tombstone-read`. Duplicate: a repeat is answered from the host's operation window (read the answer
line; one commit). Reconnect: the window drops at the session edge and the rejoin re-baselines.

S6 — **runtime entity bind and trap layout** (`runtime-entity-markerless-bind-absorption` rows 1–10;
`trap-layout-entry-snapshot-staleness` rows 1–5; `trap-layout-snapshot-recovery` rows 1–7).

- Baseline `runtime-entity-census` / `runtime-entity-tables` / `world-object-census` on every client.
- Create a runtime entity through the mod-template path the `runtime-*` recipes use; a member enters; the
  entering member's census must carry the same creation key (row 9) and the live relay must reach the
  reporter (row 10).
- Remove an entity (self-destruct / break), then have a member enter before the next repair: no phantom in
  the entering member's `world-object-census`; the reconnect (row 2) and the in-session repair (row 3) read
  the same; the alternate agrees (row 5); an empty live scan keeps the last table (row 4, attempted at the
  layer-transition window).
- The swallowed entry snapshot (blackout around the entry group) is healed by the 60 s in-session repair
  (row 1); the late joiner applies exactly once (row 2); a reconnect duplicates nothing (row 3); the layer
  command replaces the layout (row 4); a destroyed entity is not resurrected (row 5); the failing-prefab
  path is named unless storable (row 6); the alternate converges (row 7).

S7 — **turret and trap state** (`turret-stray-fire-after-reload` rows 1–5;
`trap-action-divergence-hardening`'s live residual).

- Locate a generated turret through `world-object-census`; stage an engagement (or a declared substitution
  the record names) so it fires and re-arms; read the live shot events on both sides and capture the
  non-acting client's window across the next checkpoint resend. No extra shot, tracer or sound may appear
  without a live trigger; the transient-trap filter's log lines are the machine half.
- Trip a shy crystal and read both clients' crystal positions/latches through `world-object-census` /
  `generation-read`; if the pairing cannot be staged, the ticket's own recorded residual is carried.

S8 — **session control** (`session-control-convergence` rows 1–10). A mid-join guest with the host's inbound
blackout around the third leg and the scene report: the 1 Hz re-ack, the 5 s window, the roster repair, the
`WorldReady` repeat answer, the `WorldSnapshotComplete` consumer and the exit window are read through
`gate-arm`, `scene-repeat`, `console-read` and the client states; the third member's surface must stand
still (row 6); the reconnect-while-in-world path stays green (row 7); the gate-armed-later case (row 10) is
attempted inside the guest's 60 s valve.

S9 — **close.** All three clients quit through the game; the run confirms no process it started is left, and
collects the log channels, probe dumps and window captures for the records.

## 3. Capability boundary

- Three clients in one world; the alternate client is used for the third-party rows named in §1, never for a
  `20261003-g` ticket.
- The blackout is a blunt inbound cut: single-stepped, checked before arming and after lifting, and kept
  well inside the 15 s host-silence watchdog. A missed lift ends a session rather than a row.
- The two-breaker race and the two-hit interleavings are staged sequences, not simultaneous races: the
  driver's inter-command gap is stated in the record.
- Forced states the game gives no drive for (a turret engagement without a natural target, a runtime
  building with no natural spawn) are declared substitutions, never silent setup.
- The 128-entry cap is the game's own list; the per-sender ledger's cap is unreachable and stays
  unit-pinned.
- Visual rows are judged from a window capture the agent reads; a frame that cannot be tied to the drop or
  the shot it names stays `unproven`.
- The sandbox copies' shadow is checked before launch — an older sandbox copy runs old code.
- A probe the run discovers it needs is landed before the deploy, per the batch `20261003-c`/`-d`
  precedent, never improvised inside a live session.

## 4. Exit criteria

- One record per ticket, `docs/evidence/acceptance/<slug>-20261003-f.md`, carrying the batch, the commit,
  the deployed artifact identity, one verdict and one evidence pointer per row, the dependencies used, the
  limits and any residuals.
- Transitions: all rows pass (or the remainder are residuals) → `docs/backlog/done/`; a `fail` → back to
  `docs/backlog/todo/` with the rejection marking; a `blocked` or capability-limit `unproven` row keeps the
  ticket in `review/` with the gap named. The index rows move in the same change as the tickets.
- Lessons fold into `docs/acceptance/lessons.md`, machine facts into `docs/acceptance/AGENTS.local.md`, and
  the moved-slug reference sweep re-runs before the closing commit.
- The gates run before the commit; the session ends with all three clients closed and the machine free.

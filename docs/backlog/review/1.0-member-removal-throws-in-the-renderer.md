# A member's removal throws in the remote renderer

## The reading

`BepInEx/LogOutput.log` on the host, at a member drop (2026-11-13, the pair the suite runs against):

```
[Warning:...PeerDisconnectWatchdog] Dropping 4360219206767782828 (Guest) from the session: the transport lost this peer's connection
[Warning:...SessionService] Host kicked member 4360219206767782828: the transport lost this peer's connection
[Error  :...Plugin] ICuoService.Update failed for PeerDisconnectWatchdog
System.NullReferenceException: Object reference not set to an instance of an object
at CasualtiesUnknownOnline.GameAdapter.Character.RemotePlayerRenderer.OnRemoteSceneChanged (System.UInt64 steamId, System.Boolean inWorld) [0x00040]
at (wrapper delegate-invoke) System.Action`2[System.UInt64,System.Boolean].invoke_void_T1_T2(ulong,bool)
at CasualtiesUnknownOnline.Runtime.Session.MemberPresenceTable.FireRemoteSceneChanged (...)
at CasualtiesUnknownOnline.Runtime.Session.EntitySync.EntitySyncService.OnMemberRemoved (...)
```

So the host's own member-removal path (`HostKickService.Kick` → `RemoveGuestMember` → `EntitySyncService.OnMemberRemoved`
→ `RemoteSceneChanged`) throws, and the throw lands in `PluginHost.Update`'s service loop (`ICuoService.Update failed
for PeerDisconnectWatchdog`).

## The suspect

`src/CasualtiesUnknownOnline.GameAdapter/Character/RemotePlayerRenderer.cs:405-409`:

```csharp
if (!inWorld && _remoteClones.TryGetValue(steamId, out var clone) && clone != null) // Unity object — ==
{
    Object.Destroy(clone.transform.parent.gameObject);
    _remoteClones.Remove(steamId);
}
```

The Unity-`==` guard covers the clone, not its parent: a clone whose parent was destroyed (the scene change that
precedes a removal) answers `clone != null` and then dereferences a destroyed `clone.transform.parent`, and the entry
is never removed because the throw happens before `Remove`.

## The shape of the fix

- look the clone up, remove the entry, then destroy: guard the parent chain before touching it
  (`var parent = clone.transform.parent; Object.Destroy(parent != null ? parent.gameObject : clone.gameObject);`);
- the same shape should be checked at every other clone-destroy site in the file (the disposal path and the rebuild
  path), because one guard per call site is how this class of defect survives (`RemotePlayerRenderer`'s `Destroy*
  helpers`).

## Why it matters

A member leaving is the normal path (a quit, a transport loss, a kick). A throw in the middle of the removal leaves
the rest of the removal undone — the renderer's own entry survives, and the exception is reported as a service failure
on every later tick while the entry stays. The suite's degraded-pair run (22 passed, 5 failed on the same tree) is the
kind of state this can leave behind.

## Design

Read from `docs/design/game/README.md` (the game's own systems map: the adapter's job is to mirror what the game
does, so a clone's lifetime copies the game's own lifetime — created with the member's world entry, destroyed with the
member's exit). The mod's own rule this defect breaks is the one in `AGENTS.md`: a removal path must finish its work
after a throw in any one subscriber.

## Next step

Fix the guard, then read it live: the host must log `Remote not in world (menu or disconnected) — clone destroyed.`
with no `ICuoService.Update failed` line at the same moment. A unit test cannot mount a Unity clone; the row's
reading is the log pair.

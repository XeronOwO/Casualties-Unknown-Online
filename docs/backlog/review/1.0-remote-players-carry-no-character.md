# A remote player carries no character

Every client picks one of the game's three characters on the pre-run screen, and the game spawns
that one (`PreRunScript.characterSelected`, `PlayerCamera.SpawnCharacter`: 0 Experiment, 1 Milky,
2 Dune). CUO carries none of that choice: the remote clone is `Instantiate`d from the LOCAL player's
own body, so a teammate playing a different character is drawn as the viewer's character.

## Design

The game's own character spawn table and the three character objects (`docs/design/game/README.md`
maps the game's systems; the pre-run screen is `PreRunScript`, the spawn is `PlayerCamera.Awake` →
`SpawnCharacter`). The durable half belongs to the character snapshot the session already carries
(`docs/design/cross-cutting/saves-and-recovery.md` — a character's own facts outlive a session and a
transport switch); a chosen character is a fact of the player, not of the connection.

## The reading (2026-11-14, release build)

`src/CasualtiesUnknownOnline.GameAdapter/Character/RemoteBodyFactory.cs:54-69` — the template is
`PlayerCamera.main.body.gameObject`, with the demo's `"Experiment"` scene object as the fallback, and
nothing in the wire (`WirePlayerStreamState`, `CharacterDataMsg`) names a character. Two players on
different characters therefore see each other as their own character.

## What must be decided

How a remote clone shows another character without becoming a second live body: instantiate the
chosen character's prefab and strip the components that act on the world (the remote-body
construction already disables colliders and owner-only effects), or build the presentation from that
character's own sub-objects. The reading must name the clone's source object so a wrong character is
visible in the evidence.

## Acceptance rows

1. Host on Experiment and member on Dune: each client's clone of the other is drawn from the Dune
   prefab and from the Experiment prefab respectively (a reading names the source object).
2. The choice survives a re-join and the save/continue path (it rides the character snapshot).
3. The sweep's `clone-probe` case keeps passing on the reconstructed clone, and no second live body
   appears (the member's own counts stay one).

## Design (2026-11-14, step 2)

**The player's action.** On the pre-run screen the player picks one of three portraits (the third is
locked until the previous one has won a run); the run starts and the player's own body is that
character. The player expects a teammate to see the character they picked.

**What the game runs.** `PreRunScript.SelectCharacter(int chr)` stores `PreRunScript.characterSelected`
(`reversing/release-1.0/Assembly-CSharp/PreRunScript.cs:270-272`); `PlayerCamera.Awake` writes it to
`PlayerPrefs["lastchar"]` and calls `SpawnCharacter(characterSelected)`
(`PlayerCamera.cs:797-800`), which loads `Utils.Create("Special/Characters/Experiment"|"Milky"|"Dune")`
(`PlayerCamera.cs:781-792`). The chosen character is a fact of the player's body, so its identity
belongs in the character snapshot the session already carries.

**The wire.** `CharacterDataMsg` gains `int Character` (tag 7), wire-encoded as `index + 1` (0 =
absent, the rule the file's own `HandSlot` already follows). `CharacterDataCapture.Capture` fills it
from the owning body's character: the body's own object name is the prefab name for the local player
(`Character_<hex>` clones never capture — they never report), with `PreRunScript.characterSelected`
as the fallback when the name is not one of the three.

**The clone.** `RemotePlayerRenderer` already has the member's snapshot
(`RemotePlayerRenderer.cs:198`); it hands the character index to
`RemoteBodyFactory.CreateRemoteBody`. The factory loads the remote character's own prefab with
`Resources.Load<GameObject>("Special/Characters/<name>")` and `Instantiate`s it (never
`Utils.Create`, whose scene-side effects would make a second spawn), then runs the same
collider/effect stripping the local-body clone gets. A load failure falls back to the local body
template and logs a named failure, so a wrong character is visible in the evidence rather than
silently the old body. The clone cache key becomes (SteamId, character): a member who changes
character gets a new clone instead of a stale one.

**What must not change.** The clone stays a display body with collisions off and owner-only effects
stripped (`RemoteBodyFactory`); the member's own entity counts stay one (row 3); the character id
rides the snapshot, so a re-join or a save/continue returns the same character.

## The live reading (2026-11-14, release build, desktop host + boxed guest over IP direct)

Implemented as designed and read on the pair: the snapshot carries the index, the renderer hands it
to the factory, and each client logs the prefab its clone came from (`Remote body for <id> built from
<source>.`). Two corrections came out of the first attempt:

- The Body component sits on a CHILD of the instantiated character, so `body.gameObject.name` never
  held the character's name (the factory's own comment says the proxy patches query the driver "on the
  Body (which is a CHILD of the root clone)"). The capture and the template now read
  `transform.root.name`, with Unity's `(Clone)` suffix ignored — commit `fdacf27fc`.
- `PlayerCamera.Awake` WRITES `PlayerPrefs["lastchar"]` from the field, it does not read it: setting
  the pref before launch is overwritten at spawn (measured: set to 2, read back 0 after the run).

On a pair where both clients spawn Experiment, both sides read `built from the viewer's own body` —
the same-character path is correct and the wire names the character. The different-character row is
NOT driven yet: with `PreRunScript.characterSelected` set through the new
`tools/acceptance/recipes/select-character.cs` (it answered `ok, index 2, spawn
Special/Characters/Dune`) and the run restarted through the driver, the host's own capture still
reported Experiment, because the run start re-initialises the choice. In a real session the pre-run
screen's portrait click is what sets it, and the fixture does not drive that screen.

So row 1 needs one fixture capability — driving the game's own pre-run character screen — and the
row stays open until it is read. The wire and the clone path are judged from the reading above.



## The same-eval start attempt (2026-11-14)

The fixture tried to select and start in one eval: set the field, find the screen with Object.FindObjectOfType(typeof(PreRunScript)), call StartRun() through reflection. The driver answered val 'recipe:select-character' returned no value for that form twice — once with the Runtime CharacterIndex reference and once without it — while the committed field-only form still answers ok, index 2, spawn Special/Characters/Dune. So the failure is in the extended recipe, not the channel; the next slice calls the game's own PreRunScript.SelectCharacter(int) (PreRunScript.cs:270, which sets the field and refreshes the portrait text) and StartRun() (:400) on the same instance, and if the evaluator still returns nothing, splits the two calls to read which one loses the value. The pre-run screen's own Awake writes characterSelected = 0 (PreRunScript.cs:55), which is why a field write before the menu does not survive.

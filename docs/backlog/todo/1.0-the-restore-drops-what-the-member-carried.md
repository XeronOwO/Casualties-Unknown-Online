# The restore drops what the member carried

- Status: Todo
- Priority: High
- Evidence: `.acceptance/savecont-1/report/report.md`

## What happens

A save names the member's carried item with the colour the member gave it; the archive the save writes carries it
(`save-continue` reads both colours there before the continue). Continuing from that save leaves the member's own item
count at 0: `the member's colour did not survive the save/continue: {"ok":true,"count":0,"items":[]}`.

The member's own log, at the moment the world is materialized, also carries `NullReferenceException` at
`GroundBlood.Start ()` — the game's own blood decal script, started from the restore path our adapter drives.

## Why it matters

The row is the only place a player's saved item is followed from the archive back onto their body. Today the pair
survives the save and loses the member's item on the way back, which is the difference between "continue my run" and
"start over with the host's things".

## Options

1. **Find where the restore drops the member's items** — read the restore path's character placement for the member
   (the same placement the host gets), and make it keep what the archive names. Recommended: it is the defect the row
   names, and the host's half already works.
2. **Re-baseline the member after the restore** — send the adopted character data again after the world is up, as the
   reconnect path does. Cheaper, but it hides which step dropped the item and leaves the archive as the only truth.
3. **Park the row** — unacceptable: the claim is exactly what a player does.

## Design

`docs/design/cross-cutting/saves-and-recovery.md` — the save names items by owner and slot, and the restore puts them back
through the same placement the character data uses.

## Third reading (2026-11-24 05:15) — the stored character is never claimed by a later join

With a fresh save root (one world only, `w-20261123-2921`), the cut carries the member's character in
`characters/name-guest.json` (health, limbs, skills — items live in `items.json`), and the member's own log shows the host
sending `Received character restore (0 items)` three times after the continue.

The restore binds stored characters **once**, at the continue: `WorldRestoreApplier.TryApply` calls
`binder.Plan(decode.UsableCharacters)` and `binder.Bind(plan)` with the peers present at that moment
(`WorldRestoreApplier.cs:278`, `:343`). A member that joins afterwards is not in that peer list.

Characters that no present peer claimed are kept — `WorldSaveService.PendingCharacters` is set from
`restore.Characters` (`WorldSaveService.cs:568`) and the binder logs "the file stays in the archive for a later claim"
(`WorldCharacterBinder.cs:175`) — but **nothing ever reads `PendingCharacters` again** (no reader outside the property's
own declaration). So a later join has no path to its stored character, and the host correctly sends an empty one.

**The fix to build next:** when the host is about to send saved character data to a peer that has none, claim a pending
character by that peer's display name through the existing `PlayerKeyResolution.Claim` / `CharacterAdoption` rule, seed it
under the peer's current transport id, and send that — the same identity rule the restore uses, applied at the moment the
peer actually arrives.



## First reading (2026-11-24 04:20)

The host's own log at the continue says it plainly:

```
[CUO continue: the archive carries no character this player claims; the run starts it as a new character (decision …)
```

and the host never logs a saved-character hand-off to the member afterwards (`Sent saved character data` appears nowhere
in the window). So the member's bag is empty because nothing was handed over, and nothing was handed over because the
archive the continue read carried no character record for either player.

That points upstream of the wire: the leave that precedes the continue takes a `MenuReturn` cut, and the characters are
supposed to be written with it. The next reading is the cut's own character table — how many rows it wrote, and under
which keys — rather than the restore path.

# Acceptance declarations no longer register a type

- Status: Todo
- Priority: High
- Owner: unscheduled
- Created: 2026-11-18

## What the player sees

Nothing directly: this is the acceptance instrument. Every frame-based row is blocked behind it — the
bandage minigame, the ending sequence and anything else that needs a gesture measured across frames.

## Design

The row this blocks is the medical view's bandage treatment, read from the player's own side: applying a
bandage starts the item's own minigame, and the limb it is used on stops bleeding
(`docs/design/mechanics/medical-view.md`, "a bandage or splint starts the item's own minigame"; the
angle-per-frame measurement is the game's own,
`reversing/release-1.0.2/Assembly-CSharp/BandageMinigame.cs:118-150`). The design therefore requires a
gesture the client performs across frames; an acceptance row cannot stand in a single frame without
inventing a different game.

## The reading (2026-11-18)

Sending a committed in-client declaration answers "declared" never; the driver reports

`the eval declaration 'bandage-rub6' was sent but the type is still not in the client's evaluator`
(`.acceptance/medical-bandage1`, member client), and the same shape was measured earlier the same night
with `run-ending-a` (`the type is still not in the client's evaluator`, 2026-11-18).

The declaration is sent through the suite's `declare` action, which loads the committed source into the
client's evaluator and then probes for its `// declares:` type
(`tests/CasualtiesUnknownOnline.AcceptanceSuite/SessionDriver.cs:922-946`); the probe answers absent both
times. Recipes compiled into the batch channel still run in the same session, so the channel itself is up
and only the runtime declaration path is affected.

A per-frame recipe was written as a workaround (`tools/acceptance/recipes/bandage-step.cs`, one hand
movement per driver round trip, 160 calls) and the game's own counters stayed at
`{"ran":true,"actions":0}` — the gesture never completed, so the workaround is not a substitute.

## Why it blocks a row

`MedicalBandageCase` (parked in the registry, not registered) drives a real wound, the game's own
wound-view entry and the patient's limb readback correctly; only the minigame completion is missing. The
same applies to any row whose gesture spans frames: the game measures the hand's angle per frame
(`reversing/release-1.0.2/Assembly-CSharp/BandageMinigame.cs:118-150`), so a single-frame recipe cannot
produce it.

## Options

1. **Repair the evaluator's compile path** (recommended): find why the sent source produces no type — the
   probe's lookup, the compile result, or the assembly load — and make the existing declarations work
   again. It restores every frame-based row at once and needs no new fixture shape.
2. **Convert declarations to coroutine-capable recipes**: give the recipe channel a way to start a
   coroutine on the client (the batch assembly already runs there). More tooling, but it removes the
   runtime-compile dependency for new rows.
3. **Drop frame-based rows**: not acceptable — the bandage and the ending are player-visible behaviours
   the sweep must judge.

## Acceptance

- A committed declaration (`bandage-rub6`) loads and its type is present in the evaluator on both clients.
- `MedicalBandageCase` runs green by name: a bleeding wound, the bandage applied through the wound view,
  the bleed stopped, read on the patient's own limb.
- The ending row's declaration loads the same way.

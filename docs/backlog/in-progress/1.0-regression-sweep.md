# Re-read the verified gameplay rows on the 1.0 release

- Status: In progress — batch 1 (medical view and panel) is the current batch; the domains below are the sweep's row list.
- Priority: High
- Written: 2026-11-11
- Language: English only in this file; the player-facing sentences are quoted from the evidence files.

## Why

The 1.0 adaptation is read end to end and the build is playable, but the previously verified
gameplay rows were judged on the demo build. The release changed the game under the same
ticket names (the amputation infection gate left `Item.DoAmputate`, `BuildingEntity.health`
became a property, `PlayerCamera.following` left), so a row that passed on the demo is not
evidence for the release. The user's order is to re-read the full set of rows (translated:
"run the full regression").

## What a row means

A row is one player-visible behaviour a done ticket verified (its acceptance rows, or the
verification section this corpus uses). It is re-read on the release install the same way the
original was read: a fixture derived from the ticket and the design page, a staged input through
the acceptance channel, and a measured reading from the client that experiences it. A row
passes only with a reading in this sweep's evidence file for its batch. A row that differs is
either fixed (if the adapter is at fault) or filed as its own ticket with the reading.

## Reading discipline

- A row is judged by the client that experiences it; the host's log is the corroboration.
- A reading that only proves the mechanism (a unit test) is not a row reading; the row is read on
  the running build.
- A batch's rows that fail keep the ticket open until the fix is deployed and the row re-read.

- block-sync (host break → member's block table) — carried by `tests/CasualtiesUnknownOnline.AcceptanceSuite/Cases/BlockSyncCase.cs`, green in the full run since 2026-11-13.
- eat-sound (a host's eat plays on the member's machine) — carried by `tests/CasualtiesUnknownOnline.AcceptanceSuite/Cases/EatSoundCase.cs`, green in the full run since 2026-11-13.
- water-shake (the game's own `dogshake` clip) — **manual**, and the reason is a reading: `Body.HandleDogWaterShaking`
  returns early when `!this.hasFur` (`reversing/release-1.0/Assembly-CSharp/Body.cs:3661`), so the routine is a dog's
  routine and no recipe can wet an animal; seeding the player body (`body-wet wetness=40 temperature=36`, wetness read
  back 40) left the recorder at `raw=6206|` with no `dogshake@` in twenty seconds. The row needs an animal fixture that
  does not exist, so it stays a visual/ambient row rather than a case.

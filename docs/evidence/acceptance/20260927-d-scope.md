## Run sequence (one session, one world)

1. Bring-up: launch the host through Steam, the guest through Sandboxie; both ping ready; create lobby /
   join / start run; confirm both in world and both see the other's clone.
2. Baseline, before any carry: both `body-read`s and both `carry-read`s; the non-carried idle-sit control
   (force `idleTime` on a still body, observe the native sit begin); the two world frames.
3. Scene A — guest carries host (`piggyback`): `carry-start` on the guest; both `carry-read`s; world
   frames from both windows (window-level capture with the Online UI closed); `move-drive` on the guest
   through walk, turn and crouch while both `carry-read`s are taken; the rider's idempotent forced
   `idleTime`; the ride-pose frames; `carry-stop`; both `carry-read`s.
4. Scene B — host carries guest: the same core steps in the reverse direction, plus the guest's own
   medical panel (`WoundView`) frame.
5. Scene C — unconscious carry: force the guest unconscious (`brainHealth=1`, `consciousness=0`), carry
   with `mode=carry`, vitals before/after, movement window with `limbSeparation` readings, frames,
   release and recovery reads.
6. Scene D — carrier sit: force `idleTime` on the carrying side, read back, frame; compare with the
   non-carried control.
7. Scene E — severe sleepiness: force the host's `energy`/`badSleepAmount`, read both views' frames and
   the clone's `legSpeedMult`.
8. Scene F — fall injury: force a limb injury on the host, read both views' frames of the mouth.
9. Close: quit both clients through the driver, collect the logs, verify no game process remains.

The run's own log (`.acceptance/batch-d/run-log.md`, local artifact) records which of these ran, in
which order, with the call-level detail; a deviation from this plan is recorded there and in the
records it affects.

## Method

Every row is classified before the run (above), and each ticket's record carries the same classification
with its verdict and its evidence pointer. `machine` rows are read from the probes, the logs or the
repository suites of this run; `visual` rows from window-level frames this run captures and the agent
reads; a row that stays subjective after the frame read is named a residual for the user, never a pass.
`feel` rows (smoothness) are judged from the frames the run can capture plus the instrumented
`riderDrift` readings, with the subjective remainder named as a residual.

## Limits

- Two clients only: every third-peer row is out of this run, named per ticket.
- The container/inventory scenarios are out of this run; their tickets keep the setup gap on their
  records.
- Frames are read, not measured: millisecond feel remains a residual.
- One session does not disprove a rare race; rows about timing repeat within the window they are
  observed in, and the repetition count is recorded.
